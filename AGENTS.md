# ChatSOP agent guidance

## Scope

This is the single root instruction file for changes to ChatSOP. The product has one goal (owner decision of 2026-10-01): **beat small LLMs at reasoning through symbolic processing**, and help small LLMs reason symbolically. Nothing else is in scope. The chat and the system work through **omp as the coding agent**: it picks a model from the configured subscription chain and writes only circuits from the user's message; the validator checks them, the KnowledgeLinker links their strings, the StrategyRouter sends the problem to the right reasoning strategy or the oracle, and the answer is rendered deterministically in English (omp may later formulate the final wording). Follow the current user request, this guidance and the design specifications; track outstanding work in `TODO.md` and delivered work in `PAS_TASK.md` without presenting either as product documentation. Open questions that need the owner's decision go in the root `questions.md` (always present; each question has a stable ID, context, options, a recommendation and an empty answer line); once a decision is implemented, remove the question and record the decision in the owning DS, `PAS_TASK.md` or `CHANGES.md`. Decide low-level matters yourself (correctness, genericity, production use, user value); ask only what changes what the system does.

## Names

- **SOP Lang**: the checked language of circuits (DS004); the circuit surface a coding agent may author is DS014.
- **Coding agent (omp)** and **`lib/query-author`**: omp runs a model chosen from a subscription chain (`config/runtime.json` `queryParser.models`, today `zai/glm-5.3` then `openai-codex/gpt-6-luna`); `lib/query-author` builds its context (the message and the memory vocabulary), runs the validate-and-repair loop and returns circuits. `POST /v1/author` and `server/query-parser.mjs` are the entry points.
- **Validator**: admits only what the circuit surface allows, with bounded repair rounds. **KnowledgeLinker**: links the entity strings of a circuit to the base memory; it does not parse language. **StrategyRouter** (`reasoning/router/`): chooses the strategy by problem features. **Oracle**: the exact JavaScript reference (`js-reference`) used to verify and as the fallback strategy. **Result packet**: what the runtime returns; `sop/answer-text.mjs` renders it.
- **Session**, **base memory** (core-min, core-en, world-v1, demo): DS022. Memory engines: RecallMemory, HoloMemory, SQLite, scan, hybrid (DS005, DS016 to DS021).
- **Archive**: earlier experiments (the small-model branch, paused components) live in `probably_obsolete/` and are history only; nothing there is a rule for current work and nothing is revived in the product. Say "the validator", "the runtime" or the component's name, never "host".

## Circuit-authoring boundary (non-negotiable)

The coding agent gets the user's message and the memory vocabulary (retrieved predicates and entity hints) and writes **only circuits**: queries, constraints, `unclear`/`unparsed` markers, and session definitions or assumptions marked `assumed`. It never answers and never states facts. The validator admits only what the circuit surface (DS014) allows, repairs in bounded rounds, and a refused circuit is reported, never silently replaced. The prompt never contains answers, gold, sealed tests or other sessions. There is **no SymbolicLM fallback**: when no model is available the answer is an honest `parse_unavailable`. A coding-agent circuit that is wrong executes to a wrong answer, so the benchmark (`experiments/proposal/symbolic-vs-llm-benchmark.md`) counts a wrong circuit apart from an honest unknown. Statements of the user are turn-local evidence kept only in caller-owned conversation context; suppositions, reported speech and `assumed` lines are used conditionally or reported; none is a sourced fact or a repository write. `remember` is a trusted runtime operation, not a model instruction. The answer language is English. Wire changes update `docs/wire_types.html` and `docs/wire_typs/` with examples (`tests/wire-help.test.mjs` executes them).

## Directions

1. Work toward the benchmark in `experiments/proposal/symbolic-vs-llm-benchmark.md` (the validation procedure), the subscription chain with omp answer formulation, KBQA slice runs, StrategyRouter evaluation and large-data soundness. `TODO.md` tracks the gates; product documentation never asserts progress.
2. A read must not hide a write. Proof-use promotion of an admitted, metadata-verified observed fact is allowed only when `policy.reinforce !== false` and the retention configuration (`reinforceOnUse`) both permit it, only for a real non-hypothetical proof, and the reason packet reports it. Candidate retrieval alone promotes nothing.
3. A requested backend is never substituted. An explicit unavailable solver returns `unsupported` with the backend in `route.backend` and `fallback: null`; a JS-only mode with an explicit external backend, and the reference strategy with an external backend, are rejected the same way. `advanced` is routing, not a fourth solver. A problem without an engine is `not_computable`; a link without an engine is `not_checked`.
4. SOP relations use whitespace-separated terms and JSON-quoted text, not parentheses or commas; Boolean conditions use `all`/`any`/`end` groups. Keep genuine JavaScript, solver syntax and exact source quotations apart from SOP grammar.
5. Models are used as they are; this project does not train models. Never install models, solvers or packages merely to start the runtime.
6. Source rights are per asset (`DS011`): only text recorded as cleared or permissive-attribution may be ingested, exported or published; unverified or restricted text stays in the local cache `datasets_sources/`. Released inspired-by corpora take structure and statistics, never text, and pass `node tools/datasets/no-copy.mjs`.
7. Test and data authority: sealed suites live under `eval/suites/**`; generators and tuning code never read their test files (`eval/leakage.mjs`, `tests/leakage.test.mjs`). The goal is a system as general as possible (owner, 2026-10-02; the earlier "same form, different words" rule belonged to the frozen small-model training and no longer limits evaluation). Every evaluation reports three levels separately: (a) known forms with new words (`tools/datasets/audit/content-word-overlap.mjs`, `tools/eval/query-forms/overlap.mjs`), (b) held-out forms never used in development, guides or examples, and (c) compositions of known classes and free natural questions; claims are made per level. Duplicated cases between development and test are still forbidden. Evaluations are staged small-first with a paired bootstrap interval. `eval/reports/current/` holds regenerable observations, `eval/reports/history/` archived numbers; never present a historical number as a current run.
8. Knowledge: documents, books and other sources are written into task-type base memories by a coding agent as knowledge wires with provenance (source, location, quote); sessions fork from a base memory, and the chat's default base carries encyclopedic and common-sense knowledge. There is no manual accept/reject step (owner, 2026-10-02): knowledge enters after the validator and automated checks, and errors are corrected systematically through tests and interactions. Session definitions and assumptions written while formalizing are used and labelled in the answer; they reach a base memory only through the same automated path. New knowledge needs no model change.

The normative contracts live in the DS set (`docs/specs/matrix.md`); where this file and a DS disagree, the DS is the source of truth for documented behavior. Write documentation, specifications and code comments in clear English.

## Runtime Defaults

Node.js >=22.13 with `.mjs` modules, explicit imports, `node:` built-ins, async/await and module-relative resources. Prefer built-ins and small auditable code; record a necessary dependency in `dependencies.md`. Python only for the frozen branch under its archive path. `docs/specs/DS001-coding-style.md` holds the full contract. `npm start` serves everything on one port (default `0.0.0.0:9999`); `npm run verify` runs the tests, the smoke reasoning suite, the spec-reference check, the shard check and the site-link check.

## Which path runs which model (owner rule, 2026-10-02)

Pick the execution path by the model's provider, without asking: **Anthropic models** (Haiku, Sonnet, Opus) run as Claude subagents; **every other provider** (OpenAI Codex such as gpt-6.1 and gpt-6-luna, z.ai GLM, xAI Grok, DeepSeek, OpenRouter) runs through `omp`; local GGUF models run on the local llama-server. Implementation tasks: Claude subagents, Opus or Sonnet (owner, 2026-10-02). LLM batch work (circuit authoring for experiments, validations, bulk data or fact creation, judging): Haiku subagents while the Codex and Grok subscriptions are exhausted, z.ai GLM through omp as an alternative. The product's request parser uses its configured chain (`config/runtime.json` `queryParser.models`). Draw obvious consequences yourself; do not probe or ask about what follows from known facts.

## Disk and repository hygiene

- Model files (GGUF) are never committed; `models/` is gitignored.
- `eval/reports/current/` is regenerable and gitignored. Reports moved to `eval/reports/history/` enter git as summaries only; server logs, caches and per-row dumps over 512 KB stay local. Delete server logs and caches when a run's report is written.
- Before every commit run `node tools/shard-large-files.mjs --check` and check the size of the change (`git status`, `du`). A change of more than about 100 MB is a mistake to investigate. Commit periodically after this cleanup check (owner, 2026-10-01); never push unless asked.

## Project journal and topic notes

Every agent that starts, finishes or blocks a meaningful task, or records an owner decision, appends one event to `status/journal.jsonl`: `node tools/journal.mjs add --area <data|language|eval|training|server|docs|process> --state <started|progress|done|blocked|decision> --title "…" --detail "…" [--link <path>]…` (actor from `CHATSOP_ACTOR`). The journal is append-only: correct a mistake with a new event. Experiment records (id, hypothesis, DS007 preregistration link, data version, status, results, conclusions) go to `status/experiments.json`; major work is a task record in `status/tasks.json` (owner side and agents side apart).

Record every meaningful analysis, suggestion, result, observation, plan, open question and owner decision also as a topic note: `node tools/notes.mjs add --topic <id> --kind <decision|suggestion|analysis|observation|experiment|result|plan|question|correction> --title "…" --body "…" [--link <path>]…` (topics in `status/topics.json`; failed and restarted attempts included). Notes are append-only; a correction is a new note with `--supersedes <note id>`. The server's `/experiments` section is the living index; `/eval` shows the evaluation data behind a result.

## Early stopping of experiments

**Never work or spend tokens without a reason (owner rule, 2026-10-02).** Running hundreds of cases when a conclusion can already be drawn is forbidden and harmful. Development is a loop of small runs: a few random cases (5–10 per form or family), fix what they show, rerun a fresh small random sample, until the problems stop appearing; only then measure once at a size that answers the question. When a result takes shape, stop: do not prolong the experiment, fix and restart small. Default limits: at most one rerun per question, omp tasks 2 hours unless a reason is written down, prompt cache on for local models.

Do not spend compute on an experiment whose answer is already clear. Evaluations run in stages on stratified samples (small first, then larger only if still undecided) with a paired bootstrap interval after each stage; stop when the interval is decisive in the preregistered direction by a practically relevant margin, when a useful gain is impossible (futility), or when the condition is broken (for example more than 20% unparsable or empty outputs on the first 100 rows). Write the stopping rules into the preregistration (or record a deviation) and record every stop with stage, numbers and reason in the journal, the topic notes, the experiment record and the task page. Run only one GPU-intensive job per machine at a time and never kill unrelated work.

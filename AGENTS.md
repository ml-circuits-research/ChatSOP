# ChatSOP agent guidance

## Scope

This is the single root instruction file for changes to ChatSOP. The product has one goal (owner decision of 2026-10-01): **beat small LLMs at reasoning through symbolic processing**, and help small LLMs reason symbolically. Nothing else is in scope. The chat and the system work through the **formalizer**, which is step by step (owner decision 2026-10-02; default strategy LocalLLMStepByStep): the system asks short questions about the user's message and assembles the circuit itself; a model reached through TinyAgent only answers the questions, by tier name, on the ladder `tiny`, then `small`, then `good` (a question escalates only when the lower tier's answer cannot be read or the tier does not answer); there is no omp on any path; the validator checks them, the KnowledgeLinker links their strings, the StrategyRouter sends the problem to the right reasoning strategy or the oracle, and the answer is rendered deterministically in English (a TinyAgent tier may later formulate the final wording). Follow the current user request, this guidance and the design specifications; track outstanding work in `TODO.md` and delivered work in `PAS_TASK.md` without presenting either as product documentation. Open questions that need the owner's decision go in the root `questions.md` (always present; each question has a stable ID, context, options, a recommendation and an empty answer line); once a decision is implemented, remove the question and record the decision in the owning DS, `PAS_TASK.md` or `CHANGES.md`. Decide low-level matters yourself (correctness, genericity, production use, user value); ask only what changes what the system does.

## Names

- **SOP Lang**: the checked language of circuits (DS004); the circuit surface the formalizer may author is DS014.
- **Formalizer** and **`lib/query-author`**: the formalization strategy is step by step (LocalLLMStepByStep by default, `lib/query-author/step-by-step/`; InternalReasoningStepByStep, `lib/formalize/internal-reasoning/`): the system asks short questions and assembles the circuit; the answering model is the tier ladder `config/runtime.json` `queryParser.local.ladder` (product: `tiny`, `small`, `good`), escalated per question. Larger tiers answer the SAME questions, so tiers are compared like with like. `lib/query-author` holds the shared retrieval, vocabulary and validator. The one-shot strategy LLMDirect (a model writes the whole circuit with repair rounds) is archived in `probably_obsolete/one-shot-formalization/` (owner, 2026-10-02); the names LLMDirect, CodingAgent and LocalLLMDirect run the step-by-step default with a note in the trace. `POST /v1/author` (knowledge authoring, `lib/ingest/direct-author.mjs`) and `server/query-parser.mjs` are the entry points. One formalization per turn; quality control is offline, from TinyAgent's request log and audit store.
- **Validator**: admits only what the circuit surface allows, with bounded repair rounds. **KnowledgeLinker**: links the entity strings of a circuit to the base memory; it does not parse language. **StrategyRouter** (`reasoning/router/`): chooses the strategy by problem features. **Oracle**: the exact JavaScript reference (`js-reference`) used to verify and as the fallback strategy. **Result packet**: what the runtime returns; `sop/answer-text.mjs` renders it.
- **Session**, **base memory** (core-min, core-en, world-v1, demo): DS022. Memory engines: RecallMemory, HoloMemory, SQLite, scan, hybrid (DS005, DS016 to DS021).
- **Archive**: earlier experiments (the small-model branch, paused components, the one-shot author, the formalization experiments of 2026-10-02/03: six paths, method library, stage-A decomposition, dual formalization) live in `probably_obsolete/` and are history only; nothing there is a rule for current work and nothing is revived in the product. Say "the validator", "the runtime" or the component's name, never "host".

## Circuit-authoring boundary (non-negotiable)

The formalizer gets the user's message and the memory vocabulary (retrieved predicates and entity hints) and writes **only circuits**: queries, constraints, `unclear`/`unparsed` markers, and session definitions or assumptions marked `assumed`. It never answers and never states facts. The validator admits only what the circuit surface (DS014) allows, repairs in bounded rounds, and a refused circuit is reported, never silently replaced. The prompt never contains answers, gold, sealed tests or other sessions. There is **no SymbolicLM fallback**: when no model is available the answer is an honest `parse_unavailable`. A coding-agent circuit that is wrong executes to a wrong answer, so the benchmark (`experiments/proposal/symbolic-vs-llm-benchmark.md`) counts a wrong circuit apart from an honest unknown. Statements of the user are turn-local evidence kept only in caller-owned conversation context; suppositions, reported speech and `assumed` lines are used conditionally or reported; none is a sourced fact or a repository write. `remember` is a trusted runtime operation, not a model instruction. The answer language is English. Wire changes update `docs/wire_types.html` and `docs/wire_typs/` with examples (`tests/docs/wire-help.test.mjs` executes them).

## Directions

1. Work toward the benchmark in `experiments/proposal/symbolic-vs-llm-benchmark.md` (the validation procedure), the TinyAgent tier chain with answer formulation, KBQA slice runs, StrategyRouter evaluation and large-data soundness. `TODO.md` tracks the gates; product documentation never asserts progress.
2. A read must not hide a write. Proof-use promotion of an admitted, metadata-verified observed fact is allowed only when `policy.reinforce !== false` and the retention configuration (`reinforceOnUse`) both permit it, only for a real non-hypothetical proof, and the reason packet reports it. Candidate retrieval alone promotes nothing.
3. A requested backend is never substituted. An explicit unavailable solver returns `unsupported` with the backend in `route.backend` and `fallback: null`; a JS-only mode with an explicit external backend, and the reference strategy with an external backend, are rejected the same way. `advanced` is routing, not a fourth solver. A problem without an engine is `not_computable`; a link without an engine is `not_checked`.
4. SOP relations use whitespace-separated terms and JSON-quoted text, not parentheses or commas; Boolean conditions use `all`/`any`/`end` groups. Keep genuine JavaScript, solver syntax and exact source quotations apart from SOP grammar.
5. Models are used as they are; this project does not train models. Never install models, solvers or packages merely to start the runtime.
6. Source rights are per asset (`DS011`): only text recorded as cleared or permissive-attribution may be ingested, exported or published; unverified or restricted text stays in the local cache `datasets_sources/`. Released inspired-by corpora take structure and statistics, never text, and pass `node tools/datasets/no-copy.mjs`.
7. Test and data authority: sealed suites live under `eval/suites/**`; generators and tuning code never read their test files (`eval/leakage.mjs`, `tests/project/leakage.test.mjs`). The goal is a system as general as possible (owner, 2026-10-02; the earlier "same form, different words" rule belonged to the frozen small-model training and no longer limits evaluation). Every evaluation reports three levels separately: (a) known forms with new words (`tools/datasets/audit/content-word-overlap.mjs`, `tools/eval/formalization/query-forms/overlap.mjs`), (b) held-out forms never used in development, guides or examples, and (c) compositions of known classes and free natural questions; claims are made per level. Duplicated cases between development and test are still forbidden. Evaluations are staged small-first with a paired bootstrap interval. `eval/reports/current/` holds regenerable observations, `eval/reports/history/` archived numbers; never present a historical number as a current run.
8. Knowledge: documents, books and other sources are written into task-type base memories by the direct author (a chain model) as knowledge wires with provenance (source, location, quote); sessions fork from a base memory, and the chat's default base carries encyclopedic and common-sense knowledge. There is no manual accept/reject step (owner, 2026-10-02): knowledge enters after the validator and automated checks, and errors are corrected systematically through tests and interactions. Session definitions and assumptions written while formalizing are used and labelled in the answer; they reach a base memory only through the same automated path. New knowledge needs no model change.

The normative contracts live in the DS set (`docs/specs/matrix.md`); where this file and a DS disagree, the DS is the source of truth for documented behavior. Write documentation, specifications and code comments in clear English.

## Runtime Defaults

Node.js >=22.13 with `.mjs` modules, explicit imports, `node:` built-ins, async/await and module-relative resources. Prefer built-ins and small auditable code; record a necessary dependency in `dependencies.md`. ## No hardcoded understanding (owner rule, 2026-10-02, repeated)

Language understanding (the kind of message, entities, relations, quantifiers, negation, time, courtesy, emotion) is done by the model inside the formalization step; the system's structure comes from the SOP language, the validator and the memory (vocabulary, lexemes, facts, rules: versioned, verifiable data). Hand-written word lists or regex tables over natural-language phrasings, phrase-specific branches, per-case fixes and additions made to pass a test are forbidden. Deterministic code is for structure (SOP parsing, normalising numbers and dates, rendering from the result packet), never for interpreting phrasings. Fixes are generic: the language, the validator, the protocol's questions, or memory data. **No user-facing text in code either** (owner, 2026-10-02): replies, courtesy and small-talk answers, "I don't know"/suggestion messages, tone phrases and answer templates live as SOP wires in a base-memory layer (versioned data, visible in `/review`), chosen by the renderer from the packet; code holds no phrasing. The step-by-step question templates may stay in code for now and move to wires later (InternalReasoningStepByStep).

## Which path runs which model (owner rules, 2026-10-02)

Pick the execution path by the model's provider, without asking: **Anthropic models** (Opus, Sonnet) run as Claude subagents; **every other provider** runs through `omp` or through TinyAgent (`TinyAgent/`: one server per machine, `node TinyAgent/bin/tinyagent.mjs serve`, OpenAI/Anthropic-compatible at `http://127.0.0.1:18080`; keys only in `~/.tinyagent/keys/<provider>.env`); local GGUF models run as TinyAgent's local model servers (llama-server), which it starts, shares and stops.

- **One model gateway** (owner, 2026-10-03): no component calls a model API directly; every model call goes through TinyAgent, from code through the library (`tinyAgent({purpose})` of `lib/tinyagent.mjs`) and from a command line through the CLI (`node TinyAgent/bin/tinyagent.mjs run|call|job|task|chat|stats|models|calls`). Claude subagents and external tools use the CLI (or its HTTP API). A client starts the server when none runs. `tests/tinyagent/no-direct-model-calls.test.mjs` enforces the rule. Configuration layers, each over the previous one: `TinyAgent/config.default.json`, `~/.tinyagent/config.json`, `config/tinyagent.json` (ChatSOP's layer: tiers, runner, project TaskLambdas); role prompts live in `config/prompts/`. Every call of a TaskLambda (owner, 2026-10-03) leaves an audited folder with its input, output, effects and model calls (`~/.tinyagent/calls`, `tinyagent calls list|tree|show`). Manual: `TinyAgent/README.md`.
- **Implementation work:** Claude subagents, Opus or Sonnet.
- **Default model for LLM work** (owner, 2026-10-02): **`Qwen3.8 27b` from the openference plan through TinyAgent, tier `small`** (15 requests/minute, 5-hour window of ~400 plan requests, 0.1 per call; ~38 tokens/s; 32/36 on the book calibration). Use it wherever possible: judging, labelling, data generation, knowledge authoring, and the `small` rung of the formalizer's tier ladder (answering the same step-by-step questions as `tiny`).
- **LLM batch work**, when the default is not enough or its quota is spent, in this order of preference: (1) other subscription models — larger models from the openference plan when the task needs them, z.ai GLM, Codex and Grok through omp while their quotas last; (2) the **Antigravity** subscription in omp, only when nothing else is left for large models; (3) **DeepSeek** (paid) only after every subscription is exhausted, through TinyAgent's `openrouter` provider (`/u/openrouter/v1/chat/completions`, or the library options `upstream` and `model`, model e.g. `deepseek/deepseek-v4-flash`; key in `~/.tinyagent/keys/openrouter.env`, real cost per call from OpenRouter `usage.cost`, shown by `tinyagent stats`); an official DeepSeek key, when given, goes to the `deepseek` provider. Prefer a direct call through TinyAgent (`tinyagent chat`, a skill or a job) over an omp session whenever the task is one prompt plus validation and repair (omp re-sends its system prompt, tools and files every turn). **Avoid Haiku** for batch work: it is too expensive.
- **LLM batch work is a TinyAgent job, task or skill** (owner, 2026-10-02): `node TinyAgent/bin/tinyagent.mjs job jobs/<job>` (`check` first, `--stage pilot` for the small stage), `tinyagent task --instructions ... --attach ...`, `tinyagent call <name>` or `tinyagent run "<request>"`; agents never loop over LLM calls by hand and read only the run's `summary.md` and `escalations.jsonl`. Jobs name model tiers or roles (`runner.roles` of `config/tinyagent.json`), never concrete models; every run writes only its own folder `state/llm-jobs/<job>/<run-id>/`, and a summary that enters the repository goes to a dated, run-named path, never a fixed shared name. TinyAgent refuses a run beyond its registered budget and untagged requests beyond a small daily allowance (every call carries a purpose: the library option `purpose`, the header `x-tinyagent-purpose`). Priority classes: a person waiting (purposes `chat`, `formalize`, `answer-*`) is `interactive` and served first; recurring work that can wait (regressions, bulk reviews) runs as `background`, which uses at most 70% of a plan's windows and only when nothing else waits, and is held, never refused. Responses are cached by default (cache modes `use`, `strict` for offline regressions, `record`, `off`). Project TaskLambdas are the modules of `jobs/lambdas/`, the job folders and the task templates of `jobs/templates/` (`tinyagent lambdas --server` lists them); each declares its effects, and a pure one called again with the same params and unchanged inputs returns its recorded output.
- **Local models** (tiers `nano`, `micro`, `tiny`) answer the step-by-step formalization questions, also in many parallel threads; they are not used as judges or synthetic-data generators. Qwen3.8 27B is too slow on this machine (~12 tokens/s); its openference copy runs at ~38 tokens/s.
- **Tiers** (owner, 2026-10-02; 2026-10-03: the openference plan everywhere, OpenRouter only as fallback): scripts, jobs and the product name a TinyAgent tier, never a concrete model: `nano` (local Qwen3-0.6B, started on demand and stopped after 15 idle minutes), `micro` (local Qwen3-4B, started on demand and stopped after 15 idle minutes, 32 slots; very simple high-volume tasks: equivalence, short yes/no, small talk; `supertiny` is an alias), `tiny` (local Qwen3.6-35B-A3B MoE, always on, ~66 tokens/s; owner decision 2026-10-03 after the MoE A/B; formalization and simple tasks go here), `small` (openference Qwen3.8 27b), `medium` (openference DeepSeek-V4-Flash), `good` (openference DeepSeek-V4-Flash, owner 2026-10-03 evening: GLM-5.3 ignored max_tokens), `best` (served by `tiny` until a stronger model is configured). Each cloud tier falls back to OpenRouter; with no key configured only the local tiers serve. A tier entry may carry a duration cap (`timeoutMs`): a call cut by it is answered `504 upstream_timeout`, never cached, and falls back down the chain. Planner and decider roles use `good`, audits `medium`, bulk work `small` or `tiny`. The local Qwen3.8 27B is not run.
- **Automated first, intelligent controller last** (owner, 2026-10-02): count the total cost, including the expensive orchestrating model (Claude) that reads results and repairs. Recurring work (review, repair, labelling, checks) runs as automated scripts, jobs and skills with cheap models through TinyAgent, deciding by deterministic rules: validator pass/fail, severity thresholds, agreement of two cheap passes. Only what the loop cannot resolve is escalated, as a short summary, to the intelligent controller.
- **Bulk review and fallback** (owner, 2026-10-02): review model output with `node tools/llm-review.mjs run --kind <kind>` (`lib/llm-review`, kinds in `config/review/`): `deepseek/deepseek-v4-flash` with low reasoning reads many items per call and writes only problem lines, confirmed problems are repaired by the same cheap model, validated and re-reviewed, and only the unresolved rest reaches the controller as `escalations.jsonl` plus a 10-line `summary.md`. When openference is unavailable (unreachable, 5xx or 429 after retries, a wait above `fallback.maxWaitMs`, or a call cut by its duration cap) TinyAgent serves the request with the next entry of the tier's chain (`Qwen3.8 27b` requests with `deepseek/deepseek-v4-flash` on OpenRouter), marked by the `x-tinyagent-fallback` header (reason in `x-tinyagent-fallback-reason`) and counted in `/stats`; a run that must stay on one model sends `x-tinyagent-no-fallback: 1` (library option `noFallback`).
- The product's request parser uses its configured step-by-step strategy and tier ladder (`config/runtime.json` `queryParser`). Draw obvious consequences yourself; do not probe or ask about what follows from known facts.
## Formalization improvement (owner, 2026-10-02): a permanent activity

The step-by-step formalization (LocalLLMStepByStep and InternalReasoningStepByStep) is driven by rules in the base memory, not by code or a large model: the protocol layer `config/knowledge/formalizer-protocol-v1/` plus a learned-rules layer that both strategies read. Every formalization error found anywhere (TinyAgent job audits, eval runs, agents, TinyAgent's audit store of chat traffic) is appended to `state/formalization-errors/inbox.jsonl` (append-only; source, message, expected answer or circuit, what went wrong). One improver owns the protocol: an automated TinyAgent job first (`jobs/formalization-improve`; tier `good` proposes protocol and rule wires, the validator and a regression gate on tier `tiny` decide), a Claude agent only for what the job escalates. Every case enters an accumulating regression set; a change is admitted only if it fixes cases and loses none. The goal is that `tiny` formalizes as well as `small`; the reference is the same step-by-step protocol answered by larger tiers (`small`, `good`), never a one-shot circuit (owner, 2026-10-02: one-shot LLMDirect is archived; we learn to ask the right questions, and where small models cannot answer, fine-tuning may become an option later). Other agents do not edit the protocol: they report errors to the inbox with `reportFormalizationError()` (`lib/formalization-errors.mjs`; kinds `parse_failed`, `invalid`, `wrong`, `unclear`, `missing_construct`). TinyAgent is generic and does not know about circuits, so the SOP-aware parts report: the eval harnesses (books, commonsense/query-parsers, generality) classify each failed row and report it automatically, the ChatSOP job plugins (`jobs/plugins/`) and project TaskLambdas (`jobs/lambdas/`) report circuit failures, and every agent that sees a failed formalization while doing other work reports it.

## Offline formalization regression (owner, 2026-10-02): a global concern

The translation from a message to SOP Lang (the step-by-step questions, the model's answers, their readers, the protocol decisions, the assembly into circuits and the validator) is covered by a local, fast, unit-test-like regression that calls no API and no local model: model answers are replayed from a record/replay cache, every translation step has its own expectation, and a failure names the first step that diverged. It is run often and pointedly (a fast tier in `npm test`, the full set in `npm run verify`), and every change to formalization keeps it green. Its cases are many and redundant, drawn from the thousands of problems of the owner's books as the source of diversity (never sealed suites). Execution by the reasoners is checked more carefully and more slowly elsewhere (the capability battery). Until the translator is solid, formalization is the focus and reasoning work waits.

## New wire types are a serious event (owner, 2026-10-02)

"New wires" in everyday work means new facts, rules, defaults, constraints or protocol data written with the existing wire types. Adding a wire **type** (a change of the SOP language, DS004/DS014) is rare: an agent that thinks one is needed appends a proposal to `experiments/proposal/wire-type-proposals.md` (the failing cases, why the existing types cannot express them, the proposed type, its semantics and its cost) and works around it meanwhile; only an Opus agent assigned to that review decides that a type is truly needed and the problem cannot be solved with the existing types; it then writes the syntax and semantics as a question in `questions.md`, and the type is implemented (with its docs `docs/wire_types.html`, `docs/wire_typs/` and tests) only after the owner approves them there. **Language changes need no question to the owner (owner, 2026-10-03):** "decide tu, nu mă mai întreba; ți-am dat permisiunea să extinzi firele sau să adaugi noi tipuri, cu condiția să nu strice ce există, și de asta avem regression testing". The capability battery's no-loss ledger and the offline regressions are the condition; proposals are still recorded in `experiments/proposal/wire-type-proposals.md`. **Standing authorization (owner, 2026-10-02 evening):** "I allow you, without approval, to improve wire types or add new ones; iterate all night until we can solve all the problems of the books." Until the owner revokes it, a wire-type change decided by the Opus reviewer is implemented without waiting for `questions.md`; it is still written to `experiments/proposal/wire-type-proposals.md` (cases, decision), documented (`docs/wire_types.html`, `docs/wire_typs/`, DS004/DS014), covered by the capability battery and recorded in `CHANGES.md` and the journal, so the owner can review it afterwards. Metacognition, the system's ability to reason about its own rules (which rule supports a conclusion, which premise is missing, which rule an option would add or block), must be supported (owner, 2026-10-02); when the existing types cannot express it, the reviewer proposes the needed type this way.

## ChatSOPAdapter: one backend for the chat and every evaluation (owner, 2026-10-03)

The chat, the API and every evaluation harness answer through ONE reusable module, `ChatSOPAdapter`; no evaluation keeps its own copy of the formalization and solving glue, so a result measured offline is the result the chat gives. Its behaviours (modes) are configurable in `config/runtime.json` and per chat session: the step-by-step formalizer; the routed pipeline (structure → compute path B / jsEval / FOL / engineCode, with agreement as verification); and direct-verified (the model answers directly, the adapter tries to verify that answer symbolically and declares it verified or unverified). Every answer says how it was obtained and whether it was verified. Its model calls go through TinyAgent (`lib/tinyagent.mjs`) with the purposes `chat`, `formalize` and `answer-*`, so a person waiting is served with interactive priority.

## Early stopping of experiments

**Never work or spend tokens without a reason (owner rule, 2026-10-02).** Running hundreds of cases when a conclusion can already be drawn is forbidden and harmful. Development is a loop of small runs: a few random cases (5–10 per form or family), fix what they show, rerun a fresh small random sample, until the problems stop appearing; only then measure once at a size that answers the question. When a result takes shape, stop: do not prolong the experiment, fix and restart small. Default limits: at most one rerun per question, omp tasks 2 hours unless a reason is written down, prompt cache on for local models.

Do not spend compute on an experiment whose answer is already clear. Evaluations run in stages on stratified samples (small first, then larger only if still undecided) with a paired bootstrap interval after each stage; stop when the interval is decisive in the preregistered direction by a practically relevant margin, when a useful gain is impossible (futility), or when the condition is broken (for example more than 20% unparsable or empty outputs on the first 100 rows). Write the stopping rules into the preregistration (or record a deviation) and record every stop with stage, numbers and reason in the journal, the topic notes, the experiment record and the task page. Run only one GPU-intensive job per machine at a time and never kill unrelated work.

# Local OpenAI-compatible server

## Scope and authority

`server/http.mjs` provides a localhost HTTP façade. The only conversational execution path is `Agent.turn` → the SymbolicLM service → validated declarative SOP → host-generated `Runtime` circuit. The formalizer ([DS021](specsLoader.html?spec=DS021-model-surface.md)) sees only the user's message and may author only `stated`, `assumed`, `unclear`, `query` or `constraint`, as context-free strings that the host links to its lexicon; it cannot choose `remember`, claim documentary provenance, invoke tools, or publish knowledge. A separately authenticated, explicitly supplied `chatSop.trustedSop` circuit may contain `fact`, `event`, and `remember` wires only; it runs as a trusted user action in that user's session before the question. The receipt of a stored claim is returned as `chatSop.system_receipt` and can identify the target of a later correction. This is not model output or automatic ingestion. Trusted writes persist in the repository's private session; they are not committed to another user's state or published as base knowledge.

## The formalizer service and fail-closed start

The server formalizes only through the SymbolicLM service of the registry ("Formalizer models" below). There is no prompt profile, no `formalizer` endpoint in the runtime configuration and no backend identity attestation: FormalizerLLM (a small fine-tuned LLM writing SOP Lang directly from the message, removed from the product on 2026-10-01) has no serving path, and a registry entry may formalize only as a `service`. `startServer` fails closed when the registry has no SymbolicLM service (or `formalizers: false` disables it); library and test callers inject a formalizer function into `Agent.turn({formalizer})` instead of starting a server. The service reads the message alone (DS021 "Model boundary"); no context block, vocabulary list, identifiers, earlier turns or clock reach it. The source tree ships no checkpoint, and the server process itself never loads weights. GET `/readyz` returns 503 with `{ready:false,model_available:false}` when the SymbolicLM service is absent or not ready, never a pretend success.

## Formalizer models

`config/formalizers.json` (`format: chatsop-formalizers-v1`; another file through the runtime configuration key `formalizers`) is the registry of models the chat can use: `default` names the formalizer that the façade id (`chatsop-local`) selects, `defaults` the default model of each capability (`formalize`, `proofread`, `proofread-symbolic`, `translate-clean`), and each entry of `models` has an `id` (lowercase letters, digits, `.`, `_`, `-`), a `label`, a `note`, `capabilities` (a non-empty subset of `formalize`, `proofread`, `proofread-symbolic` and `translate-clean`; there is no implicit default capability; `formalize` is allowed only on a `service` entry; `proofread` marks LanguageProofingLLM for the textToCleanEnglish step, `proofread-symbolic` marks SymbolicProofingLLM, the optional rewrite of SymbolicLM's pipeline, and `translate-clean` marks the translator) and exactly one source: `gguf`, a repository-relative model file, or `service`, a repository-relative Node script that serves the chat-completion interface itself (`<script> serve --host H --port P --device cpu`), whose only capability is `formalize`. `server/formalizers.mjs` (`loadRegistry`) refuses duplicates, an unknown or non-formalize default, a `defaults` entry naming a model without that capability, unknown capabilities, `formalize` on a `gguf` entry and an entry with both or neither source. The shipped registry has: SymbolicLM `symbolic-lm` ("SymbolicLM (Stanza + translation + rules)", the service `lib/symbolic-lm/service.mjs`: per-token language identification, symbolic Romanian-to-English translation, Stanza Universal Dependencies parses in the host environment `~/nlp-venv` with 4 CPU threads and the deterministic rules of `lib/ud-to-sop/`, [DS021](specsLoader.html?spec=DS021-model-surface.md) "SymbolicLM"); its reply carries a `symbolic_lm` object with the route, the message language, the uncertainty signal and the English text, and, when the request asks for it ("Understanding in the chat"), the analysis finally used, the rewrite trace and the per-sentence interpretation; the entry's `rewrite.mode` (`off`, `gated`, `always`) is the default of the chat's SymbolicProofingLLM setting; `language-proofing-llm` (`proofread`, the fine-tuned Gemma 3 270M production build of run `language-proofing-gemma270m-prod1`, F16 GGUF); `symbolic-proofing-llm` (`proofread-symbolic`, Gemma 3 270M iteration 3, `models/gemma/symbolic-proofing-gemma270m-it3/proofreader/gguf/ep3-f16.gguf`, message-only prompt, one sentence per request); and `translator-llm` (`translate-clean`, Qwen3-4B Q4_K_M). The GGUF models start on demand like any other. No base instruct model and no FormalizerLLM checkpoint is in the registry (their files, training code and reports stay as evidence, and `tools/` and `eval/` still evaluate them). Adding a model means adding an entry; no code changes.

`ModelManager` runs a `gguf` model in its own CPU `llama-server`, and a `service` entry as its own Node process on the CPU with the GPU hidden, when it is first selected (`POST /v1/models/<id>/start`, or the first chat message naming it): a free loopback port, `-ngl 0` with `CUDA_VISIBLE_DEVICES` empty (no GPU work, AGENTS.md), at most 8 threads, one slot, an 8192-token context and `--jinja` (the checkpoint's own chat template), as the evaluation harness. A running server is reused; one unused for the idle time is stopped unless it is kept open; the number running at once, their memory and the eviction rules are the model lifecycle below ("Model lifecycle"; until 2026-10-01 at most three ran at once, which restarted models on almost every chat message); every server is stopped when the ChatSOP server closes, on SIGINT/SIGTERM and, as a last resort, on process exit. Each model's output goes to `<state root>/formalizer-logs/<id>.log`. The binary is the first existing of `LLAMA_SERVER_BIN`, `LLAMA_SERVER` (the `training/cli.mjs serve-cpu` convention), `LLAMA_CPP_DIR/build/bin/llama-server`, `vendor/llama.cpp/build/bin/llama-server` and `~/llama-cpp-venv/llama.cpp/build/bin/llama-server`. A model's state is `stopped`, `starting`, `ready` or `error` (with the reason: missing binary or GGUF file, a server that exited or did not answer `/health` within 120 s). The request is `predictMessage` of `lib/llama-chat.mjs`, the same function the evaluation tools use: the message as the only user content, no system prompt, temperature 0 and `top_k` 1, no extra stop strings (the template's end-of-turn token ends the answer), at most 6144 new tokens, and the raw `/apply-template` + `/completion` retry when llama-server fails to parse its own finished output. A truncated generation is refused. A model is used only for the capabilities it declares (`ModelManager` refuses others with 400 `unsupported_mode`).

## Model lifecycle

Owner complaint of 2026-10-01: the check was slow; "Hello" took several seconds. Measured cause: one chat message needs up to four managed processes (LanguageProofingLLM `language-proofing-llm`, the translator `translator-llm` (Qwen3-4B Q4, about 13 s to start on the loaded host), SymbolicProofingLLM `symbolic-proofing-llm` and the SymbolicLM service with Stanza (about 25 s)), the manager kept at most three, and so it stopped and started a model on nearly every turn (a Romanian sentence evicted LanguageProofingLLM to start the translator; the next English sentence evicted the translator again). The lifecycle is now a setting, not a constant.

**Settings** (`config/server-models.json`, format `chatsop-server-models-v1`, `server/server-models.mjs`): `maxRunning` (default 5 in code, 6 in the shipped file: the four pipeline models plus a chat or base model, plus one), `idleMinutes` (60), `memoryBudgetMb` (`null`: half of the RAM), `turnWindowSeconds` (30), `warmup` (true), `warmMemories` (a list of base memory ids, default `["default"]`: with `warmup`, each is opened read-only in the background at server start and its snapshot chain and SQL view decoded by `server/warm-memories.mjs`, so that the first question over it does not pay the roughly 4 s of decoding; a missing id is skipped, the log line names each memory, its facts and milliseconds) and, per managed model, a **mode**: `keep_open`, `on_demand` or `off`. The four pipeline models are `keep_open` by default, every other model `on_demand`. The settings are read at server start, edited at runtime through `GET|POST /v1/server/models` and the chat page (Settings, Server models: one row per model with its state, memory, start cost and a three-way control) and written back to the file on every change; `CHATSOP_SERVER_MODELS` names another file (a private test server never rewrites the shared one). There is no admin gating (the API uses the server's own authentication).

**Modes.** `keep_open`: pinned, started in the background at server start, probed with one small real request, never evicted, never idled out, started again by the sweep (at most once a minute) if it dies. `on_demand`: started when a request needs it, stopped after the idle time, evicted when room is needed. `off`: never started, stopped at once when switched, and a request that needs it fails with `model_off`; the callers degrade as for any unavailable component (the translator falls back and says so, the analysis reports the component in `errors`). A mode change takes effect at once (`off` stops the model, `keep_open` starts and probes it in the background). `maxRunning` may not be below the number of kept-open models (400 `invalid_settings`).

**Eviction.** A start first makes room: fewer than `maxRunning` other models and the estimated memory of the running ones plus the one to start within `memoryBudgetMb` (resident memory measured from `/proc` including child processes, else `memoryMb` of the registry entry, else the GGUF size times 1.15 plus 300 MB, 2500 MB for a service). A victim is a ready, idle, unheld model that is not `keep_open`; the models used within `turnWindowSeconds` go last, then least recently used first. **A model is never evicted in the middle of a turn**: `ModelManager.hold(ids)` leases models for a whole turn (the cleaning step holds the proofreader and the translator, the analysis holds SymbolicLM and the rewrite model) and `use` holds its model from before the start to the end of the work; with no victim the start fails with a retryable 503 `formalizer_capacity` that names the reason. Every start, ready (with the measured start time), evict, stop, idle, revive and mode change is an event in memory (`manager.events()`) and in `<state root>/formalizer-logs/manager-events.jsonl`.

**Warmup.** After the server listens (it is usable at once), `capabilities.warmup()` runs in the background (off with the `warmup` setting or `CHATSOP_WARMUP=0`): it starts every kept-open model in parallel, loads the LanguagesUtil word lists of the cleaning gate in the server process (a synchronous read of several seconds, begun after the model processes are spawned, so `/health` can answer slowly in that window), warms the listing of the coding agent's models, and sends each model one probe request through the code a turn uses (a Romanian sentence through the translator, a misspelt English one through the proofreader, a rewrite, an English and a Romanian analysis with tone and the scope detector), because the first request of a model pages its weights in and loads parsers and dictionaries. The state is `disabled`, `warming`, `warm` or `partial` (a model that failed is named), reported in `GET /health` (also `/healthz`, no authentication) and `GET /v1/capabilities` as `warm: {state, ready, ms, resources, kept_open, models: {id: {mode, state, warm, start_ms, probe_ms}}}`.

**Latency budget.** The target of the owner request, on an idle machine with the models warm: a greeting under 1 s end to end (the page's proofread, analysis, route and formalize calls), a typical English sentence under 2 s, a Romanian sentence through the translator under about 3 s; a first message after the server start waits only for what warmup has not finished. Avoidable work removed: a pure greeting or thanks that LanguagesUtil marks English and the gate finds clean skips the cleaning model (`llm.skipGreetings`, default true; `sendAll` keeps its meaning for every other sentence; the result lists it in `skipped`); the sentences of one message are cleaned in parallel (the translator and the proofreader are different processes) and put back in order; `POST /v1/route` reads the same cached SymbolicLM call as `POST /v1/understand` (same message, interpretation and rewrite setting) instead of analysing the message again, and an analysis without the interpretation reuses a stored interpreted call; models are no longer restarted. What remains is the compute of the models themselves (Stanza parse and the interpretation round trip of the SymbolicLM service, about 0.7 to 1.5 s per sentence on this host when it is not loaded).

## textToCleanEnglish: a user-validated pre-formalization step

Owner decision of 2026-09-30: formalization handles only clean English. Before a message reaches the formalizer, the chat page may call `POST /v1/text-to-clean-english` (authenticated the same way as `/v1/chat/completions`; body `{message}`, at most `maxContextBytes`), which runs `textToCleanEnglish` (`lib/text-to-clean-english/`, [DS021](specsLoader.html?spec=DS021-model-surface.md) "textToCleanEnglish"), the chat step validated by the user that calls **LanguageProofingLLM** (the LanguageTool backend was removed on 2026-10-01), entirely as **host code before the model boundary**: it corrects spelling and grammar, translates Romanian or mixed Romanian/English text to English, and simplifies wording, then returns `{original, clean, changed, reasons, spans, backend, confidence}` (since 2026-10-01 also served as `POST /v1/language/proofread` with `status`, `errors`, `timings`, `cache` and `versions`, [DS030](specsLoader.html?spec=DS030-capability-apis.md): a sentence whose model cannot run stays as written and is listed in `errors`) — never a formalization. The host splits the message into sentences (`lib/sentence-split.mjs`); a cheap, conservative gate (non-English tokens, a spelling signal, or a handful of cheap grammar-trouble regexes) skips every already-clean English sentence without calling any backend, and only flagged sentences are sent to the model, one request each, unless `llm.sendAll` is true, which sends all sentences, clean ones included (the code default is `false`; the shipped `config/text-to-clean-english.json` sets `true`, owner decision of 2026-10-01, so every English sentence is sent) (`changed: false`, `backend: "none"`); config/text-to-clean-english.json's `enabled: false` disables the whole step the same way, for every message, without a server restart. The backend is a small, explicit, swappable choice (`config/text-to-clean-english.json`, `backends.english`/`backends.nonEnglish`: `llm`, LanguageProofingLLM, a registry model with the `proofread` capability (`language-proofing-llm`) started on demand through `ModelManager.ensure` when a sentence first needs it, `translator-llm`, or `none`); an unreachable backend degrades to `backend: "none"` (the message unchanged) rather than failing the request, so the chat stays usable without it. A backend that answers with no text is treated as unreachable, never shown as an empty proposal.

Since the owner decision of 2026-10-01 (translator for Romanian and mixed input) `backends.nonEnglish` is `translator-llm`: Romanian and mixed sentences go to the registry model `translator-llm` (capability `translate-clean`, Qwen3-4B-Instruct Q4_K_M, started on demand like any registry model), English sentences to LanguageProofingLLM as described next; a translator that cannot run is replaced by LanguageProofingLLM and the chat's review shows a *Fallback* note ([DS021](specsLoader.html?spec=DS021-model-surface.md) "textToCleanEnglish", [DS030](specsLoader.html?spec=DS030-capability-apis.md)). Earlier default (owner decision of 2026-10-01, which removed Qwen3-1.7B from the chat): the gate, then **LanguageProofingLLM** for every flagged sentence, English, Romanian and mixed alike (`backends.english = "llm"`, `backends.nonEnglish = "llm"`, `llm.model = "language-proofing-llm"`, `llm.sendAll = false`). LanguageProofingLLM is the fine-tuned Gemma 3 270M of run `language-proofing-gemma270m-it1` (GGUF Q8_0 from `models/gemma/language-proofing-gemma270m-it1/proofreader/gguf/ep3-q8_0.gguf`; report `eval/reports/history/language-proofing-it1/summary.md`). It is a registry entry of `config/formalizers.json` with the single capability `proofread`, so no chat mode lists it; it starts on demand like any registry model (CPU `llama-server`, idle stop, at most three managed models at once) and is asked exactly as in training: the sentence as the only user message, no system prompt, greedy decoding, no name masking (a reply that loses a digit run or a quoted span of its input is reported with confidence 0.5). The gate is conservative and its spelling signal is weak, so a typo in an otherwise well-formed English sentence may pass unflagged; set `llm.sendAll` to `true` to send every sentence to the model (about 110 ms per sentence on 4 CPU threads). The survey `text-to-clean-english-v1` (`eval/reports/current/text-to-clean-english/summary.md`) remains the record of the earlier LanguageTool plus Qwen3-1.7B default. The LanguageTool backend was removed on 2026-10-01 (hygiene H19). With no `llama-server` or no GGUF file the message is left unchanged and the chat keeps working.

The chat page's *Clean before formalizing* toggle (on by default, remembered per browser) calls this endpoint before sending; when it reports a change, the page shows the proposed English with a word-level diff and three choices — **Accept**, **Edit** (loads the proposal into the composer for further changes) and **Send original** — and nothing reaches the formalizer until the user picks one. Whichever text is finally sent, the request to `/v1/chat/completions` may carry an optional `cleaning: {original, backend, changed}` field recording what the cleaning step proposed; the formalized text itself is the request's `messages[0].content`, exactly as for any other turn (DS021 "Model boundary" is unaffected: the formalizer still receives only that one string). The `chatSop` trace then carries `cleaning` (the same object, or `null` when the step was skipped, off, or not used), next to the existing formalize trace fields, so both the original and the accepted wording stay visible after the fact.

**The edges of the English-only core (owner decision of 2026-10-01).** The chat page's step above is a preview: the server applies the same translation again as the **input edge** of `POST /v1/chat/completions`, `POST /v1/understand`, `POST /v1/symbolic/analyze`, `POST /v1/symbolic/rewrite` and `POST /v1/route` (`capabilities.toEnglish`): a message the gate reads as English passes unchanged; a Romanian or mixed message is translated (translator-llm, LanguageProofingLLM as the reported fallback, names, numbers and quotations masked), so SymbolicLM, the linker, the reasoner and the agent's anchoring check only ever see English (`input_translation` in the responses and the `chatSop` trace). When the translation cannot run the chat answers `503 backend_unavailable` and the capability APIs report the component error, never a silent Romanian message. The **output edge**: when the answer language is not English (API `language` or an explicit request in the message, `server/language.mjs`), `capabilities.translateTo` translates the finished English answer with the translator-llm (`lib/translator-service/answer.mjs`; names, numbers, quotations and identifiers masked); the `chatSop` trace carries `answer_translation` (language, backend, status, the original English text) and `english_text`; a translator that cannot run leaves the English answer with `answer_translation.status = backend_unavailable`. The SymbolicLM service refuses a non-English message with `422 non_english_input`.

## Understanding in the chat

Owner request of 2026-10-01: the chat shows what SymbolicLM understood, in short controlled English, so the owner can form an opinion by manual testing. It is host code after the formalizer's analysis; the formalizer's input stays exactly the user's message ([DS021](specsLoader.html?spec=DS021-model-surface.md) "Model boundary"). It needs the SymbolicLM model (`symbolic-lm`); other formalizers make no analysis and the answer carries `understanding: null`.

**Request.** `POST /v1/chat/completions` accepts `understanding: {interpret?: boolean, rewrite?: "off" | "gated" | "always", emotion?: boolean}` (any other key or value is a 400). `interpret` (default `true`) adds the interpretation CNL of the analysis SymbolicLM actually used. `emotion` (default: `enabled` of `config/emotion-detection.json`, `true`) switches the EmotionDetectionSystem ([DS029](specsLoader.html?spec=DS029-emotion-detection.md)) on or off for this message: the host then reports `understanding.emotion` (signals, emoticon suggestions, the classified leftover spans, the `pragmatic` wires; the SymbolicLM service is always asked with `emotion: false` and the detection runs on the host through the cached `emotionFor` of [DS030](specsLoader.html?spec=DS030-capability-apis.md)), the chat page lists them under "I understood" (spans classified as courtesy or tone no longer count as not represented), the agent appends the wires to the circuit and a message that only greets, thanks, apologizes or closes gets a short courtesy reply without computation. The chat setting "Detect tone and courtesy" sends it and `GET` chat settings report `emotionEnabled`. `rewrite` chooses the SymbolicProofingLLM rewrite of SymbolicLM's pipeline for this message (default: `rewrite.mode` of the `symbolic-lm` registry entry, `gated` by the owner's decision Q-PROOF-1 of 2026-10-01): `off` calls no model; `gated` sends only sentences whose default and accurate Stanza trees are not identical and keeps a rewrite only when its trees are certified and names, numbers, negation, quantifiers and the question mark are kept (`rewriteWhen: "trees"`, `rewriteAccept: "certified"`); `always` sends every sentence and keeps every rewrite (`rewriteWhen: "always"`, `rewriteAccept: "off"`). For `gated` and `always` the server starts the registry model with the `proofread-symbolic` capability (`symbolic-proofing-llm`) on demand and hands its endpoint to the SymbolicLM service in the request (`symbolic_lm: {interpret, rewrite_url, rewrite_when, rewrite_accept}`, host options beside `messages`, never part of the message). A rewrite model that cannot start leaves the rewrite off and says why in `requested.rewrite_error`. `POST /v1/text-to-clean-english` accepts `sendAll: boolean`, overriding `llm.sendAll` of `config/text-to-clean-english.json` for that call ("send every sentence").

**Response.** `chatSop.understanding` (null when the formalizer is not SymbolicLM):
- `requested` `{interpret, rewrite, rewrite_model?, rewrite_error?}`: what was applied;
- `message`, `analysed_text` (the English text the analysis belongs to: the translation of a Romanian or mixed message, or the text after an accepted rewrite), `route`, `language`, `english`, `uncertainty` `{uncertain, kinds}`;
- `rewrite`: the pipeline trace `{input, output, applied, gate, acceptance, units: [{text, sent, accepted, reasons, output, certified, uncertain}]}` (`null` without a rewrite model, `{applied: false, gate: "no rewrite function"}` when it is off);
- `interpretation` (`null` when `interpret` is false): `{version, available, reason?, text, language, sentences, not_represented, outside_sentences, framing, rewrite, certified}`. `available: false` with a `reason` for an analysis in another language (a Romanian message sent unchanged is analysed in Romanian; the CNL is English only). Per sentence: `index`, `text`, `start`, `end`, `display_text` (the sentence with a masked lead-in such as "Remind me," when one belongs to it), `status` (`verified`, `uncertain` or `empty`), `cnl` and `cnl_sentences` (only when verified), `unverified_cnl` (an uncertain sentence's CNL, kept apart), `round_trip` `{pass, reasons}` (the CNL is parsed by SymbolicLM and must give the same structures), `not_represented` (verbatim spans the CNL does not use), `framing`, `notes`, `summary` (a raw analysis summary such as `root: work; nsubj: Ana; obl: Lidl`), `certified` (identical default and accurate Stanza trees; `true`, `false` or `null` when not computed) and `rewrite` `{original, rewrite, accepted, reasons, original_certified}` for a sentence a rewrite produced or one whose rewrite was refused. `certified` of the whole interpretation is true when every sentence is.

**Page.** The *Settings* tab of `/chat` (every choice remembered per browser in `localStorage`) holds, in its Language and Understanding cards: *Clean text before formalizing* (LanguageProofingLLM, "textToCleanEnglish"), *Send every sentence* (the `sendAll` of that call; default from the server's `config/text-to-clean-english.json`), *SymbolicProofingLLM rewrite* (off, gated or always; default from the registry) and *Show what I understood (CNL)* (on by default). With the last one on, the page shows the "I understood:" panel under the user's message, built from the `POST /v1/understand` answer ([DS030](specsLoader.html?spec=DS030-capability-apis.md) "The chat page"; the answer's own `chatSop.understanding`, which has the same shape, is used only when that call failed). The panel is a collapsible, compact block: per sentence the verified CNL, or an "uncertain interpretation" marker with the raw analysis summary (never a silent CNL; the unverified CNL is only in a nested detail), a certified or not certified badge, the sentence with the not-represented spans highlighted (the same spans are highlighted in the message the user sent when they occur in it verbatim), and for a rewritten sentence the original, the rewrite and whether it was accepted (certified) or rejected with the reasons. The panel is readable at 390 px and in the light and dark themes (`tools/ui/chat-cnl-shots.mjs` takes the screenshots into `eval/reports/current/chat-cnl/`). The LanguageProofingLLM proposal keeps its own review (word diff, Accept, Edit, Send original).

## Capability APIs and caches

Owner decision of 2026-10-01: every capability has its own endpoint under `/v1` (proofread, understand, symbolic rewrite, symbolic analyze, emotion detect, plus `GET /v1/capabilities` and `GET /v1/cache/stats` and `POST /v1/cache/clear`), authenticated like every other API, with `timings`, `cache` (`hit` or `miss`) and `versions` in every answer, small version-keyed caches with in-flight de-duplication in front of every language model call and of the SymbolicLM analysis, and the principle that analysis never fails totally (`status`, `errors` and a `clarify` message instead of an error). The contract, the caches and the page flow are specified in [DS030](specsLoader.html?spec=DS030-capability-apis.md); the reference with executable examples is `docs/api.html`. The chat page uses these endpoints independently and its formalize request reuses their cached work. Limits: `limits.maxConcurrentApi` (default 16 simultaneous capability requests, 429 beyond), `limits.maxContextBytes` per message and `limits.maxRequestBytes` per body, as for the chat.

## Chat data, sessions and the coding agent

Owner decision of 2026-10-01 ([DS031](specsLoader.html?spec=DS031-sessions-and-base-memories.md)): all chat data lives under one gitignored root, `chat_data/` (`chatData.root` in `config/runtime.json`, `CHATSOP_CHAT_DATA`), with `base_memories/`, `sessions/` and `tmp/`; a cleanup policy removes temporary folders older than `chatData.tmpTtlHours` (24) and sessions idle for `chatData.sessionTtlDays` (14) at start and every `chatData.cleanupIntervalMinutes`. A chat runs in a **session**: a working copy of a chosen **base memory** (a named, forkable knowledge store of any memory strategy, DS005 and DS023 to DS028) cloned into the session folder; the chat request carries `session_id`, and one automatic session per user and conversation on the empty `default` base memory serves requests without one. The earlier chat storage under `state/` (repository snapshots, shards, sessions, `http-conversations/`) is retired; `node tools/chat-data.mjs drop-legacy` removes it (the owner allowed dropping old chats and databases). `/v1/memories`, `/v1/sessions`, `/v1/omp/models`, `/v1/author` and `/v1/route` are the HTTP surface (DS031, `docs/api.html` sections 10 to 14). Inputs SymbolicLM cannot write can be sent to a coding agent (omp) that writes circuits as proposed drafts; it starts only when the user attaches files, answers yes to a scope note or sets "Always use the coding agent", never by itself. The chat page offers the session header, the Base Memory tab (list, view, fork, add knowledge, start session), file attachment, the omp settings and model picker in the Settings tab, the scope note under the message and the draft card with Accept and Reject; its endpoint contract is `eval/reports/current/product/ui-contract.md`.

## HTTP contract

`GET /docs` redirects to `/docs/`, which serves the repository documentation site statically (`docs/index.html`, the wiki, the wire help, the specification matrix and the DS files). Static serving needs no bearer token, is read-only, never lists a directory, refuses any path that resolves outside `docs/` (encoded traversal and NUL bytes included) and sets `no-cache` for HTML and a short cache for other assets. The chat API keeps its authentication.

For a signed-in session the server also serves a fixed allowlist of repository Markdown read-only as plain text (`REPO_MARKDOWN` in `server/http.mjs`): `skills/README.md`, every `skills/<name>/SKILL.md`, `eval/README.md`, `datasets/SOURCES.md` and the root `README.md`, `AGENTS.md`, `TODO.md`, `CHANGES.md`, `questions.md` and `dependencies.md`, so the owner can read the skills and project files on the server. ### Browser pages

When the server has the administrator password store (`npm start`, `startServer`), browser pages are layered on the unchanged session-cookie authentication; they present it and never grant access themselves. Page modules live in `server/pages/` and their routing in `server/web.mjs`. All server pages and the documentation site share one top menu (Home, Chat, Audit, Eval, an Experiments dropdown with the index, Topics, Reports, Timeline & live status and Open questions, Admin, a Docs dropdown with Overview, Runtime, Training, Wiki, Specifications, Wire help, How the model writes and Question types, then Logout, or Sign in on a signed-out server page), defined once in `server/pages/site-menu.mjs` and styled by `docs/assets/site-menu.css`; `docs/partials/header.html` is generated from it by `node tools/site-menu.mjs --write`, and a test keeps the two identical. The layout works at phone width. `GET /assets/sop-code.mjs` (public) serves the shared SOP highlighter (`server/pages/sop-code.mjs`), which the documentation pages use to link SOP blocks to the wire help; the chat trace, the audit and the evaluation browser use the same renderer. It links wire types and fields to their help pages and marks a type or field outside the parser contract "undocumented". The structural words `all`, `any`, `match`, `end` and the atom prefix `not`, read from `sop/conditions.mjs` and `sop/parser.mjs`, are grammar: they are rendered as syntax keywords linked to `docs/wire_typs/syntax.html#syntax-<word>` and never flagged; inside a `match … end` block the keyword lines `relation`, `role` and `polarity` link to their definitions and any other keyword there is flagged (`tests/sop-code-syntax.test.mjs`).

- `GET /` is a public home page. It states whether the visitor is signed in, whether the administrator password is set, and the formalizer state according to the same readiness check as `/readyz`: with a registry, every model with its state (`stopped`, `starting`, `ready`, `error`; the error reason only to a signed-in session); It links to `/chat`, `/audit`, `/eval`, `/experiments`, `/admin` and `/docs/`. A server created without the password store (bearer credentials only) serves the same page without sign-in state.
- `GET /login?next=<path>` shows the first-run "choose the administrator password" form while no password exists, and the sign-in form afterwards; a request that already carries a valid session is redirected to `next`. `POST /login` (form-encoded `password`, `confirm` for the first run, `next`) calls the existing `Auth.setup`/`Auth.login`, so the minimum length (8), the throttle (ten failures within a minute) and the scrypt verification are unchanged. Success sets the HttpOnly `SameSite=Strict` session cookie and answers 303 to `next`. `next` is accepted only as a same-origin relative path (a single leading `/`, no scheme, authority, backslash or control characters); anything else becomes `/`. A post whose `Origin` differs from `Host` or that the browser marks `Sec-Fetch-Site: cross-site` is refused with 403. Failures re-render the form with a plain message: mismatched passwords or a too-short password (400), a setup attempt after a password exists (409), a wrong password (401), throttling (429).
- `POST /logout` ends the session, clears the cookie and answers 303 to `/login` (same cross-site refusal).

- `GET /chat` (authenticated) serves the browser chat. There is no mode selector ("Chat mode"); the *Model* selector lists the registry models with the `formalize` capability (SymbolicLM, the only formalizer). It posts one user message per turn to `/v1/chat/completions` through same-origin fetch with the session cookie, selects the `conversation_id` (with a *New conversation* control), and renders each answer with a collapsible trace built from `chatSop` (status, backend, fallback, completeness, the formalizer that answered and the latency (formalization time), answer language and its source, user statements, carried statements, model assumptions and policy, `unclear` kind, the not-computable reading, reinforcement, model SOP, execution circuit, provenance, pending clarification). Status codes are explained in plain words: 401/403 sign in again, 503 selected model not available (with the reason), 422 model SOP refused (the trace shows what the model wrote and why), 409 conversation busy, 429 server busy, 504 time limit, 413 message too long. The browser keeps only a local display copy of the transcript; the server owns conversation context. The selector reads `GET /v1/models`, remembers the choice per browser (`localStorage`), starts the chosen model at once (`POST /v1/models/<id>/start`) and shows its state, "starting…" while it loads; the choice is sent as `model`. An *Answer language* selector offers exactly English, Română and Any and sends `language` `en`, `ro` or `auto`: English and Română force the answer language and nothing is detected; Any lets the host infer it from the message (`server/language.mjs`: an explicit request such as "răspunde în română", otherwise English). A collapsible *Settings* block ("Understanding in the chat" above) holds the *Clean text before formalizing* toggle ("textToCleanEnglish" above), *Send every sentence*, the *SymbolicProofingLLM rewrite* choice and *Show what I understood (CNL)*; the first calls `POST /v1/text-to-clean-english` first; when it changes the message, a review panel shows the proposed English as a word diff with Accept/Edit/Send original before anything is sent. A short help line under the selectors explains all of it.
- `GET /admin` keeps server status and token mint/revoke and links to the chat and the audit; signing in and the first-run password happen on `/login`.

`GET /healthz` and its alias `GET /health` report process liveness and the warm state of the start-up warmup (`warm`, DS012 "Model lifecycle"; no authentication; no model detail beyond mode, state and warm flag). All `/v1/*` paths and `/readyz` require a bearer token or the administrator session cookie. Without a registry, `GET /v1/models` lists the façade model only when ready; with one, it lists every registry model with `default`, `defaults` (per mode) and a `chatsop` object (`label`, `note`, `kind` `gguf`, `service` or `runtime-endpoint`, `capabilities`, `default`, `default_for` (the modes it is the default of), `state`, `error`, `prompt_profile` (`null` for a model without `formalize`), and `port` and `threads` while ready), and `POST /v1/models/<id>/start` starts a `gguf` or `service` model without waiting (202 with its state; 200 for the configured endpoint; 404 for an unknown id). `/readyz` then reports `ready` while any formalize model can answer, `default_model`, `default_models` (per mode) and the same per-model list as `formalizers`. `POST /v1/chat/completions` accepts one **new** `{role:'user',content:'...'}` message, `model` (a registry id, or the façade id `chatsop-local` for the default of the mode or, without a registry, the configured endpoint; any other value is refused with 400 `unknown_model` naming the accepted ids), optional `mode` (`chat`, `formalize` or `translate`, default `formalize`; a model without that capability, an unknown mode, `chatSop.trustedSop` outside Formalize, and Chat or Translate without a registry are refused with 400 `unsupported_mode`), optional `conversation_id` (default `default`), optional `stream`, optional `language` (`en`, `ro` or `auto`; any other value is refused), and optional `chatSop.trustedSop`. The answer language is the `language` field when it is `en` or `ro`, with no detection; with `auto` or no field, an explicit request in the message detected deterministically (`server/language.mjs`), otherwise English. A selected model that cannot start answers 503 `model_unavailable` with the reason. Model output that is not admitted (DS021) or cannot be executed answers 422 `model_output_rejected` with a partial `chatSop` (`status: rejected`, `rejection`, `model_sop`, `prompt_profile`, `formalizer_model`, `formalization_ms`); nothing is executed or written. The server, not the client-supplied message list, owns conversation history; arbitrary prior roles, tools/function calling and unsupported generation parameters are refused. Supplying `user` is optional but must equal the authenticated principal. The default `CHATSOP_API_KEY` authenticates principal `local`; embedded integrations can pass separate named bearer credentials via `createServer({authTokens:{alice:'...',bob:'...'}})`. A shared token is a shared identity and cannot provide multi-user isolation.

The normal completion is an OpenAI chat-completion envelope with `choices[0].message.content` (host CNL, not an uncertified rewrite) and `chatSop` containing `model_sop`, generated `circuit`, proof `provenance`, reasoner `backend`, reported `fallback`, `completeness`, authoritative `cnl`, `status`, clarification `pendingSop` and `required` when applicable, `answer_language` and `language_source` (`request`, `prompt` or `default`), the host-rendered `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy` and `assumption_branch` of a model-origin turn, the `unclear` kind and the `understood_as` reading of a not-computable problem when present, `mode` (`formalize`), `formalizer_model` (the registry id), `formalizer_label`, `formalization_ms` and `latency_ms` (wall time of the model call, including a model start), and optional trusted circuit/receipt. Provenance is observed or conditional as recorded by the runtime; no fabricated confidence is implied. `stream:true` emits the **already validated complete result** in SSE chat-completion chunks and terminates with `data: [DONE]`; it does not stream unverified model tokens. If the client disconnects, no additional HTTP chunks are sent; an already started inference or write is not rolled back. Explicit `/v1/responses`, `/v1/embeddings`, `/v1/tools` and chat tools receive errors rather than mock behavior.

## Starting it

```sh
# local, documentation + chat API; chat needs the SymbolicLM service to become ready
CHATSOP_API_KEY=<token at least 16 chars> node server/http.mjs            # 0.0.0.0:9999, all interfaces

# loopback only
CHATSOP_HOST=127.0.0.1 npm start

```

The chat's registry models need only their GGUF files, `~/nlp-venv` for Stanza and a `llama-server` binary, and start as `config/server-models.json` says. The launcher prints the home URL first (`http://<host>:<port>/`); the documentation site is available immediately at `http://<host>:<port>/docs/`, the browser chat at `/chat`, the evaluation browser at `/eval`, the project history, journal and status at `/experiments`, and the visual corpus audit is mounted at `/audit` behind the administrator session ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)). Without a SymbolicLM service the server refuses to start; while the service is starting `GET /readyz` returns 503 with `model_available: false` and chat requests return 503.

## Locality, limits, persistence and errors

The default listener is `0.0.0.0:9999`, all IPv4 interfaces (`CHATSOP_HOST`, `CHATSOP_PORT`); set `CHATSOP_HOST=127.0.0.1` to restrict it to loopback. Because the default is reachable from the network, the unauthenticated documentation path, the home page and the first-run password setup on `/login` are exposed to that network, and anything beyond a trusted network still needs external transport security and access controls. Authentication is either the administrator password chosen on the first visit to `/login` (stored only as a scrypt hash in `state/auth.json`, handed to the browser as an HttpOnly session cookie) or a bearer token: `CHATSOP_API_KEY` from the environment, or a token minted on the admin page and stored as a SHA-256 digest. Environment tokens must be unique per principal and at least 16 characters. `limits.maxRequestBytes` (default 65536), `maxContextBytes` (4800), `maxConcurrent` (4) and `timeoutMs` (30000) can be supplied through `config.server.limits` or `createServer({limits})`. Request byte and message-context oversize return 413; overload returns 429; same-session concurrent calls return 409. Formalizer fetch uses the smaller of backend and request timeout; on timeout the façade returns 504 while the in-flight operation retains its concurrency slot until settled. Do not retry a timed-out trusted write without checking the session receipt/state. Errors have generic messages and must not echo request content, private claim details, model endpoint bodies or bearer keys.

Repository sessions are keyed by base, authenticated principal and `conversation_id`. Agent conversational context is stored alongside the repository in a private per-conversation state file; context is reloaded after restart, while repository writes survive independently. Keep the repository and conversation directory inaccessible to other local accounts, and do not expose this API publicly without an independent security review. Calibrated model quality, tokenizer equivalence and checkpoint provenance are evaluated elsewhere (DS010, DS016), not by this server; the HTTP tests use a deterministic mock endpoint and a fake `llama-server` script (`tests/formalizers.test.mjs`) to prove wire and process behavior without neural inference.

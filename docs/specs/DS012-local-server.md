# Local OpenAI-compatible server

## Scope and authority

`server/http.mjs` provides a localhost HTTP façade. The only conversational execution path is `Agent.turn` → model inference client (`server/llm.mjs`) → validated declarative SOP → host-generated `Runtime` circuit. The model ([DS021](specsLoader.html?spec=DS021-model-surface.md)) sees only the user's message and may author only `stated`, `assumed`, `unclear`, `query` or `constraint`, as context-free strings that the host links to its lexicon; it cannot choose `remember`, claim documentary provenance, invoke tools, or publish knowledge. A separately authenticated, explicitly supplied `chatSop.trustedSop` circuit may contain `fact`, `event`, and `remember` wires only; it runs as a trusted user action in that user's session before the question. The receipt of a stored claim is returned as `chatSop.system_receipt` and can identify the target of a later correction. This is not model output or automatic ingestion. Trusted writes persist in the repository's private session; they are not committed to another user's state or published as base knowledge.

## Prompt selection and backend qualification

Select `promptProfile` explicitly: `formal` sends `formalPrompt` (the fixed model-language instructions followed by MESSAGE and the user's text) to a base model; `bare` sends exactly `barePrompt`, which is the user's message alone, to a qualified fine-tuned model. Neither carries a context block, a vocabulary list, identifiers, earlier turns or the clock. An explicit `CHATSOP_PROMPT_PROFILE` may supply the choice when the runtime configuration omits it; a mismatching environment/configuration pair is rejected at startup. Mixing the two prompt forms invalidates model evaluation. The option name `promptProfile` selects a prompt form only; there is one model language and no language versions. The source tree ships no checkpoint: trained formalizers live under the gitignored `models/` directory and are listed in the formalizer registry ("Formalizer models" below), which the server runs on demand with the `bare` prompt; the configured `formalizer.url` remains available as one registry entry pointing to an independently started endpoint, which uses `promptProfile` and the identity rules of this section. The server process itself never loads weights. A `bare` backend additionally requires configured `backendIdentity` and a matching `chatSopIdentity` in the formalizer's GET `/v1/models` entry. Both identities must match on `model_id`, `revision`, `tokenizer_sha256`, `dataset_version_sha256`, and `prompt_profile: bare`; the backend operator must verify these values against the checkpoint and tokenizer artifacts before serving. These declarations are an interoperability guard, **not cryptographic attestation or evidence that a checkpoint exists**. Adapter/base compatibility and actual training qualification remain operator prerequisites. A mismatched or missing identity refuses readiness. `formal` mode requires the configured formalizer model in its reachable model listing; GET `/readyz` returns 503 with `{ready:false,model_available:false}` if absent or unreachable, never a pretend success.

## Formalizer models

`config/formalizers.json` (`format: chatsop-formalizers-v1`; another file through the runtime configuration key `formalizers`, `false` disables it) is the registry of models the chat can use: `default` names the formalizer that the façade id (`chatsop-local`) selects in Formalize mode, `defaults` the default model of each chat mode (`chat`, `formalize`, `translate`, `proofread`, `proofread-symbolic`; when absent, `default` for formalize and otherwise the first model offering the mode), and each entry of `models` has an `id` (lowercase letters, digits, `.`, `_`, `-`), a `label`, a `note`, `capabilities` (a non-empty subset of `chat`, `translate`, `formalize`, `proofread` and `proofread-symbolic`; `["formalize"]` when omitted; `proofread` marks LanguageProofingLLM for the textToCleanEnglish step and `proofread-symbolic` marks SymbolicProofingLLM, the optional rewrite of SymbolicLM's pipeline; neither is a chat mode, so no mode selector lists them) and exactly one source: `gguf`, a repository-relative model file; `service`, a repository-relative Node script that serves the same chat-completion interface itself (`<script> serve --host H --port P --device cpu`), whose only capability is `formalize`; or `endpoint: "runtime"`, the configured `formalizer.url`, whose only capability is `formalize`. `server/formalizers.mjs` (`loadRegistry`) refuses duplicates, an unknown or non-formalize default, a `defaults` entry naming a model without that capability, unknown capabilities and an entry with both or neither source. The shipped registry lists the fine-tuned Q8_0 formalizers of run `fv1-size-a4` (`models/<model>/fv1-size-a4/formalizer/merged-best/gguf/q8_0.gguf`, capability `formalize`): SmolLM2-135M (fastest), Gemma 3 270M and SmolLM2-360M (best English out-of-distribution score, the default); the unmodified base instruct models SmolLM2-135M-Instruct, SmolLM2-360M-Instruct and Gemma 3 270M-it (`models/<model>/chat-base/q8_0.gguf`, converted with llama.cpp `convert_hf_to_gguf.py --outtype q8_0` on CPU from the pinned snapshots under `models/<model>/bases/`, provenance and sha256 in `chat-base/provenance.json`; capabilities `chat` and `translate`, never `formalize`, because a base model cannot write SOP Lang); SymbolicLM `symbolic-lm` ("SymbolicLM (Stanza + translation + rules)", `service: tools/symbolic-lm.mjs`: per-token language identification, symbolic Romanian-to-English translation, Stanza Universal Dependencies parses in the host environment `~/nlp-venv` with 4 CPU threads and the deterministic rules of `lib/ud-to-sop/`, [DS021](specsLoader.html?spec=DS021-model-surface.md) "SymbolicLM"; it replaced the symbolic baseline entry `ud-rules` of experiment `baseline-ud-rules-v1`, whose script `tools/eval/ud-baseline.mjs` remains for evaluation); its reply carries a `symbolic_lm` object with the route, the message language, the uncertainty signal and the English text, and, when the request asks for it ("Understanding in the chat"), the analysis finally used, the rewrite trace and the per-sentence interpretation; the entry's `rewrite.mode` (`off`, `gated`, `always`) is the default of the chat's SymbolicProofingLLM setting; the entries `language-proofing-llm` (`proofread`) and `symbolic-proofing-llm` (`proofread-symbolic`, Gemma 3 270M iteration 2, `models/gemma/symbolic-proofing-gemma270m-it2/proofreader/gguf/ep3-q8_0.gguf`, message-only prompt, one sentence per request) are GGUF models started on demand like any other; then the configured endpoint. Defaults: SmolLM2-360M for formalize, SmolLM2-360M-Instruct for chat, Gemma 3 270M-it for translate. Adding a model means adding an entry; no code changes.

`FormalizerManager` runs a `gguf` model in its own CPU `llama-server`, and a `service` entry as its own Node process on the CPU with the GPU hidden, when it is first selected (`POST /v1/models/<id>/start`, or the first chat message naming it): a free loopback port, `-ngl 0` with `CUDA_VISIBLE_DEVICES` empty (no GPU work, AGENTS.md), at most 8 threads, one slot, an 8192-token context and `--jinja` (the checkpoint's own chat template), as the evaluation harness. A running server is reused; one unused for 15 minutes is stopped; at most three run at once, whatever their mode, and starting a fourth stops the least recently used idle one (all busy: 503 `formalizer_capacity`); every server is stopped when the ChatSOP server closes, on SIGINT/SIGTERM and, as a last resort, on process exit. Each model's output goes to `<state root>/formalizer-logs/<id>.log`. The binary is the first existing of `LLAMA_SERVER_BIN`, `LLAMA_SERVER` (the `training/cli.mjs serve-cpu` convention), `LLAMA_CPP_DIR/build/bin/llama-server`, `vendor/llama.cpp/build/bin/llama-server` and `~/llama-cpp-venv/llama.cpp/build/bin/llama-server`. A model's state is `stopped`, `starting`, `ready` or `error` (with the reason: missing binary or GGUF file, a server that exited or did not answer `/health` within 120 s). The request is `predictMessage` of `lib/formalizer-endpoint.mjs`, the same function `tools/research/predict-endpoint.mjs` uses: the message as the only user content, no system prompt, temperature 0 and `top_k` 1, no extra stop strings (the template's end-of-turn token ends the answer), at most 6144 new tokens, and the raw `/apply-template` + `/completion` retry when llama-server fails to parse its own finished output. A truncated generation is refused. The prompt of a registry model is therefore `bare` whatever `promptProfile` says; `promptProfile` governs only the configured endpoint. A model is used only for the modes in its `capabilities` (`FormalizerManager.formalize` and `.chat` refuse others with 400 `unsupported_mode`).

## Chat modes

The chat has three modes, sent as the API field `mode` (default `formalize`):

1. **Chat** (`chat`): a plain conversation with an unmodified base instruct model, to see its general ability. The request is `chatMessages` of `lib/formalizer-endpoint.mjs`: the model's own chat template (`--jinja`), temperature 0.7 and `top_p` 0.9, at most 512 new tokens (a reply cut at the cap is returned with `finish_reason: length`). Multi-turn history: the server keeps the earlier Chat turns of the conversation (`server/chat-modes.mjs` `ChatHistory`, keyed by principal and `conversation_id`, in memory only, at most 8 turns and 12,000 bytes per conversation and 200 conversations, oldest first out) and sends them before the new message. The answer language selector adds a system instruction: English → "Answer in English.", Română → "Answer in Romanian.", Any → none.
2. **Formalize (SOP Lang)** (`formalize`): the behaviour of "Formalizer models" and the rest of this specification, with fine-tuned formalizers only. The formalizer's input stays the message alone (DS021); Chat history never reaches it.
3. **Translate to English** (`translate`): a base model with the fixed system instruction "Translate the user's message into English. Keep names, numbers and quoted text exactly. Output only the translation.", the message as the user turn, no history, greedy decoding (temperature 0, `top_k` 1), at most 512 new tokens. The answer language selector does not apply.

Chat and Translate write no SOP, run no host circuit, read no repository and change no conversation context of Formalize; the reply is the model's text as generated, not a grounded answer. Their `chatSop` trace is `{mode, status: answered, formalizer_model, formalizer_label, model_label, latency_ms, finish, usage, answer_language, language_source, system_prompt, history_turns, sampling}`. The tiny base models are weak translators: in the live check of 2026-09-29 Gemma 3 270M-it and SmolLM2-135M-Instruct often returned a Romanian message unchanged and SmolLM2-360M-Instruct paraphrased freely; the mode shows their ability, it does not certify a translation.

## textToCleanEnglish: a user-validated pre-formalization step

Owner decision of 2026-09-30: formalization handles only clean English. Before a Formalize-mode message reaches the formalizer, the chat page may call `POST /v1/text-to-clean-english` (authenticated the same way as `/v1/chat/completions`; body `{message}`, at most `maxContextBytes`), which runs `textToCleanEnglish` (`lib/text-to-clean-english/`, [DS021](specsLoader.html?spec=DS021-model-surface.md) "textToCleanEnglish"), the chat step validated by the user that calls **LanguageProofingLLM** (LanguageTool is an optional backend, off by default), entirely as **host code before the model boundary**: it corrects spelling and grammar, translates Romanian or mixed Romanian/English text to English, and simplifies wording, then returns `{original, clean, changed, reasons, spans, backend, confidence}` (since 2026-10-01 also served as `POST /v1/language/proofread` with `status`, `errors`, `timings`, `cache` and `versions`, [DS030](specsLoader.html?spec=DS030-capability-apis.md): a sentence whose model cannot run stays as written and is listed in `errors`) — never a formalization. The host splits the message into sentences (`lib/sentence-split.mjs`); a cheap, conservative gate (non-English tokens, a spelling signal, or a handful of cheap grammar-trouble regexes) skips every already-clean English sentence without calling any backend, and only flagged sentences are sent to the model, one request each (`llm.sendAll: true` sends all sentences, clean ones included; default `false`) (`changed: false`, `backend: "none"`); config/text-to-clean-english.json's `enabled: false` disables the whole step the same way, for every message, without a server restart. The backend is a small, explicit, swappable choice (`config/text-to-clean-english.json`, `backends.english`/`backends.nonEnglish`: `llm`, LanguageProofingLLM, a registry model with the `proofread` capability (`language-proofing-llm`) started on demand through `FormalizerManager.ensure` when a sentence first needs it, `languagetool`, a local LanguageTool grammar/spell server (optional, off by default), or `none`); an unreachable backend degrades to `backend: "none"` (the message unchanged) rather than failing the request, so the chat stays usable without it. A backend that answers with no text is treated as unreachable, never shown as an empty proposal.

Since the owner decision of 2026-10-01 (translator for Romanian and mixed input) `backends.nonEnglish` is `translator-llm`: Romanian and mixed sentences go to the registry model `translator-llm` (capability `translate-clean`, Qwen3-4B-Instruct Q4_K_M, started on demand like any registry model), English sentences to LanguageProofingLLM as described next; a translator that cannot run is replaced by LanguageProofingLLM and the chat's review shows a *Fallback* note ([DS021](specsLoader.html?spec=DS021-model-surface.md) "textToCleanEnglish", [DS030](specsLoader.html?spec=DS030-capability-apis.md)). Earlier default (owner decision of 2026-10-01, which removed Qwen3-1.7B from the chat): the gate, then **LanguageProofingLLM** for every flagged sentence, English, Romanian and mixed alike (`backends.english = "llm"`, `backends.nonEnglish = "llm"`, `llm.model = "language-proofing-llm"`, `llm.sendAll = false`). LanguageProofingLLM is the fine-tuned Gemma 3 270M of run `language-proofing-gemma270m-it1` (GGUF Q8_0 from `models/gemma/language-proofing-gemma270m-it1/proofreader/gguf/ep3-q8_0.gguf`; report `eval/reports/current/language-proofing-it1/summary.md`). It is a registry entry of `config/formalizers.json` with the single capability `proofread`, so no chat mode lists it; it starts on demand like any registry model (CPU `llama-server`, idle stop, at most three managed models at once) and is asked exactly as in training: the sentence as the only user message, no system prompt, greedy decoding, no name masking (a reply that loses a digit run or a quoted span of its input is reported with confidence 0.5). The gate is conservative and its spelling signal is weak, so a typo in an otherwise well-formed English sentence may pass unflagged; set `llm.sendAll` to `true` to send every sentence to the model (about 110 ms per sentence on 4 CPU threads). The survey `text-to-clean-english-v1` (`eval/reports/current/text-to-clean-english/summary.md`) remains the record of the earlier LanguageTool plus Qwen3-1.7B default. LanguageTool is an optional operator step, not started by `npm start`: set `backends.english` to `languagetool` and run `node tools/languagetool-server.mjs --port 18123` (install and Java notes in its header and in `dependencies.md`); `languagetool.url` in the config names the port. With no `llama-server` or no GGUF file the message is left unchanged and the chat keeps working.

The chat page's *Clean before formalizing* toggle (on by default, remembered per browser, Formalize mode only) calls this endpoint before sending; when it reports a change, the page shows the proposed English with a word-level diff and three choices — **Accept**, **Edit** (loads the proposal into the composer for further changes) and **Send original** — and nothing reaches the formalizer until the user picks one. Whichever text is finally sent, the request to `/v1/chat/completions` may carry an optional `cleaning: {original, backend, changed}` field recording what the cleaning step proposed; the formalized text itself is the request's `messages[0].content`, exactly as for any other turn (DS021 "Model boundary" is unaffected: the formalizer still receives only that one string). The `chatSop` trace then carries `cleaning` (the same object, or `null` when the step was skipped, off, or not used), next to the existing formalize trace fields, so both the original and the accepted wording stay visible after the fact. This step never runs in Chat or Translate mode.

## Understanding in the chat

Owner request of 2026-10-01: the chat shows what SymbolicLM understood, in short controlled English, so the owner can form an opinion by manual testing. It is host code after the formalizer's analysis; the formalizer's input stays exactly the user's message ([DS021](specsLoader.html?spec=DS021-model-surface.md) "Model boundary"). It needs the SymbolicLM model (`symbolic-lm`); other formalizers make no analysis and the answer carries `understanding: null`.

**Request.** `POST /v1/chat/completions` in Formalize mode accepts `understanding: {interpret?: boolean, rewrite?: "off" | "gated" | "always", emotion?: boolean}` (any other key or value is a 400; other modes refuse the field). `interpret` (default `true`) adds the interpretation CNL of the analysis SymbolicLM actually used. `emotion` (default: `enabled` of `config/emotion-detection.json`, `true`) switches the EmotionDetectionSystem ([DS029](specsLoader.html?spec=DS029-emotion-detection.md)) on or off for this message: the host then reports `understanding.emotion` (signals, emoticon suggestions, the classified leftover spans, the `pragmatic` wires; the SymbolicLM service is always asked with `emotion: false` and the detection runs on the host through the cached `emotionFor` of [DS030](specsLoader.html?spec=DS030-capability-apis.md)), the chat page lists them under "I understood" (spans classified as courtesy or tone no longer count as not represented), the agent appends the wires to the circuit and a message that only greets, thanks, apologizes or closes gets a short courtesy reply without computation. The chat setting "Detect tone and courtesy" sends it and `GET` chat settings report `emotionEnabled`. `rewrite` chooses the SymbolicProofingLLM rewrite of SymbolicLM's pipeline for this message (default: `rewrite.mode` of the `symbolic-lm` registry entry, `gated` by the owner's decision Q-PROOF-1 of 2026-10-01): `off` calls no model; `gated` sends only sentences whose default and accurate Stanza trees are not identical and keeps a rewrite only when its trees are certified and names, numbers, negation, quantifiers and the question mark are kept (`rewriteWhen: "trees"`, `rewriteAccept: "certified"`); `always` sends every sentence and keeps every rewrite (`rewriteWhen: "always"`, `rewriteAccept: "off"`). For `gated` and `always` the server starts the registry model with the `proofread-symbolic` capability (`symbolic-proofing-llm`) on demand and hands its endpoint to the SymbolicLM service in the request (`symbolic_lm: {interpret, rewrite_url, rewrite_when, rewrite_accept}`, host options beside `messages`, never part of the message). A rewrite model that cannot start leaves the rewrite off and says why in `requested.rewrite_error`. `POST /v1/text-to-clean-english` accepts `sendAll: boolean`, overriding `llm.sendAll` of `config/text-to-clean-english.json` for that call ("send every sentence").

**Response.** `chatSop.understanding` (null when the formalizer is not SymbolicLM):
- `requested` `{interpret, rewrite, rewrite_model?, rewrite_error?}`: what was applied;
- `message`, `analysed_text` (the English text the analysis belongs to: the translation of a Romanian or mixed message, or the text after an accepted rewrite), `route`, `language`, `english`, `uncertainty` `{uncertain, kinds}`;
- `rewrite`: the pipeline trace `{input, output, applied, gate, acceptance, units: [{text, sent, accepted, reasons, output, certified, uncertain}]}` (`null` without a rewrite model, `{applied: false, gate: "no rewrite function"}` when it is off);
- `interpretation` (`null` when `interpret` is false): `{version, available, reason?, text, language, sentences, not_represented, outside_sentences, framing, rewrite, certified}`. `available: false` with a `reason` for an analysis in another language (a Romanian message sent unchanged is analysed in Romanian; the CNL is English only). Per sentence: `index`, `text`, `start`, `end`, `display_text` (the sentence with a masked lead-in such as "Remind me," when one belongs to it), `status` (`verified`, `uncertain` or `empty`), `cnl` and `cnl_sentences` (only when verified), `unverified_cnl` (an uncertain sentence's CNL, kept apart), `round_trip` `{pass, reasons}` (the CNL is parsed by SymbolicLM and must give the same structures), `not_represented` (verbatim spans the CNL does not use), `framing`, `notes`, `summary` (a raw analysis summary such as `root: work; nsubj: Ana; obl: Lidl`), `certified` (identical default and accurate Stanza trees; `true`, `false` or `null` when not computed) and `rewrite` `{original, rewrite, accepted, reasons, original_certified}` for a sentence a rewrite produced or one whose rewrite was refused. `certified` of the whole interpretation is true when every sentence is.

**Page.** The *Settings* block of `/chat` (Formalize mode only; every choice remembered per browser in `localStorage`) holds four controls: *Clean text before formalizing* (LanguageProofingLLM, "textToCleanEnglish"), *Send every sentence* (the `sendAll` of that call; default from the server's `config/text-to-clean-english.json`), *SymbolicProofingLLM rewrite* (off, gated or always; default from the registry) and *Show what I understood (CNL)* (on by default). With the last one on, the page shows the "I understood:" panel under the user's message, built from the `POST /v1/understand` answer ([DS030](specsLoader.html?spec=DS030-capability-apis.md) "The chat page"; the answer's own `chatSop.understanding`, which has the same shape, is used only when that call failed). The panel is a collapsible, compact block: per sentence the verified CNL, or an "uncertain interpretation" marker with the raw analysis summary (never a silent CNL; the unverified CNL is only in a nested detail), a certified or not certified badge, the sentence with the not-represented spans highlighted (the same spans are highlighted in the message the user sent when they occur in it verbatim), and for a rewritten sentence the original, the rewrite and whether it was accepted (certified) or rejected with the reasons. The panel is readable at 390 px and in the light and dark themes (`tools/ui/chat-cnl-shots.mjs` takes the screenshots into `eval/reports/current/chat-cnl/`). The LanguageProofingLLM proposal keeps its own review (word diff, Accept, Edit, Send original).

## Capability APIs and caches

Owner decision of 2026-10-01: every capability has its own endpoint under `/v1` (proofread, understand, symbolic rewrite, symbolic analyze, emotion detect, plus `GET /v1/capabilities` and the administrator's `GET /v1/cache/stats` and `POST /v1/cache/clear`), authenticated like every other API, with `timings`, `cache` (`hit` or `miss`) and `versions` in every answer, small version-keyed caches with in-flight de-duplication in front of every language model call and of the SymbolicLM analysis, and the principle that analysis never fails totally (`status`, `errors` and a `clarify` message instead of an error). The contract, the caches and the page flow are specified in [DS030](specsLoader.html?spec=DS030-capability-apis.md); the reference with executable examples is `docs/api.html`. The chat page uses these endpoints independently and its formalize request reuses their cached work. Limits: `limits.maxConcurrentApi` (default 16 simultaneous capability requests, 429 beyond), `limits.maxContextBytes` per message and `limits.maxRequestBytes` per body, as for the chat.

## HTTP contract

`GET /docs` redirects to `/docs/`, which serves the repository documentation site statically (`docs/index.html`, the wiki, the wire help, the specification matrix and the DS files). Static serving needs no bearer token, is read-only, never lists a directory, refuses any path that resolves outside `docs/` (encoded traversal and NUL bytes included) and sets `no-cache` for HTML and a short cache for other assets. The chat API keeps its authentication.

For a signed-in session the server also serves a fixed allowlist of repository Markdown read-only as plain text (`REPO_MARKDOWN` in `server/http.mjs`): `skills/README.md`, every `skills/<name>/SKILL.md`, `eval/README.md`, `datasets/SOURCES.md` and the root `README.md`, `AGENTS.md`, `TODO.md`, `CHANGES.md`, `questions.md` and `dependencies.md`, so the owner can read the skills and project files on the server. One shared menu (`server/pages/site-menu.mjs`, mirrored in `docs/partials/header.html` and checked by `node tools/site-menu.mjs --check`) links the server pages and the documentation, including the wire help, "How the model writes", "Question types" and the specification matrix. `node tools/check-links.mjs` crawls the served site (its own server on a temporary port with temporary state, signed in) and fails on any broken link or `#anchor`; `tests/site-links.test.mjs` runs it in `npm test`.

### Browser pages

When the server has the administrator password store (`npm start`, `startServer`), browser pages are layered on the unchanged session-cookie authentication; they present it and never grant access themselves. Page modules live in `server/pages/` and their routing in `server/web.mjs`. All server pages and the documentation site share one top menu (Home, Chat, Audit, Eval, an Experiments dropdown with the index, Topics, Reports, Timeline & live status and Open questions, Admin, a Docs dropdown with Overview, Runtime, Training, Wiki, Specifications, Wire help, How the model writes and Question types, then Logout, or Sign in on a signed-out server page), defined once in `server/pages/site-menu.mjs` and styled by `docs/assets/site-menu.css`; `docs/partials/header.html` is generated from it by `node tools/site-menu.mjs --write`, and a test keeps the two identical. The layout works at phone width. `GET /assets/sop-code.mjs` (public) serves the shared SOP highlighter (`server/pages/sop-code.mjs`), which the documentation pages use to link SOP blocks to the wire help; the chat trace, the audit and the evaluation browser use the same renderer. It links wire types and fields to their help pages and marks a type or field outside the parser contract "undocumented". The structural words `all`, `any`, `match`, `end` and the atom prefix `not`, read from `sop/conditions.mjs` and `sop/parser.mjs`, are grammar: they are rendered as syntax keywords linked to `docs/wire_typs/syntax.html#syntax-<word>` and never flagged; inside a `match … end` block the keyword lines `relation`, `role` and `polarity` link to their definitions and any other keyword there is flagged (`tests/sop-code-syntax.test.mjs`).

- `GET /` is a public home page. It states whether the visitor is signed in, whether the administrator password is set, and the formalizer state according to the same readiness check as `/readyz`: with a registry, every model with its state (`stopped`, `starting`, `ready`, `error`; the error reason only to a signed-in session); it names the configured `formalizer.url` and model only to a signed-in session. It links to `/chat`, `/audit`, `/eval`, `/experiments`, `/admin` and `/docs/`. A server created without the password store (bearer credentials only) serves the same page without sign-in state.
- `GET /login?next=<path>` shows the first-run "choose the administrator password" form while no password exists, and the sign-in form afterwards; a request that already carries a valid session is redirected to `next`. `POST /login` (form-encoded `password`, `confirm` for the first run, `next`) calls the existing `Auth.setup`/`Auth.login`, so the minimum length (8), the throttle (ten failures within a minute) and the scrypt verification are unchanged. Success sets the HttpOnly `SameSite=Strict` session cookie and answers 303 to `next`. `next` is accepted only as a same-origin relative path (a single leading `/`, no scheme, authority, backslash or control characters); anything else becomes `/`. A post whose `Origin` differs from `Host` or that the browser marks `Sec-Fetch-Site: cross-site` is refused with 403. Failures re-render the form with a plain message: mismatched passwords or a too-short password (400), a setup attempt after a password exists (409), a wrong password (401), throttling (429).
- `POST /logout` ends the session, clears the cookie and answers 303 to `/login` (same cross-site refusal).
- A signed-out `GET /chat`, `/audit`, `/eval`, `/eval/guide`, `/admin`, `/experiments` or any `/experiments/…` page that asks for HTML (`Accept: text/html`) and carries no `Authorization` header answers 303 to `/login?next=<requested path>`. Every other unauthenticated request keeps the JSON 401 (`unauthorized`) or 403 (`setup_required`) answer, including `/v1/*`, `/readyz`, `/audit/api/*`, `/eval/api/*`, `/experiments/api/*` and its alias `/project/api/*`.
- `GET /audit` (authenticated) is the visual corpus audit ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)): it browses the JSONL corpora, re-executes a case on demand and appends verdicts to `eval/reports/current/audit/<corpus>.jsonl`; its API lives under `/audit/api/*`. It shows four tabs: `bad_english`, `symbolic_english` and `neuro_english` (the three datasets, each with a statement of purpose, row counts per split, filters and its own case view: the grammatical analysis as tree and table with a SymbolicLM re-run, failure kind and rewrite diff with a SymbolicLM check, clean-English target check) and a secondary `archive / sources` tab for the legacy corpora and the local source cache; the types and files come from `config/audit-corpora.json`, sealed suites are view-only, and the phone layout stacks the panes (DS020 "Audit tabs and review types").
- `GET /eval` (authenticated) is the read-only evaluation browser (`server/eval-browser.mjs`, three-pane layout shared with the audit through `server/pages/three-pane.mjs`): the sealed suites under `eval/suites/**` (`formalizer-v1` and the out-of-distribution `formalizer-ood-v1`) and the files under `eval/predictions`, `eval/registry`, `eval/reports/current` and `eval/reports/history` (the last marked historical). For each row it shows the message (the only model input), the gold target, the evaluator steps with `file:line` citations, the expected result and world, and any prediction with its line diff and recorded outcome; evaluator reports are attached to a suite by `suite_sha256`. `POST /eval/api/execute` runs `evaluate` from `eval/run.mjs` on one row with a stored prediction or, labelled as a sanity check, the gold. `GET /eval/guide` explains splits, the sealed-test guard, admission, canonical versus execution comparison, every metric, template leakage, the out-of-distribution suite and qualified runs, citing code lines resolved when served.
- `GET /experiments` (authenticated; the menu's "Experiments" dropdown: Index, Topics, Reports, Timeline & live status, Open questions) is the living project history, rendered on the server by `server/pages/history.mjs` from `server/history.mjs`. Every list on these pages is newest first, and nothing shown is ever replaced: records accumulate across project phases.
  - `/experiments` (index): a current-status header (the phase recorded in `status/tasks.json`, the AGENTS.md training rule quoted live with the latest training decisions of the journal, the tasks and experiments in progress, the open questions of `questions.md`, the latest journal activity and a count of the computed checks), every task and experiment newest first, and every topic with its note count and latest entry.
  - `/experiments/<id>`: one page per task record of `status/tasks.json` or experiment record of `status/experiments.json` (DS010). The page keeps two sides apart: **Owner** (what the owner asked, why, the owner's decisions and corrections, then a newest-first stack of the related owner decisions from the journal and decision notes) and **Agents / analysis** (what was analysed, tried and run including failed attempts, what was obtained, the conclusions, open follow-ups and evidence links, then a newest-first stack of the related agent notes and journal events). Experiment records are shown in full: hypothesis, the preregistration record rendered, deviations, datasets and hashes, models, results, conclusions and reports. Notes and events are related to a task through its `match` phrases and experiment ids.
  - `/experiments/topics` and `/experiments/topic/<id>`: the topics of `status/topics.json` and one topic's full note stack (`status/notes/<id>.jsonl`), newest first, with browser-side filters by kind and author (`?kind=`, `?author=`) and supersede chains shown both ways ("superseded by …", "supersedes …"); a superseded note stays visible, dimmed.
  - `/experiments/reports[?dir=…]` and `/experiments/report?path=…`: a read-only, newest-first browser of `eval/reports/current/**` and `eval/reports/history/**` (the latter marked historical). Markdown is rendered, JSON is tabulated when simple and pretty-printed otherwise, JSONL, log and text files are shown as text, and a file over 2 MB shows only its first 96 KB. Paths are repository-relative and must resolve, after symlinks, inside one of the two roots; absolute paths, `..`, NUL and backslashes are refused with 400. Cache directories (`cache*`) and test leftovers are listed but not expanded.
  - `/experiments/timeline` (the former "Fine-tuning & status" page, kept as it was) polls `GET /experiments/api/status` every 15 s and on focus: the training gate (prohibited until the owner's new explicit approval) and computed checks, the append-only journal `status/journal.jsonl` newest first with an area filter, the data pipeline per corpus (rows, target form, corpus-audit verdict and metrics, vocabulary check), `status/experiments.json` and `questions.md`.
  - `/experiments/questions`: `questions.md` rendered.
  - JSON APIs for the same data: `/experiments/api/status`, `/experiments/api/tasks`, `/experiments/api/topics`, `/experiments/api/notes[?topic=&kind=&author=]` and `/experiments/api/report?path=…|?dir=…` (same path rules). `/project/api/*` answers the same endpoints as an alias; every other `/project` or `/project/…` browser path answers 301 to the same path under `/experiments`.
  - Agents write the journal with `node tools/journal.mjs` (`lib/journal.mjs`), topic notes with `node tools/notes.mjs` (`lib/notes.mjs`) and task records in `status/tasks.json` (`lib/tasks.mjs`); the schemas are in [DS010-experiment-preregistration.md](specsLoader.html?spec=DS010-experiment-preregistration.md) ("Tasks and topic notes"). The journal and the notes are append-only; neither is product documentation nor, by itself, evidence of a result: entries point at their evidence.
- `GET /chat` (authenticated) serves the browser chat. A *Mode* selector offers Chat, Formalize (SOP Lang) and Translate to English ("Chat modes"), remembered per browser and sent as `mode`; the *Model* selector then lists only the registry models whose `capabilities` include that mode (Formalize: the fine-tuned formalizers and the configured endpoint; Chat and Translate: the base models), remembering one choice per mode. A Chat or Translate answer has a short trace (mode, model, latency, decoding, system instruction, earlier turns sent, tokens); the Answer language selector is disabled in Translate. It posts one user message per turn to `/v1/chat/completions` through same-origin fetch with the session cookie, selects the `conversation_id` (with a *New conversation* control), and renders each Formalize answer with a collapsible trace built from `chatSop` (mode, status, backend, fallback, completeness, prompt choice (`prompt_profile`), the formalizer that answered and the latency (formalization time), answer language and its source, user statements, carried statements, model assumptions and policy, `unclear` kind, the not-computable reading, reinforcement, model SOP, execution circuit, provenance, pending clarification). Status codes are explained in plain words: 401/403 sign in again, 503 selected model not available (with the reason), 422 model SOP refused (the trace shows what the model wrote and why), 409 conversation busy, 429 server busy, 504 time limit, 413 message too long. The browser keeps only a local display copy of the transcript; the server owns conversation context. A *Model* selector lists the registry (`GET /v1/models`), remembers the choice per browser (`localStorage`), starts the chosen model at once (`POST /v1/models/<id>/start`) and shows its state, "starting…" while it loads; the choice is sent as `model`. An *Answer language* selector offers exactly English, Română and Any and sends `language` `en`, `ro` or `auto`: English and Română force the answer language and nothing is detected; Any lets the host infer it from the message (`server/language.mjs`: an explicit request such as "răspunde în română", otherwise English). A collapsible *Settings* block (Formalize mode only, "Understanding in the chat" above) holds the *Clean text before formalizing* toggle ("textToCleanEnglish" above), *Send every sentence*, the *SymbolicProofingLLM rewrite* choice and *Show what I understood (CNL)*; the first calls `POST /v1/text-to-clean-english` first; when it changes the message, a review panel shows the proposed English as a word diff with Accept/Edit/Send original before anything is sent. A short help line under the selectors explains all of it.
- `GET /admin` keeps server status and token mint/revoke and links to the chat and the audit; signing in and the first-run password happen on `/login`.

`GET /healthz` reports only process liveness (no authentication; no model readiness). All `/v1/*` paths and `/readyz` require a bearer token or the administrator session cookie. Without a registry, `GET /v1/models` lists the façade model only when ready; with one, it lists every registry model with `default`, `defaults` (per mode) and a `chatsop` object (`label`, `note`, `kind` `gguf`, `service` or `runtime-endpoint`, `capabilities`, `default`, `default_for` (the modes it is the default of), `state`, `error`, `prompt_profile` (`null` for a model without `formalize`), and `port` and `threads` while ready), and `POST /v1/models/<id>/start` starts a `gguf` or `service` model without waiting (202 with its state; 200 for the configured endpoint; 404 for an unknown id). `/readyz` then reports `ready` while any formalize model can answer, `default_model`, `default_models` (per mode) and the same per-model list as `formalizers`. `POST /v1/chat/completions` accepts one **new** `{role:'user',content:'...'}` message, `model` (a registry id, or the façade id `chatsop-local` for the default of the mode or, without a registry, the configured endpoint; any other value is refused with 400 `unknown_model` naming the accepted ids), optional `mode` (`chat`, `formalize` or `translate`, default `formalize`; a model without that capability, an unknown mode, `chatSop.trustedSop` outside Formalize, and Chat or Translate without a registry are refused with 400 `unsupported_mode`), optional `conversation_id` (default `default`), optional `stream`, optional `language` (`en`, `ro` or `auto`; any other value is refused), and optional `chatSop.trustedSop`. The answer language is the `language` field when it is `en` or `ro`, with no detection; with `auto` or no field, an explicit request in the message detected deterministically (`server/language.mjs`), otherwise English. A selected model that cannot start answers 503 `model_unavailable` with the reason. Model output that is not admitted (DS021) or cannot be executed answers 422 `model_output_rejected` with a partial `chatSop` (`status: rejected`, `rejection`, `model_sop`, `prompt_profile`, `formalizer_model`, `formalization_ms`); nothing is executed or written. The server, not the client-supplied message list, owns conversation history; arbitrary prior roles, tools/function calling and unsupported generation parameters are refused. Supplying `user` is optional but must equal the authenticated principal. The default `CHATSOP_API_KEY` authenticates principal `local`; embedded integrations can pass separate named bearer credentials via `createServer({authTokens:{alice:'...',bob:'...'}})`. A shared token is a shared identity and cannot provide multi-user isolation.

The normal completion is an OpenAI chat-completion envelope with `choices[0].message.content` (host CNL, not an uncertified rewrite) and `chatSop` containing `model_sop`, generated `circuit`, proof `provenance`, reasoner `backend`, reported `fallback`, `completeness`, authoritative `cnl`, `status`, clarification `pendingSop` and `required` when applicable, `answer_language` and `language_source` (`request`, `prompt` or `default`), the host-rendered `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy` and `assumption_branch` of a model-origin turn, the `unclear` kind and the `understood_as` reading of a not-computable problem when present, active `prompt_profile`, `mode` (`formalize`), `formalizer_model` (the registry id, or the configured model name), `formalizer_label`, `formalization_ms` and `latency_ms` (wall time of the model call, including a model start), and optional trusted circuit/receipt. Provenance is observed or conditional as recorded by the runtime; no fabricated confidence is implied. `stream:true` emits the **already validated complete result** in SSE chat-completion chunks and terminates with `data: [DONE]`; it does not stream unverified model tokens. If the client disconnects, no additional HTTP chunks are sent; an already started inference or write is not rolled back. Explicit `/v1/responses`, `/v1/embeddings`, `/v1/tools` and chat tools receive errors rather than mock behavior.

## Starting it

```sh
# local, documentation + chat API; chat needs a formalizer endpoint to become ready
CHATSOP_API_KEY=<token at least 16 chars> node server/http.mjs            # 0.0.0.0:9999, all interfaces

# loopback only
CHATSOP_HOST=127.0.0.1 npm start

# an explicit prompt choice is mandatory: `formal` for a base model, `bare` for a fine-tuned one
CHATSOP_PROMPT_PROFILE=formal node server/http.mjs
```

`config/runtime.json` already sets `promptProfile: "formal"` for the configured base-model endpoint, so the server starts without extra environment; the chat's registry models need only their GGUF files and a `llama-server` binary, and start when chosen in the chat. The launcher prints the home URL first (`http://<host>:<port>/`); the documentation site is available immediately at `http://<host>:<port>/docs/`, the browser chat at `/chat`, the evaluation browser at `/eval`, the project history, journal and status at `/experiments`, and the visual corpus audit is mounted at `/audit` behind the administrator session ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)); Without a registry, `GET /readyz` returns 503 with `model_available: false` and chat requests return 503 until a formalizer endpoint is running and `/v1/models` advertises the configured model identity; with the registry, a registry model answers as soon as it has started.

## Locality, limits, persistence and errors

The default listener is `0.0.0.0:9999`, all IPv4 interfaces (`CHATSOP_HOST`, `CHATSOP_PORT`); set `CHATSOP_HOST=127.0.0.1` to restrict it to loopback. Because the default is reachable from the network, the unauthenticated documentation path, the home page and the first-run password setup on `/login` are exposed to that network, and anything beyond a trusted network still needs external transport security and access controls. Authentication is either the administrator password chosen on the first visit to `/login` (stored only as a scrypt hash in `state/auth.json`, handed to the browser as an HttpOnly session cookie) or a bearer token: `CHATSOP_API_KEY` from the environment, or a token minted on the admin page and stored as a SHA-256 digest. Environment tokens must be unique per principal and at least 16 characters. `limits.maxRequestBytes` (default 65536), `maxContextBytes` (4800), `maxConcurrent` (4) and `timeoutMs` (30000) can be supplied through `config.server.limits` or `createServer({limits})`. Request byte and message-context oversize return 413; overload returns 429; same-session concurrent calls return 409. Formalizer fetch uses the smaller of backend and request timeout; on timeout the façade returns 504 while the in-flight operation retains its concurrency slot until settled. Do not retry a timed-out trusted write without checking the session receipt/state. Errors have generic messages and must not echo request content, private claim details, model endpoint bodies or bearer keys.

Repository sessions are keyed by base, authenticated principal and `conversation_id`. Agent conversational context is stored alongside the repository in a private per-conversation state file; context is reloaded after restart, while repository writes survive independently. Keep the repository and conversation directory inaccessible to other local accounts, and do not expose this API publicly without an independent security review. Calibrated model quality, tokenizer equivalence and checkpoint provenance are evaluated elsewhere (DS010, DS016), not by this server; the HTTP tests use a deterministic mock endpoint and a fake `llama-server` script (`tests/formalizers.test.mjs`) to prove wire and process behavior without neural inference.

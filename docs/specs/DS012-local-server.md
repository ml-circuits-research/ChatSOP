# Local OpenAI-compatible server

## Scope and authority

`server/http.mjs` provides a localhost HTTP façade. The only conversational execution path is `Agent.turn` → model inference client (`server/llm.mjs`) → validated declarative SOP → host-generated `Runtime` circuit. The model ([DS021](specsLoader.html?spec=DS021-model-surface.md)) sees only the user's message and may author only `stated`, `assumed`, `unclear`, `query` or `constraint`, as context-free strings that the host links to its lexicon; it cannot choose `remember`, claim documentary provenance, invoke tools, or publish knowledge. A separately authenticated, explicitly supplied `chatSop.trustedSop` circuit may contain `fact`, `event`, and `remember` wires only; it runs as a trusted user action in that user's session before the question. The receipt of a stored claim is returned as `chatSop.system_receipt` and can identify the target of a later correction. This is not model output or automatic ingestion. Trusted writes persist in the repository's private session; they are not committed to another user's state or published as base knowledge.

## Prompt selection and backend qualification

Select `promptProfile` explicitly: `formal` sends `formalPrompt` (the fixed model-language instructions followed by MESSAGE and the user's text) to a base model; `bare` sends exactly `barePrompt`, which is the user's message alone, to a qualified fine-tuned model. Neither carries a context block, a vocabulary list, identifiers, earlier turns or the clock. An explicit `CHATSOP_PROMPT_PROFILE` may supply the choice when the runtime configuration omits it; a mismatching environment/configuration pair is rejected at startup. Mixing the two prompt forms invalidates model evaluation. The option name `promptProfile` selects a prompt form only; there is one model language and no language versions. Neither runtime.json nor this source tree ships a trained ChatSOP checkpoint. The configured `formalizer.url` must point to an independently started inference endpoint; no weights are loaded by this server. A `bare` backend additionally requires configured `backendIdentity` and a matching `chatSopIdentity` in the formalizer's GET `/v1/models` entry. Both identities must match on `model_id`, `revision`, `tokenizer_sha256`, `dataset_version_sha256`, and `prompt_profile: bare`; the backend operator must verify these values against the checkpoint and tokenizer artifacts before serving. These declarations are an interoperability guard, **not cryptographic attestation or evidence that a checkpoint exists**. Adapter/base compatibility and actual training qualification remain operator prerequisites. A mismatched or missing identity refuses readiness. `formal` mode requires the configured formalizer model in its reachable model listing; GET `/readyz` returns 503 with `{ready:false,model_available:false}` if absent or unreachable, never a pretend success.

## HTTP contract

`GET /docs` redirects to `/docs/`, which serves the repository documentation site statically (`docs/index.html`, the wiki, the wire help, the specification matrix and the DS files). Static serving needs no bearer token, is read-only, never lists a directory, refuses any path that resolves outside `docs/` (encoded traversal and NUL bytes included) and sets `no-cache` for HTML and a short cache for other assets. The chat API keeps its authentication.

For a signed-in session the server also serves a fixed allowlist of repository Markdown read-only as plain text (`REPO_MARKDOWN` in `server/http.mjs`): `skills/README.md`, every `skills/<name>/SKILL.md`, `eval/README.md`, `datasets/SOURCES.md` and the root `README.md`, `AGENTS.md`, `TODO.md`, `CHANGES.md`, `questions.md` and `dependencies.md`, so the owner can read the skills and project files on the server. One shared menu (`server/pages/site-menu.mjs`, mirrored in `docs/partials/header.html` and checked by `node tools/site-menu.mjs --check`) links the server pages and the documentation, including the wire help, "How the model writes", "Question types" and the specification matrix. `node tools/check-links.mjs` crawls the served site (its own server on a temporary port with temporary state, signed in) and fails on any broken link or `#anchor`; `tests/site-links.test.mjs` runs it in `npm test`.

### Browser pages

When the server has the administrator password store (`npm start`, `startServer`), browser pages are layered on the unchanged session-cookie authentication; they present it and never grant access themselves. Page modules live in `server/pages/` and their routing in `server/web.mjs`. All server pages and the documentation site share one top menu (Home, Chat, Audit, Eval, Fine-tuning & status, Admin, a Docs dropdown with Overview, Runtime, Training, Wiki, Specifications and Wire help, then Logout, or Sign in on a signed-out server page), defined once in `server/pages/site-menu.mjs` and styled by `docs/assets/site-menu.css`; `docs/partials/header.html` is generated from it by `node tools/site-menu.mjs --write`, and a test keeps the two identical. The layout works at phone width. `GET /assets/sop-code.mjs` (public) serves the shared SOP highlighter, which the documentation pages use to link SOP blocks to the wire help; the chat trace uses the same renderer.

- `GET /` is a public home page. It states whether the visitor is signed in, whether the administrator password is set, and whether the formalizer is ready according to the same readiness check as `/readyz`; it names the configured `formalizer.url` and model only to a signed-in session. It links to `/chat`, `/audit`, `/eval`, `/project`, `/admin` and `/docs/`. A server created without the password store (bearer credentials only) serves the same page without sign-in state.
- `GET /login?next=<path>` shows the first-run "choose the administrator password" form while no password exists, and the sign-in form afterwards; a request that already carries a valid session is redirected to `next`. `POST /login` (form-encoded `password`, `confirm` for the first run, `next`) calls the existing `Auth.setup`/`Auth.login`, so the minimum length (8), the throttle (ten failures within a minute) and the scrypt verification are unchanged. Success sets the HttpOnly `SameSite=Strict` session cookie and answers 303 to `next`. `next` is accepted only as a same-origin relative path (a single leading `/`, no scheme, authority, backslash or control characters); anything else becomes `/`. A post whose `Origin` differs from `Host` or that the browser marks `Sec-Fetch-Site: cross-site` is refused with 403. Failures re-render the form with a plain message: mismatched passwords or a too-short password (400), a setup attempt after a password exists (409), a wrong password (401), throttling (429).
- `POST /logout` ends the session, clears the cookie and answers 303 to `/login` (same cross-site refusal).
- A signed-out `GET /chat`, `/audit`, `/eval`, `/eval/guide`, `/project` or `/admin` that asks for HTML (`Accept: text/html`) and carries no `Authorization` header answers 303 to `/login?next=<requested path>`. Every other unauthenticated request keeps the JSON 401 (`unauthorized`) or 403 (`setup_required`) answer, including `/v1/*`, `/readyz`, `/audit/api/*`, `/eval/api/*` and `/project/api/*`.
- `GET /audit` (authenticated) is the visual corpus audit ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)): it browses the JSONL corpora, re-executes a case on demand and appends verdicts to `eval/reports/current/audit/<corpus>.jsonl`; its API lives under `/audit/api/*`.
- `GET /eval` (authenticated) is the read-only evaluation browser (`server/eval-browser.mjs`, three-pane layout shared with the audit through `server/pages/three-pane.mjs`): the sealed suites under `eval/suites/**` (`formalizer-v1` and the out-of-distribution `formalizer-ood-v1`) and the files under `eval/predictions`, `eval/registry`, `eval/reports/current` and `eval/reports/history` (the last marked historical). For each row it shows the message (the only model input), the gold target, the evaluator steps with `file:line` citations, the expected result and world, and any prediction with its line diff and recorded outcome; evaluator reports are attached to a suite by `suite_sha256`. `POST /eval/api/execute` runs `evaluate` from `eval/run.mjs` on one row with a stored prediction or, labelled as a sanity check, the gold. `GET /eval/guide` explains splits, the sealed-test guard, admission, canonical versus execution comparison, every metric, template leakage, the out-of-distribution suite and qualified runs, citing code lines resolved when served.
- `GET /project` (authenticated, menu label "Fine-tuning & status") polls `GET /project/api/status` every 15 s and on focus: the training gate (prohibited until the owner's new explicit approval) and computed checks, the append-only journal `status/journal.jsonl` newest first with an area filter, the data pipeline per corpus (rows, target form, corpus-audit verdict and metrics, vocabulary check), `status/experiments.json` and `questions.md`. Agents append with `node tools/journal.mjs` (`lib/journal.mjs`). The journal is append-only and records what happened with links to evidence; it is not product documentation, and the experiment registry follows [DS010-experiment-preregistration.md](specsLoader.html?spec=DS010-experiment-preregistration.md).
- `GET /chat` (authenticated) serves the browser chat. It posts one user message per turn to `/v1/chat/completions` through same-origin fetch with the session cookie, selects the `conversation_id` (with a *New conversation* control), and renders each answer with a collapsible trace built from `chatSop` (status, backend, fallback, completeness, prompt choice (`prompt_profile`), answer language and its source, user statements, carried statements, model assumptions and policy, `unclear` kind, the not-computable reading, reinforcement, model SOP, execution circuit, provenance, pending clarification). Status codes are explained in plain words: 401/403 sign in again, 503 formalizer not ready, 409 conversation busy, 429 server busy, 504 time limit, 413 message too long. The browser keeps only a local display copy of the transcript; the server owns conversation context. An *Answer language* selector offers the default (English, or the language explicitly requested in the message), English or Romanian and sends the optional `language` field accordingly.
- `GET /admin` keeps server status and token mint/revoke and links to the chat and the audit; signing in and the first-run password happen on `/login`.

`GET /healthz` reports only process liveness (no authentication; no model readiness). All `/v1/*` paths and `/readyz` require a bearer token or the administrator session cookie. `GET /v1/models` lists the façade model only when ready. `POST /v1/chat/completions` accepts one **new** `{role:'user',content:'...'}` message, the configured façade `model`, optional `conversation_id` (default `default`), optional `stream`, optional `language` (`en` or `ro`; any other value is refused), and optional `chatSop.trustedSop`. The answer language is the `language` field when present, otherwise an explicit request in the message detected deterministically (`server/language.mjs`), otherwise English. The server, not the client-supplied message list, owns conversation history; arbitrary prior roles, tools/function calling and unsupported generation parameters are refused. Supplying `user` is optional but must equal the authenticated principal. The default `CHATSOP_API_KEY` authenticates principal `local`; embedded integrations can pass separate named bearer credentials via `createServer({authTokens:{alice:'...',bob:'...'}})`. A shared token is a shared identity and cannot provide multi-user isolation.

The normal completion is an OpenAI chat-completion envelope with `choices[0].message.content` (host CNL, not an uncertified rewrite) and `chatSop` containing `model_sop`, generated `circuit`, proof `provenance`, reasoner `backend`, reported `fallback`, `completeness`, authoritative `cnl`, `status`, clarification `pendingSop` and `required` when applicable, `answer_language` and `language_source` (`request`, `prompt` or `default`), the host-rendered `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy` and `assumption_branch` of a model-origin turn, the `unclear` kind and the `understood_as` reading of a not-computable problem when present, active `prompt_profile`, formalizer model, and optional trusted circuit/receipt. Provenance is observed or conditional as recorded by the runtime; no fabricated confidence is implied. `stream:true` emits the **already validated complete result** in SSE chat-completion chunks and terminates with `data: [DONE]`; it does not stream unverified model tokens. If the client disconnects, no additional HTTP chunks are sent; an already started inference or write is not rolled back. Explicit `/v1/responses`, `/v1/embeddings`, `/v1/tools` and chat tools receive errors rather than mock behavior.

## Starting it

```sh
# local, documentation + chat API; chat needs a formalizer endpoint to become ready
CHATSOP_API_KEY=<token at least 16 chars> node server/http.mjs            # 0.0.0.0:9999, all interfaces

# loopback only
CHATSOP_HOST=127.0.0.1 npm start

# an explicit prompt choice is mandatory: `formal` for a base model, `bare` for a fine-tuned one
CHATSOP_PROMPT_PROFILE=formal node server/http.mjs
```

`config/runtime.json` already sets `promptProfile: "formal"` for the configured base-model endpoint, so the server starts without extra environment. The launcher prints the home URL first (`http://<host>:<port>/`); the documentation site is available immediately at `http://<host>:<port>/docs/`, the browser chat at `/chat`, the evaluation browser at `/eval`, the project journal and status at `/project`, and the visual corpus audit is mounted at `/audit` behind the administrator session ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)); `GET /readyz` returns 503 with `model_available: false` and chat requests return 503 until a formalizer endpoint is running and `/v1/models` advertises the configured model identity.

## Locality, limits, persistence and errors

The default listener is `0.0.0.0:9999`, all IPv4 interfaces (`CHATSOP_HOST`, `CHATSOP_PORT`); set `CHATSOP_HOST=127.0.0.1` to restrict it to loopback. Because the default is reachable from the network, the unauthenticated documentation path, the home page and the first-run password setup on `/login` are exposed to that network, and anything beyond a trusted network still needs external transport security and access controls. Authentication is either the administrator password chosen on the first visit to `/login` (stored only as a scrypt hash in `state/auth.json`, handed to the browser as an HttpOnly session cookie) or a bearer token: `CHATSOP_API_KEY` from the environment, or a token minted on the admin page and stored as a SHA-256 digest. Environment tokens must be unique per principal and at least 16 characters. `limits.maxRequestBytes` (default 65536), `maxContextBytes` (4800), `maxConcurrent` (4) and `timeoutMs` (30000) can be supplied through `config.server.limits` or `createServer({limits})`. Request byte and message-context oversize return 413; overload returns 429; same-session concurrent calls return 409. Formalizer fetch uses the smaller of backend and request timeout; on timeout the façade returns 504 while the in-flight operation retains its concurrency slot until settled. Do not retry a timed-out trusted write without checking the session receipt/state. Errors have generic messages and must not echo request content, private claim details, model endpoint bodies or bearer keys.

Repository sessions are keyed by base, authenticated principal and `conversation_id`. Agent conversational context is stored alongside the repository in a private per-conversation state file; context is reloaded after restart, while repository writes survive independently. Keep the repository and conversation directory inaccessible to other local accounts, and do not expose this API publicly without an independent security review. A real model-backed smoke, calibrated model quality, tokenizer equivalence and checkpoint provenance **remain unverified** in this repository; the HTTP tests use an actual deterministic mock HTTP endpoint to prove wire behavior without neural inference.

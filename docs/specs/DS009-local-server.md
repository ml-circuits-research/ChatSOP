# Local OpenAI-compatible server

## Scope and authority

`server/http.mjs` provides an HTTP façade, listening on all interfaces by default. The only conversational execution path is `Agent.turn`: the query parser (`server/query-parser.mjs`) asks the query author (`lib/query-author`, a coding agent run through omp, `lib/omp`) for a circuit from the user's message and the vocabulary of the session's memory; the validator admits it ([DS014](specsLoader.html?spec=DS014-model-surface.md)); the KnowledgeLinker links its strings; the `Runtime` compiles the execution circuit, the StrategyRouter and a reasoning strategy execute it ([DS006](specsLoader.html?spec=DS006-reasoning.md)); the answer is rendered in English from the result packet by fixed templates. The coding agent writes only circuits (today queries, constraints, `unclear` and `unparsed` reports and `stated` suppositions; `assumed` session definitions are planned); it cannot choose `remember`, claim documentary provenance, invoke tools or publish knowledge. A separately authenticated, explicitly supplied `chatSop.trustedSop` circuit may contain `fact`, `event` and `remember` wires only; it runs as a trusted user action in that user's session before the question. The receipt of a stored claim is returned as `chatSop.system_receipt` and can identify the target of a later correction. This is not model output or automatic ingestion. Trusted writes persist in the repository's private session; they are not committed to another user's state or published as base knowledge.

## The coding agent and its availability

The model of the coding agent comes from a configured subscription chain (`queryParser.backend` and `omp` in `config/runtime.json`; the default model is `openai-codex/gpt-6-luna`); the chain is tried in order and the parse record names the models tried. There is no fallback parser and no SymbolicLM: when no model of the chain can run, the chat completion answers 503 `parse_unavailable` with `chatSop.status: parse_unavailable` and the reason; when the models ran and no valid circuit came back after the bounded repair rounds, it answers 422 `parse_failed` with `chatSop.status: rejected`. The server itself starts without a coding agent and reports its availability: `GET /v1/models` lists the façade model together with the availability of the coding agent, and `GET /readyz` reports `ready` while the server can serve and whether the coding agent is available. `GET /v1/omp/models` lists the models omp can use with their cost class (cached; `?refresh=1` re-reads). Identical requests are cached per memory version, model and guide version (`GET /v1/cache/stats`, `POST /v1/cache/clear`). The server never loads model weights and starts no model process.

## Chat data, sessions and drafts

All chat data lives under one gitignored root, `chat_data/` (`chatData.root` in `config/runtime.json`, `CHATSOP_CHAT_DATA`), with `base_memories/`, `sessions/` and `tmp/`; a cleanup policy removes temporary folders older than `chatData.tmpTtlHours` (24) and sessions idle for `chatData.sessionTtlDays` (14) at start and every `chatData.cleanupIntervalMinutes` ([DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md)). A chat runs in a **session**: a working copy of a chosen **base memory** (a named, forkable knowledge store of any memory strategy, [DS005](specsLoader.html?spec=DS005-memory.md) and DS016 to DS021) cloned into the session folder; the chat request carries `session_id`, and one automatic session per user and conversation on the empty `default` base memory serves requests without one. Knowledge circuits proposed by the coding agent (from attached files or instructions) are drafts that the user accepts or rejects; nothing is accepted by the model. The request parser keeps the parse record in the packet (`parse: {parser, model, rounds, cost_usd, ms, cache, ...}`) so the trace shows the models, rounds, time and cost.

## HTTP contract

`GET /docs` redirects to `/docs/`, which serves the repository documentation site statically (`docs/index.html`, the wiki, the wire help, the specification matrix and the DS files). Static serving needs no bearer token, is read-only, never lists a directory, refuses any path that resolves outside `docs/` (encoded traversal and NUL bytes included) and sets `no-cache` for HTML and a short cache for other assets. The chat API keeps its authentication.

For a signed-in session the server also serves a fixed allowlist of repository Markdown read-only as plain text (`REPO_MARKDOWN` in `server/http.mjs`), so the owner can read the skills and project files on the server. One shared menu (`server/pages/site-menu.mjs`, mirrored in `docs/partials/header.html` and checked by `node tools/site-menu.mjs --check`) links the server pages and the documentation. `node tools/check-links.mjs` crawls the served site (its own server on a temporary port with temporary state, signed in) and fails on any broken link or `#anchor`; `tests/site-links.test.mjs` runs it in `npm test`.

### API routes

Every `/v1/*` path requires a bearer token or the administrator session cookie.

| Route | Purpose |
| --- | --- |
| `POST /v1/chat/completions` | One chat turn: `messages` (exactly one new user message), `conversation_id`, `session_id`, `stream`, `user` and `chatSop.trustedSop`; `model` only names the façade. |
| `GET /v1/models` | The façade model and the availability of the coding agent. |
| `GET|POST /v1/memories`, `GET|DELETE /v1/memories/{id}`, `POST /v1/memories/{id}/fork`, `POST /v1/memories/{id}/knowledge` | Base memories: list, create or import, manifest, fork, add validated knowledge circuits with provenance. |
| `POST /v1/sessions`, `GET /v1/sessions`, `GET|DELETE /v1/sessions/{id}`, `POST /v1/sessions/{id}/settings`, `GET /v1/sessions/{id}/theory`, `POST /v1/sessions/{id}/commit` | Sessions on a base memory, their settings, the base circuits followed by the accepted session circuits, commit to a new fork. |
| `GET /v1/sessions/{id}/drafts`, `POST /v1/sessions/{id}/drafts/{draft}/accept|reject`, `GET /v1/sessions/{id}/requests/{request}` | Draft circuits with their validation, user acceptance or rejection, the status of an authoring request. |
| `POST /v1/sessions/{id}/query` | Runs a query circuit over the session's memory; the oracle gets the slice the query needs (`answer.retrieval`). |
| `POST /v1/author`, `GET /v1/omp/models` | Knowledge authoring by the coding agent as proposed drafts; the models omp can use. |
| `GET /v1/capabilities`, `GET /v1/cache/stats`, `POST /v1/cache/clear` | The endpoint list with versions, cache statistics, cache reset. |

The request fields `parser` and `language` do not exist: the circuit is always written by the coding agent and the answer is always English. Endpoints of the earlier tiny-model branch (`/v1/symbolic/*`, `/v1/understand`, `/v1/language/proofread`, `/v1/text-to-clean-english`, `/v1/emotion/detect`, `/v1/server/models`, `/v1/route`, `/v1/sessions/{id}/scope-answer`, `/v1/models/{id}/start`, the corpus audit page `/audit`) are not part of the product; the capability-API specification is archived at `probably_obsolete/tinyLLMExperiments/specs/DS030-capability-apis.md`. The reference with executable examples is `docs/api.html`.

`POST /v1/chat/completions` accepts one **new** `{role:'user',content:'...'}` message (any language), `model` (the façade id listed by `GET /v1/models`; any other value is refused with 400 `unknown_model`), optional `conversation_id` (default `default`), optional `session_id`, optional `stream`, and optional `chatSop.trustedSop`. Any other parameter is refused with 400. The server, not the client-supplied message list, owns conversation history; arbitrary prior roles, tools/function calling and unsupported generation parameters are refused. Supplying `user` is optional but must equal the authenticated principal. The default `CHATSOP_API_KEY` authenticates principal `local`; embedded integrations can pass separate named bearer credentials via `createServer({authTokens:{alice:'...',bob:'...'}})`. A shared token is a shared identity and cannot provide multi-user isolation. A circuit that is written but not admitted or cannot be executed answers 422 `model_output_rejected` with a partial `chatSop` (`status: rejected`, `rejection`, `model_sop`, `parse`); nothing is executed or written.

The normal completion is an OpenAI chat-completion envelope with `choices[0].message.content` (the deterministic English answer, not an uncertified rewrite) and `chatSop` containing `model_sop` (the circuit the coding agent wrote), the generated execution `circuit`, proof `provenance`, reasoner `backend`, reported `fallback`, `completeness`, authoritative `cnl`, `status`, clarification `pendingSop` and `required` when applicable, the rendered `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy` and `assumption_branch`, the `unclear` kind and the `understood_as` reading of a not-computable problem when present, the `parse` record, `session` and `latency_ms`. Provenance is observed or conditional as recorded by the runtime; no fabricated confidence is implied. `stream:true` emits the **already validated complete result** in SSE chat-completion chunks and terminates with `data: [DONE]`; it does not stream unverified model tokens. If the client disconnects, no additional HTTP chunks are sent; an already started inference or write is not rolled back. Explicit `/v1/responses`, `/v1/embeddings`, `/v1/tools` and chat tools receive errors rather than mock behavior.

`GET /healthz` and its alias `GET /health` report process liveness (no authentication).

### Browser pages

When the server has the administrator password store (`npm start`, `startServer`), browser pages are layered on the unchanged session-cookie authentication; they present it and never grant access themselves. Page modules live in `server/pages/` and their routing in `server/web.mjs`. All server pages and the documentation site share one top menu (Home, Chat, Eval, an Experiments dropdown, Admin, a Docs dropdown, then Logout, or Sign in on a signed-out page), defined once in `server/pages/site-menu.mjs` and styled by `docs/assets/site-menu.css`. The layout works at phone width. `GET /assets/sop-code.mjs` (public) serves the shared SOP highlighter (`server/pages/sop-code.mjs`), which the documentation pages use to link SOP blocks to the wire help; the chat trace and the evaluation browser use the same renderer. It links wire types and fields to their help pages and marks a type or field outside the parser contract "undocumented". The structural words `all`, `any`, `match`, `end` and the atom prefix `not`, read from `sop/conditions.mjs` and `sop/parser.mjs`, are grammar: they are rendered as syntax keywords linked to `docs/wire_typs/syntax.html#syntax-<word>` and never flagged (`tests/sop-code-syntax.test.mjs`).

- `GET /` is a public home page. It states whether the visitor is signed in, whether the administrator password is set and whether the coding agent is available, and links to `/chat`, `/eval`, `/experiments`, `/admin` and `/docs/`.
- `GET /login?next=<path>` shows the first-run "choose the administrator password" form while no password exists, and the sign-in form afterwards; a request that already carries a valid session is redirected to `next`. `POST /login` (form-encoded `password`, `confirm` for the first run, `next`) calls the existing `Auth.setup`/`Auth.login`, so the minimum length (8), the throttle (ten failures within a minute) and the scrypt verification are unchanged. Success sets the HttpOnly `SameSite=Strict` session cookie and answers 303 to `next`. `next` is accepted only as a same-origin relative path (a single leading `/`, no scheme, authority, backslash or control characters); anything else becomes `/`. A post whose `Origin` differs from `Host` or that the browser marks `Sec-Fetch-Site: cross-site` is refused with 403. Failures re-render the form with a plain message: mismatched passwords or a too-short password (400), a setup attempt after a password exists (409), a wrong password (401), throttling (429).
- `POST /logout` ends the session, clears the cookie and answers 303 to `/login` (same cross-site refusal).
- A signed-out `GET /chat`, `/eval`, `/eval/guide`, `/admin`, `/experiments` or any `/experiments/…` page that asks for HTML (`Accept: text/html`) and carries no `Authorization` header answers 303 to `/login?next=<requested path>`. Every other unauthenticated request keeps the JSON 401 (`unauthorized`) or 403 (`setup_required`) answer, including `/v1/*`, `/readyz`, `/eval/api/*`, `/experiments/api/*` and its alias `/project/api/*`.
- `GET /eval` (authenticated) is the read-only evaluation browser (`probably_obsolete/tinyLLMExperiments/server/eval-browser.mjs`, three-pane layout through `probably_obsolete/tinyLLMExperiments/server/pages/three-pane.mjs`): the sealed suites under `eval/suites/**` and the files under `eval/predictions`, `eval/registry`, `eval/reports/current` and `eval/reports/history` (the last marked historical). For each row it shows the message, the gold target, the evaluator steps with `file:line` citations, the expected result and world, and any prediction with its line diff and recorded outcome. `GET /eval/guide` explains splits, the sealed-test guard, admission, canonical versus execution comparison, the metrics and qualified runs, citing code lines resolved when served.
- `GET /experiments` (authenticated; the menu's "Experiments" dropdown: Index, Topics, Reports, Timeline & live status, Open questions) is the living project history, rendered on the server by `server/pages/history.mjs` from `server/history.mjs`. Every list on these pages is newest first, and nothing shown is ever replaced: records accumulate across project phases.
  - `/experiments` (index): a current-status header (the phase recorded in `status/tasks.json`, the tasks and experiments in progress, the open questions of `questions.md`, the latest journal activity and a count of the computed checks), every task and experiment newest first, and every topic with its note count and latest entry.
  - `/experiments/<id>`: one page per task record of `status/tasks.json` or experiment record of `status/experiments.json` (DS007). The page keeps two sides apart: **Owner** (what the owner asked, why, the owner's decisions and corrections, then a newest-first stack of the related owner decisions from the journal and decision notes) and **Agents / analysis** (what was analysed, tried and run including failed attempts, what was obtained, the conclusions, open follow-ups and evidence links, then a newest-first stack of the related agent notes and journal events). Experiment records are shown in full: hypothesis, the preregistration record rendered, deviations, datasets and hashes, models, results, conclusions and reports. Notes and events are related to a task through its `match` phrases and experiment ids.
  - `/experiments/topics` and `/experiments/topic/<id>`: the topics of `status/topics.json` and one topic's full note stack (`status/notes/<id>.jsonl`), newest first, with browser-side filters by kind and author (`?kind=`, `?author=`) and supersede chains shown both ways ("superseded by …", "supersedes …"); a superseded note stays visible, dimmed.
  - `/experiments/reports[?dir=…]` and `/experiments/report?path=…`: a read-only, newest-first browser of `eval/reports/current/**` and `eval/reports/history/**` (the latter marked historical). Markdown is rendered, JSON is tabulated when simple and pretty-printed otherwise, JSONL, log and text files are shown as text, and a file over 2 MB shows only its first 96 KB. Paths are repository-relative and must resolve, after symlinks, inside one of the two roots; absolute paths, `..`, NUL and backslashes are refused with 400. Cache directories (`cache*`) and test leftovers are listed but not expanded.
  - `/experiments/timeline` polls `GET /experiments/api/status` every 15 s and on focus: the computed checks, the append-only journal `status/journal.jsonl` newest first with an area filter, `status/experiments.json` and `questions.md`.
  - `/experiments/questions`: `questions.md` rendered.
  - JSON APIs for the same data: `/experiments/api/status`, `/experiments/api/tasks`, `/experiments/api/topics`, `/experiments/api/notes[?topic=&kind=&author=]` and `/experiments/api/report?path=…|?dir=…` (same path rules). `/project/api/*` answers the same endpoints as an alias; every other `/project` or `/project/…` browser path answers 301 to the same path under `/experiments`.
  - Agents write the journal with `node tools/journal.mjs` (`lib/journal.mjs`), topic notes with `node tools/notes.mjs` (`lib/notes.mjs`) and task records in `status/tasks.json` (`lib/tasks.mjs`); the schemas are in [DS007-experiment-preregistration.md](specsLoader.html?spec=DS007-experiment-preregistration.md) ("Tasks and topic notes"). The journal and the notes are append-only; neither is product documentation nor, by itself, evidence of a result: entries point at their evidence.
- `GET /chat` (authenticated) serves the browser chat, a sidebar of vertical tabs (Chat, Settings, Base Memory; the open tab is remembered per browser, icon rail below 760 px). *Chat*: a header with the session and its base memory, *New session* (picks a base memory from `GET /v1/memories`), *Drafts*, *Commit*, the message list (newest at the bottom, a "new messages" pill once the user scrolled up) and the composer (attach button, Enter sends, Shift+Enter adds a line). It posts one user message per turn to `/v1/chat/completions` through same-origin fetch with the session cookie and renders each answer with a collapsible trace built from `chatSop` (status, backend, fallback, completeness, the parse record with model, rounds, time and cost, user statements, carried statements, model assumptions and policy, `unclear` kind, the not-computable reading, reinforcement, the circuit the coding agent wrote, the execution circuit, provenance, pending clarification). Status codes are explained in plain words: 401/403 sign in again, 503 `parse_unavailable` (no coding-agent model could run, with the reason), 422 circuit refused (the trace shows what the coding agent wrote and why), 409 conversation busy, 429 server busy, 504 time limit, 413 message too long. The browser keeps only a local display copy of the transcript; the server owns conversation context. *Settings*: the coding-agent model picker with cost class and the authoring options. *Base Memory*: a table (name, strategy, size, created, parent) with View, Fork, Add knowledge (validation problems shown), Start session and Create empty memory. The page is `server/pages/chat.mjs` with `chat/style.mjs` and `chat-product.mjs`; `probably_obsolete/tinyLLMExperiments/tools/ui/chat-ui-shots.mjs` checks it in a browser at 1280 and 390 px, light and dark.
- `GET /admin` keeps server status and token mint/revoke and links to the chat; signing in and the first-run password happen on `/login`.

## Starting it

```sh
# local, documentation + chat API; the coding agent (omp) is needed only to answer chat turns
CHATSOP_API_KEY=<token at least 16 chars> node server/http.mjs            # 0.0.0.0:9999, all interfaces

# loopback only
CHATSOP_HOST=127.0.0.1 npm start
```

The launcher prints the home URL first (`http://<host>:<port>/`); the documentation site is available immediately at `/docs/`, the browser chat at `/chat`, the evaluation browser at `/eval`, and the project history, journal and status at `/experiments`. Without an available coding-agent model the server starts, `GET /readyz` reports the coding agent unavailable, and chat requests return 503 `parse_unavailable`.

## Locality, limits, persistence and errors

The default listener is `0.0.0.0:9999`, all IPv4 interfaces (`CHATSOP_HOST`, `CHATSOP_PORT`); set `CHATSOP_HOST=127.0.0.1` to restrict it to loopback. Because the default is reachable from the network, the unauthenticated documentation path, the home page and the first-run password setup on `/login` are exposed to that network, and anything beyond a trusted network still needs external transport security and access controls. Authentication is either the administrator password chosen on the first visit to `/login` (stored only as a scrypt hash in `state/auth.json`, handed to the browser as an HttpOnly session cookie) or a bearer token: `CHATSOP_API_KEY` from the environment, or a token minted on the admin page and stored as a SHA-256 digest. Environment tokens must be unique per principal and at least 16 characters. `limits.maxRequestBytes` (default 65536), `maxContextBytes` (4800), `maxConcurrent` (4) and `timeoutMs` (30000) can be supplied through `config.server.limits` or `createServer({limits})`. Request byte and message-context oversize return 413; overload returns 429; same-session concurrent calls return 409. On timeout the façade returns 504 while the in-flight operation retains its concurrency slot until settled. Do not retry a timed-out trusted write without checking the session receipt/state. Errors have generic messages and must not echo request content, private claim details, coding-agent output bodies or bearer keys.

Repository sessions are keyed by base, authenticated principal and `conversation_id`. Agent conversational context is stored alongside the repository in a private per-conversation state file; context is reloaded after restart, while repository writes survive independently. Keep the repository and conversation directory inaccessible to other local accounts, and do not expose this API publicly without an independent security review. The HTTP tests use a stub omp runner and a deterministic completion endpoint to prove wire and process behavior without a real coding agent; benchmark results are measured under [DS012](specsLoader.html?spec=DS012-evaluation-metrics.md), not by this server.

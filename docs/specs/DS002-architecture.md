## Introduction

ChatSOP accepts a checked [SOP](wiki.html#definition-sop) program from a file or from the SymbolicLM [formalizer](wiki.html#definition-formalizer) service, and executes it using explicit memory and reasoning components. The CLI is a local program; the local server (`npm start`) adds the documentation site, the OpenAI-compatible chat façade, and the administrator pages `/audit`, `/eval` and `/experiments` ([DS012](specsLoader.html?spec=DS012-local-server.md)).

## Core Content

### Directory responsibilities

`lib/` holds utility, time, and shared type code; `sop/` owns parsing, typing, lowering, controlled language, lexicon, ingestion checks, and runtime orchestration. `sop/knowledge/` is the single grammar source of the knowledge language (the wire-type table, the parser, the validator, governance and the desugarer, [DS004](specsLoader.html?spec=DS004-sop.md) "Knowledge wires"), imported by the reasoning strategies, the smoke harness and the wire help tests, while the model surface stays in `sop/enums.mjs`, `sop/parser.mjs` and `sop/declarative.mjs`. `sop/grammars/` carries grammar resources, `sop/contracts/` holds the generated capability catalog, `config/` contains runtime configurations and the ontology, and `tests/fixtures/` carries demo and bootstrap SOP knowledge. `memory/` owns [repository](wiki.html#definition-repository) snapshots, session isolation, retention, and interchangeable banks. `reasoning/` owns linking, the runtime bridge to the oracle (`reasoning/bridge/`), solver selection and the controllers, and `reasoning/strategies/<id>/` holds the independently selectable strategies of [DS006](specsLoader.html?spec=DS006-reasoning.md) "Strategies" (the oracle `js-reference` and the others), compared by `eval/smoke-reasoning/` ([DS013](specsLoader.html?spec=DS013-engine-and-solver-comparison.md)). `server/` contains the local conversational orchestration, model endpoint client, prompts, CLI, and the local HTTP server with its pages (chat, corpus audit, evaluation browser, project status). `status/` holds the append-only project journal `status/journal.jsonl` and the preregistered experiment registry `status/experiments.json`, written through `tools/journal.mjs` and `lib/journal.mjs` ([DS010](specsLoader.html?spec=DS010-experiment-preregistration.md)); the journal is a record of work, not product documentation. `tools/` owns conversion, validation, review and dataset tooling, and `skills/` holds task procedures. The kernel must not depend on `server/`.

### Data and model isolation

`datasets/` carries the three datasets `bad_english`, `symbolic_english` and `neuro_english` (DS008 "Three datasets") and the `natural` collection; the legacy model-language corpora (DS022: `formalizer-v1` and its shared verification world) are in `datasets_archive/`; sealed tests live under `eval/suites/`, and raw source caches under `datasets_sources/`. `eval/` holds evaluation code and immutable historical reports at `eval/reports/history/`; fresh reports belong in `eval/reports/current/` with their own observed run metadata. `models/<model>/<run>/` separates model identity from the run's training artifacts; a directory layout does not establish that a checkpoint exists or works. `training/` owns Node orchestration and the indispensable Python ML operations at `training/python/`. Archived requirements, registers, proposals and references remain under `probably_obsolete/` as historical evidence, not as an alternative current module layout.

### Trust and integration boundary

The CLI host initiates `init`, `run`, `validate`, `compile`, `chat`, and repository lifecycle commands. The parser and runtime reject unsupported fields or unauthorized effects before committing. [Linking](wiki.html#definition-linker) selects approved definitions and relevant facts; a solver receives explicit typed inputs, not unrestricted authority to search or publish. [CNL](wiki.html#definition-cnl) reports the result and supporting information. The OpenAI-compatible façade (`GET /v1/models`, `POST /v1/chat/completions`) is the host contract of [DS012](specsLoader.html?spec=DS012-local-server.md); an upstream model endpoint alone is not that contract.

Model-authored SOP contains only `stated`, `assumed`, `unclear`, `query`, and `constraint` ([DS021](specsLoader.html?spec=DS021-model-surface.md)). The model sees only the user's message, writes quoted strings with roles from the closed role set, never refuses, and reports `unclear` only as `gibberish` or `no_request`; the host links the strings to knowledge. A `stated` or `assumed` proposition has no source/quote/write field; the host lowers it to a turn-local `fact`, separate from sourced repository facts, and never records it implicitly. The host retains the original user text and model-interpretation origin, then compiles an inspectable circuit with approved operations such as `resolve` for lookup, `pack` for collections, `solve` for reasoning, and `cnl` for rendering. Symbolic orchestration may generate a `clarify` wire and suspend dependent work when identity is unresolved/ambiguous or a required scalar is unavailable/nonunique; unknown evidence alone does not imply clarification. Explicit `remember` and session commit remain trusted tool/host operations for authorized sourced facts/events, not consequences of model statements or assumptions. Expansion may choose an execution path but cannot invent an identity or turn quotations, hypotheses, or inferences into stored claims.

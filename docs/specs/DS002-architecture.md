## Introduction

ChatSOP accepts a checked [SOP](wiki.html#definition-sop) program from a file, or a circuit written for a chat message by the query author (a coding agent), and executes it using explicit memory and reasoning components. The CLI is a local program; the local server (`npm start`) adds the documentation site, the OpenAI-compatible chat façade, the product API for memories, sessions and drafts, and the owner pages `/eval`, `/experiments` and `/admin` ([DS009](specsLoader.html?spec=DS009-local-server.md)).

## Core Content

### Runtime flow of a chat turn

The user message (any language) goes to the request parser, which asks the query author for a circuit with the session's formalization strategy (CodingAgent through omp by default, LocalLLMDirect and LocalLLMStepByStep through a shared local llama-server, `lib/local-llm/`) and the schema neighbourhood of the session's memory; the validator admits it or sends bounded repair rounds, with at most two vocabulary-dialog expansions; the KnowledgeLinker links its entity and relation strings to the session's memory; slice retrieval fetches only what the question can use, under the completeness guard; the StrategyRouter selects a reasoning engine or the JavaScript reference oracle and verifies a routed answer against the oracle; the result packet is rendered as English text by fixed templates with the origin of each step. With no model of the strategy available the turn returns `parse_unavailable`; there is no fallback parser and no substitution of strategies. The pieces are specified in [DS014](specsLoader.html?spec=DS014-model-surface.md) (circuit surface and linking), [DS006](specsLoader.html?spec=DS006-reasoning.md) (strategies and router), [DS022](specsLoader.html?spec=DS022-sessions-and-base-memories.md) (sessions, memories, drafts) and [DS009](specsLoader.html?spec=DS009-local-server.md) (HTTP).

### Directory responsibilities

- `lib/` holds utility, time and shared type code. `lib/query-author/` is the query author: the prompt and context builder, retrieval of candidate predicates and entity hints from the memory vocabulary, the schema neighbourhood (`neighbourhood.mjs`), the validator and its condition-use guard (`validate.mjs`, `admit.mjs`, `condition-use.mjs`), the validate-and-repair loop with the vocabulary dialog (`loop.mjs`), the pluggable backends (`omp`, `completion`) and the step-by-step assembly of LocalLLMStepByStep (`step-by-step/`, in progress). `lib/local-llm/` is the shared local runtime of the local formalization strategies: managed llama-server instances with dedicated slots and saved prompt prefixes. `lib/omp/` is the omp integration: model discovery with cost classes, the fenced non-interactive run, and the authoring loop for knowledge circuits. `lib/chat-data/` is the gitignored chat data root (memories, sessions, lexicons). `lib/cache/` is the bounded LRU cache.
- `sop/` owns parsing, typing, lowering, controlled language, the lexicon, ingestion checks, the KnowledgeLinker and its relation linking, the symbolic repair of `unparsed` spans, the deterministic answer text (`answer-text.mjs`) and the runtime orchestration. `sop/knowledge/` is the single grammar source of the knowledge language (the wire-type table, the parser, the validator, governance and the desugarer, [DS004](specsLoader.html?spec=DS004-sop.md) "Knowledge wires"); the circuit surface stays in `sop/enums.mjs`, `sop/parser.mjs` and `sop/declarative.mjs`. `sop/grammars/` carries grammar resources and `sop/contracts/` the generated capability catalog.
- `memory/` owns [repository](wiki.html#definition-repository) snapshots, session isolation, retention and interchangeable banks ([DS005](specsLoader.html?spec=DS005-memory.md)).
- `reasoning/` owns the runtime bridge to the oracle (`bridge/`), solver selection, the StrategyRouter (`router/`), the demand-driven slice path (`slice/`) and `strategies/<id>/`, the independently selectable strategies of [DS006](specsLoader.html?spec=DS006-reasoning.md) "Strategies" (the oracle `js-reference` and the others), compared by `eval/smoke-reasoning/` ([DS010](specsLoader.html?spec=DS010-engine-and-solver-comparison.md)).
- `server/` holds the conversational orchestration (`agent.mjs`, `query-parser.mjs`, `session-runtime.mjs`), the product API (`product.mjs`), the authoring routes (`authoring.mjs`), the server status (`status.mjs`), the start-up warming (`warm-memories.mjs`), the local HTTP server with its pages (`http.mjs`, `web.mjs`, `pages/`) and the CLI (`cli.mjs`). The kernel (`lib/`, `sop/`, `memory/`, `reasoning/`) must not depend on `server/`, except that `lib/query-author/validate.mjs` reuses the admission of `server/agent.mjs`.
- `config/` contains runtime configurations and the base-memory vocabulary seeds; `tests/fixtures/` carries demo and bootstrap SOP knowledge.
- `status/` holds the append-only project journal `status/journal.jsonl`, the topic notes and the preregistered experiment registry `status/experiments.json`, written through `tools/journal.mjs`, `tools/notes.mjs` and `lib/journal.mjs` ([DS007](specsLoader.html?spec=DS007-experiment-preregistration.md)); the journal is a record of work, not product documentation.
- `tools/` owns conversion, validation, review and dataset tooling; `eval/` the evaluation code, sealed suites and reports; `experiments/` research proposals; `skills/` the task procedures.

**Dependency rules (checked by `tests/architecture-page.test.mjs`).** The product modules (`lib/`, `sop/`, `memory/`, `reasoning/`, `server/`) form an acyclic import graph at module level; `sop/` and `reasoning/` use each other's modules but no module cycle exists. A product module never imports `eval/` or `tools/` statically. Code that the evaluation and the product share, such as the id-free wire keys of `sop/wire-items.mjs`, lives with the language modules.

### Data and model isolation

Sealed tests live under `eval/suites/`, raw source caches under `datasets_sources/`, and `eval/` holds evaluation code and immutable historical reports at `eval/reports/history/`; fresh reports belong in `eval/reports/current/` with their own observed run metadata. The frozen tiny-model branch (Stanza and the UD-to-SOP rules, SymbolicLM, language and translation services, the small fine-tuned models, training, the three datasets and the corpus audit) is preserved under `probably_obsolete/tinyLLMExperiments/`, and the paused EmotionDetectionSystem under `probably_obsolete/paused/`; neither is imported by product code. Archived requirements, registers, proposals and references remain under `probably_obsolete/` as historical evidence, not as an alternative module layout.

### Trust and integration boundary

The CLI initiates `init`, `run`, `validate` and the repository lifecycle commands. The parser and runtime reject unsupported fields or unauthorized effects before committing. [Linking](wiki.html#definition-linker) selects approved definitions and relevant facts; a solver receives explicit typed inputs, not unrestricted authority to search or publish. [CNL](wiki.html#definition-cnl) reports the result and supporting information. The OpenAI-compatible façade (`GET /v1/models`, `POST /v1/chat/completions`) is the contract of [DS009](specsLoader.html?spec=DS009-local-server.md); an upstream model endpoint alone is not that contract.

Circuits written by the coding agent contain only the declarations of the circuit surface ([DS014](specsLoader.html?spec=DS014-model-surface.md)): queries, constraints, `unclear` and `unparsed` reports and `stated` suppositions (`assumed` session definitions and assumptions are planned, not yet admitted). The coding agent sees the message and the memory vocabulary, writes strings and identifiers checked against the memory, never answers and never adds a fact. A `stated` or `assumed` proposition has no source or quote field; the runtime lowers it to a turn-local `fact`, separate from sourced repository facts, and never records it implicitly. The runtime retains the original user text and the origin of the circuit, then compiles an inspectable circuit with approved operations such as `resolve` for lookup, `pack` for collections, `solve` for reasoning and `cnl` for rendering. Symbolic orchestration may generate a `clarify` wire and suspend dependent work when identity is unresolved or ambiguous or a required scalar is unavailable or nonunique; unknown evidence alone does not imply clarification. Explicit `remember` and session commit remain trusted operations for authorized sourced facts and events, not consequences of statements or assumptions. Expansion may choose an execution path but cannot invent an identity or turn quotations, hypotheses or inferences into stored claims.

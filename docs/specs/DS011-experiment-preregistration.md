## Introduction

An experiment is a predeclared comparison, not a retrospective description of a successful run. This specification defines what an operator must freeze **before** using a holdout or running a model. The thresholds below are proposed promotion gates to freeze for a particular approved study, **not measured results**, model accuracy claims, or permission to train. The source and execution boundaries of semantic cases remain in [DS008-data-evaluation.md](specsLoader.html?spec=DS008-data-evaluation.md) and [DS009-query-curriculum.md](specsLoader.html?spec=DS009-query-curriculum.md).

## Core Content

### Pre-run record and controlled hypotheses

For each proposed experiment, register an immutable ID and timestamp, question, directional hypothesis, one main changed factor, named comparator, fixed common inputs and tools, measurable endpoint with denominator, failure/falsification condition, budgets, and intended analysis slices. Record dataset manifest and content hashes, source rights and adjudication state, pinned base/model/recipe when applicable, SOP/runtime/solver versions, actual backend and fallback, prompt profile, approved knowledge snapshot, ontology, seed policy, and evaluation script revision. Record missing fields as unresolved; do not backfill a preregistration after viewing the holdout. Any new arm or threshold chosen after inspection is exploratory and needs a new sealed holdout to become confirmatory.

| Question | One changed factor and comparator | Falsification condition |
| --- | --- | --- |
| Does an approved formalizer change improve declarative SOP accuracy? | Candidate versus pinned baseline on the same input profile, knowledge, evaluation set, decoder and budgets; only the preregistered data/recipe/model factor changes in a given comparison. | Its predeclared correctness endpoint does not improve on the held-out paired cases, or a safety/promotion gate fails. This comparison does not authorize fine-tuning. |
| Does a memory route improve retrieval without changing answers? | One `memory.engine` or retrieval strategy versus a named baseline, with fixed SOP, facts, rules, reasoner and snapshot. | Evidence coverage, isolation, or correctness degrades under the predeclared case families; different storage costs are reported separately. |
| Does an external backend preserve the supported reasoning profile? | `reference` JS versus `advanced` with explicitly selected SWI for point-in-time Horn, or Z3 for declared numeric constraints, with identical problem and premises. | An admitted complete case disagrees on answer/projection or a required input disappears; unavailable binaries and incomplete results are exclusions, not a solver win. |

Register per-arm ceilings for wall time, CPU/GPU time, token usage, solver calls/timeouts, memory, disk and checkpoints **as actual study-specific quantities before execution**; no universal numeric compute budget is asserted here. State abort conditions, monitoring owner, maximum attempts, and whether an unavailable optional backend means skip rather than substitution. Only one GPU-intensive worker per machine may operate under the authorized orchestration policy. A changed model and a changed corpus are two experiments, not one confounded arm.

### Splits and locked evaluation

Assign the `semantic_case_id` group before rendering: paraphrases, EN/RO translations, hard negatives, shared source worlds and semantic duplicates stay in the same train/dev/test group. Reserve composition-family holdouts before generation; label seen-shape, structural, source-independent and external-reference tests separately. Never tune on sealed test cases, including via repeated prompt selection. Audit disjoint physical paths, group IDs, hashes, source rights, provenance and leakage; quarantine unresolved sources or non-independent reference cases. Keep EN and RO denominators and each family/negative/UNKNOWN slice visible, including exclusions and confidence intervals where estimable; a synthetic fixture and a human-reviewed external case are not interchangeable.

### Promotion gates to freeze, not observations

Before evaluating a particular authorized candidate, freeze the exact metric definitions, denominator, pass/fail policy for incomplete or abstained results, and these minimum thresholds on independently adjudicated holdouts: parse validity **≥99%**; semantic correctness for **EN ≥90% and RO ≥90% independently**; hard-negative correctness **≥95%**; unsupported assertion rate **≤2% on UNKNOWN cases**; **zero isolation violations** (unauthorized knowledge writes or cross-session/source leakage). Treat abstention and nonresponse as incorrect for a required-answer correctness denominator unless the frozen protocol explicitly designates a separate abstention endpoint; never improve a score by dropping failed cases. Each threshold requires an adequate preregistered denominator and traceable numerator; if support is insufficient, report "not qualified", never round a small sample into a promotion claim. In addition, preserve the model-origin `premise`/`query`/`constraint` boundary, independent source rights and reviewed truth; a high aggregate score does not override a gate. These are targets for a prospective decision, not measurements of any existing model or system.

Count parse-valid predictions over every designated input row (including missing and malformed outputs as failures); EN/RO semantic correctness uses all designated rows of each language with the independently adjudicated expected answer and effects. Count a hard negative correct only when the answer, bindings, or effect differ as required by its linked contrast, not merely because its generic status matches. On UNKNOWN rows, the unsupported-assertion numerator is the number of rows where an answer asserts support or an observed fact without admitted evidence; the denominator is all designated UNKNOWN rows, including abstentions. Isolation is a strict violation count, not a rate that can be averaged away.

Promote only when all frozen gates, comparator improvement where hypothesized, data rights, independent review, operational budgets and safety checks pass on the designated locked evaluation; publish counts, denominators, family/language slices, exact identities, invalid outputs, skips and actual backend routes. A failed or inconclusive hypothesis is retained as such. **Training, fine-tuning, optimizer steps, resume and training smoke runs remain unauthorized without a new explicit user approval bound to the specific dataset, recipe, model and run.** Dataset qualification, symbolic checks or this preregistration cannot supply that approval.

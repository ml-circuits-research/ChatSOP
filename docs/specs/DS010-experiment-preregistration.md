## Introduction

An experiment is a predeclared comparison, not a retrospective description of a successful run. This specification defines what an operator must freeze **before** using a holdout or running a model. The thresholds below are proposed promotion gates to freeze for a particular approved study, **not measured results**, model accuracy claims, or permission to train. The source and execution boundaries of semantic cases remain in [DS008-data-evaluation.md](specsLoader.html?spec=DS008-data-evaluation.md) and [DS009-query-curriculum.md](specsLoader.html?spec=DS009-query-curriculum.md).

## Core Content

### Registry and experiment identity

Every proposed experiment is registered in `status/experiments.json` (format `chatsop-experiments-v1`), read and written through `lib/journal.mjs` and shown on the server's `/experiments` pages (one page per entry). An entry records `id`, `hypothesis`, `preregistration` (a link to the frozen record this specification requires), `data_version`, `status` (`proposed`, `preregistered`, `approved`, `running`, `done` or `abandoned`), `results` and `conclusions`. An entry exists from preregistration on; `running` and `done` entries exist only for runs the owner approved. Meaningful work and owner decisions around an experiment are appended to the project journal `status/journal.jsonl`; the journal records what happened and points at evidence, it is not evidence of a result by itself.

An evaluation run identifies itself: `eval/run.mjs:evaluate` produces `format`, `source`, `suite_sha256`, `config_sha256`, `runtime`, `model_manifest`, `model_identity_verified`, `requests_succeeded`, `evaluation_valid` and `records`. A manifest is supplied provenance, **not** an attestation of endpoint weights. `tests/contracts-boundary.test.mjs` (“experiment hash identifies fixed suite/config…”) executes the boundary: evaluating a fixed real row with an explicit predictor yields SHA-256 suite/config identities, and changing only `config.memory.engine` changes `config_sha256` but not `suite_sha256`; a duplicate row `id` rejects the run, and supplying `modelManifest` leaves `model_identity_verified:false`, because an opaque supplied manifest is not proof of weights or neural inference.

### Experiments

`status/experiments.json` records every study that produces a number the project may cite, not only preregistered ones. Each entry has the same fields, so every study can be read the same way on `/experiments/<id>`:

| Field | Content |
| --- | --- |
| `id`, `name` | Stable identifier (never reused or renamed) and a one-line human name. |
| `category` | `preregistered` (a frozen DS010 record exists), `reference-baseline` (a comparison point, not a controlled arm) or `data-study` (data, annotation or agreement work without a model under test). A missing category means `preregistered`. |
| `kind`, `owner`, `registered_at` | Free-text kind, the actor that runs it, and when the entry was first written. |
| `hypothesis`, `preregistration` | What is tested, and the frozen record's path. A `reference-baseline` or `data-study` writes `none: <why>` instead. |
| `data_version`, `datasets` | Data identity in one line, and each dataset or suite with `name`, `path`, `sha256`, `rows` and `role`. |
| `models` | Each model with `name`, `identity` (repository and revision), `version` (run, quantization, file hash), `runtime` and `status`. |
| `status` | `proposed`, `preregistered`, `approved`, `running`, `done` or `abandoned`. |
| `done`, `metrics` | What was actually done, and the endpoints with their denominators. |
| `results_summary`, `results` | A human-readable summary with counts, and machine-readable numbers (for example the per-arm partial results that `tools/research/record-result.mjs` writes). |
| `deviations` | Each change after registration: `id`, `at`, `what`, `why`, `effect`. |
| `conclusions`, `reports` | The conclusion, including a negative or inconclusive one, and links to the reports and raw predictions. |

`lib/journal.mjs` validates the required fields (`id`, `hypothesis`, `preregistration`, `data_version`, `status`) and the types of the optional ones; `tests/journal.test.mjs` requires every running or done `preregistered` entry to point at an existing frozen record. Several agents write the file: each re-reads it immediately before writing, changes only its own entries (or adds missing fields to another's), and never drops fields it does not own.

**Naming.** An id is lower-case words joined by hyphens and ends in a protocol version: `<scope>-<topic>-v<N>`. The scope says what kind of study it is: a model or training study is named after its subject (`formalizer-size-v1`), an inference-only evaluation starts with `eval-` (`eval-spellfix-preproc-v1`, `eval-haiku-prompted-baseline-v1`) and a data or annotation study with `data-` (`data-wild-pilot-v1`). A changed protocol, suite or decision rule is a new id with the next version, never an edit of a frozen record. Runs inside an experiment keep their own identifiers (`fv1-size-a4`).

### Tasks and topic notes

The experiment registry says what a study tested and obtained; two further records keep the project's history readable over time, on the server's `/experiments` pages ([DS012](specsLoader.html?spec=DS012-local-server.md)).

**Tasks** (`status/tasks.json`, format `chatsop-tasks-v1`, `lib/tasks.mjs`). One record per major piece of work (a review, a language redesign, a data build, a training study, a baseline, a diagnosis, a plan), including those without a model under test. The registry also holds `phase` (`name`, `since`, `detail`): the current project phase as last written by an agent.

| Field | Content |
| --- | --- |
| `id`, `kind`, `title` | Stable identifier (lower-case, never reused; not `api`, `topics`, `topic`, `reports`, `report`, `timeline`, `questions` or `tasks`), `task` or `experiment`, and a one-line title. A task that is an experiment of the registry uses the experiment's id. |
| `status`, `started_at`, `updated_at` | `open`, `running`, `paused`, `blocked`, `done` or `abandoned`, and ISO times. |
| `summary` | Two or three sentences for the index. |
| `owner` | Markdown: what the owner asked, why, and the owner's decisions and corrections along the way, quoted or faithfully paraphrased from journal decision events and `questions.md`. |
| `agents` | Markdown: what agents analysed, tried and ran (including failed and restarted attempts), what was obtained with numbers and denominators, the conclusions. |
| `follow_ups`, `links` | Open follow-ups, and evidence paths. |
| `topics`, `experiments`, `match` | The topic ids, experiment ids and phrases that relate notes and journal events to the task (case-insensitive substring match on their text and links). |

The task page shows the two sides apart: **Owner** and **Agents / analysis**, each with a newest-first stack of the related notes and journal events. Several agents may write the file: re-read it immediately before writing, change only your own records and never drop fields you do not own.

**Topic notes** (`status/topics.json`, format `chatsop-topics-v1`; `status/notes/<topic>.jsonl`; `lib/notes.mjs`; CLI `node tools/notes.mjs add|list|topics|validate`). A topic has a stable `id`, a `title` and a one-paragraph `scope`. A note is one JSON line:

| Field | Content |
| --- | --- |
| `id` | Unique across the store; generated as `<topic>-<yyyymmdd-hhmmss>-<6 hex of the title>` unless given. |
| `ts` | ISO time of what the note records (a note written later about an earlier event carries the event's time and says so in its body). |
| `topic` | A registered topic id; the note is stored in that topic's file. |
| `kind` | `decision`, `suggestion`, `analysis`, `observation`, `experiment`, `result`, `plan`, `question` or `correction`. |
| `author` | `owner` for the owner's requests and decisions (from journal events with state `decision` or actor `owner`/`owner-via-orchestrator`), else the agent or review that produced it (`orchestrator`, `training-agent`, `Fable review`, …). |
| `title`, `body`, `links` | A one-line title, a Markdown body with the numbers and their denominators, and repository paths or URLs of the evidence (reports, logs, records). |
| `supersedes` | Optional: the id of an earlier note that this one corrects or replaces. |

Notes are append-only: a note is never edited or deleted, a correction is a new note whose `supersedes` names the old one, and both stay visible ("superseded by …" on the old note). `appendNote` refuses an unknown topic, a duplicate id, a `supersedes` that names no existing note and a file whose last byte is not a newline; `validate` checks the whole store. Failed, restarted and invalidated attempts are recorded like successes, with their logs. Notes and the journal record what happened and what was concluded; they are not evidence by themselves and point at the reports that are. Like the journal, the notes are frozen history for `tools/check-spec-refs.mjs`: they may cite former specification ids, which the site resolves through `docs/specs/aliases.json`.

### Registered experiments

**`formalizer-size-v1`**: the first fine-tuning comparison, approved by the owner on 2026-09-28 (journal, area `training`, state `decision`). Its frozen record is `status/preregistrations/formalizer-size-v1.json`, written before any optimizer step or fine-tuned prediction. It asks how small the formalizer can be and how fast it runs on this machine's CPU. It compares full fine-tuning of SmolLM2-135M-Instruct and Gemma 3 270M IT, both always run in that order. SmolLM2-360M-Instruct runs, and then Qwen3-0.6B, only when no smaller arm is *adequate*. Adequate means, with Q8_0 CPU predictions: parse rate ≥99%, tolerant execution equivalence ≥90% separately in English and in Romanian on the `formalizer-v1` sealed test, and ≥70% on `formalizer-ood-v1`. Every arm uses the same recipe policy: FP32 master weights with BF16 autocast, peak learning rate 5e-5, 16 sequences per step, 3 epochs, seed 42, `max_length` 8192. Every arm uses the same message-only `formalizer-v1` projection, and the data hashes are filled in once when the data is declared final. The best checkpoint is selected on the development split. Evaluation uses GGUF Q8_0 (and Q4_K_M) on the CPU with the message as the only model input. The independent `formalizer-wild-v1` suite is scored by accepted-gold match and reference-free metrics, and is reported rather than gated. CPU speed is measured with `llama-bench` and with end-to-end latency on 300 test messages, recording the thread count. The study is experiment-grade: semantic review is the independent automated auditor with no human review, so no outcome is a promotion under the gates below.

**`eval-ud-rules-v14-v1`**: an inference-only evaluation (CPU, no training, no LLM calls). Its frozen record is `status/preregistrations/eval-ud-rules-v14-v1.json`, written right after a fresh stratified sample of 600 sealed messages (test, OOD, wild; every language) was drawn and before any rule change; the sample excludes the consumed `eval-symbolic-layers-en-v1` sample and its semantic cases. It measures ud-rules-v1.4 (developed on formalizer-v1 dev only, frozen by SHA-256) against v1.3 by strict match (the unchanged harness), with a host-normalized score (owner answer to Q-SYM-2) reported beside it; paired cluster bootstrap, staged at 150/300/full with a broken-output and a harm stop rule. Result: +7.0 points [4.7, 9.3].

**`eval-clause-decomposition-v1`**: the paired flat-versus-chained clause experiment of `eval/reports/current/sop-clause-decomposition-proposal.md` (two SmolLM2-135M runs), approved by the owner (decision L6 = A, 2026-09-29) and registered as `approved`; its frozen record, with data hashes, must be written before any run, and each training run follows the one-GPU-worker rule and the owner's run-by-run approval (D5).

**`eval-spellfix-preproc-v1`**: an inference-only evaluation (no training, CPU only). Its frozen record is `status/preregistrations/eval-spellfix-preproc-v1.json`, written after the corrector was tuned on the development split and before it touched any sealed suite. It asks whether a deterministic, dictionary-based spelling correction of the message (`lib/spellfix.mjs`: Hunspell en_US and ro, keyboard-aware edits, diacritic restoration, conservative guards, every change logged), run by the host before the formalizer, improves formalization of noisy messages without hurting clean ones. The comparator is the raw-message Q8_0 prediction of the `formalizer-size-v1` SmolLM2-135M arm; only messages the corrector changes are predicted again. The primary endpoint is the paired delta of tolerant execution equivalence on the noisy rows of the `formalizer-v1` sealed test, with a 95% cluster-bootstrap interval over semantic cases; the record states the decision rule for adoption.

**`eval-translate-then-formalize-v1`**: an inference-only evaluation (no training, CPU only). Its frozen record is `status/preregistrations/eval-translate-then-formalize-v1.json`, written after the translation prompts and a simple language detector were chosen on the development split and before any sealed-suite contact. It asks whether a host pre-step that translates a Romanian or mixed message into English with an original base instruct model (Gemma 3 270M IT; SmolLM2-360M-Instruct), before the fine-tuned formalizer sees it, improves formalization. Only Romanian and mixed rows are in scope: all of them in `formalizer-ood-v1` and `formalizer-wild-v1`, and a 400-row stratified sample of the `formalizer-v1` sealed test. The comparator is the direct (untranslated) Q8_0 prediction of the same formalizer. The primary endpoint is the paired delta of tolerant execution equivalence for SmolLM2-360M on the OOD rows, with a 95% cluster-bootstrap interval; name fidelity and end-to-end latency are secondary, and the record states the decision rule for adoption.

**`text-to-clean-english-v1`**: an inference-only evaluation (no training) of candidate backends for the `textToCleanEnglish` host step (owner decision 2026-09-30, [DS012](specsLoader.html?spec=DS012-local-server.md)/[DS021](specsLoader.html?spec=DS021-model-surface.md) "textToCleanEnglish"). Its frozen record is `status/preregistrations/text-to-clean-english-v1.json`. Samples: ~40 Romanian, ~44 mixed and ~35 noisy-English rows of `datasets_archive/formalizer-v1` dev (seed 20260930), plus a 20-row already-clean control set; no `eval/suites` row used. Candidates: EuroLLM-1.7B-Instruct, Qwen3-1.7B and Gemma-3-1B-it (a combined proofread+translate+simplify prompt, zero-shot, GPU), LanguageTool (English only, masked with `lib/ud-to-sop/protect.mjs`), the already-shipped symbolic backend (LanguagesUtil + TranslatorService, no LLM, evaluated by a separate heuristic-only stage-1 cross-check), and Claude Haiku (small sample; its recorded outputs did not resemble the requested task and are not used in any conclusion — see the report's own caveat). Metrics: automatic meaning-preservation checks (entities, numbers, negation, quantifiers, question form) with Wilson 95% intervals, `execution_equivalent`/`execution_equivalent_tolerant` of the cleaned text parsed by SymbolicLM against the row's gold SOP (DS016), fluency (no `unparsed` span and all-English), edit ratio on the control set, and GPU/CPU latency. Result (`eval/reports/current/text-to-clean-english/metrics/report.json`): on GPU, Qwen3-1.7B has the best `execution_equivalent` of the three LLM candidates on every bucket (ro 0.17, mixed 0.34–0.36, noisyEn 0.54) and is inside the ~2s UI budget (282–845ms); the same model on CPU (`raw/qwen3-1.7b.cpu10.jsonl`, n=10) is far outside it (mean ≈24.6s, up to 81s) — an LLM cleaning backend needs GPU serving (or a GGUF-exported smaller checkpoint) to meet the UI latency budget. LanguageTool answers in 50–400ms regardless (a separate local Java process, not GPU-bound) but only checks English and, unmasked, corrupts unrecognized proper names; masked, it is safe. The sibling heuristic-only stage-1 check found the already-shipped symbolic backend has the best or tied-best automatic meaning preservation of everything tried and the lowest latency, but this was not scored against gold SOP and is flagged non-authoritative (a deviation of the same preregistration). Deployed default (`config/text-to-clean-english.json`): `languagetool` for English-only triggers, `llm` (via the registry's `translate`-capability model, `server/formalizers.mjs` `FormalizerManager.ensure`) for any non-English signal — today that model is a small, weak base translator (DS012 "Chat modes"), not one of the measured candidates above, since none of EuroLLM/Qwen3-1.7B/Gemma-3-1B has a GGUF export or a `config/formalizers.json` registry entry yet (`questions.md` Q-CLEAN-1); whether `nonEnglish` should instead default to the already-shipped `symbolic` backend is `questions.md` Q-CLEAN-2, open pending a non-heuristic rerun.

**`eval-symbolic-accurate-adopt-v1`**: an inference-only evaluation (Stanza on the GPU and on four CPU cores, deterministic rules, Haiku only for the no-gold rows of the dataset rebuild, 25 USD cap; no training). Its frozen record is `status/preregistrations/eval-symbolic-accurate-adopt-v1.json`, written before any v2.0 rule edit. It asks whether SymbolicLM with the Stanza `default_accurate` package and rules adapted to it beats the frozen rules v1.6 with the default package on clean English, so that the accurate package becomes the default: strict gold match on the sealed clean-English test (paired cluster bootstrap), frame-normalized score beside it, per source and question type, latency, and a five-part decision rule (non-inferiority, no decisive loss by source, none by question type, at most 1% losses on the must-not-regress development rows, CPU latency). The rules were revised five times after staged sealed results were seen; each revision is a deviation (D1 to D5) with the information used, every intermediate run is kept, and the report says the sealed numbers are optimistic (`eval/reports/current/symbolic-accurate/summary.md`). Result: strict 59.42% to 67.05% (+7.63 pp [6.52, 8.74]); adopted.

### Pre-run record and controlled hypotheses

**`eval-composed-v1`**: an inference-only evaluation (Stanza and llama.cpp on CPU, no training). Its frozen record is `status/preregistrations/eval-composed-v1.json`. It asks whether the system still makes no mistakes on forms it handles alone when many of them are put in one paragraph, and when handled forms are mixed with forms that need a rewrite; the existing fine-tuned Gemma 3 270M proofreader is measured only as a baseline. Suites: the composed suites `eval/suites/<dataset>/test-composed.jsonl` ([DS008](specsLoader.html?spec=DS008-data-evaluation.md) "Length and composed evaluation suites"), built deterministically from the sealed test rows. Endpoints: paragraph SOP equal to the concatenated component SOPs (composition effect), clean sentences left unchanged, bad sentences repaired, dropped and added text, order, end-to-end SOP equality, splitter agreement, decomposition (DS016 "Composed metrics"); Wilson intervals in nested stratified stages of 100, 300 and the full suite. The record states its hypotheses (H1 to H4), the stopping rules and a deviation: the first 400-case run of SymbolicLM on K1 was used to correct a comparison bug (statements-before-queries order) and is reported as a pilot.

For each proposed experiment, register an immutable ID and timestamp, question, directional hypothesis, one main changed factor, named comparator, fixed common inputs and tools, measurable endpoint with denominator, failure/falsification condition, budgets, and intended analysis slices. Record dataset manifest and content hashes, source rights and adjudication state, pinned base/model/recipe when applicable, SOP/runtime/solver versions, actual backend and fallback, prompt selection (`formal` or `bare`), approved knowledge snapshot, ontology, seed policy, and evaluation script revision. Record missing fields as unresolved; do not backfill a preregistration after viewing the holdout. Any new arm or threshold chosen after inspection is exploratory and needs a new sealed holdout to become confirmatory.

| Question | One changed factor and comparator | Falsification condition |
| --- | --- | --- |
| Does an approved formalizer change improve declarative SOP accuracy? | Candidate versus pinned baseline on the same input format, knowledge, evaluation set, decoder and budgets; only the preregistered data/recipe/model factor changes in a given comparison. | Its predeclared correctness endpoint does not improve on the held-out paired cases, or a safety/promotion gate fails. This comparison does not authorize fine-tuning. |
| Does a memory route improve retrieval without changing answers? | One `memory.engine` or retrieval strategy versus a named baseline, with fixed SOP, facts, rules, reasoner and snapshot. | Evidence coverage, isolation, or correctness degrades under the predeclared case families; different storage costs are reported separately. |
| Does an external backend preserve the supported reasoning fragment? | `reference` JS versus `advanced` with explicitly selected SWI for point-in-time Horn, or Z3 for declared numeric constraints, with identical problem and evidence. | An admitted complete case disagrees on answer/projection or a required input disappears; unavailable binaries and incomplete results are exclusions, not a solver win. |

Register per-arm ceilings for wall time, CPU/GPU time, token usage, solver calls/timeouts, memory, disk and checkpoints **as actual study-specific quantities before execution**; no universal numeric compute budget is asserted here. State abort conditions, monitoring owner, maximum attempts, and whether an unavailable optional backend means skip rather than substitution. Only one GPU-intensive worker per machine may operate under the authorized orchestration policy. A changed model and a changed corpus are two experiments, not one confounded arm.

### Splits and locked evaluation

Assign the `semantic_case_id` group before rendering: paraphrases, EN/RO translations, hard negatives, shared source worlds and semantic duplicates stay in the same train/dev/test group. Reserve composition-family holdouts before generation; label seen-shape, structural, source-independent and external-reference tests separately. Never tune on sealed test cases, including via repeated prompt selection. Audit disjoint physical paths, group IDs, hashes, source rights, provenance and leakage; exclude source text not cleared in [DS014-source-rights.md](specsLoader.html?spec=DS014-source-rights.md) and non-independent reference cases from the study. Keep EN and RO denominators and each family/negative/UNKNOWN slice visible, including exclusions and confidence intervals where estimable; a synthetic fixture and a human-reviewed external case are not interchangeable.

### Promotion gates to freeze, not observations

Before evaluating a particular authorized candidate, freeze the exact metric definitions, denominator, pass/fail policy for incomplete or abstained results, and these minimum thresholds on independently adjudicated holdouts: parse validity **≥99%**; semantic correctness for **EN ≥90% and RO ≥90% independently**; hard-negative correctness **≥95%**; unsupported assertion rate **≤2% on UNKNOWN cases**; **zero isolation violations** (unauthorized knowledge writes or cross-session/source leakage). Treat abstention and nonresponse as incorrect for a required-answer correctness denominator unless the frozen protocol explicitly designates a separate abstention endpoint; never improve a score by dropping failed cases. Each threshold requires an adequate preregistered denominator and traceable numerator; if support is insufficient, report "not qualified", never round a small sample into a promotion claim. In addition, preserve the model-origin `stated`/`assumed`/`unclear`/`query`/`constraint` boundary, independent source rights and reviewed truth; a high aggregate score does not override a gate. These are targets for a prospective decision, not measurements of any existing model or system.

Count parse-valid predictions over every designated input row (including missing and malformed outputs as failures); EN/RO semantic correctness uses all designated rows of each language with the independently adjudicated expected answer and effects. Count a hard negative correct only when the answer, bindings, or effect differ as required by its linked contrast, not merely because its generic status matches. On UNKNOWN rows, the unsupported-assertion numerator is the number of rows where an answer asserts support or an observed fact without admitted evidence; the denominator is all designated UNKNOWN rows, including abstentions. Isolation is a strict violation count, not a rate that can be averaged away.

Promote only when all frozen gates, comparator improvement where hypothesized, data rights, independent review, operational budgets and safety checks pass on the designated locked evaluation; publish counts, denominators, family/language slices, exact identities, invalid outputs, skips and actual backend routes. A failed or inconclusive hypothesis is retained as such. **Training, fine-tuning, optimizer steps, resume and training smoke runs remain unauthorized without a new explicit user approval bound to the specific dataset, recipe, model and run.** Dataset qualification, symbolic checks or this preregistration cannot supply that approval.

### Planned study arms (PLANNED, not reported results)

The research question these arms test is stated in [DS000-vision.md](specsLoader.html?spec=DS000-vision.md). **PLANNED** specifies a proposed future study and does not itself authorize execution; nothing here is a measured outcome.

**PLANNED.** The source-to-knowledge study has five access-controlled conditions: **S0 source-only** uses the permitted source content without a reused implicit SOP library; **S1 dynamic repair** can propose, validate and apply a repair within the current task but does not carry it over; **S2 accumulating SOP** admits separately approved rules/procedures across eligible successive tasks; **S3 frozen library** uses a versioned snapshot with no new promotion during evaluation; **S4 teacher reference** measures what a qualified teacher produces under a declared access/cost regime, not a small-model oracle. Freeze the exact source access, external tools, proposal/promotion rules, temporal state, and candidate/accepted snapshots for each arm before comparing. A candidate rule, a quoted document or a model output never silently becomes global authority; counterexamples, independent source transfer and review are required before publication. **Decision 2026-09-28 (Q-ARCH-4):** S4 is out of the first experiment, which compares S0–S3 only. A later S4 arm first freezes here the teacher's permissions, model identity, knowledge access and monetary/token budget. Independent semantic adjudication of the EN/RO holdouts still needs a reviewer named by the owner, who uses the visual audit ([DS020](specsLoader.html?spec=DS020-corpus-audit-tool.md)); that is tracked in `TODO.md`.

**PLANNED.** Compare focused, bounded broad, adaptive and near-exhaustive expansion with measured call/time/token/memory budgets, stopping conditions, source order and cost to saturation. Measure per-family semantic accuracy and abstention, UNKNOWN calibration, semantic-gap recovery, cross-source transfer, approved-rule reuse, novelty and saturation; distinguish source gaps, formalization errors, missing semantics, solver failures and over-inference. Reuse is tested on different questions and independent sources rather than only the trigger that motivated a rule. Include longitudinal corrections, rarely used but important knowledge, fork/restart and forgetting. Report coverage and unsupported/partial routes beside accuracy.

**PLANNED.** Separate the *mechanism* study (same trusted circuit, knowledge and admitted route across memory/backend choices), the *formalization* study (new EN/RO messages into only the model-authored `stated`, `assumed`, `unclear`, `query` and `constraint` declarations, with the message as the model's only input), and the *complete agent* study (source-to-answer effects). Formalizer ablations vary Romanian anchors (zero / hundreds / thousands), host linking on/off, approved-procedure availability on/off, and CNL alone versus an optional verbalizer, one principal factor at a time. Memory comparisons include exact SQLite, RecallMemory, HoloMemory and verified hybrid hints at measured total budgets, with the per-strategy experiments listed in [DS023](specsLoader.html?spec=DS023-recall-memory.md)–[DS028](specsLoader.html?spec=DS028-memory-retention-and-generations.md); backend comparisons require the same supported semantics and the actual native route rather than fallback. A syntax pass, symbolic gold execution, repository smoke or historical test count is not conversational accuracy.

**PLANNED.** Further controlled studies mined from the archived requirements, each needing its own pre-run record: temporal-update robustness (late events, retractions, contradictory sources and `asof` questions; failure is a conclusion drawn from an expired or retracted premise); differential JS/SWI and JS/Z3 runs on the common profile, where any unexplained divergence is a defect; abduction utility (top-k inclusion of the confirmed cause, test cost, false hypotheses); induction transfer against a plain exact-counting baseline on held-out sources; use of newly approved procedures without retraining, testing selection and parameter binding rather than template copying; information preservation (answers from the original documents versus from the extracted facts); inference-only quantization invariance (BF16, Q8, Q4) on negation, operators and identifiers, which is evaluation of an authorized model, not training; one shared model versus two role-specific models. Every study reports the error locus (parser, representation, retrieval, reasoning, presentation) instead of a single score.

**PLANNED.** Baselines: small model in prose, qualified small model formalizing SOP, large model in prose, and large model with **the same approved knowledge and tools**; include teacher development cost and inference/runtime costs. A comparison must not claim that a small agent beats an unassisted large model merely because one side alone received a library. A separately authorized model study requires held-out Romanian questions and a localized source→formalization→execution→CNL answer trace. No such model run is authorized by this plan.

Every arm above is frozen with the pre-run record of this specification before any authorized run: directional hypothesis, one changed factor, comparator, falsification condition, source/case-group splits, provenance/rights, model and backend identities, hashes, library snapshot, seed policy, budgets, safety stops, metrics and denominators. Translations, paraphrases, shared source worlds and hard negatives stay grouped, and the holdout stays sealed from generation and checkpoint selection. Paired uncertainty is reported at the independent case/source level, not as pseudo-replication of paraphrases, across seeds and sources, with exclusions, missing/invalid outputs, abstentions, confidence intervals where estimable, negative findings, incomparabilities and raw-result-derived tables.

### Publication route and evidence obligations (PLANNED)

**PLANNED.** An English architecture-and-mechanism paper maintains a claim→experiment→artifact→limitation ledger, distinguishes archived from fresh measurements, and explains its differences from PAL, LINC, Logic-LM, Scallop, LMQL, DSPy and RAG.

## Introduction

Dataset builders and evaluators use sourced, reviewed [semantic cases](wiki.html#definition-semantic-case) to check whether a natural-language request and its candidate [SOP](wiki.html#definition-sop) program have the same intended meaning. A seed program passing a symbolic execution check is not a trained model prediction, independently human-validated answer, or proof of broad language understanding.

## Core Content

### Data rights and provenance

Record raw source, license and redistribution rights, source location/version, transformations, generator/model identity when used, prompt/revision, reviewer decision, and executable target. The software repository's license does not license QA2D, ProofWriter, QQP, PAWS/PAWS-X, AmbigQA, AmbigNQ, model weights, or derivative datasets. These named sources are acquisition candidates, not evidence that acquisition or licensing has been completed. Keep uncertain extractions quarantined. For ingesting materials, preserve source quotations and distinguish source knowledge, reusable implicit proposals, problem state and reasoner infrastructure; only reviewed material enters approved knowledge.

### Separation and semantic checks

Keep all paraphrases, translations, and linked contrasts of one `semantic_case_id` in the same train/dev/test partition; group semantic duplicates even when identifiers differ. Reserve composition-level holdouts before generation. Primary English and stratified independent Romanian checks have different coverage obligations; neither guarantees transfer to every dialect or unseen linguistic construction. Check syntax, types, symbols, permission, canonical form, relevant-world execution, paraphrase invariance, negative contrasts, and temporal/negation fidelity separately. Executing the gold SOP checks the program against chosen worlds, not the model's first-shot formalization on unseen language.

`node tools/datasets/build-pilot.mjs --out <new-train-dir> --eval-out <separate-new-eval-dir> --worlds 100 --seed 731` deterministically writes synthetic train/dev rows and a physically separate test directory, including manifest hashes and reserved structural families. Choose new directories because the generator writes its named files. `node tools/datasets/validate.mjs --manifest <new-train-dir>/manifest.json --execute` checks the corpus, hashes, split boundaries, and runtime outcomes against a separate graph oracle in isolated repositories. Passing these checks approves generated fixture consistency only; it does not make a source human-reviewed, a source license verified, or a sampled model accurate.

ML projections are **instruction-free**: `row.prompt` contains only the scoped context (entities, predicates, approved handles) plus attached assertions and the question — `barePrompt` from `server/llm.mjs`. The operator decision: tiny SFT models must learn SOP Lang from examples; the long instruction text stays in exactly one place, `server/prompts/formalizer.txt`, used only when serving untrained/base models conversationally. Serving a model fine-tuned on this profile must use the same instruction-free input, not `formalPrompt`. The validator recomputes the projection. The pinned Qwen3-0.6B tokenizer audit on this instruction-free profile accepted 105 train and 44 dev rows with maxima of 383/502 tokens (mean ≈ 300) against a 4,096 limit, identical natively and in the bounded Podman container, with no model weights loaded. Earlier instruction-prompt measurements (1,921/2,040 max) were superseded by this decision and no longer qualify the training format.

The model target for this projection is declarative SOP only: `premise` expresses conditional input context, and `query`/`constraint` state problems. The host-generated circuit and its effects are separately evaluated system artifacts; the model does not select `remember`, `solve`, `cnl`, or `clarify`. When a specified problem has missing/ambiguous identity or a required downstream scalar is unavailable/nonunique, symbolic orchestration generates an inspectable clarification, rather than training the model to write one. The earlier tokenizer audit measured the old projection, not automatically a newly generated declarative target set. Raw input quotations remain provenance on the host side, not model-controlled `premise.source` or `premise.quote` fields.

### Evaluation and evidence

Freeze dataset and approved library before holdout. Compare predicted and gold answers, proof and completeness, abstention, unauthorized persistence, ambiguity, temporal correctness, and latency; retain errors and the actual solver/memory route. Separate memory-only comparisons with fixed SOP and reasoning, reasoning-only comparisons with fixed premises, and model-end-to-end evaluations with equal knowledge and tools. Report counts, denominators, family/language/source slices, exclusions, external backend skips, provenance, versioned manifests, and uncertainty; do not call fallback an executed solver or report synthetic seed scores as neural performance. `eval/reports/history/` retains historical results and `eval/reports/current/` carries newly observed reports, each tied to the run that produced it.

`eval/suites/core.mjs --out <new-file.jsonl>` exports six EN/RO case families as 12 authored rows, distinct from the generated pilot templates; it refuses overwrite, but is not human-validated or statistically sufficient. `eval/run.mjs --file <suite.jsonl> --predictions <predictions.jsonl> --out <report.json>` compares a full set of explicit `{id,sop}` predictions with the gold circuits, or `--config <runtime.json>` selects an explicitly configured formalizer endpoint. The evaluator can report parse/runtime validity, canonical and execution agreement, UNKNOWN, paraphrase and contrast metrics, per-family/language slices, and stage timings; a configured endpoint does not certify model identity or independent human review, and execution agreement over finite worlds does not establish universal program equivalence. Verbalizer number guards have a separate non-certifying evaluation route at `eval/verbalizer.mjs`; those results cannot be conflated with formalizer accuracy.

### Shared semantic cases and adjudication

`tools/datasets/schema.mjs` accepts sourced semantic cases with immutable source ID/kind/URI/revision/SHA-256/license, a `generation_trace`, and `quality_flags`. A raw source excerpt can be supplied as `source.content`, in which case its digest is checked; a remote/raw corpus hash without embedded bytes remains provenance to be verified by the importer and must **not** be mistaken for a hash of `context_assertions`. The historical `synthetic://pilot` rows retain their exact template/source quote checks and absent `input_mode` as an explicitly **diagnostic, unqualified** format. Production rows require `input_mode` (`query_only`, `assertions_query`, `clarification`). `context_assertions` are model input; `setup_sop` is separately approved background, and may be emp…

Each semantic case has one declarative export target (`canonicalTarget`) but multiple distinct English surfaces and selected Romanian anchors; duplicated literal surfaces are rejected, linked negatives share a split, and a negative may retain the same generic epistemic status while changing answers, bindings, outputs, or side effects. Model-origin targets contain only `premise`, `query`, and `constraint`, ending in a query, constraint, or premises alone. A `premise` carries conditional interpreted context with `holds` and optional `valid`, no `source`, `quote`, or implicit write. Expected results include four-valued query statuses and supported constraint statuses; `expected.answers` permits typed numeric/structured tuples and `expected.outputs` permits finite JSON values. Host-generated `clarify` results require a real underspecified identity or missing/nonunique required scalar, never an ungrounded model-emitted clarification string. Explicit sourced `fact`/`remember` programs, session `stored` results, and operations such as `expand` belong to a separately named trusted-system evaluation track, never formalizer targets. Distinguish reference/setup failures from candidate failures rather than calling a bad reference a model error.

The model track independently verifies that no conditional premise becomes a repository claim, while retaining original user text and model-interpretation origin separately from sourced facts. In the trusted-system evaluation track, `expected.session_claims` checks explicitly written atoms, validity intervals, source, quotation and retention independently of a gold circuit's effects. The runtime rejects result-looking literal values at `cnl`; host-expanded answer agreement must come from admitted reasoning, not fabricated packet fields.

Corpus identity compares a **conservative parser-only alpha key**, not raw SOP text: local wire renames and harmless atom spacing do not split one case, but external `~approved` handles remain exact. A genuine structural difference within one case needs explicit semantic adjudication and a selected canonical export target; it is not silently treated as equal or marked wrong solely by text inequality. A negative with only syntactic variation is not a contrast; if its structure is the same, an independently different source/problem world and oracle must substantiate the distinction. Duplicate-case checks include source, approved setup, input mode, timestamp, assertions and expected oracle so identical query text in different worlds is legitimate.

For the separate synthetic query curriculum, `node tools/datasets/validate.mjs --manifest datasets/query-v1/manifest.json --execute` verifies the sealed, physically disjoint test manifest; its matrix and formalizer export must match every row including visible background and input mode. Validating a checksum or passing the independent finite/graph oracle is **not** source-rights clearance, human semantic signoff, or training authorization. No optimizer may be run until a new explicit user approval.

`tools/datasets/semantic-compare.mjs` conservatively normalizes harmless definition-name/variable changes and compares through **the same guarded evaluator** used for model evaluations, including supplied discriminating worlds. A mismatched execution signature is a counterexample even if both status labels match.

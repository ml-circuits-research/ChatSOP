## Introduction

Owner decision of 2026-10-01: a chat does not write into one shared database. It runs in a **session** whose folder holds a clone of a chosen **base memory**; knowledge created during the conversation lands in the session layer, and a user can commit it, explicitly, to a fork of a base memory. Instruction or source files, rules, procedures and other knowledge can be sent to a **coding agent** (omp with the wire-authoring skill) that writes SOP circuits in a temporary folder. The authoring coding agent starts only when the user attaches files or asks for authoring through `POST /v1/author`; its circuits are validated and, with a session, stored in the session layer at once. There is no manual accept or reject of knowledge anywhere (AGENTS.md direction 8, owner correction of 2026-10-02): errors are corrected systematically through tests and interactions.

The circuit-authoring boundary of [DS000](specsLoader.html?spec=DS000-vision.md) and [DS014](specsLoader.html?spec=DS014-model-surface.md) is unchanged: the coding agent sees the user's message and the vocabulary of the memory and writes circuits, never answers and never facts. The rules of AGENTS.md directions 4, 5 and 7 hold: asserted statements are turn-local evidence kept in the session's conversation context; knowledge accumulates only through explicit approval; a read hides no write. [DS009](specsLoader.html?spec=DS009-local-server.md) describes the server; the memory strategies are [DS005](specsLoader.html?spec=DS005-memory.md) and DS016 to DS021.

## Core Content

**English-only base memories (owner decision of 2026-10-01).** Every base memory, the seed memories (`core-min`, `core-en`, `demo`) and `world-v1` included, holds English knowledge only: lexemes are `language en`, labels and aliases are `en`, and the validator rejects any other language tag (`non_english_knowledge`). The coding agent reads a message in any language and writes the circuit in English terms of the memory vocabulary, and answers are English, so no session depends on the language of its user. Import layers are snapshots, so a changed seed is renewed in a chat data root with `node tools/refresh-seed-memories.mjs --apply` (dry run by default; memories with circuits of their own are never deleted), and `world-v1` is rebuilt with `node tools/world-kb/build.mjs` and `node tools/world-kb/load.mjs --replace --with-core-en` (which also imports `commonsense-v1` unless `--without-commonsense` is given).

**The common-sense layer `commonsense-v1` (2026-10-02).** A seed memory (`config/knowledge/commonsense-v1/`, imports `core-min` and `core-en`) that the encyclopedic base imports, so a chat starts with common sense rather than learning it from interactions; a blank memory is for tests and specialised tasks. It holds: about 2,000 classes of common nouns with their WordNet 3.0 hypernyms (`is_a`), one-line descriptions and part/substance meronyms; typical uses, abilities, places, properties and parts of those nouns from the CC BY 4.0 edges of ConceptNet 5.7 (`used_for`, `capable_of`, `typical_property`, `found_at`, `typically_has`, `part_of`, `made_of_material`; class-level facts: a class symbol in the subject stands for a typical member); and authored rules, defaults and integrity constraints for class disjointness, lifetimes (`older_than`, `younger_than`, `contemporary_of` with a certain "no" when one died before the other was born, `lived_before`, `outlived`, ages), family (`male_child_of`, `female_child_of`, siblings by gender, `uncle_of`, `aunt_of`, `nibling_of`, in-laws, cousins, relatives), geography (`on_continent`, `in_country`, same country or continent) and units (`dimension_of`, `base_amount` in a fine base unit per dimension, `converts_to`). Every wire names its source; the generated files are rebuilt by `node tools/commonsense/build.mjs` from the gitignored caches and carry their licence notices (DS011). Like every knowledge layer it has no manual approval step: it is used once the validator and the automated checks pass (`node tools/commonsense/check.mjs [--world]`, `tests/commonsense-layer.test.mjs`, the sampled integrity check `tools/commonsense/integrity.mjs`), and errors are corrected through tests and interactions. The chat path uses its positive rules (with comparisons and computations); its defaults and integrity constraints serve the knowledge-wire path (`POST /v1/sessions/{id}/query`).

### Chat data root

One folder holds all chat data: `chat_data/` at the project root, gitignored, configured by `chatData.root` in `config/runtime.json` (relative to the project) and overridden by `CHATSOP_CHAT_DATA`. `lib/chat-data/index.mjs` owns it.

| Path | Content |
| --- | --- |
| `chat_data/base_memories/<id>/` | one base memory (below) |
| `chat_data/sessions/<id>/` | one session (below) |
| `chat_data/tmp/` | temporary folders not tied to a session |

Folder identifiers are lowercase letters, digits, `_` and `-` (1 to 64 characters), so a request value never names a path.

**Cleanup policy.** `chatData.tmpTtlHours` (default 24): a temporary folder whose newest file is older goes. `chatData.sessionTtlDays` (default 14): a session whose `last_active_at` is older is abandoned and goes, unless its `session.json` says `kept: true`. Base memories are never removed by the policy. The server runs the cleanup at start and every `chatData.cleanupIntervalMinutes`; `node tools/chat-data.mjs cleanup [--dry-run]` runs it by hand.

**Legacy storage.** Earlier versions kept chats and the memory repository under `state/` (`index.json`, `snapshots/`, `shards/`, `sessions/`, `http-conversations/`). The owner allowed dropping them. `node tools/chat-data.mjs drop-legacy [--dry-run]` removes exactly those paths and keeps `state/auth.json`, `state/cache/` and `state/formalizer-logs/`; it is run with the server stopped.

### Base memories

A base memory is a named, forkable knowledge store (`lib/chat-data/memories.mjs`):

| File | Content |
| --- | --- |
| `manifest.json` | `id`, `name`, `parent` (id, name, strategy, circuits count, fork time, or null), `strategy`, `created_at`, `description`, counters |
| `repo/` | a memory repository ([DS021](specsLoader.html?spec=DS021-memory-retention-and-generations.md)) with one base named `main`, built for the manifest's strategy |
| `circuits/NNNN-<name>.sop` | the validated knowledge circuits in the order they were added: the source of truth the repository is derived from |
| `provenance.jsonl` | one record per addition, import or fork: `approved_by`, `approved_at`, `reason`, `source`, the circuit's SHA-256, the wire count and what was ingested |

**Default base and kinds (owner decision of 2026-10-02).** The encyclopedic memory is the default, empty or minimal memories serve specialised tasks, and every session is a fork. `chatData.defaultBase` names the base memory that sessions naming none fork from; its documented value is the encyclopedic `world-v1` (`ENCYCLOPEDIC_BASE`, a Wikidata subset that imports `core-min`, `core-en` and the common-sense layer `commonsense-v1`, built by `tools/world-kb`), which gives every session common sense and basic knowledge. When `world-v1` is not loaded, the minimal memory `default` (importing `core-min`) is created and used instead, so no chat starts without a vocabulary (`ensureDefaultBase`). `GET /v1/memories` returns `default_base` and `kinds`. `POST /v1/memories` accepts `kind`:
- `encyclopedic`: a copy-on-write fork of `world-v1`; 409 `not_available` when it is not loaded.
- `minimal`: imports `core-min`; the default when neither `kind` nor `imports` is given.
- `empty`: no imports.

`kind` and `imports` are exclusive. The start-up warmup always includes the default base, and `GET /v1/status` reports `default_base`.

**Strategy.** The default is `sqlite` (owner decision of 2026-10-01: the exact, completeness-capable strategy; `memory.engine` in `config/runtime.json`, `DEFAULT_STRATEGY` in `lib/chat-data/memories.mjs`): a base memory created without a strategy, the `default` base memory and therefore the sessions cloned from it use it. `ensureDefaultBase` re-creates an EMPTY `default` base memory of another strategy at start and leaves one that holds circuits alone. The product offers SQLite base memories only (owner decision of 2026-10-01, hygiene cleanup): `/v1/memories` and the Base Memory tab accept no other strategy and refuse one with 400. The other engines of [DS005](specsLoader.html?spec=DS005-memory.md) (`recall-memory`, `holo-memory`, `scan`, `hybrid`, and `exact: true` for the sidecar of [DS019](specsLoader.html?spec=DS019-exact-reference-memory.md)) stay in `memory/` for research and comparison. The repository's memory configuration is the runtime `memory` block with the engine set.

**What the repository holds.** The `fact` wires of a circuit are ingested into the memory strategy (a fact without `valid` is stored with `valid timeless` and counted in `facts_defaulted_valid`; a fact the store cannot lower is listed in `facts_skipped` and stays in its circuit). Every other knowledge wire (rules, defaults, norms, aggregates, methods) lives as a circuit; `theory()` concatenates the circuits for the exact engines (`reasoning/strategies/js-reference`), which read the whole theory.

**Adding knowledge is open to every authenticated user** (owner decision of 2026-10-01, Q-PROD-1: there is no administrator role; every user may create, fork, extend and delete base memories, commit sessions and list the omp models; authentication itself, a bearer token or a signed-in session, is unchanged). `addKnowledge` validates the circuits with the knowledge validator of `sop/knowledge/` (authoring mode) together with the circuits already stored (duplicate ids, arity, closedness), rejects `jsEval`, any model-surface wire, any `query` wire and any governance field (`approval`, `approved_by`, `approved_at`: the server's record is the provenance), and writes nothing when anything fails (answer 422 with `problems`). On success it stores the circuit, ingests its facts and appends the provenance record with the acting user (`approved_by`: the authenticated user identity, with `approved_at`). There is no implicit write path.

**Fork.** A fork copies the circuits and the provenance, records the parent in its manifest and adds a `fork` provenance record. With the same strategy the repository is cloned by `cloneRepository`: the `snapshots/<sha256>.json` and `shards/<sha256>.json` files are content-addressed, written once through a temporary file and a rename and never modified in place, so they are hard-linked (copy-on-write, no data copy); every other file is copied, so parent and child never share a mutable inode. Isolation guarantee, for every strategy: a write to the child (or to a session clone) never changes the parent's files, and a write to the parent after the fork never reaches the child (`tests/memory-isolation.test.mjs`, which compares the parent's repository files byte for byte). The SQLite strategy keeps no mutable database file in a repository (its bank is a private in-memory SQL database rebuilt from the snapshot rows, DS018), so there is no `-wal` or `-shm` file to share; should a native `.sqlite` file ever appear in a repository folder it is copied through `VACUUM INTO` and its `-wal`/`-shm` files are never linked or copied. With another strategy the repository is rebuilt by replaying the circuits into the new engine (`method: replay`).

### Imports

A base memory may be created with `imports`: base memories whose circuits form its lower layers (`POST /v1/memories` `imports`, `create({imports})`). The manifest records `imports` as the flat, ordered list of `{id, hash}` (each imported memory's own imports first, then the memory itself), and the circuits of every layer are snapshotted under `imports/<id>/`. The theory, the validation of every addition and the lexicon of the memory are computed over its layers: the imports in order, then its own circuits. An import is a snapshot: a later change of the imported memory never reaches the importer; importing again is an explicit act. A fork keeps the imports of its parent. The seed memories `core-min` and `demo` ship in `config/knowledge/` (`lib/knowledge-seeds.mjs`, created at the first start of a chat data root); the `default` memory imports `core-min`, so no chat starts without a vocabulary.

### Lexicon of a memory

Every session links against the lexicon of its own base memory, never a global one (owner decision of 2026-10-01; the global `config/ontology.sop` is retired). The lexicon is compiled from the layered circuits of the memory (`Lexicon.fromCircuits`, DS004 "Lexicon wires": the `predicate`, `lexeme` and `entity` wires and the `is_a` facts) and cached by the hash of those circuits (`chat_data/cache/lexicon/`, a cache that is safe to delete). `BaseMemories.lexicon(id)` gives it for a memory. A session copies the layered circuits of its base into `base_circuits/` when it is created, so its lexicon is `base_circuits/` followed by the circuits stored in the session layer (`Sessions.lexicon(id)`); a circuit stored in the session is visible to the open agent at once (`SessionRuntimes.open` notices changed session circuits and refreshes the lexicon and the repository view), and nothing the base memory later gains reaches the session. The code paths without sessions (CLI, tests, examples) use `demoLexicon()`.

### Sessions

A session is one chat's working copy of a base memory (`lib/chat-data/sessions.mjs`, `server/session-runtime.mjs`):

| Path in `chat_data/sessions/<id>/` | Content |
| --- | --- |
| `session.json` | `id`, `user`, `name`, `base` (id, name, strategy, circuit count at the clone), `settings`, `kept`, `committed_to`, `created_at`, `last_active_at` |
| `repo/` | the base memory's repository, cloned (content-addressed files hard-linked, anything else copied), plus the facts of the circuits stored in the session |
| `base_circuits/` | a copy of the base memory's circuits at the time of the clone: a session is self-contained |
| `circuits/` | circuits stored during the conversation (the session layer), each validated first |
| `requests/<request>/` | one temporary folder per authoring request: `TASK.md`, `skill/`, `input/`, omp's output and session, `status.json`, `result.json` |
| `agent/` | the chat agent's conversation context and last answer (`server/session-store.mjs`) |
| `provenance.jsonl`, `transcript.jsonl` | the stored circuits (kind `add`, origin) and the turns |

**What goes where.** Asserted statements stay turn-local evidence in `agent/` (AGENTS.md direction 5); they are not committed. Persistent circuits written by the coding agent go through `Sessions.addCircuit`: it validates the circuit with the base and session circuits and stores it in the session layer at once (provenance kind `add`, with its origin); an invalid circuit is refused and nothing is stored. Definitions the query author writes while formalizing a chat turn take the same path when a chat session exists, and are also reported with `session_circuits: {origin: coding_agent, scope: turn, text}`. Committing a session to a base memory stays a separate act. Labelled assumptions follow DS014 report/branch semantics and are never persisted.

**Queries reason over base plus session.** The chat agent's repository session sits on the session repository, whose base head holds the cloned base plus the stored circuits' facts (`Repository.rebase` moves an open agent onto a new head after a circuit is stored). `GET /v1/sessions/{id}/theory` returns the base circuits followed by the session circuits, and `POST /v1/sessions/{id}/query` runs a query circuit over them on a slice, with the engine chosen by the StrategyRouter ([DS006](specsLoader.html?spec=DS006-reasoning.md) "Routing rules": body `reasoning` `auto` by default or one strategy id run exactly, `verify` `auto|always|never`; the answer's `route` names the choice, the rule and the verification against the oracle): `askMemory` (`reasoning/slice/wire.mjs`, [DS005](specsLoader.html?spec=DS005-memory.md)) takes the rules of the session's theory that can reach the query, retrieves the facts they and the query can use from the session repository by keyed lookups, and answers with `answer.retrieval` and `answer.route` (the slice's size, predicates, bounds, whether it is complete and why not). The whole theory never goes to the engine, and an answer that needs a complete slice (a count, a universal question, `absent`, a default conclusion, an aggregate) over a slice that cannot be proven complete is `status: incomplete`, `reason: partial_retrieval`.

**Commit to a fork.** Open to every authenticated user: a new base memory made as a fork of the base memory's current state plus the session's circuits, validated on top, with provenance (`kind: commit`, source `session:<id>`); the strategy is `sqlite`, the only one the product offers. The base memory the session started from never changes. A session without circuits of its own has nothing to commit (409).

**The chat request** carries `session_id` (`POST /v1/chat/completions`); the answer's `chatSop.session` names the session and its base, and the turn is appended to `transcript.jsonl`. Without `session_id` one automatic session per user and conversation is used, forked from the default base memory. `base` in `POST /v1/sessions` is optional and defaults to the default base memory as well. A session is visible to the user who started it and to an administrator. Without a chat data root (embedding the server in tests) the earlier single-repository path is unchanged.

### The coding agent (omp)

`lib/omp/` and the skill [`skills/omp-run`](../../skills/omp-run/SKILL.md) run the omp CLI non-interactively on a temporary folder:

- **Models.** `GET /v1/omp/models` (any authenticated user, cached for `omp.modelsCacheSeconds`) parses `omp models --json` into ids `provider/model` with a cost class: `subscription` (openai-codex, xai-oauth, zai, github-copilot, anything with oauth or subscription in the provider name; configurable by `omp.subscriptionProviders`), `paid_api` (deepseek, openrouter, ...) or `unknown`, the listed price per million tokens, and omp's default model. An absent or disabled omp is `available: false` with the reason, never an error.
- **Query-author transport.** The omp query backend uses `--mode rpc --no-tools --no-extensions --no-skills --no-rules --no-lsp --no-title --system-prompt` with the stable authoring guide and circuit-only rules as a byte-identical prefix. Bounded supplementary vocabulary precedes request-specific candidates, schema neighbourhood, entity hints and message in a fixed-order inline JSON payload; its values are data, not instructions. No model tool reads or writes a query file. Only the complete final assistant text is accepted: bare SOP or one complete `sop` code fence, parsed in its entirety before unchanged circuit admission. Missing, malformed or prose-mixed output is a reported failure; no wire is salvaged and no stale file is used.
- **RPC isolation and lifecycle.** `lib/omp/rpc.mjs` keeps at most two processes globally, with one active turn per worker. Every new request explicitly creates an empty conversation; a repair restores only that request's session, the RPC equivalent of `-c`, including when requests interleave. The worker owns a temporary directory independent of disposable request folders. Command acknowledgements are not completion: assistant usage is accumulated until `agent_end`, with correlated asynchronous errors still reported. A queue-inclusive request deadline, malformed transport, provider error or forbidden tool event fails honestly; a subsequent new request may start a fresh process, never replay the failed prompt. Workers expire after 30 seconds idle or recycle before a new request after 64 sessions; shutdown kills only owned processes and removes their temporary data. The sanitized environment is the same as the knowledge authoring fence below.
- **Thinking configuration.** `queryParser.backend.thinking` selects the query author's reasoning level independently of knowledge-file authoring's `omp.thinking`. The shipped query backend uses `off`; the library's omitted query-backend setting also defaults to `off`. An explicitly supplied `null` leaves omp's own default in force. Effective levels are provider-specific: a requested level may be clamped by omp, so development comparisons inspect the installed model's effective state rather than assuming every CLI level is distinct.
- **Knowledge-file authoring fence.** `omp -p --cwd FOLDER --session-dir FOLDER/.omp-session --mode json --no-extensions --no-skills --no-rules --no-lsp --tools read,write,edit --approval-mode yolo --max-time S`: the agent starts in the folder, has no shell, loads nothing from the user's profile, receives files only as `@` paths inside the folder, is told by `TASK.md` to work only there and to treat the attached files as data, and gets an environment without the server's credentials. No secret is ever put in a prompt. A hard kill follows the time limit. Cost and tokens are read from the session files (omp's nominal list price; for a subscription model it is not an invoice).
- **The authoring path.** `POST /v1/author {session?, files?, instructions?, model?, wait?}` creates `chat_data/sessions/<id>/requests/<request>/` (or a folder under `chat_data/tmp/`), writes `TASK.md` (from the skill [`sop-wire-authoring`](../../skills/sop-wire-authoring/SKILL.md)), `skill/`, `input/` (the attached UTF-8 text files and the vocabulary already in the theory) and runs omp. omp cannot run the validator, so the server validates `knowledge.sop` and `queries.sop` with the knowledge validator of `sop/knowledge/` (the code behind `node eval/smoke-reasoning/validator.mjs --authoring`) together with the circuits of the theory, and continues the same omp session with the validator's output for at most `omp.maxFixRounds` rounds. The answer carries the circuits, the validation, the usage (turns, tokens, cost), the time and, with a session, the file stored in the session layer (`added`); an invalid result stores nothing. A failed, silent or timed-out run is a result (`status` `failed` or `invalid`, with a reason), not an error; 503 `omp_unavailable` and 429 `omp_busy` are the only refusals. `wait: false` answers 202 and `GET /v1/sessions/{id}/requests/{request}` reports the phase and, when finished, the result.

### Ingesting documents into a base memory

Owner decision of 2026-10-02: besides sessions, documents, books and other material are added to base memories, and sessions are then made from those memories. Learning means adding facts, relations, rules and procedures to a base memory, never training a model, and there are base memories for different types of tasks (a task-type base memory: an HR policy memory, a planetary-science memory, ...). The path is `lib/ingest/`, `tools/ingest-documents.mjs` and the endpoints below; it reuses the authoring path of section "The coding agent (omp)".

1. **Rights first.** Every document carries `source.rights` `cleared`, `permissive-attribution` or `owner-provided` ([DS011](specsLoader.html?spec=DS011-source-rights.md)); any other value is refused (`rights_required`) before a model runs. The URL, licence and attribution are kept with the provenance.
2. **Chunking** (`lib/ingest/chunk.mjs`) follows the document's own structure: Markdown headings open sections, consecutive sections are packed while a chunk stays under the bound (default 7,000 bytes), and a larger section is cut at blank lines, so a paragraph or a table is never cut. Each chunk records its heading path, its line range and its SHA-256.
3. **Writing.** The coding agent (omp, skill [`sop-wire-authoring`](../../skills/sop-wire-authoring/SKILL.md), the knowledge-file fence) compiles the chunks in order. Each chunk's task gives its coordinates, an id prefix (`d<doc>c<chunk>_`) so ids stay unique, the memory's vocabulary together with the circuits written for the earlier chunks, and the entity symbols already in use (`known-symbols.txt`), so the same thing gets the same name across passages. Facts carry `quote` (words copied from the passage) and `source` (document and section); eligibility tests, definitions and procedures become rules or defaults over declared predicates, grouped in a `procedure` bundle with a description of the question form they answer.
4. **Checks in the repair loop.** The knowledge validator (with the memory's layers and the earlier chunks) and the quote check (`lib/ingest/checks.mjs`: every `quote` must be a contiguous passage of the chunk after typographic and whitespace normalisation) run inside the bounded repair rounds of `authorCircuits` (option `check`). After the last round, a wire whose quote is still not in the passage is rejected, not stored.
5. **Conflicts with the memory.** A ground fact written by the agent that duplicates a stored one, contradicts it (`not p a` against `p a`) or breaks a declared functional key (`key N`) is held back and reported: memory wins, and nothing is overwritten silently.
6. **Report.** The ingestion (`chat_data/base_memories/<id>/ingestions/<ingestion>/ingestion.json` and `report.md`) lists per chunk what was extracted (wires by type), rejected (quotes not in the source), held back (conflicts), uncertain (reported or hedged facts, defaults, advisory norms and methods, wires without a source sentence), the validator's problems and warnings, and what the coding agent reports as not expressed, with rounds, time and cost.
7. **Storing.** There is no manual acceptance: every validated chunk is stored in the base memory at once through `addKnowledge` (validated again with the memory's current layers) with the provenance `source: {kind: document, ingestion, document, title, document_sha256, url, licence, rights, chunk, lines, section, chunk_sha256}` and the acting user as `approved_by`. The record status is `stored`, `nothing_new` or `failed`; the chunk status is `stored` or `store_failed` (a chunk that no longer validates is not stored). Wrong knowledge is corrected through tests and interactions, not by a review step.
8. **Idempotent re-ingestion.** A chunk whose SHA-256 is already in the memory's provenance is skipped (`already_ingested`) before any model runs: ingesting the same document again adds nothing, and an edited document adds only its changed chunks (a changed chunk whose facts duplicate stored ones is held back by step 5).
9. **Sessions from it.** A session is started on the memory like on any base memory (`POST /v1/sessions {base}`); the session clones its circuits and repository, and the query author links against its lexicon.

| Endpoint | Effect |
| --- | --- |
| `POST /v1/memories/{id}/ingest` | `{documents: [{name, text, title?, source: {rights, url?, licence?}}], model?, purpose?, wait?}`: ingests the documents (200 with the record and the report; `wait: false` answers 202 with the status URL); 400 `rights_required`, 429 `omp_busy` or `ingest_busy`, 503 `omp_unavailable` |
| `GET /v1/memories/{id}/ingestions`, `GET /v1/memories/{id}/ingestions/{ingestion}` | the ingestions of a memory; one ingestion with its chunks and report |

The command line is `node tools/ingest-documents.mjs create-memory|ingest|report|list` (`draft` is an alias of `ingest`) (header of the file). Long material (a book) is ingested as several documents or as one document of many chunks; the model sees one chunk at a time plus the vocabulary, never the whole book.

### Procedure library

Owner request of 2026-10-02: procedures written by a coding agent become reusable, also by small models. A **procedure** is a `procedure` bundle wire ([DS004](specsLoader.html?spec=DS004-sop.md) "Procedures") stored in a base memory: `members` names the predicates, rules, defaults and aggregates that solve one question form, and `description` states that form in words ("Answers: how many days of annual leave does a person get?"). Sources of procedures: the rules a document ingestion grouped into a bundle, and session definitions the query author wrote for a turn that a user stores with `POST /v1/memories/{id}/procedures {id, description, definitions, reason?}` (`procedureCircuit` adds the bundle wire; the circuit is validated with the memory's layers and recorded with provenance `source: {kind: procedure}` like any knowledge).

**Retrieval.** `lib/query-author/procedures.mjs` builds the library of the stored circuits (cached by their text) and matches the message against each description by IDF-weighted content stems; a procedure is offered only when the message shares at least two stems with its description and one of them names its head predicate (the message asks what the procedure concludes). The query author's context (`buildContext`) then puts the head predicates first among the candidate predicates and adds a "Procedures in memory" section with the member wires as SOP, within the same vocabulary byte budget (at most a third of it). `parse.retrieval.procedures` reports the offered procedures. The author queries the head predicate instead of re-deriving the rule; nothing is executed or approved by the retrieval, and a procedure is in force exactly when its members are.

### Formalization strategies

The request parser obtains the circuit of a message by one of three **formalization strategies** (owner decision of 2026-10-02). The strategy is a session setting; everything after the circuit (admission and repair, vocabulary dialog, KnowledgeLinker, slice retrieval, StrategyRouter, oracle verification, completeness guard, rendering) is shared and does not depend on it.

| Strategy | What writes the circuit | Transport |
| --- | --- | --- |
| `CodingAgent` (server default) | an omp model of the model chain, one turn, no tools, thinking off | `queryParser.backend.kind: omp`, persistent RPC workers (section "The coding agent (omp)") |
| `LocalLLMDirect` | a local GGUF model writes the SOP circuit in one step, with the same guide, validator and repair rounds as CodingAgent | the `direct` slot of the shared local runtime below (`queryParser.local`); prompt cache on |
| `LocalLLMStepByStep` | the symbolic system asks a small local model short questions (numbered choices, short lists) and assembles the circuit itself | the `steps` slot of the shared local runtime; `lib/query-author/step-by-step/` (section "LocalLLMStepByStep") |

**Session setting.** `settings.formalizer` is `null` (the server default) or one of `CodingAgent`, `LocalLLMDirect`, `LocalLLMStepByStep` (`lib/chat-data/sessions.mjs`); it is set by `POST /v1/sessions/{id}/settings {omp_model?, formalizer?}` or in the `settings` of `POST /v1/sessions`. `omp_model` applies to CodingAgent only. A turn whose strategy the server cannot run is refused when it starts with 503 `parse_unavailable` naming the strategy (`server/status.mjs` `strategyRequest`), never silently replaced by another; `GET /v1/status` (DS009) lists each strategy with `available`, the `reason` when it cannot run, its backend and its models or endpoint. The parse record and `chatSop.strategy` name the strategy that wrote the circuit.

**Configuration.** `queryParser.strategy` is the server default (`CodingAgent` shipped; the environment variable `CHATSOP_FORMALIZER` overrides it); a session's `formalizer` overrides both for its turns. `queryParser.local` configures the local model of both local strategies: `gguf` (managed server, started on the first turn that needs it and stopped with the chat server) or `endpoint` (an already running server, for example one started by `node tools/local-llm/serve.mjs`), `alias`, `port`, `slots` (`["direct", "steps"]`), `ctxPerSlot`, `maxTokens`, `thinking` (false: `enable_thinking` off). The registry is `lib/formalize/strategies.mjs` (`FORMALIZATION_STRATEGIES`, `localStrategy`, `localReadiness`); `queryParser.strategies()` reports a local strategy as available when its GGUF and llama-server exist and no GPU lock is held, or when its endpoint answers, without starting anything.

**The local runtime.** `lib/local-llm/` is a process-wide registry of managed llama.cpp `llama-server` instances, so LocalLLMDirect and LocalLLMStepByStep on the same GGUF share one server (`serverArgs`): full GPU offload (`-ngl 99`), flash attention (`-fa on`), one dedicated slot per role (`--parallel 2 --no-kv-unified`, requests pinned with `id_slot`) so neither evicts the other's prompt prefix, `--cache-reuse 256`, `--slot-save-path state/local-llm/slots`, and every request with `cache_prompt` on. Prompts put the byte-identical stable prefix first (LocalLLMDirect: the author guide as system message; LocalLLMStepByStep: its rules and the list of answer kinds) and everything variable last (the request, the candidates and neighbourhood, the step answers). `prewarm(role, messages)` renders the chat template, cuts the text where the variable part begins, evaluates exactly that prefix once (`/completion`, `n_predict 0`) and saves the slot to a file named by model, role and prefix digest (a prefix that contains a memory's vocabulary therefore gets its own file per base memory; the current prefixes are memory-independent). A restored file is accepted only when the server's own `cache_n` counter shows the prefix reused; hybrid and recurrent models (Qwen3.8, Nemotron-H) resume only from a context checkpoint made by an evaluation in the same server process, which a slot file does not carry, so for them the prefix is evaluated again at start. `begin(role)` serialises the requests of one role (one conversation per slot at a time) and restores the prefix before each request, so a step evaluates only its new tokens. Only one GPU worker runs per machine: a managed server refuses to start while a training or parse lock is held and never stops a process it did not start. How to run a local formalizer is described in [docs/runtime.html](runtime.html#local-formalizer).

**LocalLLMStepByStep.** Owner decision of 2026-10-02: the small model is an oracle that classifies and points; it never writes SOP or JSON. One growing conversation per request on the `steps` slot; the symbolic system decides every next question from the previous answers and the memory:

1. **Kind** (numbered choice; the list precedes the request so it is part of the cached prefix): yes/no, reachability through a chain of steps, names, a stored value, a count, the highest, the lowest, a numeric puzzle, nothing. The grammatical cue of the question (a leading auxiliary, "how many", a question word; `cueKinds`) only detects a conflict, which is resolved by a second numbered choice among the compatible kinds.
2. **Names**: the entity hints of the message are linked symbolically; an ambiguous name is a numbered choice among its candidates; when nothing links, the model lists the names and each line is linked.
3. **Statements**: the schema neighbourhood (`collectNeighbourhood`, with the memory's repository) rendered as numbered English sentences with letters for the places ("A is assigned to B"), the memory's derived relations first and marked, a stored example or "its words are in the request" when true; the model answers with numbers or 0 (none fits: `unclear relation_not_in_memory`).
4. **Places**: for each chosen statement a lettered choice among the linked names, the request's numbers (only for a number place), "the thing the request asks for", "the value to compare" (highest/lowest) and "anything"; automatic when only one reading exists. Type errors (a name in a number place) and a missing asked place are asked once more; when every place holds a name, a numbered choice decides whether the request is a yes/no question. A count whose asked place is a stored number becomes a value lookup (a derived count relation).
5. **Truth** (yes/no only): true, explicitly false, or absent; absence is offered only for a statement the memory declares closed. **Time**: when the message has a date, the dates are read from the message (asked only when unreadable); one date gives `at`, two give a numbered choice between `during` and `overlaps`.
6. **Puzzle**: unknowns with ranges ("x: 0 to 10"), one arithmetic line per condition (read into SOP words with the usual precedence; parentheses and undeclared names are refused), the goal (possible, min, max, prove) and its expression or claim.
7. **Reachability**: the step statement, the statement the chain must avoid (or none), start and end; the system writes two labelled session definitions (an allowed step, a `default` with `except` when something is avoided, and a recursive chain) and queries the chain. When no statement links two things the kind is asked again without reachability.
8. **Assembly and confirmation**: per-form templates write the model-surface SOP (`assemble.mjs`), the same validator as every author checks it, and a validator report that a name of the request is unused leads to a numbered question for the statement and the place that name belongs to. A deterministic English paraphrase of the circuit is shown with "Is this what the request asks? yes/no"; on "no" the model names the doubtful part and that step and the steps after it are asked again, at most once.

Answers are read robustly (`answers.mjs`: the first option number, number lists, lettered lines, yes/no, ISO and month-name dates, arithmetic lines); an unreadable answer is asked once more and then the strategy stops with `failed` and the reason, never a guess. The result has the shape of `authorQuery` plus `steps` (per step: name, answer, ms, input and output tokens, cached and evaluated prompt tokens). Development measurement: `eval/reports/current/omp-tasks/t10-stepbystep.md`.

**The generic question protocol (methods B, C, D; default B).** Owner decision of 2026-10-02: the question protocol above is method A; `queryParser.local.method` (`A`, `B`, `C`, `D`, `B-cue`, `B-yesno`; `STEP_BY_STEP_METHODS`) selects the protocol, and the shipped default is `B`, adopted on the measurement of experiment `eval-stepbystep-protocol-v1`. The generic protocol (`protocol.mjs`, questions in `questions.mjs`, cue table `cues.mjs`, clause decomposition `clauses.mjs`, circuit writer `circuit.mjs`, session definitions `definitions.mjs`) keeps method A's system message and puts the 13 answer kinds (yes/no, reachability, names, a value, a count, highest, lowest, a numeric puzzle, all/none/most of a group, when/since/until/how long, why, a stated fact, nothing) and the 8 aspects (a number limit, a choice between named options, an exclusion, a date, a supposition, a two-sided comparison, a second question, a reason) in the byte-identical cached first-turn prefix (`PROTOCOL_PREFIX`). Every question is a numbered choice with "0. none", a number list or lettered lines; at most 14 questions are asked (`MAX_QUESTIONS`; optional re-asks and the confirmation are skipped when the budget is spent). The steps:

1. **Kind**, checked against the grammatical cue (`cueKinds13`, a leading phrase before the comma ignored); a literal superlative turns a list into highest/lowest.
2. **Aspects** (B, D: the checklist question) combined with the regular-expression cue table by the two-signal rule: cue and oracle agree, no question; they disagree, one yes/no question with the cue's span; literal cues win for limits, exclusions and dates. C and B-cue take the aspects from the cues only.
3. **Clauses** (C, D): deterministic sentence and clause split on link connectives (never inside relative clauses, never an elliptical comparison "before X did", never a connective group without a finite verb), one clause-role question per extra clause (supposition, stated fact, time bound, second question, same question, nothing), pre-filled when the connective and the aspects agree. B takes the supposition and the second question from the cue spans. A supposition becomes `stated` with `certainty supposed` and `if`/`unless $s` on the query; a second question its own query; a part that cannot be formalized an `unparsed` span.
4. **Statements**: the neighbourhood ranked by lexical overlap with the clause, 8 shown with "show other statements"; when the oracle answers none while exactly one statement shares a content word with the request, that statement is asked once.
5. **Places**, typed and pre-filled by the memory: each place lists only the choices that fit it (names and entity unknowns in a name place, numbers and value unknowns in a number place) and a name fits a place only when its class fits and, by **observed role fit**, when the memory records it in that place or records it together with the things that fill that place; a name recorded in exactly one place of the statement is placed without a question, and the asked unknown fills the one place left of the first statement; one name or unknown never fills two places of a statement; a choice that does not fit is asked again for that place alone. Unknowns: X (the asked thing), M (each member of a group), V (the ranked or compared value), W (a limited value, its own unknown per statement), P and Q (other shared unknowns); "anything" is a fresh unknown.
6. **Connectivity**: the statements of one question must share an unknown; the possible joins are listed and, when one join is supported by the recorded fillers, made without a question. **Answer type**: "In which country …" moves the asked unknown into the one statement place described as a country; "Where …" moves it into a place role. **Coverage**: a content word of the request that only one unchosen statement names is offered once (at most two).
7. **Truth and negation**: yes/no truth (absence only for closed statements); the statement after "no / without / missing from" is negated (absent when closed), asked or added when not chosen.
8. **Aspect handlers**: limits (`compare`; the limited value pre-filled when one place fits or the words next to the limit name its statement; a count per group as an `aggregate` session definition), options (`compare any`), exclusions (`except`), two-sided comparisons (the statement used once per name in the same place, a shared unknown or `compare ?a above|below ?b`; "how many more" a difference of two per-group counts with `compute … minus`), quantified groups (`mode every`, the restriction holds the group's name, the quantifier from the cue or one question; "nobody" a negated scope), chains (a recursive session definition, `closed` when the step statement is; a literal "reached"/"reachable" needs no question), fewest links (bounded layers ranked lowest), reachability (a derived reachability relation of the memory asked first; otherwise method A's chain with start and end read from "from … to …" and the avoided statement named by the supposition's words), puzzles (method A's questions; unknowns and a shared range written in the request are read), time (`at`/`during`/`overlaps`; a declared `time` place is reused for "when").
9. **Re-asks** driven by the validator (options, two-sided comparison, quantifier, unused name, asked place, class mismatch, absence on an open statement), at most two rounds.
10. **Confirmation by forced contrast** (B, C, D): the paraphrase of the circuit against the paraphrase of one alternative with one oracle-decided slot changed (the statement the yes/no question names after the name, a derived statement alone, a statement with the same role structure, swapped places when the recorded facts allow it, the truth, the kind within the cue's kinds, the quantifier, the avoided statement), in an order fixed by the request's hash, plus "neither"; the chosen alternative replaces the circuit when it validates, "neither" redoes one part once. Slots decided by literal cues are never contrasted. B-yesno keeps method A's yes/no confirmation.
11. **No invalid circuit**: when the answers cannot be assembled into a valid circuit after the re-asks, or no question of the circuit holds any name, number or comparison although the request names something, the strategy answers `unclear` with kind `relation_not_in_memory` and keeps the rejected circuit and the problem codes in its report (`fallback`).

Measurement (dev rows, Qwen3-4B Q4, optimised runtime): `eval/reports/current/omp-tasks/stepbystep-protocol.md`.

### The query author in the chat turn

A chat turn starts by giving the user's message (any language) to the query author, which returns the circuit of [DS014](specsLoader.html?spec=DS014-model-surface.md). There is **one request parser** with three formalization strategies (owner decision of 2026-10-02, section "Formalization strategies" below); the earlier SymbolicLM parser is frozen history (`probably_obsolete/tinyLLMExperiments/`). Library `lib/query-author/`, orchestration `server/query-parser.mjs`, skill [`coding-agent-query`](../../skills/coding-agent-query/SKILL.md).

**Model chain.** `queryParser.models` is the model chain of CodingAgent, a list of omp model ids tried in order (shipped: `zai/glm-5.3`, then `openai-codex/gpt-6-luna`; without the list, `queryParser.backend.model`); a session's `omp_model` is tried first; a model omp cannot use is skipped and a run that delivers no circuit moves on to the next model. `queryParser.backend.kind` is `omp` or `completion` (any chat-completion endpoint: llama-server, OpenRouter). Whatever produced the circuit, **the shared symbolic path runs after it**: admission, KnowledgeLinker, slice retrieval, StrategyRouter, oracle verification, completeness guard, rendering. The packet and `chatSop` carry `parse: {parser: 'coding_agent', strategy, model, tried, backend, rounds, repairs?, cost_usd, ms, cache, mode, retrieval, vocabulary_dialog?, guide, unlinked?, closest?}`; `repairs` lists, per repair or dialog round, the problem codes sent back to the author (`[{round, problems: [codes]}]`).

**codingAgentQuery: vocabulary (owner decision of 2026-10-02).** Vocabulary is detected symbolically and expanded through a bounded dialog, never by sending the whole memory to a model. `lib/query-author/retrieval.mjs` retains IDF-weighted lexical candidates (24 plus the declared core set) and exact entity hints. `lib/query-author/neighbourhood.mjs` first resolves the question's entity mentions without guessing namesakes, then performs bounded indexed lookups for the predicates used around them: one hop initially, two on expansion. Each ranked predicate carries declared roles and argument classes, stored-fact counts with their coverage, at most two schema examples rendered as SOP and deterministic English by `reasoning/slice/render-english.mjs`, related head/body definitions and declared closedness. These samples explain relation meaning and argument order; they are neither answers nor complete evidence and authorize no facts, new entity ids, inferred closedness or repository writes. This bounded schema-evidence input supersedes the earlier no-instance vocabulary restriction of DS014; the circuit-only output boundary and validation are unchanged. The shared module accepts a repository/session or the stored circuits with a cached indexed view, and is reusable independently of the query author.

**Context bound.** The author receives lexical candidates union the entity neighbourhood. Candidate schema, examples, entity hints and the optional supplementary vocabulary file share a 24,000-byte UTF-8 budget (`maxVocabularyBytes` in the library, `queryParser.maxVocabularyBytes` in the parser; range 1,024–90,000). Whole entries are retained in rank order or omitted, never cut mid-rule. The guide and user's bounded request are separate fixed inputs. The supplementary predicate-only file is supplied only when space remains; it is not a memory dump. `parse.retrieval.neighbourhood` reports linked entities, hop count, ranked schema and lookup/truncation diagnostics; `bytes`, `byte_budget` and `truncated` report the offered vocabulary.

**Bounded symbolic dialog.** `authorQuery` permits at most two extra vocabulary rounds, independently of the existing validator repair bound. Triggers are `unclear relation_not_in_memory`, unknown predicates, declared role/type mismatches, or an actual empty execution with a sampled plausible reversal of two argument positions. An empty result alone does not trigger a rewrite. Expansion adds a two-hop neighbourhood, lexical search on the missing term and related definitions. The focused circuit-only follow-up requests an existing relation, a safe session rule over available relations, or a precise ambiguity question. The runtime never swaps arguments automatically and reveals no executed answer values. Every response passes the same T1 validation; stored memory wins, a valid definition is stored in the session layer at once, and turn definitions remain labelled in the answer. `parse.vocabulary_dialog` reports the two-round limit, actual expansions and triggers. `queryParser.vocabularyDialog: false` explicitly disables these extra rounds for controlled measurements; no other parser is substituted.

**What it writes.** The result is a set of circuits (`circuits: [{file, role, text, origin: coding_agent}]`): queries and optional session `predicate`, `rule`, `default` definitions, labelled `assumed` propositions, numeric constraints and uncertainty markers. User suppositions use `stated certainty supposed`; assertions and raw `fact` wires are forbidden. Existing predicates are preferred; a new term needs a declaration and a definition over existing predicates, or a short clarification if equally plausible definitions exist. Labelled model knowledge is the last preference and remains conditional. A declaration may mark a new predicate `closed true`, but cannot replace a declaration of memory. Entity strings are names from the message or listed ids. DS014 owns the proposition language; DS004 owns the definition syntax.

**Validate, execute and self-check.** The shared author admission validates model wires and their vocabulary, while the knowledge validator checks the definition layer together with the base and session circuits. Unknown body predicates, duplicate ids, unsafe variables, arity conflicts and stratification errors reject the output. Strong unused mentions, dropped explicit quantifiers and comparisons are errors. Repair rounds are bounded by `queryParser.maxFixRounds`. `lib/query-author/runtime.mjs` retains the declarative compiler and scheduler but delegates generated query solves to `askMemory`/`routedAsk`, using the base and session circuits plus only this turn's definitions, evidence and conditional facts. Defaults, aggregates, rules and closedness therefore use the same Theory as harness execution. Used steps carry `origins` (memory, definition by coding agent, assumption by coding agent); defeated assumptions carry `session_conflicts` with `reason: memory_wins`. A request-local execution callback permits one additional circuit-only answer-shape self-check: status, cardinality and a deterministic circuit reading, never answer values. Its revision passes the same admission and executes once; invalid revisions are reported. `parse.self_check` records the outcome.

**Declaration and condition-use guards.** Admission checks declared roles on direct chat circuits and in the shared author validator; phrase-linked role mismatches are errors, not repair advice. Positional rule/default atoms are checked against declarations by the knowledge validator. Named query matches may omit roles as existential variables (DS014); omission is not a positional arity error. When accepted circuits or a repository/session are available, `validateQuery` also uses the indexed condition-domain check of DS006 before accepting a circuit. Names resolve exactly; phrase mode reuses the declarative compiler's linking semantics. Confirmed `condition_misuse` is repair feedback with the condition, position and bounded observed values, and may enter the existing two-round vocabulary dialog. This requires no execution preview and works with `selfCheck: false`. The execution guard independently protects cached or directly submitted circuits. The author never automatically swaps or drops a condition, and a refusal after the bounded rounds remains a refusal.


**Failure is honest.** There is no fallback parser. When no model of the chain is available the turn fails with `parse_unavailable` (503); when the models ran and delivered no valid circuit after the last round it fails with `parse_failed` (422); a busy agent (`queryParser.maxConcurrent`) is reported the same way; `unclear no_request` (not a question: statements and courtesy) is answered from the circuit without a query. Both errors carry the `parse` record.

**Latency and cost.** Identical requests are cached by normalized message, accepted memory version, conversation evidence, model, guide version, self-check setting and `queryParser.runTag`; fragments also require identical previous-query context. A cache hit has cost zero and executes against the current memory, without a new author round. The initial preview used by self-check performs no proof-use reinforcement or draft write. Only the final admitted turn may perform policy-authorized proof-use reinforcement and store its definitions. Request folders are removed after authoring unless `queryParser.keepFolders`.

### Knowledge browser

Owner requests of 2026-10-02: "where can I review world-v1 and core-en" and "search by keywords and see what the current memory knows". The page `/review` and the API `GET /v1/knowledge/*` (`server/review.mjs`, `server/pages/review.mjs`, `lib/review/`) show what a base memory or a chat session knows. They are read only: no route writes knowledge, any method other than `GET` answers 405, and there is no accept, reject or approve step (AGENTS.md direction 8, owner correction of 2026-10-02: errors are corrected systematically through tests and interactions). Every authenticated caller may browse (the server has one administrator identity and no read-only role); a session target must be visible to the caller.

**Targets and layers** (`lib/review/target.mjs`). A target is a base memory (`memory=<id>`) or a chat session (`session=<id>`). A base memory is its import layers in order (the snapshots under `imports/`; a layer whose id is a seed of `config/knowledge/` is marked `seed`), then its own circuits, with the own circuit files that a document ingestion stored (provenance `source.kind: document`) split into one layer per ingestion. A session is its base memory's layers (from `base_circuits/`) followed by the session layer (`circuits/`). Each layer's circuits are parsed once per fingerprint (circuit file names, sizes and modification times) into a summary: wires by type, files, facts per predicate, the vocabulary and theory wires, and a token index of the text values of facts. A fact or an entity is attributed to the first layer that holds it; the largest layer is not indexed and is the default (world-v1: about 357k facts).

**Risk views** (`lib/review/items.mjs`). The items of a layer are its predicate, lexeme, rule, default, aggregate, integrity, procedure, method and norm wires, its class entities, one group per predicate of its facts and one group per class of its plain entities (never one row per fact). A flag marks a likely problem; the risk of an item is the highest weight of each of its flag codes plus 2 for every repeated flag, and a view lists the most risk first. Flags: `no_description` (30), `form_no_evidence` (30: a form with no count in the mined corpus and no Wikidata label or alias of a property its lexeme or predicate cites), `shared_form` (30, or 15 when a `restrict` or `weight` tells the claimants apart: another predicate with the same number of roles claims the form; a role-set variant with another frame length is listed but not flagged), `undeclared` (30), `rule` (15, 5 for a generated projection rule), `converse_frame` (15), `flipped_mapping` and `merged_mapping` (15, world-v1 mapping rows), `review_dropped` (10: the core-en build dropped forms of the predicate), `no_lexeme` (10), `partial_rule` (5), `class` (5), `curated_values` (0). Evidence (`lib/review/evidence.mjs`, absent evidence reported as absent): `eval/reports/current/core-en/mined.json` (counts and example messages), `dropped.json` (forms dropped with the cross-review verdict), `datasets_sources/core-en/wikidata-properties.json`, and the world-v1 mapping of `tools/world-kb/mapping.mjs` with `datasets_sources/world-kb/build-stats.json`.

**Effect, not syntax** (`lib/review/examples.mjs`). A lexeme form is shown as a generated sentence and the atom it maps to, through the lexeme's frame and the predicate's role order ("Beta Labs employs Ana" → `works_at ana beta_labs`); fillers are the labels of one real fact of the predicate when the memory has one, else placeholder names by role class. The predicates the memory's lexicon links the phrase to are listed with it. A fact is rendered through the first English, non-converse lexeme of its predicate. A rule is shown with up to two derivations over the memory's own facts (a bounded join of keyed lookups; conditions other than plain relations are named as not checked by the preview) or, when no stored facts match, one hypothetical derivation over placeholder names, labelled as such. Generated sentences illustrate the vocabulary; they are never knowledge.

**Search and cards** (`lib/review/index.mjs`). Search reads the compiled lexicon's token index (labels, aliases, lexeme forms and ids of entities and predicates; every word must match, the last also as a prefix), the predicate descriptions, the rule wires and the per-layer text index; results are grouped (`entities`, `classes`, `predicates`, `rules`, `facts`), ranked and paged. An entity card gives the label, aliases, classes closed over `is_a`, description, every stored fact in both directions grouped by predicate (keyed lookups of the memory strategy per declared predicate and admissible position, at most 50 per lookup) with its source and layer, and the rules whose bodies use those predicates. Derive asks the oracle (`askMemory`, at most 12 select queries over the heads of those rules with the entity in each admissible position, then `mode explain` for at most 8 derived facts) and returns each derived fact that is not stored with its proof tree and the layer of each stored premise. A predicate card gives roles, description, closedness, readings, the lexemes with per-form evidence and flags, generated sentences, fact counts per layer, example facts, the rules that conclude or use it, the dropped forms and the mapping rows. A rule card gives the SOP, a deterministic English reading and the example derivation. The chat trace links the linked entity and relation symbols and the relations of the schema neighbourhood and of the retrieval slice to these cards over the turn's session.

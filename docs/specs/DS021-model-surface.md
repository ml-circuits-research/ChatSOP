# DS021 — Model surface: the one small-model language

## Scope

This specification is the normative contract of the small model's language (the model surface). The small model authors exactly six wire types: `stated`, `assumed`, `unclear`, `query`, `constraint` and `unparsed`. It never authors host plumbing (`resolve`, `pack`, `solve`, `reason`, `cnl`, `remember`, `clarify`, `expand`, `value`, `jsEval`, `fact`, definitions or policy).

**The small model has no context.** Its input is the user's message only: no entity or predicate shortlist, no identifiers, no lexicon, no background knowledge and no `now`. It writes what it understood as strings, one finite clause per wire, and marks what it could not formalize as `unparsed`. Normalizing content words (the message is English, see "Input languages and content words"), linking strings to knowledge — relations to predicates, values to entities, temporal expressions to intervals — and repairing unparsed spans are host steps after the model, performed deterministically with the reviewed English synonym sets and the lexicon; when a string stays unknown or ambiguous the host asks the user with a generated `clarify`.

There is one current model language, with no versions, no formats side by side and no compatibility paths (owner decision of 2026-09-29): the language improves step by step, each change replaces the old form, and the corpora and sealed suites are converted or regenerated to the current form (`tools/datasets/convert-targets.mjs` converts what is mechanical and lists the rows to regenerate). `premise` and the entity/predicate shortlist are removed from the language, the parser and the prompts; the model never refuses. Trusted circuits state hypothetical inputs as `fact … source assumption` consumed through `assume` (DS004). The corpora in this language are generated by DS022 (`formalizer-v1` and the out-of-distribution suite `formalizer-ood-v1`); the earlier atom/identifier/context corpora were deleted with that regeneration.

Implementation: `sop/parser.mjs` (`SPEC`, `parseProposition`, `parseMatch`, `linksOf`, `roleReferences`), `sop/enums.mjs` (`ROLE_NAMES`, `ENUMS`, `LINK_KEYWORDS`, `UNPARSED_HINTS`), `sop/clauses.mjs` (link and reference admission, the host plan of links, query chaining, placeholder pairing), `sop/repair.mjs` (symbolic repair of unparsed spans), `sop/dictionary.mjs` and `config/dictionary/` (the bilingual and synonym dictionary), `tools/dictionary.mjs` (its maintenance CLI), `sop/unclear.mjs` (`UNCLEAR_KINDS`), `sop/linking.mjs` (host linking, time normalization, anchoring), `sop/propositions.mjs` (reports and identities), `sop/declarative.mjs` (`MODEL_TYPES`, admission and compilation), `sop/lexicon.mjs` (role declarations), `server/agent.mjs` (message-only prompt, anchoring guard), `eval/llm.mjs` (the archived prompts), `server/language.mjs` (answer language), `server/http.mjs` (trace), `eval/run.mjs` and `eval/propositions.mjs` (admission and metrics).

## Scope, non-goals and extension checklist

The small language exists for one job: turning a user's message — a question together with the assertions attached to it — into a **description of a problem**. It is not an action language, not a planning language and not an advice channel. Everything a user could mistake for a suggestion is a host decision. The six authorable wire types are enforced in `sop/declarative.mjs` (`MODEL_TYPES`) and re-checked at admission in `server/agent.mjs` and `eval/run.mjs`; everything else belongs to the host or to trusted tool circuits, and is generated or supplied with recorded provenance.

### Explicit non-goals

1. **No execution.** The model never chooses an engine, a backend, a retrieval strategy or a definition handle. `dependencies(...).handles` must be empty for model output.
2. **No writes.** A `stated` or `assumed` proposition is never recorded; a sourced `fact` and an explicit trusted `remember` are separate, host-authorized operations.
3. **No advice, recommendations or action proposals, and no refusal.** If a user asks "what should I do?", the model formalizes the underlying question as it understood it; the host answers what it can compute, asks with a `clarify` when a required relation, identity, date or scalar is missing, or states "I understood the question as …; I cannot compute this kind of answer yet" when no engine exists. Presenting guidance that the runtime did not compute is forbidden, because the CNL layer renders results, it does not invent them.
4. **No procedure selection.** The model cannot pick or parameterize template/procedure handles; expansion is host-approved and audited.
5. **No vocabulary at all.** The model never sees or chooses identifiers: it writes the relation phrases and names of the message (content words normalized, see "Input languages and content words"), roles from a closed context-free inventory, and temporal expressions as stated. Wire ids (`@s1`, `@q2`) and the `$id` references to them are the output's own local names, not vocabulary. The host links the strings with its reviewed English synonym sets and lexicon, or asks the user; a string never becomes a new identifier by being written.
6. **No reasoning in the model.** The model does not judge whether a readable message is contradictory, incomplete, relevant or answerable; it formalizes it. `unclear` covers only unintelligible text and messages with neither a statement nor a question; a part the model cannot formalize is an `unparsed` span, never an invented value and never a refusal.

### Is the current construct set sufficient?

Yes, for every family whose interpreter exists and is validated in this repository: relation/role and argument reversal, multi-hop composition, joins, explicit negation and conflict, open-world absence, temporal windows and cutoffs, scoped synonym resolution, finite numeric constraints and optimization, clarification of missing/ambiguous dependencies, user assertions versus user suppositions versus model assumptions, approved-procedure reuse, expression composition, universal questions over a restriction, time questions (when, since when, until when, how long, how many times), where/how questions, and why questions answered with a derivation. Executed evidence for every family and question form lives in the DS022 corpora: each row's target is executed against its verification world and must reproduce the stored result.

The families that the corpus manifests list as blocked (abduction, default-with-exception, counterfactual, planning, causal, agentive intention, general quantification) are **model-formalizable**; general quantification is the universal question form (`mode every`, computed over the known members): the model writes what the message says with `stated`, `assumed` (for example `basis default` for a default) and `query`, and never refuses. How the reasoning engine treats these families is not decided by this specification; until an audited interpreter exists, the host reports an understood-but-not-computable problem rather than guessing.

### Conservative checklist for a future construct

A new model-authorable construct is admissible only when **all** of the following hold. Until then it stays a proposal (recorded in `questions.md` or `TODO.md`), never in the parser.

1. **Problem-shaped.** It states something about the problem (a proposition, a question, a restriction), never a procedure, action, preference or suggestion.
2. **Context-free.** The model can write it from the message alone, as strings, without identifiers, vocabulary, knowledge or a clock; any linking is host work.
3. **Host-evaluable.** An audited interpreter exists that decides the construct without inventing meaning, and it reports status, completeness and route.
4. **Independently oracle-able.** A second, independent reference can produce the expected result for the corpus, so the corpus never confirms itself.
5. **Non-writing.** The construct cannot change memory; any write stays a separate trusted operation.
6. **Honest when not computable.** When the construct's interpreter is absent, the host answers that it understood the problem but cannot compute it, and the model cannot force a fallback; the only `unsupported` result left is an explicitly requested, unavailable backend in a trusted circuit (AGENTS rule 8).
7. **Reviewable.** The field set, cardinality, canonical form and rejection cases are documented in the wire reference, with valid and invalid examples that `tests/wire-help.test.mjs` executes.

### Host-rendered explanation of statements and assumptions

The user asked that the system can explain the assumptions it made. That does not require a model capability: every model-origin turn returns `user_statements` and `model_assumptions` in the packet (and in the HTTP `chatSop` trace), each with a host-rendered sentence built from the wire's own strings — "You stated: …", "You supposed: …", "According to Ana: …", "The model assumed: … (basis: closure)" — plus the linked predicate and atom, validity, treatment and, for conditional use, whether the proof used it and whether it was defeated. Because the prose is produced by the host from the recorded wire, an explanation can never claim a reading the model did not declare.

## Input languages and content words

**English-only core (owner decision of 2026-10-01; it supersedes decision D1 of 2026-09-29).** The core (SymbolicLM, the small formalizer's language, the host linking, the knowledge, the reasoner and the rendering of answers) knows English only: "we do not want all the languages in the core, it becomes too expensive; we always translate into English and, if needed, translate the answer from English into another language". Language is handled at two edges and nowhere else:

1. **Input edge.** Every message that is not English (Romanian or mixed, misspelled or not) is translated into English before it reaches SymbolicLM, in the chat and in every API route that analyses a message (`/v1/chat/completions`, `/v1/understand`, `/v1/symbolic/analyze`, `/v1/symbolic/rewrite`, `/v1/route`). The edge is textToCleanEnglish: the translator-llm (Qwen3-4B), with LanguageProofingLLM as the reported fallback; names, numbers and quotations are masked by placeholders before the call and restored after it, and a translation that loses one is not accepted. The chat UI shows the proposal to the user (accept, edit, send the original); the server applies the same translation again for any message that is still not English, so a client that skips the UI cannot put Romanian into the core. When no translation can be made the request fails with `backend_unavailable` and the message is not analysed. The SymbolicLM service itself refuses a message that its language identification does not read as English (`422 non_english_input`; the library option `englishOnly`); the research routes `direct` Romanian and `translate` of the library remain only as archived evidence for the evaluations that measured them.
2. **Output edge.** Every answer is rendered in English by the core (there are no Romanian rendering templates in the reasoning and rendering layers). When the caller asks for another answer language (API `language`, or an explicit request in the message, see "Answer language"), TranslatorService translates the final English answer from English with the translator-llm; names, numbers with units, quoted values and SOP identifiers are masked and restored. The packet records the step (`answer_translation`: language, backend, the original English text, status) and the HTTP trace adds `english_text`; the conversation memory keeps the English text. A translator that cannot run leaves the English answer and reports `answer_translation.status = backend_unavailable`; nothing is silently substituted.

The consequences for content words: the formalizer receives English, so a relation phrase is the lemma of the message's predicate words in English (an English verb in its base form: "works at" → `"work at"`; particles, prepositions and modals are kept: "be allowed to sign"), a common-noun value keeps its determiners and is lower case, proper names stay exactly as written ("Ayşe Şahin", "Pitești"), temporal expressions are copied as written ("12 March 2020", "now", "next Friday"; the linking normalizes English dates), and the structural keywords are the fixed English words of this specification. For `stated`, "surely from the message" means a proper name as written or the message's own words, normalized; a value the message does not express is `assumed`. Answer rendering is a separate concern (the output edge) and never changes the target.

**English synonyms (`sop/dictionary.mjs`).** The linking keeps the reviewed English synonym sets of `config/dictionary/` (`"work at"`, `"be employed by"` and `"have a job at"` are one entry that links to `works_at`) through the English view `englishDictionary()`: it carries no Romanian surface or form and never translates a content string. Before linking, a relation phrase or a value that does not link as written is retried, in tiers, with its English synonyms and, for a relation, the phrases of an `unparsed` relation span near the wire; the first tier that links to exactly one predicate or entity wins, two predicates in one tier are ambiguous and the linker asks. Proper names are never translated. Each applied synonym is reported in `translations` (`source`: `synonym`). The full bilingual dictionary (the Romanian columns, the Wiktionary data of [DS014](specsLoader.html?spec=DS014-source-rights.md)) is language data of the edges and of the evaluation only: language identification (LanguagesUtil), the gloss backend of TranslatorService and the tolerant scoring of archived Romanian gold; it is not on the product linking path. Its files are reviewable TSV under `config/dictionary/` listed in `manifest.json`; `node tools/dictionary.mjs propose|review|approve` maintains them.

**Knowledge is English only.** A `lexeme` has `language en`, an `entity` or `predicate` has `label en` and `alias en` lines, and the knowledge validator rejects any other language tag (`non_english_knowledge`) in core-min, core-en, demo, world-v1 and every base memory. The seed memories stored in a chat data root are renewed with `node tools/refresh-seed-memories.mjs --apply` when `config/knowledge` changes (a dry run lists what would be re-created; a memory with circuits of its own is never deleted).

History: until 2026-09-29 the model wrote canonical English content words (owner decision Q-DATA-6); decision D1 (2026-09-29) let the model keep the message's language and made the host dictionary translate it; the decision of 2026-10-01 moved all translation to the edges. Archived corpora, gold SOP with Romanian content words, the Romanian UD rules and the evaluations that used them are history, not product behaviour.

**Host frame normalization (`sop/frames.mjs`, owner answer to Q-SYM-2 of 2026-09-29).** A reviewable frame and synonym list plays the host's role after the formalizer and normalizes what it produced; the model language and the golds do not change. The frames are TSV files listed in `config/dictionary/manifest.json` under `frames` (columns `id relation roles surfaces source note`), built by `node tools/frames.mjs build` from training-side sources only: the verification world of the training corpus (`frames-world.tsv`), training golds the world does not name (`frames-train.tsv`) and English verb synonyms of the most frequent WordNet 3.0 sense (`frames-wordnet.tsv`, [DS014](specsLoader.html?spec=DS014-source-rights.md)). One proposition is normalized in four levels, each reported as a change (`kind`, `from`, `to`): `synonym` (a relation found among a frame's surfaces, directly or through the dictionary's English candidates, becomes the frame's canonical relation), `role` (a role name the frame does not declare is renamed when exactly one declared non-subject role is free; frames that share one role set fix the names even when the relation is ambiguous; never with two undeclared roles), `boundary` (a relation that names no frame, or a frame without an object, joined with its object value — "get" + "the flu shot" → "get the flu shot" — or split before its last words when that names a frame) and `time` (a quoted `role time` on a relation without a time role becomes the validity or the query period). Strict scoring never applies it (owner answer to Q-SYM-1: what fails strictly stays visible); evaluations report the host-normalized score beside the strict one ([DS016](specsLoader.html?spec=DS016-evaluation-metrics.md)). The chat runtime does not call it yet.

## Proposition form

`stated`, `assumed` and every query `match` block carry one proposition — one finite clause of the message — as keyword lines, one keyword per line.

| Keyword | Cardinality | Value | Meaning |
| --- | --- | --- | --- |
| `relation` | exactly once, required | one JSON-quoted nonempty phrase | The relation as meant, the lemma of the message's predicate words in the message's language (or English): `"work at"`, `"parent of"`, `"lucra la"` for "lucrează la". |
| `role` | 1–4 lines, required; a name at most once | `role NAME VALUE` | NAME is from the closed inventory `ROLE_NAMES` = `subject`, `object`, `recipient`, `location`, `source`, `destination`, `instrument`, `time`, `topic` (`role_unknown`, `role_duplicate`). VALUE is a JSON-quoted string — a proper name exactly as mentioned in the message, any other value normalized in the message's language or in English (see "Input languages and content words") — or a safe integer; `$id`, another wire of this output (at most one per wire; see "Clauses and links"); in a query `match` also a `?variable`; in `stated`/`assumed` a `?variable` only as the placeholder of an `unparsed` span (see "Honest partial formalization"). Never a `~handle`, a bare identifier or quoted sigil text (`proposition_not_ground`). |
| `polarity` | exactly once, required | `affirmed` \| `negated` | `negated` is explicit negation; absence of evidence is never expressed this way. |
| `valid` | `stated`/`assumed` only; at most one line per form; optional | `valid on "TEXT"`, `valid from "TEXT"`, `valid until "TEXT"` | The temporal expression as stated in the message ("12 martie 2020"). `on` excludes `from`/`until` (`time_form`). Absent means timeless: the model states no time it was not given. |
| link lines | `stated`, `assumed` and `query` wires only (not inside a `match` block); 0–3 per wire | `because`, `so`, `if`, `unless`, `although`, `so_that`, `before`, `after`, `when`, `while`, each followed by exactly one `$id` | The relation of this clause to another clause of the message; see "Clauses and links". |

**Content words.** Every value and phrase follows "Input languages and content words" above.

**Time of a clause.** A statement's own time is written `valid on|from|until`; a question's time is its `at`, `during` or `asof` line (see "Question forms"). `role time` holds the `?t` variable of a when-question, or a time that the relation itself takes as an argument. A quoted `role time "…"` on a relation that declares no time role is read by the host frame normalization (level `time`, below) as the statement's validity or the query's period, so both spellings link alike; new targets use `valid`, `at` and `during`, and the independent wild suite keeps the quoted times its annotators wrote (owner answer to Q-SYM-3, 2026-09-29).

**Values as written, relations as meant.** A proper name in a role value or a `speaker` is quoted exactly as the message writes it, typos and missing diacritics included; the host matches entity strings after case and accent folding and asks when a misspelled name does not resolve (it never resolves an identity by similarity). The relation phrase is the intended relation, normalized to a lemma when the message inflects or misspells it (`"work at"` for "wroks at", `"lucra la"` for "lucreaza la"). "Because of <entity>" is a role of the causal relation (`role topic` for the cause, `role source` for "from"/"de la"), and its preposition stays in the relation phrase like any other (C2): "Who did she quit because of?" is `relation "quit because of"` with `role topic ?x` (owner answer to Q-SYM-3); a "because" clause that is a whole proposition is its own wire, linked with `because $id` (see "Clauses and links"). Remarks about the user's own situation or purpose ("I have a meeting tomorrow", "My boss asked me") are not part of the problem and are not formalized.

**Host linking.** After the model, the host repairs `unparsed` spans, applies the English synonym step of "Input languages and content words" and links each proposition (`sop/linking.mjs`):

1. *Relation.* The phrase is compared, after case and accent folding, with every lexicon predicate's identifier (underscores as spaces), labels, labels and lexeme forms in all languages and gloss (`description`). Auxiliaries and articles (`is`, `are`, `a`, `the`, `este`, …) are dropped and a plural or third-person `-s` and a final `-e` are ignored, so `"work at"` meets the alias `works at` and `"is a parent of"` meets `parent of`; other inflections (for example `-ing` forms) need a lexicon alias. Among the matching predicates, the role set decides: a `stated`/`assumed` proposition must bind exactly the roles the predicate declares; a query `match` must use only declared roles, and each unmentioned role becomes a fresh host variable. No match → `unknown`; several fitting predicates → `ambiguous`; matches with other role sets → `role_mismatch`. Each of these stops the turn with a host `clarify` (`reason: unresolved_link`) naming the candidates; nothing is guessed.
2. *Roles.* A predicate maps its argument positions to the inventory with `role NAME TYPE` lines (DS004 "Lexicon wires"; any other name is reported by the validator, `bad_role`). A predicate that only has legacy `args` is unnamed: with one or two arguments its positions are `subject` and `object`; with more it cannot be linked until roles are declared, and the corpus audit flags it.
3. *Values.* Quoted strings are resolved as entities of the argument's type by the generated `resolve` wires (exact, then accent-folded aliases; the existing identity rules of DS004). Unknown or ambiguous entities block dependent work and produce the existing host clarification (`reason: unresolved_dependency`). A numeral string fills an integer argument as a number.
4. *Time.* `valid`, and a model query's `at`, `during` and `asof`, are normalized against the runtime clock: ISO dates and UTC timestamps, `YYYY`, `YYYY-MM`, an English or Romanian month name or abbreviation with a year, a day, month and year ("3 March 2025", "March 3, 2025", "the 3rd of March 2025", "3 martie 2025", "3 mar. 2025", "03.03.2025"), a range "A – B" (from the start of A to the start of B), `now`/`acum`, today/yesterday/tomorrow (`azi`, `astăzi`, `ieri`, `mâine`), last/this/next year (the calendar year of the host clock), with an optional leading preposition. `on` is the whole period; `from` starts at the period's start; `until` ends, exclusively, at the period's start; `at` is the period's start; `during` is the period. Anything else becomes a host `clarify` ("Which date or period do you mean by …?").

5. *Time variables.* In a query match block, `role time ?t` on a relation that declares a `time` role is an ordinary argument. On a relation without one it asks for the validity interval of the matched fact: the host drops the role from the atom and writes the host-only field `span ?t`, which binds `?t` to the interval (with several match blocks, the interval in which they hold together). A query with a span and neither `at` nor `during` looks at the whole timeline. With `order ?t1 before ?t2` each time variable is the interval of its own match block; the host writes `order ?t1 before ?t2 leaves I J` instead of `span` (see "Words, not operators").
6. *Quoted literals of `except` and `compare`.* A quoted value in `except ?x "Ana"` ("besides Ana") or in an `equal`/`not_equal` comparison is an entity as written; the host resolves it like a role value and asks when it is unknown or ambiguous. A compared string that names no entity ("2380 lei") stays a value. "the user" is linked to the caller's own entity when the caller-owned context supplies one (`context.user`, or the agent configuration `user`); otherwise it resolves like any other surface.

The linked result is the existing positional atom (`works_at maria lab_alpha`), so the reasoners, the Prolog route and the oracles are unchanged.

## `stated`

A formalized report of one proposition that the user's message puts forward (the question and the attached assertions). Additional fields:

| Keyword | Cardinality | Values | Meaning |
| --- | --- | --- | --- |
| `certainty` | exactly once, required | `asserted` \| `hedged` \| `supposed` | The user's commitment: `asserted` (the user asserts it), `hedged` ("I think …"), `supposed` ("suppose …", "if …"). |
| `speaker` | at most once, default `user` | `user` or a JSON-quoted name | Reported speech ("Ion says that …"). |

No other field is accepted; in particular there is no `holds`, `quote`, `source`, `basis` or write field.

**Anchoring.** There is no quotation. The agent guard (`server/agent.mjs` `validateVocabulary`) checks mechanically that every role value of a `stated` wire, and a non-user speaker, appears in this turn's message (question plus attached assertions): the value's tokens must match consecutive message tokens after case, whitespace and accent folding, each within a small edit distance (optimal string alignment: 0 for tokens up to 3 characters, 1 up to 7, otherwise 2) or as a short inflection sharing all but the last character of a token of at least four characters. Otherwise the turn is rejected with `stated_value_not_in_message`, and the model should use `assumed` or a query variable. The relation phrase is not anchored, because the model normalizes it. A normalized value in the message's language ("sala de sport" for "sălii de sport") passes through the inflection tolerance above. A value written in English for a word of a Romanian message ("the gym" for "sala de sport") is anchored cross-lingually: through the host dictionary (`sop/linking.mjs` `mentionedThroughDictionary`: a Romanian or English surface of an entry the value belongs to, lemma or inflected form, is mentioned in the message; a multiword value when each of its content words is; "the user" by a first-person word) or through the host lexicon (`mentionedThroughLexicon`: another label or alias of the same entity occurs in the message). The corpus audit and the reference-free metrics additionally use the row's verification entities (`tools/datasets/audit/translation.mjs`, DS016, DS020, DS022). Names and numbers keep the in-message check. A `$id` value and a placeholder `?variable` are structural and are anchored through the wires they name; every `unparsed` span must be a verbatim part of the message after case and whitespace folding (`unparsed_span_not_in_message`).

**Semantics.**

| Statement | Lowered host value | Used by the generated `solve` as | Result marking |
| --- | --- | --- | --- |
| `certainty asserted`, speaker `user` | turn-local `fact … source user` | `data` (evidence) | not hypothetical |
| `certainty hedged` or `supposed` | turn-local `fact … source assumption` | `assume` (DS004 defeat semantics) | `hypothetical: true` when the proof uses it |
| any certainty with a `speaker` | turn-local `fact … source assumption` | `assume` | `hypothetical: true`; reported "According to …" |
| a supposition named by `if $id` (or `unless $id`) on a query | turn-local `fact … source assumption` (for `unless`, the negated atom) | `assume` of that query only | `hypothetical: true` when the proof uses it |
| a statement that carries `if`/`unless` itself, one with a `$id` role value, or one held by an unresolved `unparsed` span | none | not used | reported only (`treatment: conditional_statement`, `reported` or `incomplete`) |

User suppositions always take part in the primary result: the user authorized them. A supposition that a query names with `if`/`unless` applies to that query only; one that no query names applies to every query of the message. A contrary admitted fact or asserted statement defeats them exactly as DS004 describes, and the report marks `defeated: true`. Exact duplicates (same folded relation, role values, polarity and validity text, certainty and speaker) are rejected (`stated_duplicate`); contrary statements are accepted and the result exposes the conflict. Constraint problems do not consume statements.

**Lifecycle.** Authored → parsed → anchored → linked → lowered to a turn-local `fact` → consumed by this turn's generated `solve` wires → reported → discarded from execution state. A statement is never recorded by `remember` (none is generated), never published and never reinforced (local facts are excluded from proof-use promotion). Asserted user statements are carried across turns in caller-owned conversation context (`context.statements`, origin `user-statement`, linked atom, validity and the original input text) and re-supplied by the host as turn-local `fact … source user` evidence; they are not sent to the model. Hedged, supposed and reported statements are not carried. A statement-only turn returns `status: context_updated`.

## `assumed`

One proposition the model adds during intent detection. One wire type, no subtypes, no `certainty`; its values need not appear in the message. Additional field:

| Keyword | Cardinality | Values | Meaning |
| --- | --- | --- | --- |
| `basis` | at most once; optional, absent means `unspecified` | `closure` \| `default` \| `disambiguation` \| `implicature` \| `world` | Descriptive label: treating a list as complete; a typical case applied to this instance; a chosen reading of an ambiguous word, referent or scope (never an entity identity); a presupposition of the wording; general world knowledge. |

**Making an interpretation explicit (owner decisions Q-DATA-4 and Q-ARCH-1).** `assumed` is optional and need not be tied to the other wires. The model uses it to state the reading it chose whenever a message is vague or has several readings, so the choice is visible and reported:

- *An ambiguous word*: `relation "mean"` (also for a Romanian message), `role subject` the words as written, `role object` the chosen reading, `basis disambiguation` ("Who made The Salt Road?" → `"made"` means `"wrote"`). The query keeps the words of the message; the host still links them and asks when they are ambiguous.
- *An ambiguous referent*: `relation "refer to"`, `role subject` the pronoun or description as written, `role object` the chosen antecedent as written, `basis disambiguation`. The convention is the subject of the preceding asymmetric sentence ("Ana manages Irina. Does she live in Cluj?" → `"she"` refers to `"Ana"`), and the query uses the antecedent. A pronoun with a single possible antecedent is resolved without an assumption. **Pronouns resolve backwards only** (rules v2.6): the antecedent stands in the pronoun's own sentence or in an earlier one, never in a later sentence, so adding a sentence to a message never changes the wires of the sentences before it (`tools/eval/stability.mjs`); a pronoun with no antecedent so far stays as written.
- *A presupposition of the wording*: "still", "again" and similar triggers presuppose an earlier state or occurrence; the assumption states that proposition with `basis implicature` and no validity (the message names no time). Such an assumption may restate the queried proposition; the corpora keep these cases few.
- *An ambiguity with no preferable reading* is reported instead with `unclear kind ambiguous` and its readings (see `unclear`).

**Ambiguity tolerance (owner decision Q-DATA-5).** A genuinely ambiguous phrasing is never dropped from the data and never refused. When the readings are plausible formalizations of the same message ("Pentru ce e închisă sala?" reads as "why is the gym closed?" — `mode explain` — or as "what is the gym closed for?" — `select ?x` with `role topic ?x`), the model writes one of them, and every plausible reading is correct: a corpus row carries `sop_target` (the primary reading) and `sop_targets_accepted` (the other accepted readings, each a complete model output), and evaluation counts a prediction as matching when it matches any accepted gold (canonical match and execution equivalence alike; DS016). `unclear kind ambiguous` remains for ambiguities the model prefers not to resolve, such as a pronoun after two parallel clauses. The generator applies the rule (DS022).

Assumptions that restate the queried proposition (closure, defaults, presuppositions) are allowed but not over-generated.

**Validation.** The proposition rules above apply. An assumption equal to a statement of the same turn is rejected as redundant (`assumed_duplicates_stated`); a contrary one is accepted. At most `policy.maxModelAssumptions` (default 8) are accepted; more reject the turn (`too_many_assumptions`).

**Semantics.** Host policy `modelAssumptions` decides the treatment; `basis` never influences trust, admission or reasoning.

| Policy | Linking and lowering | Effect | Report |
| --- | --- | --- | --- |
| `report` (default) | linked only for the report; an unlinkable assumption is reported with `predicate: null` and never blocks the turn | The primary answer is computed without assumptions. | `treatment: "reported"`, `used_in_proof: null`, `defeated: null` |
| `branch` | linked and resolved like a statement (an unknown or ambiguous string becomes a host `clarify`, so an assumption never chooses an identity); turn-local `fact … source assumption` consumed by a second generated `solve` per query, together with the user's evidence and suppositions | The primary answer is unchanged and assumption-free; the branch result is reported separately and marked hypothetical when its proof uses an assumption. | `treatment: "branched"`, `used_in_proof`, `defeated`; `assumption_branch` per query |

**Lifecycle.** Authored → validated → reported (and, under `branch`, linked and solved in the branch) → discarded. Never stored, never reinforced, never rendered with fact wording ("The model assumed: …"), never carried across turns; the model restates an assumption when it still needs it.

## `query`

A model query keeps the `query` fields of DS004 (`where`, `select`, `mode` (the five older modes and the five reasoning modes of "Question forms"), `at`, `during`, `asof`, `limit`; `filter` is trusted-circuit syntax that the model replaces by words) and adds `scope`, `measure` and the word fields `compare`, `except`, `rank`, `quantifier`, `order` and `fragment` (below), with two differences. Every `where` leaf is a `match … end` block holding one proposition (the keyword lines above, `?variables` allowed, no `valid`); `all`/`any`/`end` groups combine match blocks. An atom leaf is rejected (`query_needs_match`). `at`, `during` and `asof` take a JSON-quoted temporal expression normalized by the host. The canonical form nests the block lines under `match` and closes each block with `end`:

```sop
@q query
  where all
    match
      relation "works at"
      role subject ?who
      role object "Alpha Lab"
      polarity affirmed
    end
    match
      relation "member of project"
      role subject ?who
      role object "Delta Project"
      polarity affirmed
    end
  end
  select ?who
  at "2026-09-01"
```

`match` blocks belong to the model language; the trusted runtime only lowers linked atom queries.

### Question forms

Every question word has one formalization; the model writes the question it reads and never rewrites it into another form (owner decisions Q-DATA-1 and Q-DATA-2, 2026-09-28). The semantics are computed by the reference route (the oracle `js-reference` through `reasoning/bridge/reason.mjs`; the question forms are `js-reference/forms.mjs`, DS006 "The js-reference oracle"); a form without an interpreter would be answered `not_computable` with the formalization shown.

| Question | Formalization | Host semantics |
| --- | --- | --- |
| yes/no, "is it true that …" | `where` match blocks, no `select` (`mode exists` when variables occur) | status of the proposition: `supported`, `refuted`, `both`, `unknown` |
| who / what / which | `select ?x`, the asked role as `?x` | the bindings |
| how many | `mode count`, `select ?x` | distinct bindings |
| all / every / each ("Is everyone at X certified?") | `mode every`; `where` is the restriction (the domain), `scope` what must hold for each member, sharing its variables | `refuted` with `counterexamples` when a known member explicitly fails the scope; `supported` when every known member satisfies it and the restriction has a member; otherwise `unknown`. The check covers the members known to the host. |
| no / nobody / none ("Is nobody at X certified?") | `mode every` with a `negated` scope | as above; the determiner "no" is the only form written with a negated scope, and "all" is never rewritten as "nobody … not" |
| which groups have only … ("Which teams have only certified players?") | `mode every` with `select`; members are grouped by the selected variables | the groups whose members all satisfy the scope |
| is anyone … not … | `mode exists` with a negated match block | an explicit counterexample |
| when | `role time ?t` in the match block, `select ?t` | the validity interval of the matched fact (`span`) |
| since when / until when / how long | the same, plus `measure start`, `measure end` or `measure duration` | the interval's start, its end (`open` when ongoing) or its length in whole days up to the runtime clock |
| how many times | `mode count`, `select ?t`, `role time ?t` | the number of distinct validity intervals |
| where (where to, where from) | `role location ?place` (`destination`, `source`) | the bindings |
| how (means or manner: "How does Ana commute?") | `role instrument ?how` | the bindings |
| why / how come / how did … come to be | `mode explain` over the proposition (negated for "why not") | the status plus `explanation`: `derivation` (the rules and the facts they used), `recorded` (a recorded fact, no further reason) or `none` |
| why not / what is missing ("Why can't I hard-reset the router?", "What would make this true?") | `mode why_not` over the proposition or goal | the minimal base atoms whose addition would make the claim derivable plus the blocking atoms, or on a planning goal the blocking norm or requirement (`blocked`, `blocked_by`) |
| how do I / what are the steps ("How do I reset the router?") | `mode plan` with the goal as the match block | a sequence of actions reaching the goal under the norms in force |
| what could explain / which cause ("What could explain the outage?") | `mode abduce` over the observation | all inclusion-minimal explanations |
| did we follow the procedure / is this compliant ("Was the reset compliant?") | `mode conform` over the task; the performed trace is supplied by the host | `compliant` or `non_compliant` with the violated norms and deviations |
| what is the procedure for … ("What is the reset procedure?") | `mode procedure` over the task | the approved procedure as written, its version and the norms in force |
| conditional: "if P, is Q?", "dacă P, Q?" | `stated certainty supposed` for P and `if $p` on the query (`unless $p` for "unless P") | the answer under P, for that question only |
| a question about an earlier answer: "Who coaches X? And where does he work?" | two queries, the second with `role subject $q` | the join of both |
| a question bounded by a clause: "was it paid before the audit on 12 May?" | the clause as a `stated` wire with its time, `before $s` on the query | the query period until that time |

A claim check ("True or false: …") is a yes/no query and the claim is not `stated`; a conditional question links its supposition with `if`; several questions in one message are one `query` each; a numeric problem is a `constraint`; a message with statements only has no query (`status: context_updated`); `unclear` covers the unintelligible, the no-request and the ambiguous message. The corpora label these eighteen question types (`yes_no`, `wh`, `count`, `universal`, `when`, `since_when`, `until_when`, `how_long`, `how_many_times`, `where`, `why`, `how`, `claim_check`, `multi`, `numeric`, `none`, `unclear`, `ambiguous`); the wire help page `docs/wire_typs/question-types.html` gives one executed example of each, and `docs/wire_typs/model-guide.html` explains the language from the model's point of view with English and Romanian examples.

`scope` is required by `mode every` and forbidden otherwise (`every_needs_scope`, `scope_needs_every`); `measure` needs exactly one selected variable written as `role time ?t` (`measure_needs_time_variable`); a query asks for at most one time (`time_variable_multiple`) unless `order` compares two; `mode explain` selects nothing (`explain_no_select`); `span` is host plumbing and is rejected in model output. Attribute values, comparisons, superlatives, quantifiers, temporal order and follow-ups have the word forms of the next section.

### Where the model and the knowledge meet

The knowledge a coding agent writes from a source ([DS004](specsLoader.html?spec=DS004-sop.md) "Knowledge wires") and the question the model writes share only predicates and entities, and the host links them; the model never sees an identifier. The bridge is the roles of the `predicate` declaration: the model writes `role subject "Ann"` and `role object "Alpha Lab"`, the reviewed lexicon maps the relation phrase `"work at"` to the predicate `works_at`, and the predicate's `args subject:entity object:entity` says which position takes the subject and which the object; the dictionary turns the strings into the symbols `ann` and `alpha`. A relation whose declaration has no roles cannot be linked (`args_without_roles`). The host links, routes to a strategy, runs it under the budget and renders the packet:

```
user:   "If Ann worked at Alpha Lab, who works at Alpha Lab?"
model:  @s1 stated   relation "work at"  role subject "Ann"  role object "Alpha Lab"  polarity affirmed  certainty supposed
        @q  query    where match relation "work at" role subject ?who role object "Alpha Lab" polarity affirmed end
                     select ?who  if $s1
host:   predicate works_at (subject:entity object:entity); entities ann and alpha;
        @s1 fact holds works_at ann alpha status supposed;  @q query where works_at ?who alpha  select ?who  if $s1
packet: {status supported, rows [ann (conditional [s1]), bob], conditional [s1], used [...], strategy, route reason}
text:   "Ann, if she works there, and Bob."
```

The five reasoning modes `why_not`, `plan`, `abduce`, `conform` and `procedure` are question forms the model may write as the `mode` of a `query`; the model never writes `via`, `trace`, `policy` or an identifier, and never writes `absent`, a knowledge wire, an `amendment` or a governance field (the model-origin compiler rejects them). A closed-world question ("which nodes are not blocked") is a `polarity negated` match on a predicate the author declared `closed`: the host links it first to an explicit `not` fact and then to `absent` over a complete view, answers `refuted` when the atom is not derivable over a complete view and `unknown` otherwise, and renders "no record of" with the source of the closedness. A question with a reasoning mode that no strategy declares is understood and answered `not_computable` with the formalization shown, never answered as a plain `select`. The decoding grammar `tools/sop-gbnf.mjs` lists the five older modes only.

## Words, not operators (owner decisions Q-LANG-1 to Q-LANG-7)

**Principle (owner, 2026-09-28).** Every model construct stays as close to natural language as possible: keyword lines of words, no parentheses and no operator symbols (`?v > 80`, `?t1 < ?t2`, `?x != "Ana"` are never model output). The small model does not think or decide: it writes the best literal approximation of what the message says, and the host and the reasoner deal with the rest. The host lowers the words to its internal operators; trusted circuits may still spell the operators. Model admission rejects `filter` in a model query and any operator symbol (`< > = ! + * / % & |`, parentheses, a spaced `-`) in a model constraint with `operator_not_words` (`sop/declarative.mjs` `checkModelWire`).

| Message | Model form | Host semantics |
| --- | --- | --- |
| attribute value: "how much does X cost", "how old is X", "what time does X open", "cât costă X" (Q-LANG-1) | a match with a value variable: `relation "cost"`, `role subject "X"`, `role object ?price`, `select ?price` (`role time ?v` for a clock time) | the bindings; the lexicon declares the attribute with an integer argument |
| comparison: "over 80", "more than 10 years", "older than Ion" (Q-LANG-1) | `compare ?v above 80`; comparators `above`, `below`, `at_least`, `at_most`, `equal`, `not_equal`; the operand is an integer, a JSON-quoted string or a `?variable` ("older than": two value matches and `compare ?a above ?b`) | each value is read as a number (a string that starts with a number, "2380 lei", counts as it); an ordering comparison with a non-numeric value is `not_computable`; a yes/no question whose known values all fail is `refuted` |
| superlative: "the cheapest", "the oldest" (Q-LANG-1) | `rank lowest ?price` / `rank highest ?age` | the rows with the best numeric value; ties keep all; no numeric value is `not_computable`; valid only over a complete view of the facts (over a partial slice the answer is `incomplete`) |
| ordinal and top-N: "the second largest country", "the three most populous cities" (rules v2.9) | `rank highest ?v position 2`, `rank highest ?v top 3` | `position N`: the rows with the N-th best distinct value; `top N`: the rows among the N best distinct values; ties are never split; a position beyond the distinct values gives no row |
| superlative of a class in a place: "the largest country in Europe", "the most populous city in Canada", "which country has the biggest area in Africa" (rules v2.9) | one query: `be a` with the class, `be in` with the place, the gradable adjective as an attribute match with a value variable (`relation "be large"`, `role subject ?x`, `role object ?v`; for "has the biggest area": `relation "have an area of"`) and `rank highest ?v` (`lowest` for "smallest", "shortest", "youngest", "least") | the linker maps the adjective to a measure through the lexemes of the memory (`config/knowledge/core-en/0200-measures.sop`: "be large" is `area_of`, "be populous" `population_of`); the language layer never decides which measure an adjective means |
| comparative choice: "Which is bigger, Canada or Brazil?", "Who was born first, Einstein or Newton?" (rules v2.9) | the attribute match (`role time ?v` for "born first"), `compare any` over the options (`?x equal "Canada"`), `rank highest ?v` | the option with the best value |
| nested description: "Where was the director of Inception born?", "the capital of the country where Einstein was born", "the population of the capital of France" (rules v2.9) | the inner noun phrase is a query of its own (`relation "be the director of"`, `role subject ?x`, `role object "Inception"`; for a `where` relative clause the clause asked as a where-question plus `be a` with the noun), written first; the outer question takes its answers with `role subject $q` | the host answers the chain; the last query is the answer. Only the question that asks for something nests (a variable in it); "Is Lin the author of X?" stays one fact, and a statement keeps its noun phrase as one value (C9) |
| age at death: "How old was Marie Curie when she died?", "At what age did Newton die?" (rules v2.9) | `relation "die at the age of"`, `role subject "Marie Curie"`, `role object ?age`, `select ?age` | the memory derives the age from the birth and death dates (`lived_years`, rule `r_lived_years` in `0200-measures.sop`); the language layer writes no event and no `when` link |
| superlative of a count: "who closed the most tickets", "cine a vândut cele mai multe bilete" (owner answer to Q-SYM-3) | written literally: the superlative stays in the relation (`relation "close the most"`), the counted noun is the value (`role object "tickets in the L2 queue"`), `select ?x` | `not_computable`: `rank` orders a numeric value, and ranking by a count has no engine |
| "besides Ana", "în afară de Ana" | `except ?x "Ana"` | bindings where `?x` is another entity |
| a value among options: "at BT or UniCredit" | `compare any` with `?bank equal "BT"` and `?bank equal "UniCredit"` lines, then `end` (`all` groups and nesting as in `where`) | the bindings whose value is one of the options |
| quantifiers: "most", "half", "at least 3", "not all", "none" (Q-LANG-2) | `mode every` plus `quantifier most` (`all` default, `none`, `not_all`, `most`, `half`, `at_least N`) | over the known members: `all` as before; `none` supported when every member fails the scope; `not_all` supported by any failing member; `most` more than half supported; `half` exactly half supported with every member decided; `at_least N` at least N supported; an outcome the unknown members could change is `unknown` |
| a quantified statement ("most employees are certified") (Q-LANG-2) | formalized literally: `stated` with the quantified noun phrase as the value ("most employees") | linked like any value; no new construct |
| "before or after", "which happened first" (Q-LANG-3) | two match blocks with `role time ?t1` and `role time ?t2`, `order ?t1 before ?t2` (`after`, `same_time`); yes/no, or `select` when something else is asked | each time variable is the validity interval of its own match (no intersection); `before`/`after` compare the starts, `same_time` asks for overlap; unknown starts give `unknown` |
| elliptical follow-up: "and Priya?", "dar anul trecut?" (Q-LANG-4) | `fragment follow_up` with match blocks that carry only what the message gives (`relation` and `polarity` may be missing) | completed from the previous query of the caller-owned conversation: a given role replaces the same role (or is added to the first match), a given relation or polarity replaces the first match's, a quoted `role time` becomes the query period; without a previous query the host asks "What would you like to know about Priya?". Not an `unclear` kind; the model decides nothing |
| first person: "I work at Acme", "my brother lives in Cluj", "eu", "fratele meu" (Q-LANG-5) | values `"the user"` and `"the user's brother"` for an English message; in a Romanian message the message's own words in the nominative (`"eu"`, `"fratele meu"`), which the host dictionary reads as "the user" and "the user's brother"; everything stated about other people and the case is formalized | "the user" is the caller's entity when the caller-owned context supplies one (`context.user`), otherwise an unresolved surface (host clarification) |
| modality: "is X allowed to sign", "can I park here" (Q-LANG-6) | the modal stays inside the relation phrase: `relation "be allowed to sign"`, `relation "can park"` | linked like any relation |
| advice: "should I negotiate", "is it worth it" (Q-LANG-6) | formalized literally: `relation "should negotiate"`, `role subject "the user"` | `not_computable` (host list `ADVICE_MODALS`: should, ought to, had better, be worth, be a good idea to, be advisable to), with the formalization shown |
| alternatives: "X or Y?" (Q-LANG-7) | one yes/no query per option (`@q`, `@q2`) | each option answered |
| arithmetic: "what is 19% of 2380 lei" (Q-LANG-7) | `constraint` in words, integers scaled by the model: `var ?vat int`, `require ?vat equal 2380 times 19`, `select ?vat`, `task possible` (hundredths); arithmetic words `plus`, `minus`, `times`, `divided_by` with the usual precedence (`times` and `divided_by` first, then left to right; no parentheses), exactly one comparator word per line, and `all`/`any`/`end` groups of such lines | `require ?v equal <numbers>` makes the host compute `?v`; a computation needs no `claim`; `divided_by` and decimal numbers are `not_computable` |

The host's `not_computable` answer repeats the formalization ("I understood the question as: …"), as for any problem without an engine.

## Conventions C1–C14

The independent annotation pilot showed that two careful annotators agreed on the top-level decision for 99% of real messages but on the exact program for only about 40%; the disagreements came from under-specified details (relation wording, value spans, roles, the remark boundary). These conventions close them (source: the wild suite's annotation guide, `eval/reports/history/wild-suite/annotation-guide.md`, adopted by the owner with Q-LANG-1 to Q-LANG-7):

1. **C1 Content words normalized English.** As "Input languages and content words": relation phrases lemmatized and common nouns in the nominative singular (the message is English); time expressions copied as written; proper names exactly as written, including Romanian place, country and institution names ("Craiova", "Primăria Craiova"). Archived targets with Romanian content words are history.
2. **C2 Relation phrase.** The message's predicate words, lemmatized, keeping particles and prepositions ("work at", "move from", "buy from"); an agentless passive keeps the passive with the patient as subject ("be repaired"); a by-agent passive keeps the passive with the agent as `role object`; modals stay inside the phrase ("be allowed to sign", "must register", "should negotiate").
3. **C3 Roles.** Membership in or affiliation with an organization or group ("from the choir", "de la Vertex") is `object`; geographic origin is `source`; "because of X" is `topic`; "at/in a place" after a noun is `location`; means ("with a card", "by car") is `instrument`.
4. **C4 Remarks and first person.** Formalize every assertion about other people, things and the case, and facts about the user as `"the user"` (Q-LANG-5; in a Romanian message the message's own words in the nominative, `"eu"`, `"fratele meu"`, which the host reads as the user). Leave out only the user's own purpose, plans, feelings, apologies, self-description and chit-chat ("sorry for the typos", "I'm tired today").
5. **C5 Coordination.** Split coordinated subjects or objects of a distributive predicate into one proposition each ("Ana and Ion work at X" → two `stated`); an explicitly collective predicate ("together", "co-own", "amândoi pe acte") keeps one conjoined value in the message's words ("Ioana și Sorin").
6. **C6 Question forms.** The question-form table. Tag questions ("…, right?", "…, nu?") are yes/no queries; an offered answer after a wh-question ("Where does she work, Acme right?") is a yes/no query on the offered answer, with the wh-query as an accepted alternative in evaluation data; embedded or imperative questions ("can you tell me", "list all", "spune-mi") are the underlying query; a clause complement ("did anyone confirm whether …") queries the embedded proposition; conjoined clauses inside one embedded question ("do you know if P and Q?") are one query with a `where all` group, and so are two questions under an explicit conjunction frame that asks both at once ("Both at once: does Emma sing in X, and does she plant Y?", "Amândouă deodată: …"); without such a frame, several questions are one query each; greetings and thanks around a question are ignored (owner answer to Q-SYM-3).
7. **C7 Alternative questions.** One yes/no query per option (Q-LANG-7).
8. **C8 Constructs the language did not have.** Superseded by "Words, not operators": comparatives, superlatives and attribute values (Q-LANG-1), quantifiers (Q-LANG-2), temporal order (Q-LANG-3), follow-ups (Q-LANG-4), first person (Q-LANG-5), advice (Q-LANG-6) and arithmetic (Q-LANG-7) have their forms above. A pure action or writing request with no checkable question (book, write, translate, remind) is `unclear kind no_request`; one that also asks something checkable formalizes only that question. A question about the conversation itself ("what did I just say") is `no_request`. A definition question ("what does X mean", "ce înseamnă X") is `select ?m` with `relation "mean"`, `role subject` the term as written and `role object ?m`.
9. **C9 Relative clauses and long noun phrases.** A definite description that names one thing, without a finite verb, stays one value ("the dental clinic on the ground floor of the tall glass building"); a question about an entity through a relative clause ("who approved the report that was sent by the new chief accountant") becomes match blocks that share a variable; a relative clause in a statement is its own `stated` wire that repeats the head noun.
10. **C10 Certainty and speaker.** "I think", "probably", "cred că" → `hedged`; a supposition ("suppose", "să zicem") → `supposed`; "X says that" → `asserted` + `speaker "X"`; "X thinks that" → `hedged` + `speaker "X"`.
11. **C11 Numbers.** Plain integers are integers; amounts with separators, currency, units or decimals stay as written strings ("1.140 euro", "2380 lei"); the host reads a leading number when it compares.
12. **C12 Unclear.** `gibberish` for unintelligible text as a whole; `no_request` as in C8 plus greetings, thanks and small talk alone; `ambiguous` only when the text itself has two readings and none is preferable (otherwise `assumed … basis disambiguation`). A part of a readable message that cannot be formalized is `unparsed` (C14), never `unclear`.
13. **C13 Clauses.** One finite clause is one wire; a whole clause is never a string value. Subordinate, conditional, concessive, purpose, temporal and result clauses are linked with the keyword of their conjunction ("Clauses and links"); coordination (and, or, but between clauses) is one wire per clause without a link; a connective that explains the user's asking ("I ask because …", "Întreb pentru că …") is not a link: its clause is an ordinary `stated`.
14. **C14 Unparsed.** A span the model cannot formalize (jargon, an idiom, a garbled fragment, a reference to an earlier turn) is copied verbatim into an `unparsed` wire, `near` the wire it belongs to and with the `hint` of the slot it probably fills; the role it would fill holds a fresh placeholder `?variable`; the understood parts are formalized normally ("Honest partial formalization").

## Clauses and links (owner decisions L1–L4)

**One finite clause, one wire.** The model splits a compound sentence the way clause analysis does ("analiza frazei"): each finite clause becomes its own short `stated`, `assumed` or `query` wire, and it never stuffs a whole clause into a string value. A subordinate or result clause is related to its main clause by one **link keyword line** `KEYWORD $id`, where `$id` names the related clause's wire. The keywords are the English conjunctions themselves, a closed set kept in one exported table (`sop/enums.mjs` `LINK_KEYWORDS`, so an experiment can swap it); each maps to one semantic type that the host acts on:

| Keyword | Type | English conjunctions | Romanian conjunctions | The linked clause must be |
| --- | --- | --- | --- | --- |
| `because` | `cause` | because, since (causal), as, given that | pentru că, fiindcă, deoarece, căci, că (causal), dat fiind că | a `stated` or `assumed` wire |
| `so` | `cause` | so, therefore, that is why | așa că, deci, de aceea, încât | a `stated` or `assumed` wire |
| `if` | `condition` | if, in case, provided that, assuming | dacă, în caz că, cu condiția să, presupunând că | a `stated` wire with `certainty supposed` |
| `unless` | `negative_condition` | unless | dacă nu, decât dacă, doar dacă nu | a `stated` wire with `certainty supposed` (the clause as written, not negated) |
| `although` | `concession` | although, even though, though | deși, cu toate că, chiar dacă, măcar că | a `stated` or `assumed` wire |
| `so_that` | `purpose` | so that, in order to/that | ca să, pentru ca să, pentru a | a `stated` wire with `certainty supposed` |
| `before` | `before` | before, until (clausal) | înainte să, înainte ca, până să | a `stated` or `assumed` wire |
| `after` | `after` | after, once, since (temporal), as soon as | după ce, odată ce, de când, imediat ce | a `stated` or `assumed` wire |
| `when` | `during` | when, whenever | când, ori de câte ori | a `stated` or `assumed` wire |
| `while` | `during` | while, as | în timp ce, pe când, cât timp | a `stated` or `assumed` wire |

**Placement.** The link line sits on the **main clause** and points at the clause the conjunction introduces ("the rollback failed because the migration is not idempotent": `because $s2` on the rollback wire). `so` is the one exception: it sits on the **effect** clause, the one "so" introduces, and points at its cause ("HID sent the wrong plates, so floor 3 is waiting": `so $s1` on the waiting wire). A link may name a wire written before or after it; references are resolved by name, and links and references form no cycle. On a `query`, the link qualifies the whole question ("if the invoice is paid late, is interest due?": `if $s1` on the query). Link lines are wire-level: a `match` block carries none. At most three link lines per wire.

**`$id` as a role value.** A role value may name another wire of the output instead of a string, at most once per wire:

- in `stated`/`assumed`, `$s` names a `stated`/`assumed` wire: that clause's proposition used as an argument ("is **that** fair", "…, **which** isn't OK there");
- in a query `match`, `$s` does the same, or `$q` names another query that selects exactly one variable: its answers (query chaining, "Who coaches CS Craiova? And where does **he** work?");
- in a `constraint` expression, `$q` is that query's single answer (a scalar).

A relative clause inside one question keeps the shared-variable form of C9; `$q` chains two questions of the message.

**Host semantics (L4).** The atomic propositions always execute as before; links add only what an engine can check, and report the rest:

| Construct | Host behaviour | `clause_links[].status` |
| --- | --- | --- |
| `if $s` / `unless $s` on a query | the supposition `s` (for `unless`, its negation) is consumed through `assume` only by that query; the answer is marked hypothetical when the proof uses it. A supposition that no query links keeps applying to every query of the message | `applied` (`effect: condition_scoped` or `negated_condition_scoped`) |
| `before`/`after`/`when`/`while $s` on a query, `s` with a readable time (a quoted `role time` or `valid`) | the query period becomes until the start of that time, from its start, or during it (intersected when there are several) | `applied` (`effect: until`, `from`, `during`) |
| the same, `s` untimed, or the query already has `at`/`during` | reported | `not_checked` (`reason: untimed`, `query_has_time`) |
| `because`, `so`, `although`, `so_that` on a query | reported with the answer ("Not checked: because: …") | `not_checked` (`reason: no_engine`) |
| any link on a `stated`/`assumed` wire | reported in the host sentence of the statement ("You stated: …, because: … [not checked].") | `not_checked` (`reason: statement_link`) |
| a statement that carries `if`/`unless` itself ("if it rains, the match is cancelled") | conditional: reported only, never evidence, never carried | `not_checked` |
| `$q` in a query | the host inlines `q`'s conditions, renamed apart, with a fresh variable in place of `$q` (a join); `q` is also answered | — |
| `$q` in a constraint | `q`'s selected variable as a projected scalar (DS004 `output ?x one`); several answers ask for clarification | — |
| `$s` in a query | `not_computable` with `understood_as` showing the referenced clause in brackets | — |
| `$s` in a `stated`/`assumed` wire | reported with `predicate: null`; never blocks the turn | — |

**Admission** (`sop/parser.mjs`, `sop/clauses.mjs`): `link_form` (a link line takes exactly one `$id`), `link_too_many` (more than three), `link_duplicate`, `reference_multiple` (more than one `$id` role value in a wire), `link_reference_unknown` / `reference_unknown` (no such wire), `link_self_reference` / `reference_self`, `link_target_type` (a link names a `stated` or `assumed` wire), `link_condition_not_supposed` (`if`, `unless` and `so_that` name a `stated certainty supposed` wire), `link_conflict` (one clause under both `if` and `unless`), `reference_target_type` (a statement's `$id` names a `stated`/`assumed` wire; a query's may also name a query), `reference_query_not_single` (a chained query selects exactly one variable), `link_cycle`.

## Honest partial formalization: `unparsed`

The small model formalizes what it understood and says what it did not, instead of giving up or inventing (owner decision of 2026-09-29; on the wild suite the fine-tuned models give up on 2–9% of content rows but corrupt about 15% of names and invent about 8% of values).

| Keyword | Cardinality | Values | Meaning |
| --- | --- | --- | --- |
| `span` | exactly once, required | one JSON-quoted string of at most 200 characters | A verbatim part of the message that the model could not formalize (`unparsed_span_form`); the agent guard requires it to occur in the message after case and whitespace folding (`unparsed_span_not_in_message`). |
| `near` | at most once | `$id` of a `stated`, `assumed`, `query` or `constraint` wire | The wire the span most likely belongs to (`unparsed_near_unknown`, `unparsed_near_type`). |
| `hint` | at most once | `subject` \| `object` \| `time` \| `location` \| `value` \| `relation` \| `reference` \| `other` (`UNPARSED_HINTS`) | The slot the span probably fills: a role, a value, the relation of the `near` wire, a reference to something said earlier, or other. |

**Target conventions (for the generator and the annotators).**

1. Formalize every understood part normally; add one `unparsed` wire per span that could not be formalized (jargon, an idiom, a garbled fragment, a reference to an earlier turn such as "aia", "el", "de mai devreme", "that one"). Several `unparsed` wires are allowed; two with the same span are not (`unparsed_duplicate`).
2. The span is copied verbatim: the shortest contiguous part of the message that carries the unknown slot, without the surrounding function words that the formalized part already covers.
3. When the span is the value of a role, that role holds a fresh placeholder variable (`role object ?x`, also in `stated` and `assumed`), and the `unparsed` wire names the wire with `near $id` and the role with `hint` (`subject`, `object`, `time`, `location`, or `value`/`reference`/`other` for any role when it is the only such span near that wire). An unpaired placeholder in a `stated`/`assumed` wire is rejected (`proposition_not_ground`). In a query, the placeholder is a non-selected variable of the role named by the hint.
4. When the span is the predicate, the wire keeps the model's best relation phrase (the message's words, normalized) and the `unparsed` wire has `hint relation` and `near` that wire.
5. The `unparsed` wires follow the wires they belong to. `unclear gibberish` and `unclear no_request` remain for whole messages only; an output may consist of `unparsed` wires alone when nothing could be formalized in a readable message.

**Host repair (`sop/repair.mjs`), before linking.** For each span, in order: dates and times (the host's time normalization); numbers, money and units ("12", "doisprezece", "1.140 euro" → `"1140 EUR"`, "2380 lei" → `"2380 RON"`, "12,5 km"); a reference to the conversation, resolved from the caller-owned context (the quoted values of the previous query) only when there is exactly one candidate; a proper name (capitalized words, or a surface the host lexicon knows as exactly one entity); the dictionary (a common noun with one reading, or the one the lexicon accepts). A `relation` span is tried as a relation phrase of its `near` wire during linking. A resolved span fills its placeholder and is reported in `repairs` (`unparsed`, `span`, `hint`, `near`, `wire`, `role`, `method`, `value`, `filled`). An unresolved span becomes **one targeted clarification question** ("Which date or period do you mean by …?", "La cine sau la ce vă referiți prin „…”?") in `unresolved_spans` (`blocking` when a placeholder depends on it): only the wires that need it (and the queries that name them) are held back and reported as `treatment: incomplete`; every other question of the message is answered, and the questions follow the answers (`next: answer_clarification`). When every problem is held back, the turn is one clarification (`reason: unresolved_span`).

## `constraint`

A model `constraint` must state `task` (`prove` \| `possible` \| `optimize`): `prove` and `possible` give opposite readings of the same claim, so the choice is never a silent default (`constraint_task_required`). Trusted circuits keep the `prove` default. Constraints are numeric and need no linking. A model constraint writes its comparisons and arithmetic in words (`require ?x at_least 5`, `claim ?x equal 12`, `?a times 19`; see "Words, not operators"); a computation that `select`s its result needs no `claim`.

## `unclear`

| Keyword | Cardinality | Values |
| --- | --- | --- |
| `kind` | exactly once, required | `gibberish` \| `no_request` \| `ambiguous` |
| `reading` | 2–4 lines with `kind ambiguous`, none otherwise | one JSON-quoted short paraphrase of a candidate reading, in the message's language (names as written) |
| `language` | at most once | `en` \| `ro` |

The model does not reason, so it reports only what it can recognise from the text: `gibberish` (unintelligible text), `no_request` (neither a statement nor a question: "ok", "thanks", a greeting, or a request for something unrelated such as "write a poem") and `ambiguous` (owner decision Q-ARCH-1): the text itself shows two or more readings and none is clearly preferable — a pronoun after two parallel clauses, a bare homonym ("Is the court free?"), the scope of "all … not", a prepositional-phrase attachment. When one reading is preferable the model resolves it with `assumed` (`basis disambiguation`) instead; resolved ambiguity is the common case. The scope of "all … not" ("All the invoices were not paid", "Toate coletele nu au ajuns") is the exception: it is always `ambiguous`, with one reading for "none" and one for "not all", even when the rest of the message makes one reading likely, because choosing would need reasoning about the situation (owner answer to Q-SYM-3, 2026-09-29); an explicit "not all" or "none" is not ambiguous (`quantifier not_all`, `quantifier none`). The host lists the readings, numbered, after the fixed reply, and the packet adds `readings` and `next: 'choose_reading'` (`unclear_readings` rejects fewer than two, more than four, repeated, empty or unquoted readings, and readings on another kind). A semantically odd but readable message is formalized normally; the model does not judge contradictions, completeness or relevance. `unclear` must be the only wire of the output (`unclear_not_alone`). The host executes no circuit and renders the fixed reply for the kind from the single table `UNCLEAR_KINDS` in `sop/unclear.mjs` (English and Romanian); the packet is `{kind: 'unclear', status: 'unclear', unclear_kind, language, next: 'rephrase'}`. Renaming or adding a kind changes that table, this section and the help page only. `language` selects the reply language only when the caller selected none.

`unclear` differs from `clarify`: `clarify` remains host-generated and never model-authored (DS004; see "Scope, non-goals and extension checklist"); it asks for a relation, entity, date or scalar that the host could not link or determine for a formalized problem. `unclear` is the model's report that there is nothing to formalize.

## No model refusal

The model always formalizes a readable request; there is no model-level `unsupported`. When the host has no engine for a formalized problem (the reasoning route returns `unsupported` for a model-origin problem), the answer is `status: not_computable` with `engine_status: unsupported`, `understood_as` (the one-line canonical formalization) and the controlled reply "I understood the question as: …. I cannot compute this kind of answer yet." (Romanian: "Am înțeles întrebarea astfel: …. Încă nu pot calcula acest tip de răspuns."). The formalization is also in the trace. The only `unsupported` result that remains is AGENTS rule 8 in trusted circuits: an explicitly requested, unavailable backend, reported with `route.backend` and `fallback: null`. How the reasoning engine will treat the formerly blocked families (see "Is the current construct set sufficient?") is not decided by this specification.

## Prompts

The prompt of a model that writes SOP Lang is the user's text alone (`barePrompt(text)` in `eval/llm.mjs`, used by the archived FormalizerLLM evaluation tools; the chat has no prompt choice and the SymbolicLM service reads no instructions: the `formal` prompt profile and `server/prompts/formalizer.txt` were removed on 2026-10-01). It includes no `CONTEXT` block, earlier turns, carried statements, a pending clarification or the host clock. Because the model sees no pending clarification, an answer to a host question is formalized from the new message alone; the host keeps the pending authored SOP in the packet.

### The copula

"Is" has five readings, and SymbolicLM writes each one so that the host can link it (owner request 2026-10-01, after "I do not know the relation 'be'" in the chat). The host side is the declared copula readings of the base memory (`reading class|occupation|attribute|identity|location|describe` and `describe_rank` on a `predicate` wire, `COPULA_READINGS` in `sop/enums.mjs`): the linker names no predicate itself.

| Sentence | Model form | Host reading |
| --- | --- | --- |
| "Who is Ada Lovelace?", "What is Python?" (identity, description) | `relation "be"`, `role subject "Ada Lovelace"`, `role object ?x`, `select ?x` | `describe` (ranked by `describe_rank`) |
| "Ana is a doctor.", "Is Paris a city?" (class membership; SymbolicLM v2.7) | `relation "be a"`, `role subject "Ana"`, `role object "doctor"`: the article inside the relation, like "be a member of", and the class noun without article as the object | `class` or `occupation`, tried in order (see "KnowledgeLinker: the copula and the relation lexicon"); never an unknown relation |
| "Paris is the capital of France.", "Who is the CEO of Acme?" (a role relation) | `relation "be the capital of"`, `role subject "Paris"`, `role object "France"` | an ordinary relation phrase: the predicate's alias (world-v1 `capital_of`) |
| "Ana is sick.", "Is Ion certified?" (attribute or state) | `relation "be sick"`, `role subject "Ana"` | an ordinary relation phrase (or the `attribute` reading) |
| "Ana is in Cluj.", "Where is Ana?" (location) | `relation "be in"` with `role location "Cluj"`; the question is `relation "be"` with `role location ?place` | "be in" is the alias of `located_in`; the bare "be" with a location role takes `location` |

The model never writes a predicate name: "doctor" is a string, `is_a` and `occupation` are the host's. The corpora contain no copular class or identity sentence, so these forms are tested on recorded parses (`tests/ud-to-sop-v27.test.mjs`) and executed end to end (`tools/eval/query-surface/execute.mjs`, cases `copula-*`).

### KnowledgeLinker: the copula and the relation lexicon

The **KnowledgeLinker** (name pending the owner's confirmation; `sop/linking.mjs`, `sop/copula-linker.mjs`, `sop/relation-lexicon.mjs`) links the words of a message to the predicates of the chosen base memory. It is deterministic, never guesses beyond reviewed data and explains each reading it takes. The failure the owner saw ("I do not know the relation 'be'") was in this layer, not in SymbolicLM: the parse (`relation "be"`, `role object "a doctor"`) was right, no predicate carried the string `be`, and the default base memory held no knowledge.

**What the code knows and what the memory declares.** The code knows six closed readings (`COPULA_READINGS`): `class` (Paris is a city), `occupation` (Ana is a doctor), `attribute` (Ana is happy), `identity` (Mark Twain is Samuel Clemens), `location` (Paris is in France) and `describe` (the facts that answer "Who is Ana?"). It names no predicate. A base memory declares which of its predicates carry a reading on the `predicate` wire (`reading NAME`, repeatable, and `describe_rank N` for the order of the describing predicates), validated by `sop/lexicon.mjs` and by the knowledge grammar (`sop/knowledge/grammar.mjs`, `docs/wire_typs/predicate.html`). A memory without these lines answers honestly with a question; it never gets a guessed predicate. World-v1 declares its readings in its mapping table (`tools/world-kb/mapping.mjs`, `READINGS`).

**The relation lexicon** (`config/relation-lexicon.json`, loader `sop/relation-lexicon.mjs`) is reviewed language data, the only place such words live: the copula verb forms (English `be`, Romanian `fi`, `este`), the articles, the locative phrases (`in`, `located in`), the occupation nouns and the attribute adjectives (English and Romanian, accent-folded), and `relations`, extra relation phrases a base memory maps to its own predicates (`{relation, lang, predicate}`; an entry whose predicate the memory does not declare is inert). The shipped file names no predicate (`relations` is empty); a base memory may ship its own file of the same shape, which extends it (`RelationLexicon.extend`). The lexicon is the review: a phrase it does not cover and no predicate alias covers stays `unknown` and the user is asked; Romanian relation phrases still go through the dictionary of "Input languages and content words".

**Order of linking for one relation string.** (1) A predicate whose id, alias or description equals the phrase, then a relation-lexicon entry: `be the capital of` links to `capital_of` by its alias, `be in` to the memory's `located_in` alias; the roles must fit the declared roles. (2) Only when that does not bind and the string is a plain copula (`be`, `be a`, `be an`, `be in`, `be located in`, Romanian `fi`, `fi un`), the readings below.

| Message | Model form | Readings tried, in order | Result |
| --- | --- | --- | --- |
| "Who is Ana?", "What is Paris?" | `be`, `subject "Ana"`, `object ?x` | `describe`: every predicate that declares it, by `describe_rank` then id | an `any` group over those predicates with the same `?x`; the answer is the union of their facts |
| "Ana is a doctor.", "Was Leonardo a painter?" | `be` with `object "a doctor"` (or `be a` with `object "doctor"`) | indefinite noun: `occupation` when the noun is an occupation noun of the relation lexicon, then `class` | statement: the first reading that has exactly one predicate (several: a question that lists them); question: all readings that have a predicate, as an `any` group, so the knowledge decides |
| "Ana is happy." | `be` with `object "happy"` | a one-argument predicate named after the adjective, if declared; else `attribute` | `tall ana`, or `has_property ana "happy"` in a memory that declares `attribute` |
| "Mark Twain is Samuel Clemens." | `be` with a capitalized name as object | `identity` | `same_as` of the memory |
| "Where is Paris?", "Is Paris in France?" | `be in`, `be located in`, or `be` with `role location` | `location`; the object role is renamed to the predicate's second role | the memory's location predicate |
| "Ana is not a doctor." | any of the above with `polarity negated` | as above | the same atom, negated |

Every linked copula is reported in the packet as `copula_readings` (wire, relation, the readings tried with the predicates each found, the reading taken, the alternatives), so the reading is inspectable. A definite noun phrase ("the doctor"), an unknown class noun or no declared reading never produce "unknown relation be": an unknown noun is an entity question ("Which entity do you mean by "flibber"?"); a definite phrase or a missing reading lists the declared readings ("Do you mean: Ana is a kind of "the doctor" or …?"); a memory without a describing predicate asks "Do you mean what Ana does, or who Ana is related to?"; a memory without a location predicate says so. Tests: `tests/knowledge-linker-copula.test.mjs` (a hand-made knowledge base, SymbolicLM-shaped programs through the Runtime and the js-reference oracle).

### KnowledgeLinker: scoring and ambiguity

Since linking milestone M3 (`sop/knowledge-linker.mjs`, used by `sop/linking.mjs`, `sop/propositions.mjs` and `sop/declarative.mjs`) the KnowledgeLinker is a **scored, per-base-memory, joint linker**. SymbolicLM stays knowledge-blind; the lexicon (the `predicate`, `lexeme` and `entity` wires of the memory's circuits, DS004 "Lexicon wires") is knowledge. For one proposition the linker builds the candidates of the relation phrase and of every role string and decides them together:

| Signal | Applies to | Score or effect |
| --- | --- | --- |
| form authority: a lexeme form, label, alias or id equals the phrase | relation | 100 |
| the memory's gloss of the predicate equals the phrase | relation | 90 |
| a reviewed relation-lexicon phrase reaches a predicate the memory declares | relation | 80 |
| the host dictionary: canonical translation, other translation, English synonym, phrase of a nearby unparsed span | relation | 90, 85, 80, 70 |
| same head verb, other particles ("work for" for "work at"); queries only, never a stated or assumed proposition | relation | 50 |
| role class: an entity the message names in a role is of the class the role declares | relation, entity | +10; an entity of another class is a hard clash |
| `restrict ROLE CLASS` of the matching lexeme is violated by an entity of the message | relation | hard clash |
| the predicate's `domain` is the domain of an entity of the message | relation, entity | +3 |
| facts in the memory: only some of the equally good readings have `holds` facts (the lexicon counts them per predicate, `predicate.factCount`) | relation | decides (`facts`); the head-verb tier only offers predicates with facts |
| lexeme `weight` (1 to 10; no weight counts as 5) | relation | decides between equal forms; adds `weight - 5` to the reported score |
| a declared role a query leaves open | relation | -2 each |
| the entity is at least four times as notable as the next namesake | entity | +5; orders options, never decides alone |

Scores are integers so that reports can show them. The decision runs in named stages and the stage that decided is reported as `decided_by`: `only_candidate`; `constraint` (hard clashes removed all but one; a constraint never removes the last candidate); `form_tier` (the best form authority leads by `MARGIN` = 10); `facts` (only some of the equally good readings have facts in the memory: a predicate that cannot answer anything there loses to one that can); `weight` (distinct declared lexeme weights, which the lexicon validator demands for a shared form); `evidence` (class support and coherence lead by `MARGIN`); `class` (for entities, exactly one namesake is of the role's class). When the stages do not separate two or more candidates the linker returns an **ambiguity**, never a guess: a relation is `ambiguous` with its candidates (`required[].scored` lists their scores) and the question names them; an entity surface that names several entities becomes the issue `{kind: entity, status: ambiguous, candidates: [{id, label, class, score}]}` and the question reads "Which entity do you mean by "Paris": Paris (city) or Paris (person)?". The measured result (judged open-vocabulary questions on world-v1 with core-en; the numbers and their caveats are in the report of `eval-linking-v1`) is that merged vocabularies with parallel general and specific predicates are the main source of wrong links, not the scorer. A role that declares a class also accepts an entity of a subclass (`is_a` closure), bound by its id. Evidence about a particular entity (a fact of the predicate that mentions it) is not yet a signal; it needs the repository and belongs to the slice interface. The report entry of a relation also carries `facts`, the number of facts the memory holds for the bound predicate.

**Role relabeling, converse frames, frames, boundaries and names (linking R2, `eval-linking-v2`).** These rules close gaps between the words SymbolicLM writes and the names the memory declares, all by principle and all reported:

- *Single-oblique relabeling* (`sop/propositions.mjs`). A memory names the roles of its predicates (`died_in` takes a `location`, `death_year` a `time`); SymbolicLM names a role by the preposition it saw. When a relation phrase reaches predicates whose roles do not fit, the linker looks for the case that exactly ONE used role name is not declared and exactly ONE declared role is not used, neither being the subject; that role is renamed. The rename counts only when exactly one renaming links the proposition (two readings are a `role_mismatch` as before). The `linking` entry of the relation carries `relabeled {from, to}`.
- *Frame tier* (`sop/frames.mjs`, owner answer Q-SYM-2). When a relation phrase does not link as written (and is not a copula), the reviewed frames (synonyms, Romanian surfaces, single-oblique role relabeling; the `synonym` and `role` levels only) rewrite the proposition BEFORE the dictionary tiers, and the rewrite counts only when the lexicon then links it to a predicate that has facts (like the head-verb tier, a synonym tier only reaches readings that can answer). Without these two guards it turned clarifications into wrong links on the dev half ("be" to `costs`, "win" to `salary`, "touch" to `repairs`); with them it changes no link of the dev half, so it is a safety net, not a recall lever. The packet reports `frame_changes` (`wire`, `from`, `to`, the individual `changes`, the `predicate`), the relation also appears in `translations` with `source: frame`, and its `linking` entry has `via: frame`. The strict link (`dictionary: null`, or `frames: false`) never uses frames, so strict scoring stays free of them.
- *Converse frames* (`sop/knowledge-linker.mjs`, `sop/propositions.mjs`). A `lexeme` whose `frame` lists the object role first ("name of", "be the currency of") is a converse: when every applicable lexeme of the matched form is a converse and the clause has exactly a subject and an object, the two are swapped before the atom is built, the constraints are read again with the values in their new roles, and the swap stands only when the same predicate still binds. The `linking` entry carries `converse: true`.
- *Integer roles* (`sop/propositions.mjs`). A name in a role the predicate types as an integer ("Population of Qena": the name came as the object) moves to the ONE free declared role (`relabeled {from, to, reason: type}`); what is left is the issue `type_mismatch` (role, value, expected type) with a precise question, never a failure when the atom is built. A class clash of an entity role stays an entity question.
- *Relation/object boundary* (`shiftBoundary` in `sop/propositions.mjs`). "be the head of" with the object "state of France" becomes "be the head of state of" with "France" when the lexicon declares the longer form, the whole object string names no entity and the rest does. One possible shift only; the entry carries `boundary {from, to}`.
- *Namesake descriptions* (`sop/lexicon.mjs`). The `description` facts of the memory are kept on the entity (160 characters) and an entity clarification names each namesake with it ("Paris (capital and largest city of France) or Paris (city in Texas)"), the class otherwise; the issue candidates carry `description`.
- *Leading article* (`sop/lexicon.mjs`). When a whole entity surface finds nothing, a leading English article is dropped and the lookup is retried ("the United Kingdom" finds the label "United Kingdom"); a label that carries the article is found first.

**Chat turn and circuit rules.** The rules of the memory's circuits (`rule` wires of the base memory and the accepted session circuits: `located_in` transitivity, container rules) reach the chat turn's query side the same way they reach `POST /v1/sessions/{id}/query`: the session runtime hands the Agent a `circuitRules` function (`reasoning/slice` `Theory.chatRules`, memoized per circuit digest), `Runtime.rules` adds them to the approved library's rules, and the slice planner selects those that can reach the query. Rules with a negated body atom, defaults, aggregates and integrity constraints are not carried (they stay with the oracle path of the session query).

**Evaluation hygiene.** Parts 2 and 3 of `eval/suites/linking-v1` were looked at while the M3 linker was tuned, so the numbers of `eval-linking-v1` are on the full, partially seen set. Since `eval-linking-v2` they are split by form (part x gold relation, or "ask") with a fixed seed into a `dev` half (tuned on freely) and a sealed `test` half (`eval/suites/linking-v1/split.json`, `tools/eval/linking-split.mjs`; `tools/eval/linking-open.mjs run --half dev|test|all`); the sealed half is measured once, at the end.

**Report.** Each `linking` entry of the packet gains `score`, `decided_by` and `scored_alternatives` (`[{id, score, tier, weight?, rejected?}]` for a relation, `[{id, score}]` for an entity); the existing fields (`wire`, `kind`, `surface`, `symbol`, `via`, `form`, `match`, `class`, `alternatives`) keep their meaning, so consumers of the report are unaffected. The chat panel shows "score 100 by only_candidate; alternatives: manages_team (110)".

**Measurement.** `tools/eval/linking-suite.mjs` (part 1, mechanical labels: the generated-world floor) and `tools/eval/linking-open.mjs` (parts 2 and 3: open-vocabulary questions labelled by judge consensus, `tools/linking/judge/`) run the arms `exact` (the M1 linker), `scored-no-head`, `scored` and `scored@world-only` through `configureLinker`; preregistered as `eval-linking-v1`.

## SymbolicLM: the symbolic formalizer

**SymbolicLM** (`lib/symbolic-lm/`, chat registry entry `symbolic-lm`, [DS012](specsLoader.html?spec=DS012-local-server.md)) is the current formalizer: Stanza grammatical analysis plus the UD-to-SOP rules, packaged as one component with one API. It returns the grammatical `analysis` and, at a later stage, SOP Lang. It stands in the small model's place and is evaluated on clean English. It obeys the same boundary as the small model — its only input is the message, it writes the model language of this specification, it never reasons and never refuses — and it owns exactly three things:

1. **UD parsing.** The message (or its translated English form) is parsed by the Stanza model of its language. The English package is a configuration of SymbolicLM (`config/symbolic-lm.json`, key `stanza.package`, overridden by `CHATSOP_STANZA_PACKAGE`): `accurate` (the default since the owner decision of 2026-09-30 and experiment `eval-symbolic-accurate-adopt-v1`: Stanza `default_accurate`, electra-large POS, dependency parser and NER, with the default package's `combined_nocharlm` lemmatizer because the charlm one lemmatizes "leases" as "leas") or `default` (the charlm models, kept installed). One worker (`training/python/ud_parse_worker.py`, options `--en-package`, `--en-dir`, `--hf-home`, `--lemma-model`) serves both; the Romanian pipeline and the sentence splitter do not depend on the package. The model id of the analysis (`analysis.parser`, `stanzaModelId`) names the package. On the GPU `analyzeMany(messages, options)` parses a batch in one pass and answers exactly like single `analyze` calls.
2. **Generate SOP Lang from the grammatical analysis.** The parse is converted by the UD-to-SOP rules of `lib/ud-to-sop/`. Every value of a translated program is mapped back to the verbatim message span its English words came from (`mapValues`), so values stay spans of the message as in the direct route; a pronoun the translation inserted for a Romanian pro-drop subject leaves the role open. Relations stay English (rule 6 of "Input languages and content words").
   The rules are written for the accurate parse only (rules v2.7, `lib/ud-to-sop/`, frozen in `eval/reports/history/baseline-ud-rules/frozen-rules-v2.7`; the v2.6 rules are frozen in `frozen-rules-v2.6`; the v1.6 rules, written for the default parser's tree shapes, are frozen in `eval/reports/history/baseline-ud-rules/frozen-rules-v1.6`). Where the accurate parser attaches a construction differently, a tree repair (`lib/ud-to-sop/repair.mjs`) brings it to the shape the rules read, using function words, part of speech and morphology only: a question word or phrase under a wrapper verb or noun (`do you know why …`, `since when`, `how many times`, `the date since when …`, `any idea …`), a passive `be` with its participle, a stranded preposition under a copula, adjacent names split into two subjects, dates and months, "other than", "how come", a verb tagged as a noun, vague time phrases. **Admission drops wires, not messages** (v2.6): when the program is inadmissible the host drops links and references, then the offending wires one by one (a repeated identical statement, a bad reference), the bound being the wire count before dropping; the `fallback` outcome (`unclear no_request`) is reserved for a program with no admissible wire left, so one bad sentence never erases the wires of the good ones. **File names and paths** (`@questions.md`, `docs/wire_types.html`, `tools/x.mjs`) are one name word (`lib/ud-to-sop/filenames.mjs`, applied to every parse of `SymbolicLM`), never split at the dot or the slash. The interpretation marks a sentence `partial` when its restatement leaves a span of the sentence out (`not represented`). A repair that never changes an output on the development rows is dead and removed (the v1.3 re-rooting of a predicate noun under a wh word and the copula-plus-preposition repair were).
   **Query forms of the rules (v2.7, owner priority 2026-10-01).** `lib/ud-to-sop/reasoning-forms.mjs` and the query rules of `analyze.mjs` read the question forms of "Question forms" from the UD tree (function words, lemmas, part of speech, morphology; never a lexicon of the knowledge) and write the message's own words. `why_not`: a modal negative "why" ("Why can't I hard-reset the router?", "Why isn't Ana allowed to approve X?") writes the claim affirmed and drops the modal (the mode says "can"), and "What is stopping/preventing X from V-ing?", "What is missing for X to be approved?", "What would it take for X to V?" take the blocked clause as the claim; "Why isn't Ana a member?" and "What is the reason that X doesn't Y?" stay `explain` with a negated claim (the corpus convention). `plan`: "How do/can/should I|we|one V X?", "How to V X?", "What are the steps/the way to V X?", "What do I need to do to V X?" take the goal as the claim with the asker as `"the user"`; a third-person "How does Ana commute?" stays an instrument question. `abduce`: a modal ("could", "might", "may", "would") with explain, cause, trigger or account for, "What could be the cause of X?", "What may be behind X?" take the observation as the claim, a noun observation being the subject of `relation "occur"`; "What caused X?" without a modal stays a select. `procedure`: "What is the procedure/process/protocol for V-ing X?" and "What is the reset procedure?" take the task (a gerund repaired to its base form, or the compound word with an unselected `?x`). `conform`: following, observing, complying with or violating a procedure, or being compliant, keeps the literal match under `mode conform`. Beyond the reasoning modes: "Which teams have only certified players?" is a grouped universal (`mode every` with `select`, the members' relation as the restriction and the property as the scope); an explicit "both" ("Both at once: A, and B?", "Does Ana both work at X and live in Y?") makes the yes/no clauses of that sentence one conjunction (`where all`, rules v2.8), and nothing else does: coordinated questions follow the grammar only, so each question clause ("Does Ana go to X and does she attend Y?", "Does he play for X? Also, does Costin have an allergy?") is its own query, the same subject or not, and a clause with a period of its own is never merged; predicates conjoined inside ONE clause ("Does Ana work at X and live in Y?") stay one conjunctive query by their grammar (v2.8 removed the v2.7 same-subject heuristic: the host asks several queries and answers each, which is the correct reading of two questions); "go to the jazz evening" names an event, not a time, and its place phrase is the object; a measured amount is a value variable ("Does X cost more than 30000 lei?" is `object ?price` with `compare ?price above 30000`, and "at least" is a comparison here, never a quantifier); "at any point in 2025" is `overlaps "2025"` (the model-surface field of DS004, run by the host as its overlapping `during` window); "What time does X open?" is `relation "open at"` with `role time ?hour`; "What is the reason that P?" explains P; "Who is a parent of a parent of X?" chains through a variable; "any employee of X" in a yes/no question is an existential variable restricted to its class; "still" and "again" add the presupposition as `assumed … basis implicature` (kept in v2.8: a question that says "still" or "again" assumes the state it asks about, so the baselines carry the `assumed` wire); a trailing "Can you explain that?" asks nothing checkable; "X is a Y" is `relation "be a"` with the class noun as the object ("The copula"). "What if P, Q?" supposes P and queries Q (`if $s`); a bare "What would happen if P?" keeps the plain verb of the open question. Evidence: `eval/reports/current/query-rules/` (`results-before.jsonl` and `results-after.jsonl` per question, `judged.json` the LLM judge, `regression-diff.md` every changed row of the regression, `execution.json` the end-to-end check on js-reference), `tests/ud-to-sop-v27.test.mjs` (recorded parses), `tools/eval/query-surface.mjs` and the authored probes `tools/eval/query-surface/probes.mjs`.
   **Measure and chain question forms (rules v2.9, owner priority 2026-10-01).** `lib/ud-to-sop/measure-forms.mjs` (hooked into `Analysis.query` after the reasoning forms) reads the degree features of the UD tree (never a lexicon of the knowledge) and writes the forms of "Words, not operators": superlatives and ordinals of a class in a place (`rank highest ?v [position N]` with `be a`, `be in` and an attribute match; "has the biggest area" writes `have an area of`), comparative choices over a pair (`compare any` + `rank`; "born first" ranks the `time` role lowest), the age at death (`die at the age of`) and the nested noun phrases of a question (`nestDescriptions`: "the N of Y" with a named Y, and "the N where P"; the inner query is written first and the outer takes `$q`). Adjectives whose superlative is the lowest value (small, short, young, low, light, narrow, cheap) are a closed grammar class of the rules (`LOWEST`), like the existing "less". What a gradable adjective measures is knowledge, declared by lexemes of the memory (`0200-measures.sop`); an adjective with no lexeme ends in a clarification, never in a guessed measure. English only: the rules receive English (owner decision 2026-10-01). Counted classes ("How many films did X direct?") keep the v2.8 form without a class block, so existing rows do not change; replay of the 8049 symbolic_english rows changes one row (`wild_we_069`, "the most senior partner in the Bucharest office": now a `rank` over "be senior").
   **Rules budget (termination, 2026-10-01).** The rules always end. (1) Every tree repair of `lib/ud-to-sop/repair.mjs` runs guarded: a repair that leaves a head cycle is undone and named in `repairs.rejected`; TR-NAME heads a span only with a word that has no ancestor among the span's other outside-attached words ("How many Billboard Music Awards did …" once closed a cycle and hung the service). (2) `indexSentence` cuts any remaining head cycle (a parser or future rule error) and reports `cycleCuts`, so every walk of the tree is bounded by the sentence length. (3) `Analysis` counts its clause calls and checks a wall-clock deadline (`RULES_BUDGET`: 20000 calls, 3000 ms); beyond it `convertParse` ends with outcome `budget`: one `unparsed` span holding the message, `valid`, which the service reports as uncertain. The budget is cooperative (no worker thread): a thread hop per call would cost more than the rules themselves (median 0.4 ms) and every loop is bounded by construction. `node tools/ud-rules-fuzz.mjs [--collect]` replays the rules over recorded parses of every message of `datasets/` and `eval/suites/` and fails on a budget hit, a throw or a cyclic tree; `tests/ud-rules-termination.test.mjs` holds the Jonas Brothers case. The output of the rules is unchanged (replay of the 8049 symbolic_english rows: all `same`), so the rules version stays v2.8.
3. **The uncertainty signal and routing.** `direct`/`translate`/`auto` route selection and the reasons a formalization may be unreliable (below).

Per-token language identification and symbolic spelling correction are LanguagesUtil's job, and translation toward English is TranslatorService's job (both below, owner decision 2026-09-29); SymbolicLM calls them, it does not implement either itself.

Routes: `direct` (the message parsed in its own language and converted by the rules, Romanian lemmas kept) and `translate` (Romanian parsed, translated through TranslatorService, English text parsed and converted). The default routes (`DEFAULT_ROUTES` in `lib/symbolic-lm/index.mjs`) are `direct` for English and for monolingual Romanian and `translate` for mixed messages (measured in `eval-symbolic-lm-v1`, revisited per message class by `eval-translator-compare-v1` on 2026-09-30, see "TranslatorService" below). Translation is therefore a secondary route: bad input is meant to reach SymbolicLM as acceptable English through textToCleanEnglish; gibberish, pure requests and labelled simple texts keep the direct outcome.

**API.** `createSymbolicLM(options)` starts the component; `analyze(message, {route, language, spell, values, rewrite, rewriteWhen})` returns `{sop, valid, route, language, outcome, english, uncertain, reasons, uncertainty, analysis, trace}` (`analysis` is the grammatical analysis finally used, `{parser, columns, language, sentences: [{text, start, end, tokens}]}` with one `[id, form, lemma, upos, head, deprel]` row per token, `parser` the Stanza model id, null when nothing was parsed; DS008 "Three datasets" stores it and `tools/symbolic-regression.mjs` compares it; `english` is the English text finally parsed, null on a direct non-English route or when a Romanian direct outcome was kept before translation; `uncertain`/`reasons` are the shorthand of `uncertainty.uncertain`/`uncertainty.reasons`); `toEnglish(message)` returns the English rendering alone (`{text, language, untranslated, spelling, pieces}`). The trace holds the language label of every token, the spelling changes, the English text with each piece's source words, the dictionary decisions, the Romanian and English parses, the rule outcome and notes, the value mapping and the `unparsed` spans. `tools/symbolic-lm.mjs` offers `analyze`, `english` (single or batch JSONL) and `serve` (the chat service).

**Parse device (owner request 2026-10-01).** The Stanza worker takes `device` `auto`, `cuda` or `cpu` (`lib/ud-to-sop/device.mjs`, `lib/ud-to-sop/stanza.mjs`; `CHATSOP_UD_DEVICE`). `auto` picks `cuda` only when `nvidia-smi` lists a GPU, `models/.training.lock` is absent, no `/opt/trainer/bin/python` process runs and no other GPU parse worker is alive; otherwise the CPU. At most one GPU parse worker runs at a time: it holds `models/.parse-gpu.lock` (its pid; released on stop and on exit; the lock of a dead process is taken over), and a second worker, even an explicit `cuda` one, falls back to the CPU. Nothing is ever killed. `auto` is the default of the batch tools (`tools/symbolic-regression.mjs` `record-parses` and the live run, the analysis cache `analyseTexts`, the eval scorers `decomposition-score`, `stability`, `severity-local`, `analysis-compare`); the chat's SymbolicLM service keeps `cpu` unless configured otherwise. `worker.device` is the device finally used and `worker.deviceReason` says why (tests: `tests/parse-device.test.mjs`).

**Uncertainty and the rewrite hook.** `uncertainty` is `{uncertain, score, kinds, reasons}`; each reason is a fact about the analysis: `untranslated`, `spelling`, `unparsed`, `rule_fallback` (admission repair, dropped wire, fallback outcome), `value_unmapped`, `oov` (a sentence mostly outside the parser's vocabulary), `tree_shape` (a root that is not a predicate, `dep`/`orphan`/`goeswith`/`list` arcs, two subjects of one head, a long verbless sentence), and, with `parsersDisagree` (config `uncertainty.parsers_disagree`, off by default), `parsers_disagree` (the other Stanza package parses each English sentence with a different core arc: root, subject, object, oblique, clausal complement, conjunct, copula, auxiliary or mark; the most useful signal of the evidence in `eval/reports/current/stanza-accurate/`, lift 1.66, flagging 21.5% of messages). It runs a second worker, so it costs about 1.5 times the single-message latency (a measured 119 ms against 79 ms per message on the GPU, 801 ms against 539 ms on four CPU cores) and far more in batches, which is why it is off. `rewrite` is an optional external function from English text to English text (a proofreading model); it is called on the English text before it is parsed again, only when the signal fires (`rewriteWhen: "uncertain"`, default) or always, and never sees anything but that text. Values of a rewritten text are mapped back where the rewrite kept the translation's words.

**Optional rewrite backend: SymbolicProofingLLM (off by default).** (Formerly called the fine-tuned proofreader; role id and paths are frozen, see the alias note above.) `tools/symbolic-lm.mjs serve` accepts `--rewrite-url <endpoint>` (a running llama.cpp-compatible chat-completion endpoint, message-only, greedy) and `--rewrite-when always|uncertain` (default `uncertain`, SymbolicLM's own signal above) to supply the `rewrite`/`rewriteWhen` hook at the chat service; `config/formalizers.json`'s `symbolic-lm.rewrite` field documents the option (`mode: "off"` by default; it is the default of the chat's rewrite setting, "Wiring in the chat" under "Interpretation CNL"; on the command line only the explicit flag turns the hook on). The backend of the chat is SymbolicProofingLLM iteration 3, run `symbolic-proofing-gemma270m-it3` (registry entry `symbolic-proofing-llm`, F16 GGUF, rewrite gated by default; report `eval/reports/current/symbolic-proofing-it3/summary.md`). Its first candidate was iteration 1, run `symbolic-proofing-gemma270m-it1` (a pilot LoRA fine-tune of `google/gemma-3-270m-it` on `neuro_english/proofing`, served from its GGUF Q8_0 export `models/gemma/symbolic-proofing-gemma270m-it1/proofreader/gguf/ep3-q8_0.gguf`; report `eval/reports/history/symbolic-proofing-it1/summary.md`); that pilot is history. The earlier candidate was `train-proofreader-gemma270m-v1` (same base on `datasets_archive/proofing`), whose evidence follows (experiment `eval-proofreader-e2e-v1`, `status/preregistrations/eval-proofreader-e2e-v1.json`, `eval/reports/history/proofreader-e2e/`): on the sealed proofing test at natural proportions (1,135 rows, hard cases included) the checkpoint's unconditional net gain is positive but smaller than the conditional (repairable-only) number the training run first reported (break rate unchanged, <1%); end to end, wiring it ahead of the frozen rules raises strict gold-SOP match on `formalizer-v1` and `formalizer-ood-v1` EN rows by a margin whose 95% CI excludes 0, with a null/futile effect on the independently-written `formalizer-wild-v1` EN rows and no claim for monolingual Romanian (route `direct` has no English text to proofread). This evidence justifies documenting and wiring the option; it does not by itself change any default (`questions.md` records the open owner decision on whether to change one).

**Optional rewrite pipeline: local routing gate and acceptance check (off by default).** (Experiment `eval-symbolic-pipeline-gate-v1`, `lib/symbolic-lm/rewrite-gate.mjs`, report `eval/reports/current/symbolic-pipeline-gate/summary.md`.) Iteration 2 of SymbolicProofingLLM repairs well but changes 15 to 20% of working sentences, because the boundary between working and failing sentences is parser behaviour, not surface form. SymbolicLM therefore decides both questions itself, locally and deterministically, with no model: (1) which sentence units go to the backend and (2) whether a rewritten unit replaces the original. A text is **certified** when every sentence has identical Stanza default and accurate trees (same tokens, same head and relation on every token; the local part of the analysis gate that defines `symbolic_english`). The host splitter cuts the English text into units; the options of `analyze` are `rewriteWhen` (`uncertain`, the default and the earlier behaviour; `trees`: send a unit that is not certified; `trees_or_uncertain`: also send a unit SymbolicLM does not handle alone, that is invalid, not converted, with an unparsed span or any uncertainty reason; `always`: send every unit) and `rewriteAccept` (`off`, the default: keep every rewrite; `certified`: keep a rewrite only when its own trees are certified AND the mechanical meaning checks hold, namely non-initial capitalized names, numbers, negation, quantifiers, question mark and non-empty; `certified_compare`: the same and the analysis comparison `analysis-compare-v1` of unit and rewrite does not say `different`). A refused rewrite leaves the original unit in place; `trace.rewrite.units` lists, per unit, whether it was sent, accepted and why not. The gate runs both Stanza packages on every unit (the other package in a second worker) and again on a rewritten unit, so it costs about two extra parses per unit. `tools/symbolic-lm.mjs serve` takes `--rewrite-when` and `--rewrite-accept`; with `rewriteWhen: "uncertain"` and `rewriteAccept: "off"` behaviour is unchanged. Nothing turns the pipeline on by default and no registry entry points at it; the evidence and the decision are in the report. The mechanical name check does not see a capitalized word at the start of a sentence.

## LanguagesUtil: language identification and spelling

**LanguagesUtil** (`lib/languages-util/`) is the language-level utility component split out of SymbolicLM by the same owner decision of 2026-09-29 as TranslatorService. It knows nothing about UD, SOP or translation; it answers two questions about text:

1. **Per-token language identification** (`langid.mjs`, moved unchanged from the former `lib/symbolic-lm/langid.mjs`). Every token of the message gets a language label (`ro`, `en`, `name`, `num`, `punct`, `other`) with its evidence: Romanian diacritics and function words, the Hunspell word lists, frequency, morphology, then the nearest decided neighbours; a capitalized word inside a sentence, or at a sentence start when the rest of the sentence is in the other language, is a name. `functionLanguage(text)` classifies one token as a Romanian, English, shared or neither closed-class function word (conjunctions, prepositions, determiners, pronouns, auxiliaries), used by `frame.mjs`'s matrix-language detection (`detectFrame(message)`, Myers-Scotton's Matrix Language Frame model: the language with strictly more function-word tokens is the frame; a tie or no function word leaves `frame: null`) for the mixed-message `matrix` route of `eval-translator-compare-v1`, below.
2. **Spell-check** (`spellfix.mjs`, moved unchanged from the former `lib/spellfix.mjs`). The conservative dictionary corrector (names, numbers, quotes and short words protected, every change logged) SymbolicLM runs first when enabled (`spell`); off by default.

Both SymbolicLM (for its own per-token labels and optional spell-check) and TranslatorService (to decide which words of a message need translating) call LanguagesUtil; LanguagesUtil calls neither.

### Jargon detection and protection (proposal, translate-compare study 2026-10-01; not adopted, not wired)

Owner decision of 2026-10-01: a model is never fine-tuned on this project's jargon; jargon is handled by quoting it before translation and restoring it afterwards, and by a component that discovers jargon. `tools/eval/translate-compare/jargon.mjs` is the prototype of both (deterministic, CPU, no model):

- `detectJargon(text, {spellfix, dictionary?, listed?})` flags spans a translator should keep verbatim, each with a reason: `code` (file names and paths, snake_case, camelCase, CLI flags, `@mentions`, dotted or colon-separated identifiers, ids with digits), `english` (an English word of the English word list, absent from the Romanian one, in a mostly Romanian sentence), `capitalised` (a capitalised or ALL-CAPS word that is not at a sentence start and is not an ordinary frequent word), `unknown` (in neither word list, diacritics folded, with no known word within two edits, so a probable typo is not quoted) and `listed` (a word of a reviewed or discovered jargon list, which may be an ordinary Romanian word with a project sense such as "fire" for wires or "teste" for sealed tests).
- `protectJargon` wraps every span in double quotes, `restoreJargon` puts the original spans back inside the quotes the translator kept (only when the number of quoted groups equals the number of protected spans; otherwise nothing is replaced and the loss is reported), and `discoverJargon(texts, {spellfix})` proposes `listed` candidates: words far more frequent in the user's own messages than in general Romanian and English. The owner reviews the proposals before a word becomes `listed`; the list is host data, never training data.
- Measured limits (`eval/reports/current/translate-compare/summary.md`, 226 natural messages): quoting keeps the span verbatim 3 to 15 points more often than the translator does alone (Qwen3-4B 90% against 81%), but it did not raise the judged meaning faithfulness of any translator (paired difference -0.5 to -2.6 points, every interval includes 0); the translators drop, add or move the quotes in 7% (Qwen3-4B) to 49% (prod1) of the sentences and the machine-translation models sometimes translate inside the quotes; an ordinary word that only looks English ("rind", the typo of "rand") is quoted wrongly; and an ordinary Romanian word with a project sense ("fire" for wires) cannot be found by a general word list: the detector flags it only after it is on the reviewed list. Hence the proposal is not wired into translation; its uses are showing the user which terms were kept or are unknown, and proposing glossary candidates for review.


## TranslatorService: pluggable translation toward English

**TranslatorService** (`lib/translator-service/`) is the dedicated translation component split out of SymbolicLM by owner decision of 2026-09-29. It has one job — render a message (or the parts of it that need it) intelligibly in English for the English Stanza parser and UD-to-SOP rules — and nothing else: it never parses UD, never generates SOP, never reasons. Backends are loaded by name from `lib/translator-service/index.mjs` (`loadBackend(name)`, `BACKENDS` registry):

- **`symbolic`** (`backends/symbolic.mjs`, `backends/english.mjs`) is the deterministic dictionary-and-rules translator moved unchanged from the former `lib/symbolic-lm/translate.mjs`/`english.mjs`: relation phrases from the host dictionary as a whole ("lucra la" → "work at"), other words from closed function-word tables and the dictionary, a small English realizer (word order, articles from the Romanian definite suffix, tense/person, negation with do-support, question inversion, fronted question phrases, relative clauses, pro-drop subjects). Names, numbers, dates and English words are copied verbatim; an unknown Romanian word is copied and reported as `untranslated`, never guessed. This is the only backend SymbolicLM's `translate` route calls.
- **`opus-mt`** and **`apertium`** (`tools/research/translator-backends/opus-mt.mjs`, `apertium.mjs`; moved out of `lib/` on 2026-10-01, hygiene H14) are research backends that translate raw, name/number/quote-masked text (`lib/ud-to-sop/protect.mjs`) through an external CPU translator. They are exercised only by `tools/research/translator-compare-eval.mjs` (experiment `eval-translator-compare-v1`) and are not called by SymbolicLM; a backend is adopted into the runtime pipeline only after a preregistered comparison (DS010).

- **`gloss`** (`backends/gloss.mjs`, owner idea of 2026-10-01; a mode beside `symbolic`, whose behaviour is unchanged — it only exports its closed tables read-only as `GLOSS_TABLES`) is a **morphology-aware word-by-word gloss that keeps the Romanian word order**. It is the input of LanguageProofingLLM as a post-editor (the model fixes word order and grammar, it does not have to know the vocabulary) and is never shown to anyone and never parsed for SOP. `glossMessage(lm, message, {spell, senses, mark})` (`lib/translator-service/index.mjs`) works as follows. LanguagesUtil gives the spelling and the per-token language; the Romanian parse (Stanza lemma, UPOS, features) gives each Romanian token its English form: nouns take the dictionary sense of the lemma, the plural from Number, "the" from Definite and "of" before a genitive; verbs take the dictionary verb inflected from the features, including the compound forms (perfect "am lucrat" → "I worked", future "va lucra" → "will work", conditional "aș vrea" → "would want", passive "este înscris" → "is enrolled", "se" passive or dropped reflexive), negation "nu" with do-support when the group is simple, clitic pronouns ("mi-" → "to me"), a pro-drop first or second person subject ("am nevoie" → "I need"); function words, possessives, numerals, prepositions and multiword expressions ("de la" → "from", "de câte ori" → "how many times") come from the closed tables of `symbolic`. The word order stays Romanian ("nepoata mea" → "the niece my"). Names, numbers, quoted text and English words are copied unchanged. **Unknown lemmas are copied unchanged in square brackets, `[nepoată]`** (the surface as written): the post-editor learns that a bracket means "translate or keep, the gloss could not", the marker is two ASCII tokens and does not occur in the training prompts otherwise; `mark: ['', '']` disables it. `senses: 2` writes the first two dictionary senses as `granddaughter/niece` and leaves the choice to the post-editor (on `formalizer`-derived dev data the target uses only the second sense for 19.7% of the multi-sense words, 7.5% of all glossed words). **Romglish** (Romanian grammar with English words): an English stem with a Romanian enclitic article or plural, hyphenated or not ("deadline-ul", "update-urile", "updateurile"), becomes "the deadline", "the updates"; an English verb with Romanian inflection ("forwardat", "share-uiesc", "checkuiesc", "a share-ui") is recovered by a suffix rule set against the English spellchecker lexicon and re-inflected from the Romanian morphology ("am forwardat" → "I forwarded", "am dat check" → "I checked"); a sentence is cut into clause chunks and each chunk gets its frame from LanguagesUtil (`detectFrame`, token counts on a tie): a Romanian frame is parsed whole with the English tokens copied, an English frame keeps its English and only the inserted Romanian runs are parsed on their own and glossed in place ("Can you check the factura from yesterday?" → "Can you check the invoice from yesterday?"), a chunk without Romanian is copied. Results and the post-editor experiment are in `eval/reports/current/gloss/summary.md` (experiments `eval-gloss-v1` and `train-language-proofing-gloss-gemma270m`).

**`eval-translator-compare-v1`** (owner questions of 2026-09-29, `status/preregistrations/eval-translator-compare-v1.json`, results and full detail in `eval/reports/current/translator-compare/summary.md`) compared the `symbolic` backend against Opus-MT and Apertium on 150 monolingual Romanian and 100 mixed rows of `formalizer-v1` train.jsonl (dev.jsonl was fully consumed by `eval-symbolic-lm-v1`, a recorded deviation), plus a 40-message niche-word probe, per the preregistered decision rule for Q-PIPE-1 (default route per message class becomes the best-scoring one only if its lower 95% CI bound over the current default is above 0; Romanian's explicit fallback is `direct` when nothing wins).

Apertium was dropped before running: no Romanian→English pair exists, packaged or in the `apertium` GitHub organization's 655 repositories (`tools/research/translator-backends/apertium.mjs`).

**Romanian (150 rows): no arm beat `direct`** (symbolic-hybrid tolerant +4.7 [-1.3, +10.7], symbolic +2.0 [-4.7, +8.7]); **Opus-MT was decisively worse** (-15.3 [-22.7, -8.0]) and about 6× slower than `direct`, also 60% slower than the symbolic backend once its own CPU translation time is added to its English parse time. This is the second independent experiment, after `eval-symbolic-lm-v1`, to find the same thing. **Decision: Romanian's default changes from `translate` to `direct`** (`DEFAULT_ROUTES` in `lib/symbolic-lm/index.mjs`).

**Mixed (100 rows): `symbolic`/`symbolic-hybrid` lead `direct` by +7.0 points, 95% CI exactly [0.0, +14.0]** — the closest possible miss of the decisive threshold. A new `matrix` route (`lib/languages-util/frame.mjs` `detectFrame`: the Matrix Language Frame model, frame language from closed-class function words; an English frame gets its Romanian content words glossed in place from the dictionary, an unknown word left as written) scored -3.0 [-8.0, +1.0] against direct, not decisively different and not better than `symbolic`. Opus-MT scored -7.0 [-17.0, +2.0]. **Decision: mixed keeps its current default (`translate`, the `symbolic` backend)** — the evidence is not decisive enough to switch away from it, which is the correct outcome of the rule, not an oversight.

**Owner question 1 (can Opus-MT clean up "romgleza"?): no, not reliably.** Manual reading of all 50 Opus-MT outputs of the mixed stage-50 sample: 21/50 (42%, Wilson 95% CI [29%, 56%]) are fully fluent, complete English; the rest keep at least one untranslated Romanian function word, discourse marker or whole subordinate clause (`Vreau`, `Poți`, `Cine`, `Deci`, `Adică`, `Învață la … din …`), because the model was never trained on code-switched input and does not recognize short Romanian "frame" grammar as needing translation when English already dominates the sentence.

**Owner question 2 (unknown words): the symbolic backend is far safer.** On the 40-message niche-word probe (57 judged word instances per backend): symbolic 70% correct, 21% copied (honestly reported `untranslated`), 4% hallucinated, 4% dropped, 2% transliterated; Opus-MT 32% correct, 37% copied, **21% hallucinated**, 11% dropped. The symbolic backend's two hallucinations trace to two actual dictionary-entry bugs (`girant` → "manager", `user` → "royal curt usher"), not guessing; a generative model with no "I don't know" mechanism hallucinates a wrong meaning about five times as often. A separate, pipeline-level finding (not a translator behaviour): `lib/ud-to-sop/protect.mjs`'s name masking checks a sentence-initial capitalized word only against an *English* common-word list, so an ordinary Romanian common noun capitalized at a Romanian sentence's start (`Clanța`, `Bostanul`) is mismasked as a name before an external translator ever sees it.

## textToCleanEnglish: a user-validated pre-formalization step

**textToCleanEnglish** (`lib/text-to-clean-english/`, owner decision 2026-09-30) is a host step that runs entirely **before** the model boundary above, in the chat UI, not inside SymbolicLM or the small formalizer: formalization itself handles only clean English, and getting there is a UI-mediated, user-validated step, not a silent host rewrite. Given a chat message it turns bad input into acceptable English: it corrects spelling and grammar, translates Romanian or mixed Romanian/English text to English, and simplifies wording, by calling LanguageProofingLLM (the LanguageTool backend was removed on 2026-10-01), returning `{original, clean, changed, reasons, spans, backend, confidence}`; the host splits the message into sentences (`lib/sentence-split.mjs`) and a cheap, conservative gate (non-English tokens, a spelling signal, a handful of cheap grammar-trouble regexes) skips every already-clean English sentence without calling any backend; only flagged sentences go to the model, one request per sentence, and `llm.sendAll: true` sends every sentence instead (the fine-tuned model changes about 0.2% of clean sentences, so this is safe but costs a model call per sentence; the code default is `false`, and the shipped `config/text-to-clean-english.json` sets `true`, owner decision of 2026-10-01). The backend is a small, explicit, swappable choice (`config/text-to-clean-english.json`): `llm` (LanguageProofingLLM, the default for English and for Romanian and mixed text: a registry model with the `proofread` capability, started on demand, for proofreading, translation and simplification together) or `translator-llm`; an unreachable backend degrades to `backend: "none"` (the message unchanged) rather than failing the request or inventing text.

The chat page shows the user the proposed English (a word-level diff) and requires a choice — **Accept**, **Edit**, or **Send original** — before anything is formalized; the accepted text becomes the formalizer's whole input, exactly as any other message under "Model boundary" above (no context block, no vocabulary, no identifiers are added by this step), and the original message is kept beside it in the request (`cleaning: {original, backend, changed}`) and the HTTP trace ([DS012](specsLoader.html?spec=DS012-local-server.md) "textToCleanEnglish"), so a reviewer can always see what the user actually typed. The user, not the model or the host, is the one who validates that meaning was preserved; a user who accepts or sends a nonsensical rewrite is responsible for that choice, the same way a user is responsible for what they type.

**Translator for Romanian and mixed sentences (owner decision 2026-10-01).** `backends.nonEnglish` is `translator-llm`: a sentence whose LanguagesUtil language is Romanian or mixed goes to the translator LLM, unmodified Qwen3-4B-Instruct-2507 Q4_K_M (registry id `translator-llm`, capability `translate-clean`, `models/qwen3-4b-instruct/provenance.json`, Apache-2.0), one sentence per request with the plain translate prompt of the winning `translate-compare` arm (`lib/text-to-clean-english/backends/translator.mjs`), greedy, thinking off; English sentences keep `backends.english` (`llm`, LanguageProofingLLM) and the `llm.sendAll` semantics. Reason: on the 425 natural sentences of `datasets/natural`, 64.9% keep their meaning (S0 to S2, worse of Grok and GLM) against 10.6% for LanguageProofingLLM prod1 (`eval/reports/current/translate-compare/summary.md`); quality outranks speed and 15 to 20 tokens per second is accepted for this step (owner, 2026-10-01). It never fails totally: when the translator cannot start or answer, `translator.fallback` (default `llm`) names the backend that takes the sentence, and the result carries `fallback: {from, to, reason, sentences}` plus per-sentence `routes`; the HTTP trace and the chat's review note show it, so a substitution is never silent, and `translator.fallback: "none"` turns it into `backend_unavailable`. The user still validates the proposal before anything is formalized.

The model behind the `llm` backend is **LanguageProofingLLM**. Since 2026-10-01 (owner decision "remove Qwen3-1.7B from the chat") it was the fine-tuned Gemma 3 270M of iteration 1, run `language-proofing-gemma270m-it1` (LoRA on `bad_english` sentence pairs, merged, GGUF Q8_0 `models/gemma/language-proofing-gemma270m-it1/proofreader/gguf/ep3-q8_0.gguf`, registry id `language-proofing-llm`, capability `proofread`); the evaluation, its limits and the open failures (for example "child" turned into "parent", 94.8% of clean sentences left untouched against a 95% bar) are in `eval/reports/history/language-proofing-it1/summary.md`, and it is compared with its untrained base only on our synthetic data. It runs at about 110 ms per sentence on 4 CPU threads, meeting the 30 to 40 tokens per second laptop target. Its request is exactly the training request: one sentence as the only user message, no system prompt, greedy decoding, the checkpoint's own chat template, no name masking. Rewriting correct English into the limited English SymbolicLM understands is a different job, done by SymbolicProofingLLM (trained on `neuro_english`), and only for what SymbolicLM's rules cannot fix.

**Production build, proper-noun protection and quantization (prod1, 2026-10-01).** The production candidate of LanguageProofingLLM is the fine-tuned Gemma 3 270M run `language-proofing-gemma270m-prod1` (epoch 3, trained on `bad_english/proofing-prod1`; all eighteen probe words in the data, institution and place names kept, typo'd child words). On the sealed data it keeps every name on 99.2% of the units that have one (it3: 65.6%, 380 of 1,122 names lost against 9), reads the fresh 18-word probe at 88.2% (it3 69.6%) and leaves the judged composite unchanged (79.8% against 78.3%, not significant); evaluation, caveats (the eight-word dev set shares paraphrase siblings with training and undercounts "owner" for "landlord"; invented or substituted words in 30 judged units) and the switch rule are in `eval/reports/current/language-proofing-prod1/summary.md`. The runtime protection stays as a safety net after the model: the `llm` backend asks the bare sentence first and, only when the reply lost a multi-word proper name of the input (`lib/text-to-clean-english/protected-names.mjs`), asks once more with the names masked as `Ent1`, `Ent2`, ..., restoring them afterwards; with the real F16 file it triggered on 63 of 1,106 sealed units with a name, used the masked reply 62 times and ended with zero lost names (`tools/eval/language-proofing-prod1-guard.mjs`). The shipped file is the **F16 GGUF** (greedy agreement with HF bf16 97.0%, 90 tokens/s on 4 CPU threads) rather than Q8_0 (93.8%, 139 tokens/s) because Q8_0 loses more than 2 points of agreement while F16 stays far above the 30 tokens/s floor ([DS007](specsLoader.html?spec=DS007-training.md) "Production-build policy"). **Switch rule:** the chat entry `language-proofing-llm` changes to a new build only when the preregistered gates hold, or by an explicit owner decision recorded as a deviation; the evaluation recommends and never edits `config/formalizers.json`, and the previous GGUF stays on disk for a revert.

**Gloss post-editor (language-proofing-gloss-gemma270m, 2026-10-01).** Design: TranslatorService `gloss` (dictionary lemma senses, morphology, spelling, unknown lemmas in square brackets) produces a word-by-word English text and the model is trained to post-edit it; the original Romanian is never in the prompt, so the model cannot fall back on memorized Romanian vocabulary; English input passes through the gloss unchanged. Result on the sealed and probe sets (epoch 2 chosen by the dev rule): unseen words 71.8% (it3 52.0%), clean900 untouched 93.2% (it3 98.2%), sealed units with a name 68.4% (prod1 99.2%), fresh 18-word probe 77.5% (prod1 88.2%). The gloss does not replace training on the words and does not protect names, so textToCleanEnglish keeps prod1 with the message-only prompt; the gloss stays a research component of TranslatorService. Details: `eval/reports/current/language-proofing-gloss/summary.md`.

**First-layer comparison on the owner's natural messages (`translate-compare`, 2026-10-01; research, nothing adopted).** On the 226 messages of `datasets/natural` (425 sentences), judged per sentence and per message by Grok and GLM (good enough = S0 to S2 by the worse judge; judges that disagree on S3 or S4 are reported apart as excusable ambiguity), per-sentence good-enough rates were: prod1 10.6%, `symbolic` and `gloss` 5% to 7% (stage 1 only), opus-mt ROMANCE-en 33.2%, opus-mt bible-big roa-en 44.2% (48.0% after the LanguagesUtil spelling corrector), Qwen3-1.7B Q8 44.2%, EuroLLM-1.7B Q4 20.7% (stage 1 only), Qwen3-4B-Instruct Q8_0 62.6% and Q4_K_M 64.9% (no measurable loss from quantisation), DeepSeek flash 89.9% as the ceiling; per message prod1 3.5%, bible-big 31.0%, Qwen3-4B Q4 54.4%, DeepSeek 83.2%. Splitting long run-ons into chunks and running prod1 after a translator gained nothing; quoting jargon gained nothing (above). `opus-mt-ro-en` does not exist on the Hub; the arms used ROMANCE-en and `opus-mt-tc-bible-big-roa-en`. On CPU Qwen3-4B Q4_K_M generates 21 to 26 tok/s (Qwen3-1.7B 38, so only the 4B misses the 30 to 40 tok/s base-model rule). The study recommends a general instruction-following translator (Qwen3-4B-Instruct Q4_K_M) as the first layer for Romanian and mixed input with the user-validation step kept; the owner's decision is open (`questions.md` Q-TRANS-2). Full tables, examples and the jargon probe: `eval/reports/current/translate-compare/summary.md`.

This is a different, broader mechanism than SymbolicLM's own optional internal rewrite hook described above ("Uncertainty and the rewrite hook"): that hook rewrites English text in place, only ahead of the symbolic parser, only conditionally on SymbolicLM's own uncertainty signal or always, and silently (no user review) when turned on; by the owner's decision Q-PROOF-1 (2026-10-01) the chat runs it gated by default (`rewriteWhen: "trees"`, `rewriteAccept: "certified"`), with a setting to switch it off or to always. textToCleanEnglish instead sits in front of *any* formalizer (fine-tuned or symbolic), handles Romanian and mixed text as well as English, and is always shown to the user for review rather than applied silently. Turning one on or off does not change the other.

A small, staged, preregistered comparison of candidate backends (symbolic spelling and translation, Opus-MT, LanguageTool, EuroLLM-1.7B-Instruct, Qwen3-1.7B, Gemma 3 1B-it and Claude Haiku as a reference ceiling; `status/preregistrations/text-to-clean-english-v1.json`, experiment `text-to-clean-english-v1`, report `eval/reports/current/text-to-clean-english/summary.md`) decided the default until 2026-09-30: the gate, LanguageTool (masked) for English and Qwen3-1.7B Q8_0 GGUF (masked) for Romanian and mixed text. That default was replaced on 2026-10-01 by the fine-tuned LanguageProofingLLM for every flagged sentence (`backends.english = "llm"`, `backends.nonEnglish = "llm"`, `llm.model = "language-proofing-llm"`); the survey stays the record of the earlier choice. The evidence is small-sample and says so: cleaning noisy English is a resolved gain over sending the original, unmasked LanguageTool corrupts names (hence the masking), and the value of the Romanian and mixed path is the user's review of a readable English proposal, not a measured accuracy gain (the gold SOP of a Romanian row keeps Romanian content words, so an English rewrite is penalised by that measure).

## Limited English for SymbolicLM (target-style contract)

The target of SymbolicProofingLLM, and of LanguageProofingLLM where it has to do more than repair spelling or translate, is **limited English**: short simple sentences SymbolicLM parses as a known form. The hardest and most important job of both models is **decomposition**: a tangled sentence with several clauses becomes several short sentences, each with an explicit subject and predicate where the text allows it. The contract is derived from what SymbolicLM handles (`eval/reports/current/three-datasets/symbolic-forms-inventory.md`, `new_cases.md` section 3, `eval/reports/current/symbolic-layers/summary.md` section 4) and is what the rewrite targets of `neuro_english` and `bad_english` follow (their READMEs refer here). Both models work **one sentence at a time**: they need no other sentence, and they never resolve a reference.

1. **One clause per sentence, one question per sentence.** A run-on, a chain of `and`/`or`/`but`, a list (one sentence per item) and a message with several questions each become several sentences. A sentence ends with its terminal punctuation.
2. **Explicit subject and predicate.** A subject shared by coordinated or relative clauses of the same sentence is repeated as written (the name, the noun phrase), not dropped: `Does Ion teach math? Does Ion coach the team?`, never `Does Ion teach math and coach the team?`.
3. **Connectives that carry meaning are kept**, in a form SymbolicLM parses (the forms of the forms inventory, each a subordinate clause with its own subject): `because`, `if`, `unless`, `although`, `before`, `after`, `when`, `while`, `so` (also `since`, `until`, `though`), the clause before or after its main clause (`Since Iancu reports to Wojciech, is it the case that Wojciech reports to Iancu?`, `Did Oliver start working at Tisa Textiles after Paula did?`, `The mirror looks cloudy because Alex used the wrong cloth.`). The frames of a question that SymbolicLM reads as a frame keep their complement clause: `Do you know whether …`, `Tell me whether …`, `I need to know if …`, `Can you confirm that …`, `Is it correct/true/the case that …`. A sentence with a connective-linked clause or a frame complement is one sentence; it is not split further.
4. **Names, numbers, negation, quantifiers and hedges are unchanged; nothing is added or dropped.** Only filler (`hey`, `quick q`, `lol`, `pls`, emojis, `Fact-check:`) may go. Reported speech keeps who said it; an ambiguous message stays ambiguous; a question stays a question.
5. **A pronoun that refers outside its sentence stays a pronoun.** SymbolicLM resolves it when it turns the analysis into SOP (a pronoun resolves to the subject of the preceding sentence once the whole message is read). The proofing models never replace a pronoun by a name and never need the previous sentence. A Romanian dropped subject becomes the pronoun that fits the verb (`She works at the hospital.`); which pronoun is chosen does not matter for the SOP.
6. **Standard surface.** Spelling, casing and spacing repaired; question word first with a full subject and verb (`To whom does Hao report?`, not a stranded preposition); a title or an odd name in double quotes; plain everyday words, no paraphrase for style.

## Never NONE, never catastrophic (owner direction 2026-10-01)

The product aims at "good enough", not perfect: a slightly off interpretation is acceptable because the user rephrases, as in a conversation with a person or a large LLM. Two rules follow, measured with the graded severity of [DS016](specsLoader.html?spec=DS016-evaluation-metrics.md) "Graded severity (S0–S4, NONE)":

1. **Never NONE when an interpretation exists.** When SymbolicLM yields no certified interpretation, the host tries, in order and stopping at the first accepted candidate: the SymbolicProofingLLM greedy rewrite; k sampled rewrites (temperature 0.7); LanguageProofingLLM as an alternative paraphraser; symbolic simplifications (drop lead-ins and tags, split a coordinated question, keep the certified sentences); and finally a clarification question to the user, which is a reply, not an interpretation. A candidate is accepted only when SymbolicLM handles it without doubt and the local severity checks (names, numbers, negation, quantifiers, conditions, reported claims, roles) find nothing catastrophic. The prototype and its evaluation are `tools/eval/fallback-cascade.mjs`; it is not wired into `lib/` (the routing gate and acceptance check of the rewrite pipeline are `lib/symbolic-lm/rewrite-gate.mjs`).
2. **Catastrophic interpretations (S4) must be about zero.** Negation or polarity flips, swapped roles, wrong or invented entities, names or numbers, flipped quantifiers, and a condition, supposition, question or reported claim turned into an asserted fact are never traded for coverage. A rewrite or fallback that cannot pass the S4 checks is refused and the original text is kept, or the user is asked.

## Partial acceptance of a decomposition (proposal, owner direction 2026-10-01)

**Status: a proposal, evaluated as the extra arm `it2-partial` of `eval-decomposition-v1` ([DS016](specsLoader.html?spec=DS016-evaluation-metrics.md) "Decomposition and detectability"); not implemented in `lib/`.**

The analysis never fails completely, and a lost indication is tolerable when it is visible. The acceptance check of the optional rewrite pipeline (`certified`, above) is all or nothing per sentence unit: when the model splits a tangled unit into sentences and only some of them are certified, the whole output is refused and the original tangled unit stays, which is why the gate-and-accept pipeline reaches the expected sentence count only rarely (`eval/reports/current/symbolic-pipeline-gate/summary.md`, point 6). The partial-acceptance rule keeps what is certain:

1. The gate is unchanged: only a unit whose default and accurate trees differ is sent. A unit that passes the mechanical meaning checks (names, numbers, negation, quantifiers, question mark) is examined sentence by sentence.
2. If every sentence of the output is certified, the output replaces the unit (as today).
3. If some sentences are certified and some are not, the certified sentences are kept and the **original unit follows, marked not represented** in the interpretation: the user sees the understood part as verified CNL and the leftover as flagged text. The interpretation never presents the leftover as understood.
4. If no sentence is certified, or a meaning check fails, the original unit is kept, as today.

What the rule trades: it adds some duplicated content (the original unit repeats facts that the certified sentences already state) in exchange for decomposition that the pipeline could not accept before, and the duplication is always on the flagged side. The rule must not raise the silent meaning change rate: its acceptance criterion is the preregistered H4 of `eval-decomposition-v1`.

**Decomposition contract for the models (summary of the limited-English contract above, as a test target).** A tangled sentence (several finite clauses, several questions, a run-on or a list) becomes short sentences with explicit subjects and the connectives kept, within the rules of "Limited English for SymbolicLM"; a clause the model cannot split or restate certifiably is left in its original wording, never paraphrased into something else. The catastrophic failures to avoid are the ones the user would not notice: a role or negation flip, invented content, and a dropped question or request. The training data that teaches this, `datasets/neuro_english/proofing-it3-decomp`, is built in the reverse direction (a certified group of short sentences is tangled into one sentence, so every target sentence is certified by construction) and includes partial-acceptance pairs whose target keeps one uncertified sentence verbatim; it is prepared, not trained.

## Interpretation CNL

The **interpretation CNL** (`lib/languages-util/analysis-cnl.mjs`, experiment `eval-analysis-cnl-v1`, evaluation `tools/eval/analysis-cnl.mjs`) is a deterministic realizer from SymbolicLM's grammatical `analysis` (the compact UD parse of the accurate Stanza package) to a controlled English: a few short sentences that say exactly what the analysis says, no more and no less. The realizer is a pure function of the analysis (no model, no parser call, no context). Since 2026-10-01 the chat shows it ("Wiring in the chat" below).

**Structures.** Per clause the extractor builds a predicate-argument structure (an *atom*): the clause type (statement, yes/no question, wh-question with the questioned role, imperative), the predicate lemma (with its particle), voice normalized to active when the agent is present (an agentless passive stays passive), tense and aspect, polarity, modality (`can`, `must`, `might`, `should`, `would`, `will` as future), subject, object, indirect object, obliques with their preposition, quantifiers and determiners inside the argument, an infinitive or `that`/`whether` complement, adverbials, and clause links (`because`, `if`, `unless`, `although`, `before`, `after`, `when`, `while`, `since`, `until`; `and`/`or`/`but`/`so` between clauses).

**Templates (the whole set).** `S V O.` and `S is C.`; `S does not V O.`; `Does S V O?`; `Wh does S V?` and `Who V O?`; `If A, then B.`; `Because A, B.` (every other link is written first, so it cannot attach to a neighbouring clause); `A, or B.`; `X says that A.` (for `according to X` and any `that` complement); `There is C.`; imperative `V O.`. Names, numbers and quoted text are copied token for token.

**Rules that keep it equivalent.**
- A request wrapper (`Can you confirm that`, `Is it true that`, `Any idea who`, `Please find out whether`, `Tell me whether`) is not a statement: the wrapped clause becomes a question, and the wrapper is listed as a normalization. `Please tell the crew that A` is an imperative, not a wrapper (the wrapper verbs must address the speaker).
- A relative clause becomes a separate statement about the head noun only in an affirmative top-level statement whose head has no quantifier (`the` replaces `a` in the second mention); otherwise it stays inline, copied.
- Coordinated subjects or objects become separate sentences only for `and`, in an affirmative top-level statement, when the predicate is not collective or reciprocal (`meet`, `marry`, `be married to`, ...) and the clause has no `together`, `both`, `each other` or `between`; `or`, negation, questions and conditions keep the coordination inline. Coordinated questions stay one sentence (`Does A, and does B?`).
- Reported speech (`according to X`, `X says that`) and hedges (`I think that`, `maybe`) stay explicit markers.
- A pronoun is kept as written; the tokens of a framing list (`please`, `thanks`, `also`, `okay`, lead-in labels ending in `:`) are listed under `framing`.

**Nothing is dropped silently.** Every word the extraction does not use, and every span of the message the analysis does not cover (text SymbolicLM masked before parsing), is listed as `not represented: "<span>"`; a fragment without a predicate gives an empty CNL and only that list. This is the "what the system did NOT understand" list.

**Round trip (the equivalence check).** The CNL is parsed with SymbolicLM and the same extractor runs on that parse; `roundTrip(source, cnlStructures)` requires the same multiset of canonical atom keys (the key normalizes voice, contraction, commas and hyphens, the order of obliques, `Who is X` against `X is who`, a participle complement against an agentless passive, and flattens chains of one connective) and no unused word in the CNL parse. A CNL that fails is reported with the differing atoms and is never shown as `I understood`. The check proves that the realizer and the parser agree on the structure; it does not prove that the source analysis is right, which is the point of showing the CNL to the user.

**Measured (eval-analysis-cnl-v1, 300 symbolic_english and 200 neuro_english sealed test rows, CPU; `eval/reports/current/analysis-cnl/summary.md`).** Round trip passes on 98.6% of symbolic_english rows with a CNL and 86.6% of neuro_english rows; 9.3% and 27.0% of the rows have `not represented` spans; the CNL has 0.84 times the words of the message; 91.4% of the symbolic_english CNL texts (93.4% of their sentences) are certified, that is, identical Stanza default and accurate trees (neuro_english: 44.3% of texts, 78.4% of sentences, texts being long).

**Uses.**
1. *Chat display.* `I understood: <CNL>` (and the `not represented` list) lets the user correct a slightly-off interpretation; shown only when the round trip passed.
2. *Analysis-layer comparison.* Two texts are compared by comparing the atom keys of their CNLs (a deterministic, voice-insensitive key), a stricter and more explainable companion of `analysis-compare-v1`.
3. *Candidate canonical target style* for SymbolicProofingLLM: the CNL sentences are short, one clause each and mostly certified; it follows the limited-English contract above (one clause per sentence, repeated subjects, links kept, names, numbers, negation and quantifiers unchanged). Whether a model trained on it beats the current targets is not measured.


**Wiring in the chat (2026-10-01).** `lib/symbolic-lm/interpretation.mjs` (`interpretResult(lm, result)`) turns a `SymbolicLM.analyze` result into the per-sentence report the chat shows, for the analysis SymbolicLM finally used (after a rewrite, and of the English translation for a Romanian or mixed message; an analysis in Romanian gets no CNL). Per sentence: the extracted structures and the CNL; the **round trip** (SymbolicLM parses the CNL and the extracted structures must equal the source's: a failed round trip is never shown as CNL, the sentence is `uncertain` and carries a raw analysis summary, the unverified CNL is kept apart); the `not represented` spans, assigned to their sentence (a masked lead-in goes to the next sentence and `display_text` shows it); **certification** (identical default and accurate Stanza trees of the sentence; `lm.inspectUnit`, reusing the pipeline's verdict for an unrewritten unit); and the rewrite trace of the sentence (`original`, `rewrite`, accepted or refused with the acceptance reasons). The `serve` command of `tools/symbolic-lm.mjs` computes it on request (`symbolic_lm: {interpret: true}`) and the chat server relays it in `chatSop.understanding` ([DS012](specsLoader.html?spec=DS012-local-server.md) "Understanding in the chat"). The same request can switch the SymbolicProofingLLM rewrite per message (`off`, `gated` = `rewriteWhen: "trees"` + `rewriteAccept: "certified"`, `always`) through the registry entry `symbolic-proofing-llm` (capability `proofread-symbolic`, the it2 GGUF, message-only prompt, one sentence per request, started on demand); the default of that switch is `rewrite.mode` of the `symbolic-lm` registry entry (`gated` by the owner's decision Q-PROOF-1 of 2026-10-01). The panel's purpose is manual evaluation by the owner: what the system understood, where it is unsure and what it did not represent.

## Packet and trace fields

A model-origin turn adds to the result packet:

- `user_statements`: one entry per authored `stated`: `id`, the authored `relation`, `roles`, `polarity` and `valid_text`, the linked `predicate` and `atom`, the normalized `valid {from, until}`, `certainty`, `speaker`, `treatment` (`evidence` \| `supposition`), `conditional`, `in_circuit`, for suppositions `used_in_proof` and `defeated`, and the host-rendered `statement` repeating the model's strings ("You stated: works at (subject: Maria; object: Alpha Lab).", "You stated tentatively: …", "You supposed: …", "According to Ana: …").
- `carried_statements`: asserted statements supplied from earlier turns.
- `model_assumptions`: one entry per `assumed`: the same fields, `basis` (or `unspecified`), `treatment`, `used_in_proof`, `defeated`, `statement` ("The model assumed: …").
- `assumption_policy`: `report` or `branch`; `assumption_branch` under `branch`: `{problem, status, answers, hypothetical, defeatedAssumptions, route, text}` per query.
- `clause_links`: one entry per link line: `from`, `keyword`, `type`, `to`, `status` (`applied` or `not_checked`), `effect` or `reason` ("Clauses and links"); statements carry their own `links` and a host sentence that names them.
- `linking`: one entry per bound mention, in wire order: `wire`, `kind` (`relation` or `entity`), the `surface` as written, the `symbol` it was bound to and `via` (`lexicon`, with `form {kind lexeme|label|alias|id|description, text, language}` for a relation and `match` `exact` or `accent-folded` plus the `class` for an entity; `copula_reading` with the `reading`; `dictionary`, `synonym` or `unparsed_span` with the `form` the phrase was translated to), and for a relation the `alternatives` not taken (the other readings of a copula). Since M3 each entry also carries `score`, `decided_by`, `scored_alternatives` and, for a relation, `facts` ("KnowledgeLinker: scoring and ambiguity"). Since R2 a relation whose role was renamed carries `relabeled {from, to}`, one linked by a frame has `via: frame`, and the packet lists `frame_changes` beside `translations`. It lists what the KnowledgeLinker decided from the lexicon of the session's base memory (DS031 "Lexicon of a memory"), so the chat trace shows "work at" linked to `works_at` by the lexeme form "works at"; an unlinked or ambiguous mention is not listed, it is the clarification.
- `translations` and `untranslated`: the dictionary step (`wire`, `field`, `from`, `to`, `source`; an unknown Romanian word with its `tokens`).
- `repairs` and `unresolved_spans`: the symbolic repair of `unparsed` spans and the one question per unresolved span ("Honest partial formalization").
- A host link failure returns `status: clarify` with `reason: unresolved_link` and `required` listing each unlinked relation (`status`, `candidates` with their roles) or time expression; a turn whose every problem waits for an unresolved span returns `reason: unresolved_span`.

When a primary result is hypothetical, the controlled text lists each conditional statement it rests on ("Condition: …"); under `branch` it adds "Only under the model's assumptions: …". The HTTP trace (`chatSop`) carries `answer_language`, `language_source`, `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy`, `assumption_branch`, `unclear`, `understood_as` and `linking`, next to the existing fields; the packet carries `clause_links`, `linking`, `translations`, `untranslated`, `repairs` and `unresolved_spans`.

## Answer language

The default answer and CNL language is English (`cnl.language` defaults to `en`). The chat API accepts an optional `language` (`en` \| `ro` \| `auto`): `en` and `ro` force the answer language and nothing is detected; with `auto` or no field the agent honours an explicit request in the message, detected deterministically by `server/language.mjs`: a fixed list of request phrases next to a language name, after accent folding ("răspunde în română", "answer in Romanian", "please reply in English", …). Writing in Romanian is not a request. Precedence: API field `en`/`ro`, then message request, then English; the trace reports `language_source` (`request`, `prompt` or `default`). The core renders every answer in English: the host-generated `cnl`, the `unclear` reply, the not-computable reply, the clarification questions of host linking and the report sentences have no Romanian templates. When the selected language is not English, the output edge translates the final English text with TranslatorService ("Input languages and content words", output edge): names, numbers, quoted values and SOP identifiers are preserved, the packet carries `answer_translation` (language, backend, the original English text, status) and the trace `english_text`. A translator that is unavailable leaves the English answer with `answer_translation.status = backend_unavailable`. The chat page offers exactly English, Română and Any (`auto`) ([DS012](specsLoader.html?spec=DS012-local-server.md)).

## Boundary rule and borderline cases

> `stated` only when the model is sure the claim comes from the user's message. Anything the model adds, infers, completes or presupposes is `assumed`. When in doubt, `assumed`.

| Utterance | Formalization |
| --- | --- |
| "Since Nera left the lab, who runs it now?" | `stated` (relation "leave", subject "Nera", object "the lab", asserted) + `query` with `because $s1`: an assertion embedded in a question is still asserted, and the causal "since" is a link. |
| "The rollback failed because the migration is not idempotent." | `@s1 stated` ("fail", "the rollback") with `because $s2`; `@s2 stated` ("be idempotent", "the migration", `polarity negated`). |
| "If Ana works at Acme, does she have access to the lab?" | `@s1 stated` ("work at", `certainty supposed`) + `query` with `if $s1`. |
| "I am asking because Wojciech grows lavender." | a plain `stated` ("grow"); no link: the connective explains the asking. |
| "Is the flumbix of Ana paid?" | the understood part as a query with a placeholder, and `unparsed` with the span "flumbix", `near $q`, `hint subject`. |
| "Ana is a parent of Maria. Is Ana a parent of Maria?" | `stated` + `query`; the result is not hypothetical. |
| "Is Ana *still* at Acme?" | `assumed` (Ana works at Acme, `basis implicature`, no validity: the message names no time) + `query`. |
| "Did Ana visit Cluj *again*?" | `assumed` (Ana visited Cluj, `basis implicature`) + `query`. |
| "Who made The Salt Road?" | `assumed` (`relation "mean"`, `"made"` → `"wrote"`, `basis disambiguation`) + `query` with `relation "make"`; the host asks when "make" is ambiguous in its lexicon. |
| "Ana manages Irina. Does she live in Cluj?" | `stated` + `assumed` (`relation "refer to"`, `"she"` → `"Ana"`, `basis disambiguation`) + `query` about Ana. |
| "Ana works at Acme and Irina works at Zeta. Does she live in Cluj?" | `unclear kind ambiguous` with the readings "she is Ana" and "she is Irina". |
| "Is everyone at Acme certified?" / "Is nobody at Acme certified?" | `mode every` with a `scope`, affirmed or negated. |
| "Why is the billing service down?" | `mode explain`. |
| "Aurelia quit because of Shirin." / "Ana got sick from the oysters." | the cause is a role of the causal relation: `role topic "Shirin"` for "because of", `role source "the oysters"` for "from"; a "because" clause that is a whole proposition is its own wire, linked with `because $id`. |
| "Room A and room B are booked. Is room C free?" | two `stated` + `assumed` (room C not booked, `basis closure`) + `query`. |
| "Dorin finished before Avela." | `stated` + optionally `assumed` (the reversed relation negated, `basis world`). |
| "Suppose Maria works at Acme. Would she work at Acme?" | `stated certainty supposed` + `query`. |
| "I think the door is open. Are the rooms connected?" | `stated certainty hedged` + `query`. |
| "Ion says that Maria left." | `stated speaker "Ion"`: attributed, conditional. |
| "Is the bank open?" (two banks known to the host) | `query` with `"the bank"`; the host finds two entities and asks. The model never chooses. |
| "Tweety is a bird. Can Tweety fly?" | `stated` + optional `assumed` (`basis default`) + `query`; the default is ignored unless the host branches. |
| "asdf qwer" | `unclear kind gibberish`, alone. |
| "Thanks!" / "Write a poem." | `unclear kind no_request`, alone. |
| "The square circle is red. Is it red?" | formalized as written (`stated` + `query`); the model does not judge sense. |

## Evaluation and the preregistered `basis` criterion

Formalization metrics ignore `basis`: canonical match compares programs with every `assumed.basis` removed, and execution signatures are unaffected because `basis` has no runtime effect. The evaluator reports separately (`report.propositions`, `eval/propositions.mjs`): propositions matched by identity (folded relation phrase, sorted folded role values, polarity, validity text), proposition recall and precision, **stated/assumed separation accuracy** (matched propositions whose wire type agrees), the counts of stated-as-assumed and assumed-as-stated confusions, and **basis** coverage (labelled gold assumptions whose matched predicted assumption carries any basis; an omitted basis is uncovered, not wrong), accuracy (exact agreement among covered ones) and a confusion matrix. Gold rows may also declare `expected.user_statements` and `expected.model_assumptions` (linked atom, validity, certainty or basis).

Preregistered keep/drop criterion for `basis` (DS010): the criterion is evaluated only when the sealed test under `eval/suites/**` has at least **50 labelled `assumed` wires**. If, for a qualified model, basis accuracy is below **0.80** or coverage below **0.50**, `basis` is removed from the model language. If accuracy ≥ 0.80 and coverage ≥ 0.50 hold on **two consecutive qualified runs**, a specification amendment may consider making `basis` influential (for example allowing `branch` only for `world` or `default`). Until such an amendment, `basis` has no runtime effect whatever its accuracy. No training is authorized by this section.

# DS021 — Model surface: the one small-model language

## Scope

This specification is the normative contract of the small model's language (the model surface). The small model authors exactly five wire types: `stated`, `assumed`, `unclear`, `query` and `constraint`. It never authors host plumbing (`resolve`, `pack`, `solve`, `reason`, `cnl`, `remember`, `clarify`, `expand`, `value`, `jsEval`, `fact`, definitions or policy).

**The small model has no context.** Its input is the user's message only: no entity or predicate shortlist, no identifiers, no lexicon, no background knowledge and no `now`. It writes what it understood as strings. Linking those strings to knowledge — relations to predicates, values to entities, temporal expressions to intervals — is a host step after the model, performed deterministically with the reviewed lexicon; when it is unknown or ambiguous the host asks the user with a generated `clarify`.

There is one model language, with no versions or backward compatibility. `premise` and the entity/predicate shortlist are removed from the language, the parser and the prompts; the model never refuses. Trusted circuits state hypothetical inputs as `fact … source assumption` consumed through `assume` (DS004). The corpora in this language are generated by DS022 (`formalizer-v1` and the out-of-distribution suite `formalizer-ood-v1`); the earlier atom/identifier/context corpora were deleted with that regeneration.

Implementation: `sop/parser.mjs` (`SPEC`, `parseProposition`, `parseMatch`), `sop/enums.mjs` (`ROLE_NAMES`, `ENUMS`), `sop/unclear.mjs` (`UNCLEAR_KINDS`), `sop/linking.mjs` (host linking, time normalization, anchoring), `sop/propositions.mjs` (reports and identities), `sop/declarative.mjs` (`MODEL_TYPES`, admission and compilation), `sop/lexicon.mjs` (role declarations), `server/agent.mjs` (message-only prompt, anchoring guard), `server/llm.mjs` (prompts), `server/language.mjs` (answer language), `server/http.mjs` (trace), `eval/run.mjs` and `eval/propositions.mjs` (admission and metrics).

## Scope, non-goals and extension checklist

The small language exists for one job: turning a user's message — a question together with the assertions attached to it — into a **description of a problem**. It is not an action language, not a planning language and not an advice channel. Everything a user could mistake for a suggestion is a host decision. The five authorable wire types are enforced in `sop/declarative.mjs` (`MODEL_TYPES`) and re-checked at admission in `server/agent.mjs` and `eval/run.mjs`; everything else belongs to the host or to trusted tool circuits, and is generated or supplied with recorded provenance.

### Explicit non-goals

1. **No execution.** The model never chooses an engine, a backend, a retrieval strategy or a definition handle. `dependencies(...).handles` must be empty for model output.
2. **No writes.** A `stated` or `assumed` proposition is never recorded; a sourced `fact` and an explicit trusted `remember` are separate, host-authorized operations.
3. **No advice, recommendations or action proposals, and no refusal.** If a user asks "what should I do?", the model formalizes the underlying question as it understood it; the host answers what it can compute, asks with a `clarify` when a required relation, identity, date or scalar is missing, or states "I understood the question as …; I cannot compute this kind of answer yet" when no engine exists. Presenting guidance that the runtime did not compute is forbidden, because the CNL layer renders results, it does not invent them.
4. **No procedure selection.** The model cannot pick or parameterize template/procedure handles; expansion is host-approved and audited.
5. **No vocabulary at all.** The model never sees or chooses identifiers: it writes the relation phrases and names of the message, roles from a closed context-free inventory, and temporal expressions as written. The host links them to its reviewed lexicon or asks the user; a string never becomes a new identifier by being written.
6. **No reasoning in the model.** The model does not judge whether a readable message is contradictory, incomplete, relevant or answerable; it formalizes it. `unclear` covers only unintelligible text and messages with neither a statement nor a question.

### Is the current construct set sufficient?

Yes, for every family whose interpreter exists and is validated in this repository: relation/role and argument reversal, multi-hop composition, joins, explicit negation and conflict, open-world absence, temporal windows and cutoffs, scoped synonym resolution, finite numeric constraints and optimization, clarification of missing/ambiguous dependencies, user assertions versus user suppositions versus model assumptions, approved-procedure reuse, expression composition, universal questions over a restriction, time questions (when, since when, until when, how long, how many times), where/how questions, and why questions answered with a derivation. Executed evidence for every family and question form lives in the DS022 corpora: each row's target is executed against its verification world and must reproduce the stored result.

The families that the corpus manifests list as blocked (abduction, default-with-exception, counterfactual, planning, causal, agentive intention, general quantification) are **model-formalizable**; general quantification is the universal question form (`mode every`, computed over the known members): the model writes what the message says with `stated`, `assumed` (for example `basis default` for a default) and `query`, and never refuses. How the reasoning engine treats these families is not decided by this specification; until an audited interpreter exists, the host reports an understood-but-not-computable problem rather than guessing.

### Conservative checklist for a future construct

A new model-authorable construct is admissible only when **all** of the following hold. Until then it stays a proposal (recorded in `questions.md` or `TODO.md`), never in the parser.

1. **Problem-shaped.** It states something about the problem (a proposition, a question, a restriction), never a procedure, action, preference or suggestion.
2. **Context-free.** The model can write it from the message alone, as strings, without identifiers, vocabulary, knowledge or a clock; any linking is host work.
3. **Host-evaluable.** An audited interpreter exists that decides the construct without inventing meaning, and it reports status, completeness and route.
4. **Independently oracle-able.** A second, independent reference can produce the expected result for the corpus, so the corpus never confirms itself.
5. **Non-writing.** The construct cannot change memory; any write stays a separate trusted operation.
6. **Honest when not computable.** When the construct's interpreter is absent, the host answers that it understood the problem but cannot compute it, and the model cannot force a fallback; the only `unsupported` result left is an explicitly requested, unavailable backend in a trusted circuit (AGENTS rule 8).
7. **Reviewable.** The field set, cardinality, canonical form and rejection cases are documented in the wire reference, with valid and invalid examples that `tests/wire-help.test.mjs` executes.

### Host-rendered explanation of statements and assumptions

The user asked that the system can explain the assumptions it made. That does not require a model capability: every model-origin turn returns `user_statements` and `model_assumptions` in the packet (and in the HTTP `chatSop` trace), each with a host-rendered sentence built from the wire's own strings — "You stated: …", "You supposed: …", "According to Ana: …", "The model assumed: … (basis: closure)" — plus the linked predicate and atom, validity, treatment and, for conditional use, whether the proof used it and whether it was defeated. Because the prose is produced by the host from the recorded wire, an explanation can never claim a reading the model did not declare.

## Proposition form

`stated`, `assumed` and every query `match` block carry one proposition as keyword lines, one keyword per line.

| Keyword | Cardinality | Value | Meaning |
| --- | --- | --- | --- |
| `relation` | exactly once, required | one JSON-quoted nonempty phrase | The relation in the message's language or normalized: `"works at"`, `"parent of"`, `"lucrează la"`. |
| `role` | 1–4 lines, required; a name at most once | `role NAME VALUE` | NAME is from the closed inventory `ROLE_NAMES` = `subject`, `object`, `recipient`, `location`, `source`, `destination`, `instrument`, `time`, `topic` (`role_unknown`, `role_duplicate`). VALUE is a JSON-quoted string exactly as the thing is mentioned in the message, or a safe integer; in a query `match` also a `?variable`. Never a `$reference`, `~handle`, bare identifier, or quoted sigil text (`proposition_not_ground`). |
| `polarity` | exactly once, required | `affirmed` \| `negated` | `negated` is explicit negation; absence of evidence is never expressed this way. |
| `valid` | `stated`/`assumed` only; at most one line per form; optional | `valid on "TEXT"`, `valid from "TEXT"`, `valid until "TEXT"` | The temporal expression as written. `on` excludes `from`/`until` (`time_form`). Absent means timeless: the model states no time it was not given. |

**Values as written, relations as meant.** A role value, a `speaker` and a `valid` text are quoted exactly as the message writes them, typos and missing diacritics included; the host matches entity strings after case and accent folding and asks when a misspelled name does not resolve (it never resolves an identity by similarity). The relation phrase is the intended relation, normalized to a lemma when the message inflects or misspells it (`"work at"` for "wroks at"). "Because of <entity>" is a role of the causal relation (`role topic` for the cause, `role source` for "from"/"de la"); a "because" clause that is a whole proposition is its own proposition (the observation `stated`, the asked explanation a query). Remarks about the user's own situation or purpose ("I have a meeting tomorrow", "My boss asked me") are not part of the problem and are not formalized.

**Host linking.** After the model, the host links each proposition (`sop/linking.mjs`):

1. *Relation.* The phrase is compared, after case and accent folding, with every lexicon predicate's identifier (underscores as spaces), labels, aliases in all languages and gloss (`description`). Auxiliaries and articles (`is`, `are`, `a`, `the`, `este`, …) are dropped and a plural or third-person `-s` and a final `-e` are ignored, so `"work at"` meets the alias `works at` and `"is a parent of"` meets `parent of`; other inflections (for example `-ing` forms) need a lexicon alias. Among the matching predicates, the role set decides: a `stated`/`assumed` proposition must bind exactly the roles the predicate declares; a query `match` must use only declared roles, and each unmentioned role becomes a fresh host variable. No match → `unknown`; several fitting predicates → `ambiguous`; matches with other role sets → `role_mismatch`. Each of these stops the turn with a host `clarify` (`reason: unresolved_link`) naming the candidates; nothing is guessed.
2. *Roles.* A predicate maps its argument positions to the inventory with `role NAME TYPE` lines (DS004 ontology SPEC; any other name is rejected by the lexicon). A predicate that only has legacy `args` is unnamed: with one or two arguments its positions are `subject` and `object`; with more it cannot be linked until roles are declared, and the corpus audit flags it.
3. *Values.* Quoted strings are resolved as entities of the argument's type by the generated `resolve` wires (exact, then accent-folded aliases; the existing identity rules of DS004). Unknown or ambiguous entities block dependent work and produce the existing host clarification (`reason: unresolved_dependency`). A numeral string fills an integer argument as a number.
4. *Time.* `valid`, and a model query's `at`, `during` and `asof`, are normalized against the runtime clock: ISO dates and UTC timestamps, `YYYY`, `YYYY-MM`, an English or Romanian month name or abbreviation with a year, a day, month and year ("3 March 2025", "March 3, 2025", "the 3rd of March 2025", "3 martie 2025", "3 mar. 2025", "03.03.2025"), a range "A – B" (from the start of A to the start of B), `now`/`acum`, today/yesterday/tomorrow (`azi`, `astăzi`, `ieri`, `mâine`), with an optional leading preposition. `on` is the whole period; `from` starts at the period's start; `until` ends, exclusively, at the period's start; `at` is the period's start; `during` is the period. Anything else becomes a host `clarify` ("Which date or period do you mean by …?").

5. *Time variables.* In a query match block, `role time ?t` on a relation that declares a `time` role is an ordinary argument. On a relation without one it asks for the validity interval of the matched fact: the host drops the role from the atom and writes the host-only field `span ?t`, which binds `?t` to the interval (with several match blocks, the interval in which they hold together). A query with a span and neither `at` nor `during` looks at the whole timeline.
6. *Filter literals.* A quoted literal in a model `filter` (`filter ?x != "Ana"`, "besides Ana") is an entity as written; the host resolves it like a role value and asks when it is unknown or ambiguous.

The linked result is the existing positional atom (`works_at maria lab_alpha`), so reasoners, the SWI adapter and the oracles are unchanged.

## `stated`

A formalized report of one proposition that the user's message puts forward (the question and the attached assertions). Additional fields:

| Keyword | Cardinality | Values | Meaning |
| --- | --- | --- | --- |
| `certainty` | exactly once, required | `asserted` \| `hedged` \| `supposed` | The user's commitment: `asserted` (the user asserts it), `hedged` ("I think …"), `supposed` ("suppose …", "if …"). |
| `speaker` | at most once, default `user` | `user` or a JSON-quoted name | Reported speech ("Ion says that …"). |

No other field is accepted; in particular there is no `holds`, `quote`, `source`, `basis` or write field.

**Anchoring.** There is no quotation. The agent guard checks mechanically that every role value of a `stated` wire, and a non-user speaker, appears in this turn's message (question plus attached assertions): the value's tokens must match consecutive message tokens after case, whitespace and accent folding, each within a small edit distance (optimal string alignment: 0 for tokens up to 3 characters, 1 up to 7, otherwise 2) or as a short inflection sharing all but the last character of a token of at least four characters. Otherwise the turn is rejected with `stated_value_not_in_message`, and the model should use `assumed` or a query variable. The relation phrase is not anchored, because the model may normalize it.

**Semantics.**

| Statement | Lowered host value | Used by the generated `solve` as | Result marking |
| --- | --- | --- | --- |
| `certainty asserted`, speaker `user` | turn-local `fact … source user` | `data` (evidence) | not hypothetical |
| `certainty hedged` or `supposed` | turn-local `fact … source assumption` | `assume` (DS004 defeat semantics) | `hypothetical: true` when the proof uses it |
| any certainty with a `speaker` | turn-local `fact … source assumption` | `assume` | `hypothetical: true`; reported "According to …" |

User suppositions always take part in the primary result: the user authorized them. A contrary admitted fact or asserted statement defeats them exactly as DS004 describes, and the report marks `defeated: true`. Exact duplicates (same folded relation, role values, polarity and validity text, certainty and speaker) are rejected (`stated_duplicate`); contrary statements are accepted and the result exposes the conflict. Constraint problems do not consume statements.

**Lifecycle.** Authored → parsed → anchored → linked → lowered to a turn-local `fact` → consumed by this turn's generated `solve` wires → reported → discarded from execution state. A statement is never recorded by `remember` (none is generated), never published and never reinforced (local facts are excluded from proof-use promotion). Asserted user statements are carried across turns in caller-owned conversation context (`context.statements`, origin `user-statement`, linked atom, validity and the original input text) and re-supplied by the host as turn-local `fact … source user` evidence; they are not sent to the model. Hedged, supposed and reported statements are not carried. A statement-only turn returns `status: context_updated`.

## `assumed`

One proposition the model adds during intent detection. One wire type, no subtypes, no `certainty`; its values need not appear in the message. Additional field:

| Keyword | Cardinality | Values | Meaning |
| --- | --- | --- | --- |
| `basis` | at most once; optional, absent means `unspecified` | `closure` \| `default` \| `disambiguation` \| `implicature` \| `world` | Descriptive label: treating a list as complete; a typical case applied to this instance; a chosen reading of an ambiguous word, referent or scope (never an entity identity); a presupposition of the wording; general world knowledge. |

**Making an interpretation explicit (owner decisions Q-DATA-4 and Q-ARCH-1).** `assumed` is optional and need not be tied to the other wires. The model uses it to state the reading it chose whenever a message is vague or has several readings, so the choice is visible and reported:

- *An ambiguous word*: `relation "mean"` (Romanian `"însemna"`), `role subject` the words as written, `role object` the chosen reading, `basis disambiguation` ("Who made The Salt Road?" → `"made"` means `"wrote"`). The query keeps the words of the message; the host still links them and asks when they are ambiguous.
- *An ambiguous referent*: `relation "refer to"`, `role subject` the pronoun or description as written, `role object` the chosen antecedent as written, `basis disambiguation`. The convention is the subject of the preceding asymmetric sentence ("Ana manages Irina. Does she live in Cluj?" → `"she"` refers to `"Ana"`), and the query uses the antecedent. A pronoun with a single possible antecedent is resolved without an assumption.
- *A presupposition of the wording*: "still", "again" and similar triggers presuppose an earlier state or occurrence; the assumption states that proposition with `basis implicature` and no validity (the message names no time). Such an assumption may restate the queried proposition; the corpora keep these cases few.
- *An ambiguity with no preferable reading* is reported instead with `unclear kind ambiguous` and its readings (see `unclear`).

Assumptions that restate the queried proposition (closure, defaults, presuppositions) are allowed but not over-generated.

**Validation.** The proposition rules above apply. An assumption equal to a statement of the same turn is rejected as redundant (`assumed_duplicates_stated`); a contrary one is accepted. At most `policy.maxModelAssumptions` (default 8) are accepted; more reject the turn (`too_many_assumptions`).

**Semantics.** Host policy `modelAssumptions` decides the treatment; `basis` never influences trust, admission or reasoning.

| Policy | Linking and lowering | Effect | Report |
| --- | --- | --- | --- |
| `report` (default) | linked only for the report; an unlinkable assumption is reported with `predicate: null` and never blocks the turn | The primary answer is computed without assumptions. | `treatment: "reported"`, `used_in_proof: null`, `defeated: null` |
| `branch` | linked and resolved like a statement (an unknown or ambiguous string becomes a host `clarify`, so an assumption never chooses an identity); turn-local `fact … source assumption` consumed by a second generated `solve` per query, together with the user's evidence and suppositions | The primary answer is unchanged and assumption-free; the branch result is reported separately and marked hypothetical when its proof uses an assumption. | `treatment: "branched"`, `used_in_proof`, `defeated`; `assumption_branch` per query |

**Lifecycle.** Authored → validated → reported (and, under `branch`, linked and solved in the branch) → discarded. Never stored, never reinforced, never rendered with fact wording ("The model assumed: …"), never carried across turns; the model restates an assumption when it still needs it.

## `query`

A model query keeps the `query` fields of DS004 (`where`, `select`, `filter`, `mode`, `at`, `during`, `asof`, `limit`) and adds `scope` and `measure` (below), with two differences. Every `where` leaf is a `match … end` block holding one proposition (the keyword lines above, `?variables` allowed, no `valid`); `all`/`any`/`end` groups combine match blocks. An atom leaf is rejected (`query_needs_match`). `at`, `during` and `asof` take a JSON-quoted temporal expression normalized by the host. The canonical form nests the block lines under `match` and closes each block with `end`:

```sop
@q query
  where all
    match
      relation "works at"
      role subject ?who
      role object "Alpha Lab"
      polarity affirmed
    end
    match
      relation "member of project"
      role subject ?who
      role object "Delta Project"
      polarity affirmed
    end
  end
  select ?who
  at "2026-09-01"
```

`match` blocks belong to the model language; the trusted runtime only lowers linked atom queries.

### Question forms

Every question word has one formalization; the model writes the question it reads and never rewrites it into another form (owner decisions Q-DATA-1 and Q-DATA-2, 2026-09-28). The semantics are computed by the reference reasoner (`reasoning/reasoner.mjs` `evaluate`); a form without an interpreter would be answered `not_computable` with the formalization shown.

| Question | Formalization | Host semantics |
| --- | --- | --- |
| yes/no, "is it true that …" | `where` match blocks, no `select` (`mode exists` when variables occur) | status of the proposition: `supported`, `refuted`, `both`, `unknown` |
| who / what / which | `select ?x`, the asked role as `?x` | the bindings |
| how many | `mode count`, `select ?x` | distinct bindings |
| all / every / each ("Is everyone at X certified?") | `mode every`; `where` is the restriction (the domain), `scope` what must hold for each member, sharing its variables | `refuted` with `counterexamples` when a known member explicitly fails the scope; `supported` when every known member satisfies it and the restriction has a member; otherwise `unknown`. The check covers the members known to the host. |
| no / nobody / none ("Is nobody at X certified?") | `mode every` with a `negated` scope | as above; the determiner "no" is the only form written with a negated scope, and "all" is never rewritten as "nobody … not" |
| which groups have only … ("Which teams have only certified players?") | `mode every` with `select`; members are grouped by the selected variables | the groups whose members all satisfy the scope |
| is anyone … not … | `mode exists` with a negated match block | an explicit counterexample |
| when | `role time ?t` in the match block, `select ?t` | the validity interval of the matched fact (`span`) |
| since when / until when / how long | the same, plus `measure start`, `measure end` or `measure duration` | the interval's start, its end (`open` when ongoing) or its length in whole days up to the runtime clock |
| how many times | `mode count`, `select ?t`, `role time ?t` | the number of distinct validity intervals |
| where (where to, where from) | `role location ?place` (`destination`, `source`) | the bindings |
| how (means or manner: "How does Ana commute?") | `role instrument ?how` | the bindings |
| why / how come / how did … come to be | `mode explain` over the proposition (negated for "why not") | the status plus `explanation`: `derivation` (the rules and the facts they used), `recorded` (a recorded fact, no further reason) or `none` |

A claim check ("True or false: …") is a yes/no query and the claim is not `stated`; several questions in one message are one `query` each; a numeric problem is a `constraint`; a message with statements only has no query (`status: context_updated`); `unclear` covers the unintelligible, the no-request and the ambiguous message. The corpora label these eighteen question types (`yes_no`, `wh`, `count`, `universal`, `when`, `since_when`, `until_when`, `how_long`, `how_many_times`, `where`, `why`, `how`, `claim_check`, `multi`, `numeric`, `none`, `unclear`, `ambiguous`); the wire help page `docs/wire_typs/question-types.html` gives one executed example of each, and `docs/wire_typs/model-guide.html` explains the language from the model's point of view with English and Romanian examples.

`scope` is required by `mode every` and forbidden otherwise (`every_needs_scope`, `scope_needs_every`); `measure` needs exactly one selected variable written as `role time ?t` (`measure_needs_time_variable`); a query asks for at most one time (`time_variable_multiple`); `mode explain` selects nothing (`explain_no_select`); `span` is host plumbing and is rejected in model output. A proportional quantifier ("most", "half") has no form yet; it is recorded as a proposal in `TODO.md`.

## `constraint`

A model `constraint` must state `task` (`prove` \| `possible` \| `optimize`): `prove` and `possible` give opposite readings of the same claim, so the choice is never a silent default (`constraint_task_required`). Trusted circuits keep the `prove` default. Constraints are numeric and need no linking.

## `unclear`

| Keyword | Cardinality | Values |
| --- | --- | --- |
| `kind` | exactly once, required | `gibberish` \| `no_request` \| `ambiguous` |
| `reading` | 2–4 lines with `kind ambiguous`, none otherwise | one JSON-quoted short paraphrase of a candidate reading, in the message's language |
| `language` | at most once | `en` \| `ro` |

The model does not reason, so it reports only what it can recognise from the text: `gibberish` (unintelligible text), `no_request` (neither a statement nor a question: "ok", "thanks", a greeting, or a request for something unrelated such as "write a poem") and `ambiguous` (owner decision Q-ARCH-1): the text itself shows two or more readings and none is clearly preferable — a pronoun after two parallel clauses, a bare homonym ("Is the court free?"), the scope of "all … not", a prepositional-phrase attachment. When one reading is preferable the model resolves it with `assumed` (`basis disambiguation`) instead; resolved ambiguity is the common case. The host lists the readings, numbered, after the fixed reply, and the packet adds `readings` and `next: 'choose_reading'` (`unclear_readings` rejects fewer than two, more than four, repeated, empty or unquoted readings, and readings on another kind). A semantically odd but readable message is formalized normally; the model does not judge contradictions, completeness or relevance. `unclear` must be the only wire of the output (`unclear_not_alone`). The host executes no circuit and renders the fixed reply for the kind from the single table `UNCLEAR_KINDS` in `sop/unclear.mjs` (English and Romanian); the packet is `{kind: 'unclear', status: 'unclear', unclear_kind, language, next: 'rephrase'}`. Renaming or adding a kind changes that table, this section and the help page only. `language` selects the reply language only when the caller selected none.

`unclear` differs from `clarify`: `clarify` remains host-generated and never model-authored (DS004; see "Scope, non-goals and extension checklist"); it asks for a relation, entity, date or scalar that the host could not link or determine for a formalized problem. `unclear` is the model's report that there is nothing to formalize.

## No model refusal

The model always formalizes a readable request; there is no model-level `unsupported`. When the host has no engine for a formalized problem (the reasoning route returns `unsupported` for a model-origin problem), the answer is `status: not_computable` with `engine_status: unsupported`, `understood_as` (the one-line canonical formalization) and the controlled reply "I understood the question as: …. I cannot compute this kind of answer yet." (Romanian: "Am înțeles întrebarea astfel: …. Încă nu pot calcula acest tip de răspuns."). The formalization is also in the trace. The only `unsupported` result that remains is AGENTS rule 8 in trusted circuits: an explicitly requested, unavailable backend, reported with `route.backend` and `fallback: null`. How the reasoning engine will treat the formerly blocked families (see "Is the current construct set sufficient?") is not decided by this specification.

## Prompts

The `formal` prompt choice (`promptProfile`, [DS012](specsLoader.html?spec=DS012-local-server.md)) sends the fixed model-language instructions (`server/prompts/formalizer.txt`) followed by `MESSAGE` and the user's text; the `bare` choice for a fine-tuned formalizer sends the user's text alone (`barePrompt(text)`). Neither includes a `CONTEXT` block, earlier turns, carried statements, a pending clarification or the host clock. Because the model sees no pending clarification, an answer to a host question is formalized from the new message alone; the host keeps the pending authored SOP in the packet.

## Packet and trace fields

A model-origin turn adds to the result packet:

- `user_statements`: one entry per authored `stated`: `id`, the authored `relation`, `roles`, `polarity` and `valid_text`, the linked `predicate` and `atom`, the normalized `valid {from, until}`, `certainty`, `speaker`, `treatment` (`evidence` \| `supposition`), `conditional`, `in_circuit`, for suppositions `used_in_proof` and `defeated`, and the host-rendered `statement` repeating the model's strings ("You stated: works at (subject: Maria; object: Alpha Lab).", "You stated tentatively: …", "You supposed: …", "According to Ana: …").
- `carried_statements`: asserted statements supplied from earlier turns.
- `model_assumptions`: one entry per `assumed`: the same fields, `basis` (or `unspecified`), `treatment`, `used_in_proof`, `defeated`, `statement` ("The model assumed: …").
- `assumption_policy`: `report` or `branch`; `assumption_branch` under `branch`: `{problem, status, answers, hypothetical, defeatedAssumptions, route, text}` per query.
- A host link failure returns `status: clarify` with `reason: unresolved_link` and `required` listing each unlinked relation (`status`, `candidates` with their roles) or time expression.

When a primary result is hypothetical, the controlled text lists each conditional statement it rests on ("Condition: …"); under `branch` it adds "Only under the model's assumptions: …". The HTTP trace (`chatSop`) carries `answer_language`, `language_source`, `user_statements`, `carried_statements`, `model_assumptions`, `assumption_policy`, `assumption_branch`, `unclear` and `understood_as`, next to the existing fields.

## Answer language

The default answer and CNL language is English (`cnl.language` defaults to `en`). The chat API accepts an optional `language` (`en` \| `ro`); otherwise the agent honours an explicit request in the message, detected deterministically by `server/language.mjs`: a fixed list of request phrases next to a language name, after accent folding ("răspunde în română", "answer in Romanian", "please reply in English", …). Writing in Romanian is not a request. Precedence: API field, then message request, then English; the trace reports `language_source` (`request`, `prompt` or `default`). The host-generated `cnl`, the `unclear` reply, the not-computable reply, the clarification questions of host linking and the report sentences use the selected language. The chat page offers the selection.

## Boundary rule and borderline cases

> `stated` only when the model is sure the claim comes from the user's message. Anything the model adds, infers, completes or presupposes is `assumed`. When in doubt, `assumed`.

| Utterance | Formalization |
| --- | --- |
| "Since Nera left the lab, who runs it now?" | `stated` (relation "left", subject "Nera", object "the lab", asserted) + `query`: an assertion embedded in a question is still asserted. |
| "Ana is a parent of Maria. Is Ana a parent of Maria?" | `stated` + `query`; the result is not hypothetical. |
| "Is Ana *still* at Acme?" | `assumed` (Ana works at Acme, `basis implicature`, no validity: the message names no time) + `query`. |
| "Did Ana visit Cluj *again*?" | `assumed` (Ana visited Cluj, `basis implicature`) + `query`. |
| "Who made The Salt Road?" | `assumed` (`relation "mean"`, `"made"` → `"wrote"`, `basis disambiguation`) + `query` with `relation "make"`; the host asks when "make" is ambiguous in its lexicon. |
| "Ana manages Irina. Does she live in Cluj?" | `stated` + `assumed` (`relation "refer to"`, `"she"` → `"Ana"`, `basis disambiguation`) + `query` about Ana. |
| "Ana works at Acme and Irina works at Zeta. Does she live in Cluj?" | `unclear kind ambiguous` with the readings "she is Ana" and "she is Irina". |
| "Is everyone at Acme certified?" / "Is nobody at Acme certified?" | `mode every` with a `scope`, affirmed or negated. |
| "Why is the billing service down?" | `mode explain`. |
| "Aurelia quit because of Shirin." / "Ana got sick from the oysters." | the cause is a role of the causal relation: `role topic "Shirin"` for "because of", `role source "the oysters"` for "from"; a "because" clause that is a whole proposition is its own proposition. |
| "Room A and room B are booked. Is room C free?" | two `stated` + `assumed` (room C not booked, `basis closure`) + `query`. |
| "Dorin finished before Avela." | `stated` + optionally `assumed` (the reversed relation negated, `basis world`). |
| "Suppose Maria works at Acme. Would she work at Acme?" | `stated certainty supposed` + `query`. |
| "I think the door is open. Are the rooms connected?" | `stated certainty hedged` + `query`. |
| "Ion says that Maria left." | `stated speaker "Ion"`: attributed, conditional. |
| "Is the bank open?" (two banks known to the host) | `query` with `"the bank"`; the host finds two entities and asks. The model never chooses. |
| "Tweety is a bird. Can Tweety fly?" | `stated` + optional `assumed` (`basis default`) + `query`; the default is ignored unless the host branches. |
| "asdf qwer" | `unclear kind gibberish`, alone. |
| "Thanks!" / "Write a poem." | `unclear kind no_request`, alone. |
| "The square circle is red. Is it red?" | formalized as written (`stated` + `query`); the model does not judge sense. |

## Examples

Valid:

```sop
@s1 stated
  relation "works at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  certainty asserted
@q query
  where match
    relation "work at"
    role subject ?who
    role object "Acme"
    polarity affirmed
  end
  select ?who
```

```sop
@a1 assumed
  relation "be booked"
  role subject "room C"
  polarity negated
  basis closure
```

```sop
@u unclear
  kind no_request
```

Invalid: `holds` on `stated` (parse); a missing `polarity` (parse); `relation works_at` unquoted (parse); `role employee "Maria"` (parse, `role_unknown`); `role subject maria` unquoted (parse); `role subject ?who` in `stated` (parse, `proposition_not_ground`); `quote "…"` (parse); `valid on "…"` together with `valid from "…"` (parse); `basis world` on `stated` (parse); `certainty hedged` on `assumed` (parse); `basis guess` (parse); `role object $company` (parse); an atom `where` leaf in a model query (`query_needs_match`); an `unclear` next to a `query` (`unclear_not_alone`); `kind contradictory` (parse); an `assumed` equal to a statement (`assumed_duplicates_stated`); a `constraint` without `task` (`constraint_task_required`); a `stated` value absent from the message (agent guard, `stated_value_not_in_message`). The wire help pages (`docs/wire_typs/stated.html`, `assumed.html`, `unclear.html`, `query.html`) carry these as executed examples.

## Evaluation and the preregistered `basis` criterion

Formalization metrics ignore `basis`: canonical match compares programs with every `assumed.basis` removed, and execution signatures are unaffected because `basis` has no runtime effect. The evaluator reports separately (`report.propositions`, `eval/propositions.mjs`): propositions matched by identity (folded relation phrase, sorted folded role values, polarity, validity text), proposition recall and precision, **stated/assumed separation accuracy** (matched propositions whose wire type agrees), the counts of stated-as-assumed and assumed-as-stated confusions, and **basis** coverage (labelled gold assumptions whose matched predicted assumption carries any basis; an omitted basis is uncovered, not wrong), accuracy (exact agreement among covered ones) and a confusion matrix. Gold rows may also declare `expected.user_statements` and `expected.model_assumptions` (linked atom, validity, certainty or basis).

Preregistered keep/drop criterion for `basis` (DS010): the criterion is evaluated only when the sealed test under `eval/suites/**` has at least **50 labelled `assumed` wires**. If, for a qualified model, basis accuracy is below **0.80** or coverage below **0.50**, `basis` is removed from the model language. If accuracy ≥ 0.80 and coverage ≥ 0.50 hold on **two consecutive qualified runs**, a specification amendment may consider making `basis` influential (for example allowing `branch` only for `world` or `default`). Until such an amendment, `basis` has no runtime effect whatever its accuracy. No training is authorized by this section.

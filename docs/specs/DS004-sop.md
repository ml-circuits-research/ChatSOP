## Introduction

The `sop-agent-3` [SOP](wiki.html#definition-sop) profile is the executable knowledge and program language used for local circuits. JSON configurations, AST objects, and JSONL training rows transport or represent SOP; they are not alternative fact or query languages generated by the model.

## Core Content

### Parsing and wires

A declaration `@id type` creates a typed wire; `$id` consumes a value from that wire; `~id` names an approved definition; `?x` is a local logic unknown and is not a Prolog variable carried across unrelated queries. The parser and validator must reject unknown fields, invalid references, unresolved dependencies, and unsupported effects. `output ?x one` on a `solve` materializes a consumable `$x` wire only after a justified unique result; `many` retains a collection and `rows` preserves tuples. Ambiguous, incomplete, and unsupported results must not be silently collapsed into one answer.

### Reviewed lexical resolution

`resolve` is an executable lookup against the host-supplied, reviewed ontology, not a model-authored alias declaration. For example:

```sop
@company resolve
  text "Alpha Lab"
  language en
  kind entity
  type organization
@q query
  where works_at(maria, $company)
```

`text`, `language` (explicit two- or three-letter code), and `kind` (`entity`, `predicate`, or `concept`) are required; `type` is optional only for entities, and `domain` is an optional exact host-ontology scope. The host injects a `Lexicon` into `Runtime`; resolution yields a canonical symbolic ID when exactly one alias matches the requested language, kind, and explicit type/domain. Its indexed lookup applies bounded Unicode normalization, case and whitespace normalization, and accent folding only as a second exact-match pass. A folded collision is ambiguous, never settled by a ranking score. No substring, embedding, synonym inference, or negation removal proves identity. Results expose ontology content hash (`version`), host provenance, and match mode in output metadata. Unknown and ambiguous results leave dependent wires blocked; request clarification rather than choosing an arbitrary candidate.

An entity `$company` may occupy an atom argument and is checked against the predicate's argument type. A predicate ID cannot occupy a dynamically generated atom head (`$predicate(...)` is not SOP syntax): the host must pre-resolve the reviewed predicate, including its arity and argument direction, before emitting a literal canonical predicate head. Concepts are control-plane symbols, not executable predicate declarations. Runtime `resolve` never edits the lexicon, publishes assertions, grants permissions, or widens a model's vocabulary shortlist. Before the Agent formalizer call, deterministic retrieval supplies compact canonical mentions, blocked ambiguity and polarity cues alongside the *original* utterance; ordinary alias lookup adds no model call. A model-generated `resolve` is limited to surface forms from its input and canonical entities/predicates already authorized in that turn. Ontology aliases must be reviewed true same-role names: `mother` is not `parent`, `works_at` is not `employed_by`, and argument reversal is not a synonym.

### Execution and evidence

A `solve` may invoke the [linker](wiki.html#definition-linker) to select approved rules and relevant premises, then a reasoner to produce the result and binding; a [CNL](wiki.html#definition-cnl) wire exposes that controlled result. Facts, rules, queries, constraints, hypotheses, patterns, plans, and traces keep their distinct meanings. Absence of a premise does not establish explicit negation; a satisfiable model does not establish necessary truth. `jsEval` uses the restricted expression interpreter or approved handlers, never JavaScript `eval`, `Function`, `node:vm`, or executable code recovered from probabilistic memory.

Conversational agent turns must end in `cnl`, `clarify` or `assert`. The runtime tracks operation-produced packet identities: `cnl` rejects literal or expression-created imitations of result packets. Copying `status`, `answers` or proof-looking fields does not establish reasoning provenance. Approved expansion can forward the original packet without copying it.

Model output and document text are untrusted proposals: they cannot execute their own suggested rules, plugins, or policy, cannot publish reviewed facts, executable definitions, or ontology, cannot select identity, and cannot commit repository changes. Only the host performs those actions after validation and authorization.

### Assumptions and defeat

A `fact` wire declares `source user` when it records a quoted user assertion, and `source assumption` when the program states a guessed premise that must be consumed by an `assume` reference on `solve`/`reason`; an assumption-sourced fact without such a consumer is rejected, and it is never published, stored, or reinforced. The reasoner admits the assumption only while no admitted fact or rule-derived conclusion supports the explicit contrary of that atom: a contrary fact defeats the assumption entirely, so its derivations disappear instead of producing a conflict report. An assumption never defeats an admitted fact or its explicit negation, and two contradicting assumptions keep the `both` status rather than silently electing a winner. Every result whose evidence touches a kept assumption is reported with `hypothetical: true`; when the answer's proof rests only on admitted facts, the same assumption remains admissible but the result is not marked hypothetical. `hypothetical` never appears for an answer whose proof does not use an assumption.

### Publication and permissions

The host selects the user identity and write permissions, reviews executable definitions, and admits factual sources through `publishKnowledge`/ingestion. A document quotation and source hash are required when the ingestion contract calls for them. A generated SOP circuit cannot authorize its own publication or alter the library of approved rules, procedures, policies, and ontology definitions. The stable machine-readable capability catalog belongs at `sop/contracts/`; the retained requirements under `docs/legacy/requirements/` are supporting evidence, not an alternate runtime parser.

The `skills/material-to-sop/` workflow accepts UTF-8 TXT or Markdown sources no larger than 2 MB into a private hashed workspace. Its `prepare`, `review`, `curriculum`, `diagnose`, `candidate`, `probe`, `decide`, `freeze`, and `publish` commands separate quoted unapproved fact drafts from approved source claims and scoped rule candidates. Only a host-approved HARD candidate with executed positive, negative and boundary probes, matching decision and freeze hashes, and explicit authorization for a new empty base can be published; DEFAULT and PLAUSIBLE remain non-executable proposals. Probe results establish runtime behavior, not document truth, reviewer identity or permission. Retraction prevents future reuse without erasing earlier published history.

Overview / Input language

Input language: from what the user types to the circuit

Users write in any language, with typos and in several sentences. Since the owner decision of 2026-10-01 the system has no language pipeline of its own: the coding agent (omp) reads the message, in whatever language, and writes only circuits. Everything after it is symbolic and English: the validator, the KnowledgeLinker, the StrategyRouter, the reasoning strategies and the answer rendering. The small-model chain that used to clean, translate and parse the input (language identification, translation, proofing models, Stanza parsing) is frozen and archived in probably_obsolete/tinyLLMExperiments/.

1. The chain

  1. User messageAny language, with typos; one or several sentences.
  2. Query authorThe coding agent receives the message and the memory vocabulary (retrieved predicates by id, hints for names) and writes circuits: queries, constraints, unclear/unparsed markers, and session definitions or assumptions marked assumed. lib/query-author/
  3. ValidatorAdmits only what the circuit surface allows (DS014); bounded repair rounds.
  4. KnowledgeLinkerLinks entity strings to the base memory; asks when a name is ambiguous.
  5. Reasoning and English answerThe StrategyRouter chooses the strategy; the result packet is rendered in English.

There is no fallback parser. When no coding-agent model is available the turn answers parse_unavailable; the system never guesses a reading.

2. Behaviour on difficult input

  • Typos and mixed languages. The coding agent normalizes them while writing the circuit. A name stays as the user wrote it and is resolved by the KnowledgeLinker through the labels and aliases of the memory.
  • Unknown words. The query author handles an unknown word agentically (decision of 2026-10-01): it defines the word as a session definition marked assumed, asks the user, or assumes a reading and says so. The validator admits only what DS014 allows, and an assumption is reported, never used silently.
  • Ambiguity. Two equally good readings give one unclear wire with kind ambiguous and two to four reading lines; one clearly better reading is written as the query and the choice is reported. Gibberish and a message with no request are unclear too.
  • What the user states. A statement is turn-local evidence held in the caller's conversation context; a supposition, a hedge or reported speech is used only conditionally. Nothing a chat turn does writes to a repository.
  • Several questions become several query wires, answered together.

3. How the input stage is evaluated

The author is measured, not trusted: the query-forms dev set and the calibration of candidate models (tools/eval/query-forms, tools/eval/query-model-calibration) count correct circuits, wrong circuits (a definite wrong answer after execution, the dangerous class) and honest unknowns apart, and the planned benchmark (experiments/proposal/symbolic-vs-llm-benchmark.md) compares circuits written by small models against the same models answering from text. Evaluation is an engineering check: tests are lexically disjoint variants of the forms the system was built on, staged with a paired bootstrap interval and preregistered stopping rules (DS007, DS012).

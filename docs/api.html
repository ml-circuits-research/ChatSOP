Overview / API

API

The server exposes an OpenAI-compatible chat endpoint and the endpoints around it (base memories, sessions, drafts, the coding agent) under /v1. Normative contracts: DS009 for the server and DS022 for sessions and base memories. The commands below use $TOKEN, a bearer token minted on /admin or the CHATSOP_API_KEY value, and the default address http://127.0.0.1:9999. The JSON examples marked as product examples are executed against the live handlers by tests/product-api-docs.test.mjs. The capability endpoints of the frozen small-model branch (/v1/symbolic/*, /v1/understand, /v1/language/proofread, /v1/text-to-clean-english, /v1/emotion/detect, /v1/server/models, /v1/route, /v1/sessions/{id}/scope-answer, /v1/models/{id}/start) are removed.

2. Conventions

  • Authentication. Authorization: Bearer <token>, or the administrator session cookie of /login (the chat page uses it). Without either: 401 unauthorized; before the administrator password is set: 403 setup_required.
  • Errors. An invalid request, a limit or authentication is an HTTP error, always {"error": {"message", "type": "invalid_request_error", "code"}}: 400 invalid_request, unsupported_parameter; 401 unauthorized; 403 forbidden; 404 not_found; 413 request_limit; 429 concurrency_limit. An unknown parameter is refused, not ignored.
  • Answer language. A message may be in any language: the request parser reads it and writes an English circuit, and the answer is first rendered deterministically in English. When the message does not look English, an optional last step (answerLanguage, section 3) phrases that answer in the message's language. The English rendering is always kept in chatSop.english_text. There is no language or parser field; the formalization strategy is a session setting (section 6).
  • No available model. When no model of the session's formalization strategy can write the circuit, the chat turn answers parse_unavailable honestly; there is no fallback parser and another strategy is never substituted.

3. POST /v1/chat/completions

Body: model (the facade id listed by GET /v1/models, chatsop-local by default; another value is 400 unknown_model), messages (exactly one new user message; the server owns the history), conversation_id (a stable id keeps the conversation-local statements), session_id (the session whose base memory, settings and drafts the turn uses; without it, one automatic session per user and conversation on the default base memory), stream (true sends the verified result as server-sent events), user (must equal the authenticated principal) and chatSop.trustedSop (a trusted circuit of fact, event and remember wires run before the question). Any other field is refused. The answer is an OpenAI-style completion whose text is the deterministic English rendering of the result packet. The extension chatSop is the trace:

  • strategy: the formalization strategy that wrote the circuit (CodingAgent, LocalLLMDirect, LocalLLMStepByStep).
  • parse: parser, strategy, model, tried (models tried before it), backend, rounds, repairs ([{round, problems: [codes]}], the problem codes each repair round was asked to fix), vocabulary_dialog ({max_rounds: 2, rounds, expansions: [{round, trigger, hops, predicates, bytes}]}), retrieval (the offered vocabulary: predicate count, entity mentions, the schema neighbourhood, bytes, byte_budget, truncated), cost_usd, ms, cache.
  • model_sop (the authored circuit), circuit (the generated execution circuit), linking (surface, symbol, matched form, alternatives), session_circuits (session definitions proposed this turn, each with draft_id; accept or reject them with POST /v1/sessions/{id}/drafts/{draft}/accept|reject), user_statements, carried_statements, model_assumptions, assumption_policy, assumption_branch, unclear, understood_as.
  • status, completeness, retrieval (the slice: size, predicates, bounds, complete or not and why), route (requested, chosen, rule, features, alternatives, backend, fallback), verification (the oracle check of a routed answer, route.verification), provenance, reinforcement, cnl and english_text (the deterministic English answer), answer_language ({mode, message_language, applied, model, ms, tried, reason}: whether and by which model the answer was phrased in the message's language), pendingSop and required for a clarification, session (id, base memory, formalizer), latency_ms and formalization_ms, turn_ms.
curl -s -X POST http://127.0.0.1:9999/v1/chat/completions -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"model": "chatsop-local", "session_id": "demo-session", "messages": [{"role": "user", "content": "Where does Maria work?"}]}'

Answer language. Settings answerLanguage in config/runtime.json: mode is auto (the default: on when the message does not look English, off for English), always or off; models defaults to queryParser.models, GLM first, and is always non-Anthropic, through omp; timeoutSeconds is 40 and thinking is off. The model works strictly from the English answer and a compact result packet (status, answers, count, facts used with their sources). Every number and Wikidata id of the English answer must appear in its text; otherwise the next model is tried, and in the end the English answer is returned.

Chat errors: 503 parse_unavailable (no model of the strategy can run; chatSop.status: parse_unavailable with the reason), 422 parse_failed (the models ran and no valid circuit came back after the last repair round), 422 model_output_rejected (a circuit was written but not admitted or not executable; chatSop carries model_sop and rejection), 409 the conversation is still answering, 429 the server is busy, 504 the time limit (limits.timeoutMs, 180,000 ms by default) was reached, 413 the message is too long. Every error with a chatSop carries the parse record. GET /v1/models lists the facade and whether a coding-agent model is available.

ready is true when the default strategy can run; default_base names the base memory new sessions fork. The values above are illustrative. /v1/capabilities lists the endpoints with their parameters, the limits and the availability of the coding agent. /v1/cache/stats returns per-cache statistics (entries, bytes, hits, misses, evictions; any authenticated user) and /v1/cache/clear empties the caches; a failed computation is never cached.

5. Base memories

Sections 5 to 8 are the product endpoints (sessions, base memories, the coding agent). Their examples are executed against a live test server by tests/product-api-docs.test.mjs, with the repository's stub of the omp CLI (no model is called), so the model list and the costs below are those of the stub.

A base memory is a named, forkable knowledge store of the one memory strategy the product offers (sqlite; the associative and scan engines of memory/ are research engines), kept under chat_data/base_memories/<id>/ (DS022). Reading needs any token; creating, importing, forking, adding knowledge and deleting need the administrator session (the cookie of /login), because adding knowledge is an approval recorded with the approver in the memory's provenance. Circuits are checked by the knowledge validator (sop/knowledge/) together with the circuits already stored; a failing circuit answers 422 validation_failed with problems and warnings and nothing is written. A circuit may not contain jsEval, model-surface wires, query wires or governance fields.

Create or import

default_base is the base memory that sessions naming none fork from: chatData.defaultBase, which is the encyclopedic world-v1. When world-v1 is not loaded, as on the test server above, the minimal default (which imports core-min) is used. kind (optional) chooses what a new memory is built on: encyclopedic is a copy-on-write fork of world-v1 and answers 409 not_available when it is not loaded; minimal imports core-min and is the default when neither kind nor imports is given; empty has no imports. kind and imports are exclusive. Without circuits the memory holds no circuits of its own; with them it is imported all or nothing. id is optional (lowercase letters, digits, _, -). imports (optional array of base memory ids, default ["core-min"], [] for none) names the memories whose circuits are the lower layers of the new one: their classes, predicates and lexemes are its vocabulary, snapshotted at creation (a later change of the imported memory does not reach it). Chats link words against the vocabulary of their session's memory.

6. Sessions

A session works on its own copy of a base memory under chat_data/sessions/<id>/: the repository is cloned by hard links, the base circuits are copied. What the conversation adds stays in the session; it is visible to the user who started it and to an administrator. The chat request POST /v1/chat/completions carries session_id; without it one automatic session per user and conversation is used, on the default base memory. base in POST /v1/sessions is optional; without it the session forks the default base memory. Sessions abandoned for chatData.sessionTtlDays (14) are removed.

Settings

Body {omp_model?, formalizer?}; the same object is accepted as settings in POST /v1/sessions.

  • formalizer: the formalization strategy of the session's chat turns, CodingAgent, LocalLLMDirect or LocalLLMStepByStep; null uses the server default (CodingAgent). Another value is refused with 400. A turn whose strategy this server cannot run (see GET /v1/status) is refused with 503 parse_unavailable naming the strategy; it is never silently replaced by another.
  • omp_model: a model id from GET /v1/omp/models; CodingAgent tries it first for the session's chat turns and authoring requests, before the configured model chain (queryParser.models, zai/glm-5.3 then openai-codex/gpt-6-luna). null uses the chain.

7. The coding agent: models and authoring

Attached instruction or source files go to a coding agent (omp, with the skill sop-wire-authoring) that writes SOP circuits in a temporary folder. The circuits come back as proposed drafts; nothing is knowledge until the user accepts a draft. Setting omp.enabled, omp.bin, omp.timeoutSeconds, omp.maxFixRounds and the others are in config/runtime.json (DS022, skill omp-run).

GET /v1/omp/models

The models omp can use, each with a cost class: subscription (no per-token cost to the owner), paid_api or unknown. The list is cached; ?refresh=1 reads it again. An absent omp answers available: false with the reason.

POST /v1/author

files are UTF-8 text files (at most 10, 2 MB each); session makes the circuits a draft of that session (without it only the circuits are returned and the temporary folder is under chat_data/tmp/); wait: false answers 202 at once and GET /v1/sessions/<id>/requests/<request> reports the progress and the result. The folder holds TASK.md, the skill, the input and omp's output; the validator checks the circuits and sends the validator's output back to omp for at most omp.maxFixRounds rounds. Errors: 503 omp_unavailable, 429 omp_busy, 400 unknown_model.

8. Using the session: theory, query, commit

Circuits for a message

A message becomes a query through lib/query-author: the coding agent writes the query circuit from the memory\'s vocabulary (DS022). POST /v1/sessions/{id}/query takes either query (a query circuit, run as written) or message (a request in any language; the answer carries parse, model_sop and circuit). Whoever wrote the query, it is linked, retrieved over a slice, routed, verified and rendered by the same symbolic path. The answer packet and chatSop carry parse: {model, backend, rounds, cost_usd, ms, cache, ...}; with no available model the answer is parse_unavailable. A clear question that no predicate of the memory expresses is answered unclear (relation_not_in_memory), never with an invented relation.

The theory and a query over it

The theory is the base circuits followed by the circuits accepted in the session; a query circuit runs over it with the exact oracle.

Optional body parameters: reasoning (auto, the default, or one strategy id: reference, sql-sqlite, datalog-souffle, asp-clingo, datalog-e10, prolog-tabling) and verify (auto, always, never). With auto the StrategyRouter (DS006 "Routing rules") chooses the engine from the features of the circuit and the size of the retrieved slice; the answer carries route with requested, chosen, rule (small, scale, proof_or_mode_of_work, caller_budget, oracle, discrepancy), reason, features, alternatives and verification (a routed answer is re-checked by the oracle; on a disagreement the oracle's answer is returned with outcome: discrepancy). A named strategy runs exactly that engine and never another: an engine that is not installed or cannot express the circuit answers status: unsupported with the engine in route.backend and route.fallback: null.

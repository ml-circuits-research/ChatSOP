Overview / Capability APIs

Capability APIs

Every capability of the server has its own endpoint under /v1, usable alone by other projects and used one by one by the chat page. Normative contract: DS030 (with DS012 for the server, DS021 for the components and DS029 for tone). The commands below use $TOKEN, a bearer token minted on /admin or the CHATSOP_API_KEY value, and the default address http://127.0.0.1:9999. Every JSON example under "request" is executed against the live handlers by tests/capability-api.test.mjs.

2. Conventions

  • Authentication. Exactly as the other APIs: Authorization: Bearer <token>, or the administrator session cookie of /login (the chat page uses it). Without either: 401 unauthorized; before the administrator password is set: 403 setup_required.
  • Request. (The capability endpoints of sections 3 to 7; the product endpoints of sections 10 to 14 take the parameters listed there.) A JSON object with a non-empty string message and only the parameters listed for the endpoint (an unknown parameter is 400 unsupported_parameter). A message is limited to maxContextBytes (default 4800 bytes, 413 request_limit), a body to maxRequestBytes (default 65536), and at most maxConcurrentApi (default 16) capability requests run at once (429 concurrency_limit).
  • Answer. HTTP 200 with object (the result type), status (ok, partial or unavailable), errors (a list of {component, code, message, span?}), timings (total_ms of this request and compute_ms, the time of the computation that produced the result, so a hit shows the cost it saved), cache (hit when every expensive component came from a cache, else miss), cache_detail (each component: hit, miss or shared, a request that joined a computation already in flight) and versions (the API version and, for each component used, its version: SymbolicLM and interpretation versions, the model id, run, file and stamp of each language model, the tone configuration signature).
  • Errors. Only an invalid request, a limit or authentication is an HTTP error, always {"error": {"message", "type": "invalid_request_error", "code"}}: 400 invalid_request, invalid_message, invalid_parameter, unsupported_parameter; 401 unauthorized; 403 forbidden; 404 not_found; 413 request_limit; 429 concurrency_limit.
  • Never a total failure. Analysis returns what was understood and marks the rest. A model that cannot start, a sentence the parser fails on or a span the interpretation does not represent never turns the answer into an error: the answer is 200 with status: "partial" (or "unavailable" when nothing could be done), the failure is in errors and, where the message was not fully understood, clarify holds a follow-up for the user, for example I did not understand: “xyz”. Could you rephrase it?, with clarify_items (not_represented, uncertain or failed, each with its text). Degraded answers are never cached.

3. POST /v1/language/proofread

Parameters: message; sendAll (boolean, default from config/text-to-clean-english.json: every sentence goes to LanguageProofingLLM instead of only the sentences the cheap gate flags). The message is split into sentences and each is cleaned alone. The result is a proposal: original, clean, changed, spans (a word-level diff of equal, delete and insert parts), reasons (what the gate found), backend, confidence. A sentence whose model failed stays as written and is listed in errors with its span; sentence_cache counts the sentences served from the per-sentence cache. Each sentence is routed by its language: Romanian or mixed to the translator LLM (translator-llm, Qwen3-4B-Instruct Q4_K_M), English to LanguageProofingLLM (llm); routes lists, per sentence, {start, end, language, backend, ms?}, and versions.translator_llm names the translator file. When the translator cannot run, LanguageProofingLLM takes the sentence and the substitution is never silent: fallback is {from, to, reason, sentences} (otherwise null) and warnings holds one fallback entry; such an answer is not cached.

curl -s -X POST http://127.0.0.1:9999/v1/language/proofread -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"message": "Who manages the team.", "sendAll": true}'

4. POST /v1/understand

Parameters: message; rewrite (off, gated, always; default the registry setting of SymbolicLM; the SymbolicProofingLLM rewrite of DS021, gated sends only sentences whose Stanza trees are not certified and keeps a rewrite only when it is certified and keeps names, numbers, negation and quantifiers); accept (off, certified, certified_compare, the acceptance check; default of the chosen rewrite mode); emotion (boolean, default from config/emotion-detection.json); interpret (boolean, default true).

The result: interpretation.sentences, one row per sentence with status (verified: the CNL restates the sentence and a round trip through SymbolicLM gives the same structures; uncertain: no CNL is shown, only a raw analysis summary; failed: the sentence could not be analysed; empty: nothing to restate), cnl and cnl_sentences, certified (identical default and accurate Stanza trees), not_represented spans and the rewrite trace of that sentence; certified for the whole message; rewrite (the unit trace); emotion (signals, emoji, leftovers, the host-generated pragmatic circuit sop); leftovers (classified: not-represented spans explained as a pragmatic kind such as a greeting or politeness, with kinds; remaining: spans that stay unclassified); clarify and clarify_items. If the whole message cannot be analysed, the sentences are analysed one by one so that one failing sentence is marked failed while the others keep their interpretation.

5. POST /v1/symbolic/rewrite

Parameters: message; mode (gated, default, or always); accept (default certified for gated and off for always). always with accept: off calls SymbolicProofingLLM alone, sentence by sentence, without any Stanza analysis; every other combination runs SymbolicLM's gated pipeline. The result has input, output, applied and units (text, sent, accepted, reasons, output, certified). The rewrite model is started on demand; if it cannot start the answer is status: "unavailable" with the input unchanged.

curl -s -X POST http://127.0.0.1:9999/v1/symbolic/rewrite -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"message": "Whom does Ana like?", "mode": "always"}'

7. POST /v1/emotion/detect

Parameters: message; hasContent (boolean, default true: whether the message also states or asks something, for the advice). The EmotionDetectionSystem of DS029 (symbolic lexicons and patterns on; neural classifiers off): signals (kind, score, span, source, basis, emoji), emoji (one suggestion per kind, strongest first, with the span for a tooltip), leftovers, sop (the host-generated advisory pragmatic wires) and advice (how a reasoner may adapt). Signals are the system's subjective perception: advisory, never facts.

9. Cache behaviour

  • What is cached. Each LanguageProofingLLM and translator LLM call (per sentence), each SymbolicProofingLLM call (per sentence), the whole SymbolicLM analysis with its interpretation, the Stanza parse and the certification inside the SymbolicLM service (per sentence), the tone detection, and the proofread answer. Named caches: proofread, proofread-llm, symbolic-lm, symbolic-proofing-llm, emotion.
  • Key. A SHA-256 of the capability, the model or run version (registry file path, size and modification time of the model file, SymbolicLM version), the exact input and the options. A different option is a different entry; switching or replacing a model file never serves a result of the old one.
  • Bounds. Each cache holds tens to hundreds of recent entries (default 200 to 600), at most a few megabytes, evicts the least recently used entry and expires an entry after 15 minutes (30 minutes inside the SymbolicLM service).
  • Parallel use. Concurrent identical requests share one computation (shared in cache_detail); the other keys proceed independently. This holds for all users of one server process.
  • Failures. A failed or degraded computation is not stored.
  • Reuse by the chat. The chat page calls proofread, emotion detect and understand while the user reads the proposal, then sends the final formalize request, which calls the same cached analysis and tone detection instead of recomputing them.

10. Base memories

Sections 10 to 14 are the product endpoints (sessions, base memories, the coding agent). Their examples are executed against a live test server by tests/product-api-docs.test.mjs, with the repository's stub of the omp CLI (no model is called), so the model list and the costs below are those of the stub.

A base memory is a named, forkable knowledge store of one memory strategy (recall-memory, holo-memory, sqlite, scan, hybrid), kept under chat_data/base_memories/<id>/ (DS031). Reading needs any token; creating, importing, forking, adding knowledge and deleting need the administrator session (the cookie of /login), because adding knowledge is an approval recorded with the approver in the memory's provenance. Circuits are checked by the knowledge validator (sop/knowledge/) together with the circuits already stored; a failing circuit answers 422 validation_failed with problems and warnings and nothing is written. A circuit may not contain jsEval, model-surface wires, query wires or governance fields.

11. Sessions

A session works on its own copy of a base memory under chat_data/sessions/<id>/: the repository is cloned by hard links, the base circuits are copied. What the conversation adds stays in the session; it is visible to the user who started it and to an administrator. The chat request POST /v1/chat/completions carries session_id; without it one automatic session per user and conversation is used, on the empty default base memory. Sessions abandoned for chatData.sessionTtlDays (14) are removed.

12. The coding agent: models and authoring

Complex inputs, attached instruction or source files and the sentences the scope detector marks go to a coding agent (omp, with the skill sop-wire-authoring) that writes SOP circuits in a temporary folder. The circuits come back as proposed drafts; nothing is knowledge until the user accepts a draft. Setting omp.enabled, omp.bin, omp.timeoutSeconds, omp.maxFixRounds and the others are in config/runtime.json (DS031, skill omp-run).

POST /v1/author

files are UTF-8 text files (at most 10, 2 MB each); session makes the circuits a draft of that session (without it only the circuits are returned and the temporary folder is under chat_data/tmp/); wait: false answers 202 at once and GET /v1/sessions/<id>/requests/<request> reports the progress and the result. Errors: 503 omp_unavailable, 429 omp_busy, 400 unknown_model.

13. Routing: which path a message takes

POST /v1/route {session?, message, files?, understanding?, analysis?} says whether a message goes to SymbolicLM or to the coding agent, and why. Only the user's own act sends a message to the coding agent: attached files (files is their number) and the setting authoring: always. A detection only returns a suggestion (the scope detector says a sentence needs knowledge authoring, with the wire types, their confidence and the cue quoted; or SymbolicLM failed: a failed sentence, half the sentences uncertain, a clarify result, an unavailable analysis) and, with scope_note: ask, ask: true: the page then asks the user. A wire type the user declined is not suggested again in that session. When the coding agent is wanted but omp is unavailable the answer is the SymbolicLM path with a fallback that says why.

15. Server models: what the server keeps open

The model processes of the chat pipeline (SymbolicLM, LanguageProofingLLM, the translator LLM, SymbolicProofingLLM) take seconds to start, so the server starts them once and keeps them. GET /v1/server/models reads the lifecycle settings and the live state of every managed model; POST /v1/server/models changes them at once and persists them in config/server-models.json. The same controls are in the chat page under Settings, Server models. GET /health (no authentication) and GET /v1/capabilities carry the warm state of the start-up warmup.

  • keep_open: started in the background when the server starts, probed with one small real request (so the first message is not slow), never evicted or idled out, started again if it dies.
  • on_demand: started by the first request that needs it, stopped after idleMinutes without use, evicted least-recently-used when room is needed.
  • off: never started; a request that needs it gets model_off and the caller degrades (the translator falls back to LanguageProofingLLM and says so).
curl -s -X GET http://127.0.0.1:9999/v1/server/models -H "Authorization: Bearer $TOKEN"

Abridged response (memory_mb is the resident memory of a running model, measured; start_ms the measured start time, start_estimate_ms what a start would cost):

 "models": [{"id": "translator-llm", "mode": "keep_open", "state": "ready", "warm": true, "memory_mb": 3784, "start_ms": 13163, "start_estimate_ms": 13163, "idle_s": 29, "...": "..."}, "..."],

Change it with a partial object (not run by the page tests, because it writes the configuration): models (model id to mode), maxRunning (1 to 32, at least the number kept open), idleMinutes, memoryBudgetMb (null: half of the RAM), turnWindowSeconds, warmup. An unknown model, an invalid mode or a maxRunning below the number kept open is a 400 and changes nothing.

curl -s -X POST http://127.0.0.1:9999/v1/server/models -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"models": {"smollm2-360m-base": "keep_open", "gemma-3-270m-base": "off"}, "maxRunning": 7}'

Limits that protect a turn: a model held by a running turn, a busy model and a kept-open model are never evicted; the memory budget compares the measured or estimated memory of the running models plus the one to start; with no model to evict the start fails with a retryable 503 formalizer_capacity.

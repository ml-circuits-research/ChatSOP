Overview / Training

ChatSOP Documentation

Model training has two separate tasks: a formalizer maps the user's message into declarative SOP, and an optional verbalizer rewrites an established CNL answer. Model roles, the Python ML boundary, run artifacts and preflight obligations are specified in DS007.

Models, datasets and the no-fine-tuning state (2026-09-30)

The two models that may be fine-tuned are LanguageProofingLLM (Romanian, mixed and badly written English into acceptable English; data bad_english) and SymbolicProofingLLM (correct English into the limited English SymbolicLM understands; data neuro_english; the model earlier records call the "proofreader", role id and run path frozen). symbolic_english is the regression suite of SymbolicLM and the inventory of target forms. The default base for both is Gemma 3 270M; a larger model only if it fails. Base models must run at 30 to 40 tokens per second on an ordinary laptop CPU; the measured table is eval/reports/current/cpu-speed/cpu-speed-table.json (Gemma 3 270M and Qwen3-0.6B meet it; the Qwen3-1.7B that currently serves LanguageProofingLLM does not). The priority is to improve SymbolicLM by rules and repairs, and formalization is evaluated on clean English. No fine-tuning starts until the three datasets are completely cleaned, on disk, well presented in the audit page and the owner gives an explicit OK; the earlier scoped approval is spent. The small formalizer LLM described below is earlier work with results in the archive and history reports.

The model language

There is one small-model language. The formalizer's prompt is exactly the user's message: no identifiers, lexicon, background knowledge or clock. It writes only stated (what surely comes from the message), assumed (what the model adds), unclear (gibberish, no_request or ambiguous with its readings), query and constraint, as quoted strings: a relation phrase, roles from the closed set subject, object, recipient, location, source, destination, instrument, time, topic, and values as mentioned in the message or ?variables. The model never reasons and never refuses. The host links the strings to knowledge and generates the execution circuit; fact, remember, resolve, solve, cnl and clarify are trusted host operations, not model lessons. The full contract is DS021.

Multilingual formalizer, English knowledge

Fine-tuning teaches the small formalizer one skill: turning a message in any supported input language (English and Romanian today, mixed and misspelled text included) into SOP whose content words are normalized in the message's language (relation lemmas such as "lucra la", common nouns in the nominative), with proper names kept exactly as written, one finite clause per wire, and the parts it could not formalize marked unparsed. The model does not translate (owner decision D1 of 2026-09-29): a deterministic host step translates content words with a reviewed bilingual and synonym dictionary (config/dictionary/) and reports unknown words as untranslated. The reasoner and all knowledge stay English-only, so adding a language means extending the corpora, the fine-tuning and the dictionary, never adding language-specific knowledge. Rendering the answer in the user's language is a separate host step (DS021, DS007).

Cases, corpora and source rights

Each semantic case links the intended meaning, its target and its provenance; every paraphrase, translation and linked contrast of one meaning stays in one split. Case schema, split safety and evaluation tracks are in DS008. The model-language corpora are built by the diversity generator (DS022): formalizer-v1 (train and dev under datasets_archive/formalizer-v1/, the sealed test under eval/suites/formalizer-v1/) and the out-of-distribution suite formalizer-ood-v1, covering every question form of the model language (the eighteen question types: yes/no, wh, count, universal, when, since when, until when, how long, how many times, where, how, why, claim checks, several questions, numeric problems, statements only, unclear and ambiguous messages), interpretation assumptions, visible ambiguity, EN, RO and code-switched messages with labelled typing noise. The training projection is the message only (datasets_archive/formalizer-v1/formalizer/). The earlier corpora (DS009, DS015, DS018, DS019) were deleted with the regeneration of 2026-09-28. The corpora are JSONL-first: datasets/<corpus>/{train,dev}.jsonl for training and selection, the sealed test under eval/suites/<corpus>/test.jsonl. Humans review them through the visual corpus audit at /audit, and tools/datasets/audit-corpus.mjs is the machine audit (DS020).

Source rights are decided per asset in DS014. By the owner's decision of 2026-09-28 the corpora inspired by QQP, PAWS, ProofWriter, AmbigNQ, QA2D and SQuAD are released: they take structure, label types, phenomena and statistics, never text, and each must pass node tools/datasets/no-copy.mjs. Every row records its inspiration sources and text_copied: false; the manifests carry the full rights block.

Evaluation

Report the small model's message-to-SOP fidelity separately from host-generated execution, clarification, memory and reasoning; gold-program execution is not model evaluation. Metric definitions are in DS016, controlled experiments are preregistered under DS010 and listed on the /experiments page, fresh observations go to eval/reports/current/ (browsable at /eval) and archived numbers stay in eval/reports/history/. Engine and solver comparisons are in DS013; see also the evaluation layout.

Fine-tuning, once approved

This is the path a formalizer fine-tuning run will follow after the owner's explicit approval; none of it is authorized now.

  1. Input and target. The training input is exactly the user's message (question); the target is the row's sop_target, in the model language described in How the model writes. Verification fields (setup_sop, ontology_sop, context, expected) are never input. node tools/research/prepare-experiment.mjs writes the message-only projection datasets_archive/formalizer-v1/formalizer/{train,dev}.jsonl (prompt_profile: message-only) and refuses a prompt that differs from its message.
  2. Qualification. The corpus passes node tools/datasets/verify-corpus.mjs --corpus formalizer-v1 --all, the machine audit, node tools/datasets/no-copy.mjs, the human review at /audit, and a token audit with the real tokenizer (node training/cli.mjs token-audit); the outcome is a chatsop-dataset-qualification-v1 receipt.
  3. Authorization. node training/cli.mjs train … --qualification FILE --authorization FILE refuses to start without that receipt and a chatsop-training-authorization-v1 receipt of the owner's new explicit approval. The experiment is preregistered first (DS010) and appears on /experiments.
  4. Selection and evaluation. Checkpoints are selected on dev only. The selected checkpoint is evaluated once on the sealed formalizer-v1 test and on the out-of-distribution formalizer-ood-v1 suite with node eval/run.mjs, broken down by question type, language and noise; the results are browsable at /eval. Serving the fine-tuned model uses the bare prompt choice: the message alone, as in training.

The step-by-step procedures are the repository skills skills/training-rules/SKILL.md, skills/training-runbook/SKILL.md and skills/night-orchestration/SKILL.md.

Current training authorization

The operator has explicitly deferred all model training until a new explicit approval (the earlier scoped approval is spent; Gemma 3 270M is the base to try first for LanguageProofingLLM and SymbolicProofingLLM). Image build and dependency setup, CUDA infrastructure preflight, safe container stop, dataset qualification, and evaluation of existing artifacts may proceed; do not invoke train, --resume, fine-tuning, optimizer steps or a training smoke run. A passing preflight or qualification report does not grant permission to train.

GPU environment and recovery

Node .mjs handles orchestration and validation; indispensable ML operations stay under training/python/ with an explicit run directory at models/<model>/<run>/. Only one GPU-intensive worker may run per machine, across native and container modes. The recommended path is a rootless Podman image with NVIDIA CDI; build, preflight, stop and recovery commands live in the Spark training skill, and the rules in the training rules skill. Never kill a process by a generic name, clean unknown checkpoints or auto-restart failed training. An image build, import, dry-run or generated fixture is not proof of model quality or training-pressure safety.

Overview / Runtime

ChatSOP Documentation

Local users run typed SOP circuits against reviewed knowledge and receive checked results. The runtime, not a source document or a language model, chooses the active user, permissions, runtime configuration and approved definitions; a formalization strategy only writes circuits. The components, trust boundaries and call paths behind this page are drawn from the code on the Architecture page.

Local CLI

From the repository root, node server/cli.mjs help lists the local commands: init publishes a small reviewed fictional fixture, run --file examples/query.sop executes a circuit and validate checks a program. The command list and each command's observable behavior are owned by DS003. A chosen runtime configuration belongs under config/; chat runs the product chain of the chat pipeline against one local repository, with the deterministic answer and no language-model answer.

Local server

npm start serves everything on one port (default 0.0.0.0:9999; CHATSOP_PORT, CHATSOP_HOST) and prints the home URL first. CHATSOP_CONFIG selects another runtime configuration and CHATSOP_CHAT_DATA another chat data root, so a private server on another port never touches the main one's sessions. The home page at / shows whether you are signed in and whether the administrator password is set, and links to the browser chat (/chat), the knowledge browser (/review), the evaluation page (/eval, guide at /eval/guide), the project page (/experiments, with the append-only journal status/journal.jsonl and the preregistered experiments in status/experiments.json), the admin page (/admin) and this documentation. A signed-out browser opening a protected page is sent to /login, which chooses the administrator password on the first run; API calls keep answering JSON 401/403. At start the base memories of server.warmMemories and the default base are decoded in the background (world-v1, about 357k facts in 221 layers, takes about 12 s); the server answers at once. GET /v1/status reports readiness, the formalization strategies with their availability, the base memories with their warmup, the reasoning engines and the caches.

The chat page answers in plain English. Under every answer a trace panel follows the pipeline below: Pragmatic signals (kind, score, span, source and basis of each detected signal, the tone applied), Formalization (strategy, model, models tried, repair rounds with their problem codes, cache, latency, cost), Vocabulary (the size of the schema neighbourhood and the vocabulary dialog), Session definitions and assumptions (each session definition), Linking, Retrieval (complete or not, the bounds), Route and verification, and the circuits. The Settings tab chooses the formalization strategy of the session (a strategy that cannot run is shown disabled with its reason), the CodingAgent model, and shows a server status card; a new session forks the default base memory, the encyclopedic world-v1 (chatData.defaultBase; when it is not loaded, the minimal default, which imports core-min); another base memory is chosen in the New session dialog. The Base Memory tab marks the default and creates memories built on the encyclopedic, minimal or empty base. The contract is DS009; the API is on the API page.

The chat pipeline

One user message, in any language, goes through these steps. Only the request parser uses a language model; everything after it is checked code, and it is the same code whichever strategy wrote the circuit.

  1. Courtesy and emotion. The formalizer understands the whole message in one step: besides the query or the statements it writes what the message also does (a greeting, thanks, an apology, a goodbye, a polite word, a feeling such as frustration, confusion or urgency) as advisory pragmatic wires (the CodingAgent and LocalLLMDirect through the author guide, LocalLLMStepByStep through its acts question). There is no word list or pattern pre-step (the earlier lexicon EmotionDetectionSystem is archived). A message of pragmatic wires only ("hello", "thanks!") gets a short reply rendered from them, status: courtesy, no computation and no memory change; otherwise the wires never change the question and only set the tone of the answer: a courtesy phrase, a brief apology on frustration, a clarifying sentence on confusion, a one-line answer on urgency. The output edge phrases the reply in the language of the message. Contract: DS023.
  2. Request parser: formalization. server/query-parser.mjs asks lib/query-author for circuits with the session's formalization strategy. CodingAgent (the default) runs omp for one turn with no tools and thinking off, on persistent RPC workers, trying the models of queryParser.models in order (zai/glm-5.3, then openai-codex/gpt-6-luna; a session's omp_model is tried first). LocalLLMDirect asks a local GGUF model served by llama-server (lib/local-llm/) to write the circuit in one step. LocalLLMStepByStep asks a local model short questions (the kind of answer, which statements of the memory, which name fills which place, true or absent, the period) and writes the circuit itself (running a local formalizer). The author receives the message, the authoring guide and the schema neighbourhood of the session's memory (lib/query-author/neighbourhood.mjs: the entities the message names, the relations used around them with roles, fact counts, two examples each and related rules), within a 24,000-byte budget. It writes only queries, constraints, unclear/unparsed markers, labelled session definitions and assumed lines; it never answers and never states a fact.
  3. Admission and repair. The validator (lib/query-author/validate.mjs, admit.mjs, condition-use.mjs) admits only the circuit surface of DS014 with the memory's declarations: an unknown predicate, an undeclared role, an unused mention, a dropped quantifier, a condition misuse (a constant in a position where the memory never holds it), a range given as a point in time (time_not_a_point) or as a bare role time (time_range_needs_quantifier) goes back to the author with the problem codes for a bounded number of repair rounds (queryParser.maxFixRounds, 2). When the vocabulary is missing or a condition is misused, a vocabulary dialog widens the neighbourhood to two hops, at most twice (lib/query-author/loop.mjs). A circuit that stays invalid is reported, never replaced by a guess.
  4. Session definitions and assumptions. A term the memory lacks may be defined by the author as a session predicate and rule over existing relations. Such a session definition is used for this turn only, labelled in the answer, and, once valid, stored in the session layer; assumed lines are reported or run as a separate hypothetical branch. Memory always wins over a conflicting assumption.
  5. Linking. The KnowledgeLinker links relation phrases and entity names to the base memory and asks when a name is ambiguous. It does not parse language.
  6. Slice retrieval and the completeness guard. Only the facts the question and the reachable rules can use are fetched by keyed lookups (slices, reasoning/slice/); the completeness guard never gives a count, a universal answer or an unknown from a partial slice.
  7. Routing and verification. The StrategyRouter chooses the js-reference oracle or an engine (sql-sqlite, datalog-souffle, asp-clingo) by the features of the circuit and the size of the slice; a routed answer is checked by oracle verification (route.verification). A requested backend is never substituted.
  8. Rendering. sop/answer-text.mjs renders the result packet as English text deterministically, naming the origin of each step (memory, definition by the author, assumption by the author) and the sources used. The English rendering is always kept in the trace (chatSop.english_text).
  9. Answer formulation. When the message does not look English (answerLanguage.mode auto, the default; always or off are the other modes), server/answer-language.mjs asks omp, using a non-Anthropic model of answerLanguage.models (by default queryParser.models, GLM first; thinking off, 40 s), to phrase the answer in the message's language. The model sees only the English answer and a compact result packet (status, answers, count, facts used with sources). Every number and Wikidata id of the English answer must survive; otherwise the next model is tried, and in the end the English answer is returned. The trace reports answer_language (mode, message language, applied, model, time, models tried, reason). Example: "Unde s-a născut Ada Lovelace?" is answered in Romanian from world-v1 (Londra, Regatul Unit…), with the formulation taking 2 s on zai/glm-5.3.

There is no fallback parser and no silent substitution of strategies. When no model of the chosen strategy can run the turn answers 503 parse_unavailable; when the models ran and no valid circuit came back after the last round it answers 422 parse_failed; a circuit that is written but cannot be admitted or executed answers 422 model_output_rejected. Each error carries the parse record. A wrong circuit executes to a wrong answer, which is why the benchmark counts a wrong circuit apart from an honest unknown. What the user states is turn-local evidence kept in the caller's conversation context; nothing in a chat turn writes to a repository.

Worked example: one chat turn on world-v1

A real turn, recorded on 2026-10-02 in a session on the base memory world-v1 (a Wikidata subset, about 357k facts) with CodingAgent on zai/glm-5.3. The user asks: "Is Paris located in Europe?"

  1. Formalization. The schema neighbourhood offered 11 predicates (born_in, contains, died_in, is_a, located_in, part_of, …; 23,832 of 24,000 bytes) and two ambiguous mentions (Paris: paris, san_francisco, bucharest; Europe: europe, council_of_europe, …). GLM 5.3 wrote the circuit in one round, 6.8 s, cost class subscription (nominal 0.0104 USD), cache miss; the vocabulary dialog was not needed (0 of 2 expansions):
    @q query
  where match
    relation "located_in"
    role subject "paris"
    role location "europe"
    polarity affirmed
  end
  2. Admission accepted it without repairs (parse.rounds: 1).
  3. Linking. The relation linked to located_in through the lexeme "be located in" (lx_located_in_en_copula, the only candidate, 9,453 facts); the names linked to paris and europe. The generated execution circuit:
    @q query
  where located_in paris europe

@host0 solve
  query $q

@host1 cnl
  result $host0
  language en
  4. Retrieval. The slice was complete (guard complete_slice): 4 facts and 8 rules over located_in, contains, capital_of and headquartered_in, class recursive, 32 keyed lookups, no scan, within the bounds of 10,000 facts and 60 s.
  5. Route. Requested auto, chosen js-reference by the rule caller_budget (the oracle defines the budget keys of a chat turn); datalog-souffle, sql-sqlite and asp-clingo were eligible alternatives; no fallback.
  6. Answer (status: supported, complete), rendered from the packet:
    Yes.
Paris is based in France (memory: Wikidata Q90 P17).
France is based in Europe (memory: Wikidata Q142 P30).
Sources used: memory (r_located_in_transitive), memory (c_2e2ee…) and memory (c_f061d…).

Formalization took about 7 s of the turn and the whole turn about 10 s. The proof used the rule r_located_in_transitive and two Wikidata facts; both facts were reinforced by proof use as the retention policy allows.

Running a local formalizer

Two formalization strategies run on a local GGUF model through the shared runtime lib/local-llm/: LocalLLMDirect (the model writes the circuit, with the same guide, validator and repair rounds as CodingAgent) and LocalLLMStepByStep (the model only answers short questions and numbered choices; the symbolic system assembles the circuit). Both use one llama-server with one dedicated slot each, flash attention, full GPU offload, prompt cache on, and a stable prompt prefix evaluated once and restored before every request. The model is configured in config/runtime.json under queryParser.local (shipped: Qwen3.8-27B Q4_K_M, ~/models/qwen3.8-27b/Qwen3.8-27B-UD-Q4_K_M.gguf, alias qwen3.8-27b, port 19601).

Chat with a local formalizer, one command. Choose the strategy and start the server; the chat server starts the model on the first turn (about 30 s to load the 27B model and 10 s to evaluate the author guide once) and stops it when it exits:

CHATSOP_FORMALIZER=LocalLLMDirect npm start        # or LocalLLMStepByStep

Instead of the environment variable, set "strategy": "LocalLLMDirect" in queryParser of the runtime configuration, or pick the strategy per session in the chat's Settings (Formalization card; POST /v1/sessions/{id}/settings {"formalizer": "LocalLLMStepByStep"}). GET /v1/status shows whether the local strategies can run (model file, llama-server, no GPU lock) and whether the model is loaded.

Keep the model loaded across chat-server restarts. Start it once with the same optimised flags, then point the chat server at it:

node tools/local-llm/serve.mjs --gguf ~/models/qwen3.8-27b/Qwen3.8-27B-UD-Q4_K_M.gguf --port 19601 --alias qwen3.8-27b --slots direct,steps --ctx-per-slot 16384
# then in config/runtime.json: "queryParser": {"strategy": "LocalLLMStepByStep", "local": {"endpoint": "http://127.0.0.1:19601/v1", "alias": "qwen3.8-27b"}}

Question protocol of LocalLLMStepByStep. queryParser.local.method chooses the protocol: B (default) is the generic protocol of DS022 "LocalLLMStepByStep": 13 answer kinds and 8 aspects in the cached prefix (3 more aspects in the checklist question), the message acts (greeting, thanks, apology, goodbye, politeness, a feeling) as pragmatic wires, places typed and pre-filled from the memory's facts, limits, options, exclusions, two-sided comparisons, groups, suppositions, chains and per-group counts written by the system, a forced-contrast confirmation, and an honest unclear instead of an invalid circuit. A is the first protocol; D and B-yesno are the measured variants (C and B-cue, which read a regular-expression cue table, were removed on 2026-10-02 with the table: every aspect, limit, option, exclusion, supposition and the message acts now come from the model's answers). After the removal, on 24 known-form and 10 natural rows, method B stayed at 21 of 24 and went from 6 to 7 of 10 correct, with about 1.7 more questions per request. On 89 development rows (known forms, held-out forms, compositions, natural questions) Qwen3-4B Q4 went from 23 correct and 24 wrong (A) to 73 correct and 3 wrong (B) at a median of 0.4–0.9 s per message; see eval/reports/current/omp-tasks/stepbystep-protocol.md.

Only one GPU worker runs per machine: the managed server refuses to start while models/.training.lock or models/.parse-gpu.lock exists. A smaller model is a configuration change (gguf, alias); measured on the development benchmark (40 rows, 5 per family F2–F9), Qwen3.8-27B answers 36 of 40 correctly with LocalLLMStepByStep at a median of 2.2 s per request and Qwen3-4B Q4 27 of 40 at 0.34 s (eval/reports/current/omp-tasks/t10-stepbystep.md). The protocol is specified in DS022 "LocalLLMStepByStep".

Evaluating on the owner's problem books

The owner's problem books (datasets_sources/books/*.docx, rights owner-provided; the books and everything derived from their text stay in the gitignored datasets_sources/ and eval/reports/current/) are an end-to-end test of understanding, formalization, the memory and the reasoning engine. node tools/eval/books/extract.mjs reads the DOCX files with Node built-ins and writes about 7000 problems with answers to datasets_sources/books/eval/items.jsonl (node tools/eval/books/validate.mjs checks that every question and answer is verbatim in the book). node tools/eval/books/run.mjs --n 100 draws a stratified random sample (equal share per book, areas cycled, never an item run before unless --include-seen; also --seed, --books, --areas, --arms steps,direct[,coding-agent]) and runs the arms: steps is the product chat turn with LocalLLMStepByStep (method B) on a local Qwen3-4B-Instruct Q4_K_M, the problem text being the user message and the default base memory the base; direct is the same model answering directly. Then score.mjs --run DIR scores by rule (yes/no, numbers, entities) and prepares blind judge batches for the rest, score.mjs --run DIR --merge adds the judge verdicts, and report.mjs --run DIR writes summary.md (per arm, book and area, what the system did, failure classes with examples) and eval/reports/current/books-eval/index.md.

Execution and publication

The parser checks each typed declaration. SOP relations use whitespace-separated terms such as works_at maria acme, with no parenthesized arguments or comma separators; arithmetic and solver-internal languages retain their own syntax. A stated or assumed wire of a coding-agent circuit is a string proposition that the KnowledgeLinker links and lowers to a turn-local fact, never a sourced repository fact or a write. The runtime compiles an inspectable circuit for linking, identity lookup, conditional assumptions, reasoning and rendering, and generates a specific clarify wire only when identity is unresolved or ambiguous or a required scalar is missing or nonunique; lack of evidence alone is not a clarification request. A linker selects approved definitions and retrieves facts from a memory engine; the selected reasoning strategy computes a result, binding, evidence and completeness information; CNL renders the result without changing it. Only an explicit trusted remember records facts in the selected session, and committing that session is a separate act. The grammar and execution contract are in DS004.

The repository separates users, sessions and forks. A claim's valid interval is distinct from when the claim became known; correction and retraction cannot be erased by choosing another memory engine. Referenced snapshots remain reachable GC roots. A missed retrieved fact is not a proof that it is false. See DS005.

Worked example on the fictional fixture: circuit to checked answer

The author sees the user's message and the schema neighbourhood and writes the circuit; the runtime links the strings, builds the execution circuit, and every reported value below comes from an actual runtime result over the reviewed fictional fixture.

Answer supported by reviewed knowledge

"Where does Maria work?"

@question query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

Generated execution circuit: the phrase "works at" with roles subject and object links to works_at; "Maria" is resolved as a person; the object role stays the variable.

@host0 resolve
  text "Maria"
  language en
  kind entity
  type person

@question query
  where works_at $host0 ?org
  select ?org

@host1 solve
  query $question

@host2 cnl
  result $host1
  language en

Observed result: status: supported, ?org = "lab_alpha", evidence works_at maria lab_alpha with SOURCE demo; the coding agent authored none of the resolve, solve or cnl steps

A user supposition stays hypothetical

"Suppose Carina is a parent of Ana. Who is Carina a parent of?"

@context stated
  relation "parent of"
  role subject "Carina"
  role object "Ana"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "parent of"
    role subject "Carina"
    role object ?who
    polarity affirmed
  end
  select ?who

The generated circuit lowers the supposition to @context fact … source assumption and adds assume $context to its solve. Observed result: status: supported with hypothetical: true, ?who = "ana", evidence SOURCE assumption, the rendered condition "You supposed: parent of (subject: Carina; object: Ana).", and the session still holds zero repository claims after the turn. Had the user asserted it (certainty asserted), the statement would be turn-local user evidence and the answer would not be hypothetical; it is still never recorded.

Both outputs were produced on 2026-09-28 by executing these programs with the runtime against tests/fixtures/bootstrap.sop at a fixed evaluation time.

KnowledgeLinker: strings to the predicates of the base memory

After the coding agent, the KnowledgeLinker links each relation phrase to a predicate of the chosen base memory. The words come from the base memory itself: a predicate whose id, label, lexeme form or reviewed relation lexicon entry equals the phrase binds first ("be the capital of" to capital_of), and an entity is found by its labels and aliases. Every session links against the lexicon of its own base memory (compiled from its circuits and those of the memories it imports, DS022 "Lexicon of a memory"), never a global one. The packet and the chat trace report what was linked as linking (surface, symbol, matched form, alternatives not taken). The plain copula has no predicate of its own: "Ana is a doctor.", "Is Paris in France?" and "Who is Ana?" are read with the copula readings the memory itself declares (reading class|occupation|attribute|identity|location|describe on its predicate wires), tried in order against the knowledge; a question keeps every reading that fits as an any group and a statement takes the first. The packet lists them as copula_readings; "Where is Paris?" (the bare copula with a location role) is the location reading. A memory that declares no reading gets a precise question ("Do you mean what Ana does, or who Ana is related to?"), never "I do not know the relation be". Details: DS014, "KnowledgeLinker: the copula and the relation lexicon". Three further rules close the gap between the words a circuit uses and the names a memory declares: a phrase that does not link as written is rewritten by the reviewed frames before the dictionary tiers (reported as frame_changes, never used by the strict link), a query role the predicate does not declare is renamed to the one declared role that is free (relabeled in the linking entry; never the subject), and a leading article is dropped from an entity name when the whole surface finds nothing. The rules of the memory's circuits (for example located_in transitivity) reach the chat turn's query the same way they reach POST /v1/sessions/{id}/query.

Knowledge wires and reasoning strategies

Knowledge written from a source (a manual, a regulation, an article) is a set of knowledge wires: predicate declarations with roles and types, fact, rule, default, integrity, aggregate, action, method, norm and procedure. They are written by a coding agent or the owner, never by the query author, and checked before they are stored: node eval/smoke-reasoning/validator.mjs [--authoring] knowledge.sop query.sop runs the validator of sop/knowledge/, the single grammar source. The runtime stores the approved wires, selects a slice relevant to a question, and a strategy answers it; a question reaches the strategy only through the KnowledgeLinker, where the roles of a predicate place the circuit's strings in the predicate's positions.

What a question returns is a result packet: a status (supported, refuted, both, unknown, and for planning and conformance plan_found, blocked, compliant, non_compliant), complete, the rows with their own conditional assumptions, used (one sufficient set of claims with their versions), the route and a budget block. Two negations are never confused (not is explicit evidence, absent works only over a predicate declared closed); positive and negative evidence propagate independently, so a contradiction is reported as both and stays local; a default is blocked by an exception, a strict contrary or an overriding default that fires; counts and "every" over an open predicate are lower bounds or unknown; time is a snapshot (at, during throughout, overlaps, asof). A strategy that cannot express a question says not_expressible and never weakens it; a budget cut is budget_exhausted with a reason, never unknown or no_plan. Approved methods and norms (a "mode of work") bound what a plan may do, mode why_not names what blocks a step, and a change is negotiated as an amendment composed by the runtime and evaluated as a what-if. The manual is the section "Knowledge wires" of DS004, the strategy interface, budgets, shadow gate and routing rules are in DS006 "Strategies", and the comparison suite is in DS010. node eval/smoke-reasoning/run.mjs runs every strategy on the smoke cases.

From a memory to the reasoner: slices and the completeness guard

A base memory can hold hundreds of thousands of facts, so the reasoner never receives the memory. For each question linkKnowledge (reasoning/linker.mjs) takes the rules that can reach it and asks SliceRetrieval (reasoning/slice/) for the facts those rules and the question can use. A static plan, a magic-set style rewriting (demand.mjs), orders every conjunction by sideways information passing and decides, for each atom, whether it is keyed (a constant, a variable of an earlier atom, a head variable that every call site binds) or must be scanned. Keyed atoms are fetched by lookups of one position and value through the memory strategy (the SQLite bank indexes each position), the values coming from the facts already retrieved, until nothing more is owed: the fixpoint of the demand. A relation too large to read whole is never scanned when a constant can key it.

The slice is complete when that fixpoint was reached with no lookup truncated and no budget stopped it (facts, probes, lookups, wall-clock retrievalMs), and settled when every lookup was also answered by an exact view (an associative memory returns candidates and never closes a relation). The completeness guard (guard.mjs) then decides what may be said: a proof, a counterexample or an opposing fact stays valid over a partial slice and is returned with complete: false; a list of rows is widened and, if it cannot be completed, returned as a partial list; a count, a universal answer no counterexample decided, a ranking, and an unknown obtained by failure are widened and otherwise answered status: incomplete, reason: partial_retrieval, with the lower bound of a count as at_least. They are never given as closed-world answers. Every packet carries retrieval: the slice's size, its predicates, the bounds in force, whether it is complete, why not, and one trail entry per widening step. Retrieval reads only; it reinforces nothing.

POST /v1/sessions/{id}/query answers a knowledge-wire query circuit over the session's memory the same way (askMemory): the oracle gets the rules, defaults, aggregates and predicate declarations that can reach the query and the facts they need, and the guard reads the oracle's own sensitivity, so absent, aggregates and default conclusions are judged on the desugared program. Timing on synthetic SQLite memories: node tools/eval/slice-timing.mjs (report in eval/reports/current/slice-path/timing.json). Specifications: DS005, DS006, DS018.

Sessions, base memories and the coding agent

Every chat runs in a session: a working copy of a chosen base memory under the gitignored folder chat_data/ (DS022). The lifecycle: (1) the owner prepares base memories: POST /v1/memories creates or imports one of a chosen memory strategy, POST /v1/memories/{id}/knowledge adds circuits that pass the knowledge validator, recorded with the acting user, and POST /v1/memories/{id}/fork forks one (a copy-on-write clone, or a replay into another strategy). (2) A chat starts with POST /v1/sessions {base}: the base memory's repository is cloned by hard links and its circuits are copied into chat_data/sessions/<id>/. (3) Each message is answered over base plus session (session_id in the chat request); asserted statements stay turn-local. (4) Attached files go to the coding agent (omp, with the skill sop-wire-authoring) in a temporary folder under the session; the validator checks the circuits it writes and, with a session, the valid ones join the session layer at once (POST /v1/author; an invalid circuit is refused and nothing is stored). (5) There is no manual accept or reject: wrong knowledge is corrected through tests and interactions. (6) A user may commit the session to a new fork of its base memory (.../commit), validated again and recorded with provenance; the base memory the session started from does not change. (7) Temporary folders older than 24 hours and sessions idle for 14 days are removed. The endpoints, with executed examples, are in the API page sections 5 to 8.

The knowledge browser: what a memory knows

The page /review (menu Knowledge, signed in) shows what a base memory or a chat session knows, read only. A memory is seen as its layers: the import snapshots (core-min, core-en, commonsense-v1, …), its own circuits, one layer per document ingestion, and for a chat session the session layer. For each layer the page gives its provenance (who added it, from which source, when) and a risk view: the vocabulary and theory items with the most likely problems first. A flag is a hint, not a verdict: a lexeme form with no count in the mined corpus and no Wikidata label or alias of the property its source cites, a form that two predicates of the same arity claim (told apart only by restrict or weight), a converse frame ("employ" for works_at), a rule (it derives new facts), a predicate without a description or without an English form, and for world-v1 the mapping choices (a Wikidata property emitted flipped, several properties merged into one predicate); facts and plain entities are shown as groups per predicate and class with sample facts, never one by one. Next to each item is its evidence, and its effect rather than its syntax: a generated sentence for each form and the atom it maps to ("Ana works at Beta Labs" → works_at ana beta_labs, with real entities when the memory has facts of the predicate), the predicates the lexicon links the phrase to, and for a rule a derivation over the memory's own facts ("Babeș-Bolyai University is based in Cluj-Napoca" and "Cluj-Napoca is based in Romania" ⇒ "Babeș-Bolyai University is based in Romania"). A search box finds entities by label and alias, classes, predicates by their forms and descriptions, rules and the text values of facts, using the lexicon's token index and a per-layer index, never a scan of all facts. An entity card lists the classes closed over is_a, every stored fact in both directions with its layer and source, and the rules that can derive more; Derive asks the oracle, through bounded queries, what those rules conclude and shows each derived fact with its proof. A predicate card gives the roles, how people say it (forms with evidence), example facts and the rules that use or conclude it. There is no approve or reject step (AGENTS.md direction 8): problems found here are corrected systematically, through tests and interactions. The API is GET /v1/knowledge/* (API page section 9); the contract is DS022 "Knowledge browser".

Task-type base memories from documents

Learning in ChatSOP is adding knowledge to a base memory, not training a model (owner decision of 2026-10-02). A task-type base memory holds the facts, relations, rules and procedures of one kind of task, built from documents: (1) create the memory, usually importing core-min for the shared vocabulary (node tools/ingest-documents.mjs create-memory or POST /v1/memories); (2) ingest the document (tools/ingest-documents.mjs ingest --memory ID --file doc.md --rights cleared or POST /v1/memories/{id}/ingest): only documents with recorded rights are taken (DS011); the document is cut into chunks along its headings, and the coding agent (omp, skill sop-wire-authoring) compiles one chunk at a time over the memory's vocabulary, the chunks before it and the entity symbols already in use, with a quote and a source on every fact and rule; (3) the validator and the quote check (each quote must be a passage of the chunk) run in the bounded repair rounds; a fact that duplicates or contradicts the memory is held back (memory wins); (4) read the report, whose chunks are already stored (report.md of the ingestion: extracted wires by type, rejected quotes, held-back conflicts, uncertain wires, what the agent could not express, rounds, time, cost); (5) every validated chunk is stored at once, with no acceptance step, through the knowledge validator with the document's provenance (SHA-256, URL, licence, section, lines) and the acting user; (6) start sessions on the memory (POST /v1/sessions {base}). Re-ingesting a document adds nothing, and an edited document adds only its changed chunks. Rules that answer one question form are kept as a procedure (a procedure bundle with a description of the form, POST /v1/memories/{id}/procedures); when a message matches the description, the query author is offered the procedure's head predicate and its rules and queries it instead of re-deriving it. Contract: DS022 "Ingesting documents into a base memory" and "Procedure library"; examples on the API page.

Alternative routes and limits

A runtime configuration under config/ independently selects memory.engine (recall-memory for RecallMemory, holo-memory for HoloMemory, sqlite, scan or hybrid; see DS005 and the per-strategy specifications DS016–DS021) and policy.reasoningStrategy (reference, the js-reference oracle through the runtime bridge; a wire that names an external backend maps to that backend's strategy id or returns unsupported with the backend named and fallback: null; the former separate JavaScript reasoner was retired on 2026-10-01). policy.reasoningStrategy (or a wire line reasoning auto) also accepts auto, the StrategyRouter v1 of DS006 "Routing rules": on the knowledge-wire path (POST /v1/sessions/{id}/query, body reasoning and verify) it chooses between the oracle and the engines sql-sqlite, datalog-souffle and asp-clingo by the features of the circuit (recursion, negation, aggregates, time, modes of work) and the size of the slice, reports the choice, the rule and the alternatives in route, and checks a routed answer against the oracle (a disagreement returns the oracle's answer with the discrepancy); on the typed path every answer carries a proof, so auto reports the oracle. The result records the actual route and fallback; a requested backend is never silently substituted, and a JavaScript result is never reported as a Prolog or Z3 measurement. Associative recall produces candidates subject to verification. The routing rules and the strategy × backend matrix are in DS006.

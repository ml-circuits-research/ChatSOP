Overview / Runtime

ChatSOP Documentation

Local users run typed SOP circuits against reviewed knowledge and receive checked results. The host, not a source document or a language model, chooses the active user, permissions, runtime configuration, and approved definitions.

Local CLI

From the repository root, node server/cli.mjs help lists the local commands: init publishes a small reviewed fictional fixture, run --file examples/query.sop executes a circuit and validate checks a program. The command list and each command's observable behavior are owned by DS003. A chosen runtime configuration belongs under config/; model-backed chat requires a separately configured model endpoint.

Local server

npm start serves everything on one port (default 0.0.0.0:9999) and prints the home URL first. The home page at / shows whether you are signed in, whether the administrator password is set and the state of every formalizer model (stopped, starting, ready or error), and links to the browser chat (/chat), the corpus audit (/audit), the evaluation page (/eval, with its guide at /eval/guide), the project page (/experiments, which shows the append-only journal status/journal.jsonl and the preregistered experiments in status/experiments.json), the admin page (/admin) and this documentation. A signed-out browser opening a protected page is sent to /login, which chooses the administrator password on the first run and signs in afterwards; API calls keep answering JSON 401/403. The chat page has a Mode list: Chat (a plain multi-turn conversation with an unmodified base instruct model, SmolLM2-135M-Instruct, SmolLM2-360M-Instruct or Gemma 3 270M-it, sampled at temperature 0.7, to see its general ability), Formalize (SOP Lang) (the ChatSOP path: a fine-tuned formalizer reads the message alone and the host answers) and Translate to English (a base model with a fixed prompt, greedy). The Model list shows the models of the chosen mode, read from config/formalizers.json by their capabilities (Formalize: the fine-tuned SmolLM2-135M, Gemma 3 270M and SmolLM2-360M formalizers, SymbolicLM and the configured external endpoint; Chat and Translate: the base models, which never formalize): the chosen model runs in a CPU llama-server that the server starts on demand, reuses, stops after 15 idle minutes (at most three at once) and stops on exit; a formalizer gets the evaluation harness's message-only greedy request. An Answer language list offers English, Română and Any: the answer language in Formalize, an "Answer in …" instruction in Chat, not applicable in Translate. Each answer shows a collapsible trace with the mode, the model that answered and the latency; a Formalize trace adds the model SOP, the host-generated execution circuit, status, backend, fallback, assumptions and reinforcement. A model that cannot start is reported with its reason (HTTP 503). The contract is DS012.

textToCleanEnglish: a user-validated step before formalization

Owner decision of 2026-09-30: formalization handles only clean English. Before a Formalize-mode message is sent, the chat page's Clean before formalizing toggle (on by default, Formalize mode only) calls POST /v1/text-to-clean-english, which runs textToCleanEnglish (lib/text-to-clean-english/) entirely as host code before the model boundary: it corrects spelling and grammar, translates Romanian or mixed Romanian/English text to English, and simplifies wording, returning {original, clean, changed, reasons, spans, backend, confidence}. The host splits the message into sentences and a cheap gate skips every already-clean English sentence; only flagged sentences go to the backend, one request each (llm.sendAll: true sends all sentences; default false). The default backend is LanguageProofingLLM, the fine-tuned Gemma 3 270M of run language-proofing-gemma270m-it1 (registry entry language-proofing-llm, capability proofread, a CPU llama-server started on demand, message-only prompt); a local LanguageTool server is an optional backend, off by default, and the choice is in config/text-to-clean-english.json. An unavailable backend degrades to "no change", and an unreachable backend degrades to "no change" rather than blocking the message. When cleaning changes the message, the page shows the proposal as a word-level diff with three choices — Accept, Edit, or Send original — before anything reaches the formalizer; whichever text is finally sent is the formalizer's whole input, unchanged from DS021 "Model boundary", and the request may carry cleaning: {original, backend, changed} so the trace keeps both the original and the accepted wording. The contract is DS012 "textToCleanEnglish" and DS021 "textToCleanEnglish".

Understanding in the chat

With the SymbolicLM model selected in Formalize mode, each answer carries a collapsible "I understood:" panel (the Show what I understood (CNL) setting, on by default): per sentence, short controlled English restating the analysis SymbolicLM actually used (DS021 "Interpretation CNL"), checked by a round trip; a sentence whose round trip fails is shown as an "uncertain interpretation" with a raw analysis summary, never as silent CNL. The panel also shows the spans that were not represented (highlighted in the message), whether each sentence's analysis is certified (identical default and accurate Stanza trees) and, when the SymbolicProofingLLM rewrite setting is gated or always, the original sentence, the rewrite and whether it was accepted. The Clean text before formalizing and Send every sentence settings control the LanguageProofingLLM step above. All settings are remembered per browser; the chat API takes the same choices (understanding, sendAll) and returns chatSop.understanding (DS012 "Understanding in the chat").

SymbolicLM: the symbolic formalizer

SymbolicLM (lib/symbolic-lm/) formalizes a message without a neural model and reads the message alone. On route translate it parses a Romanian sentence with the Romanian Stanza model and calls TranslatorService to realize it in plain English; it parses the English with the English Stanza model; and converts the parse into SOP Lang with the UD-to-SOP rules of lib/ud-to-sop/, mapping every value back to the words of the original message. English messages skip translation. Per-token language identification and the optional spelling correction are LanguagesUtil's job, called before routing. Every step is in the trace: token languages, spelling changes, the English text and where each word came from, both parses, rule notes and unparsed spans. An uncertainty signal lists why an analysis may be wrong (untranslated words, unparsed spans, rule fallbacks, unusual trees, and optionally disagreement with the spaCy parser); an optional rewrite function, such as SymbolicProofingLLM, may rewrite the English text before it is parsed again, only when the signal fires or always. Commands: node tools/symbolic-lm.mjs analyze "<message>" --trace, node tools/symbolic-lm.mjs english "<message>" (or --in rows.jsonl --out out.jsonl), and serve, which the chat starts on demand as the model symbolic-lm on the CPU. serve --rewrite-url <endpoint> [--rewrite-when always|uncertain] wires an OPTIONAL SymbolicProofingLLM rewrite backend (off unless passed; config/formalizers.json's symbolic-lm.rewrite documents the option, default mode: "off"): a candidate is the fine-tuned Gemma 3 270M checkpoint of run train-proofreader-gemma270m-v1 (SymbolicProofingLLM; the run id is frozen) served as a GGUF Q8_0 llama-server endpoint. Experiment eval-proofreader-e2e-v1 found a positive, CI-excluding-0 end-to-end accuracy gain on formalizer-v1/formalizer-ood-v1 English rows and a null effect on the independently-written formalizer-wild-v1 English rows; no default changed. The contract is DS021 "SymbolicLM".

LanguagesUtil: language identification and spelling

LanguagesUtil (lib/languages-util/) answers two questions about text, and nothing about UD, SOP or translation: per-token language identification (Romanian, English, name, number, punctuation, other, with its evidence) and matrix-language (frame) detection for a code-switched message, from its closed-class function words; and a conservative symbolic spelling correction. SymbolicLM and TranslatorService both call it; it calls neither. The contract is DS021 "LanguagesUtil".

TranslatorService: pluggable translation toward English

TranslatorService (lib/translator-service/) is the dedicated translation component SymbolicLM calls on route translate; SymbolicLM itself keeps only UD parsing, SOP generation, the uncertainty signal and routing. Backends are loaded by name (lib/translator-service/index.mjs): symbolic, the deterministic dictionary-and-rules translator (moved unchanged from the former lib/symbolic-lm/translate.mjs), is the only backend wired into the runtime pipeline; opus-mt and apertium are research backends, translating masked raw text through an external CPU translator, exercised only by the preregistered comparison eval-translator-compare-v1. The contract is DS021 "TranslatorService".

Execution and publication

The parser checks each typed declaration. SOP relations use whitespace-separated terms such as works_at maria acme, with no parenthesized arguments or comma separators; arithmetic and solver-internal languages retain their own syntax. A model-origin stated or assumed wire is a string proposition that the host links and lowers to a turn-local fact, never a sourced repository fact or a write. Approved host code compiles an inspectable circuit for linking, identity lookup, conditional assumptions, reasoning and rendering, and generates a specific clarify wire only when identity is unresolved or ambiguous or a required scalar is missing or nonunique; lack of evidence alone is not a clarification request. A linker selects approved definitions and retrieves facts from a memory engine; the selected reasoning strategy computes a result, binding, evidence and completeness information; CNL renders the result without changing it. Only an explicit trusted remember records facts in the selected session, and committing that session is a separate host action. The grammar and execution contract are in DS004.

The repository separates users, sessions and forks. A claim's valid interval is distinct from when the claim became known; correction and retraction cannot be erased by choosing another memory engine. Referenced snapshots remain reachable GC roots. A missed retrieved fact is not a proof that it is false. See DS005.

What the small language is for

(The current formalizer is SymbolicLM, which writes this language from a grammatical analysis; the small model was the earlier formalizer, and the boundary is the same. SymbolicLM parses English with the Stanza accurate package (electra-large parser, configuration config/symbolic-lm.json, environment CHATSOP_STANZA_PACKAGE=default|accurate); a batch of messages is parsed in one GPU pass, the optional uncertainty reason parsers_disagree compares the two packages and is off by default because it runs a second worker.) The small model describes problems, never actions or advice. It sees only the user's message — no vocabulary, identifiers, knowledge or clock — and may author only stated, assumed, unclear, query and constraint, as strings: what the user's message puts forward, what the model added, that the message is unintelligible, contains no request, or has several equally good readings, what is being asked, and which finite numeric claim must be decided. Linking the strings to knowledge, identity lookup, retrieval, reasoning, recording and rendering stay host work. The model never refuses: a request phrased as guidance ("what should I do?") is formalized into the question behind it; the host answers it, asks with a clarify when a relation, identity, date or scalar cannot be linked or determined, or states "I understood the question as …; I cannot compute this kind of answer yet" — the runtime never invents a recommendation, and the model cannot select a procedure or write memory. Answers are in English unless the user requests Romanian. The model surface, its scope, its non-goals and the conservative checklist for any future construct are specified in DS021.

Worked example: context-free question to checked answer

The model sees only the user's message and writes declarative SOP as strings; the host links the strings to its reviewed lexicon, builds the circuit, and every reported value below comes from an actual runtime result over the reviewed fictional fixture.

Answer supported by reviewed knowledge

"Where does Maria work?"

@question query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

Host-generated circuit: the phrase "works at" with roles subject and object links to works_at; "Maria" is resolved as a person; the object role stays the variable.

@host0 resolve
  text "Maria"
  language en
  kind entity
  type person

@question query
  where works_at $host0 ?org
  select ?org

@host1 solve
  query $question

@host2 cnl
  result $host1
  language en

Observed result: status: supported, ?org = "lab_alpha", evidence works_at maria lab_alpha with SOURCE demo; no model authored the resolve, solve or cnl steps.

A user supposition stays hypothetical

"Suppose Carina is a parent of Ana. Who is Carina a parent of?"

@context stated
  relation "parent of"
  role subject "Carina"
  role object "Ana"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "parent of"
    role subject "Carina"
    role object ?who
    polarity affirmed
  end
  select ?who

The generated circuit lowers the supposition to @context fact … source assumption and adds assume $context to its solve. Observed result: status: supported with hypothetical: true, ?who = "ana", evidence SOURCE assumption, the rendered condition "You supposed: parent of (subject: Carina; object: Ana).", and the session still holds zero repository claims after the turn. Had the user asserted it (certainty asserted), the statement would be turn-local user evidence and the answer would not be hypothetical; it is still never recorded.

Both outputs were produced on 2026-09-28 by executing these programs with the runtime against tests/fixtures/bootstrap.sop at a fixed evaluation time.

Alternative routes and limits

A runtime configuration under config/ independently selects memory.engine (recall-memory for RecallMemory, holo-memory for HoloMemory, sqlite, scan or hybrid; see DS005 and the per-strategy specifications DS023–DS028) and policy.reasoningStrategy (reference JavaScript, or advanced routing to optional SWI-Prolog or Z3). The result records the actual route and fallback; a requested backend is never silently substituted, and advanced with a JavaScript fallback is not a Prolog or Z3 measurement. Associative recall produces candidates subject to verification. The routing rules and the strategy × backend matrix are in DS006.

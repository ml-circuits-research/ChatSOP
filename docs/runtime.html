Overview / Runtime

ChatSOP Documentation

Local users run typed SOP circuits against reviewed knowledge and receive checked results. The runtime, not a source document or a language model, chooses the active user, permissions, runtime configuration and approved definitions; a formalization strategy only writes circuits. The components, trust boundaries and call paths behind this page are drawn from the code on the Architecture page.

Local CLI

From the repository root, node server/cli.mjs help lists the local commands: init publishes a small reviewed fictional fixture, run --file examples/query.sop executes a circuit and validate checks a program. The command list and each command's observable behavior are owned by DS003. A chosen runtime configuration belongs under config/; chat runs the product chain of the chat pipeline against one local repository, with the deterministic answer and no language-model answer.

Local server

npm start serves everything on one port (default 0.0.0.0:9999; CHATSOP_PORT, CHATSOP_HOST) and prints the home URL first. CHATSOP_CONFIG selects another runtime configuration and CHATSOP_CHAT_DATA another chat data root, so a private server on another port never touches the main one's sessions. The home page at / shows whether you are signed in and whether the administrator password is set, and links to the browser chat (/chat), the knowledge browser (/review), the evaluation page (/eval, guide at /eval/guide), the project page (/experiments, with the append-only journal status/journal.jsonl and the preregistered experiments in status/experiments.json), the admin page (/admin) and this documentation. A signed-out browser opening a protected page is sent to /login, which chooses the administrator password on the first run; API calls keep answering JSON 401/403. At start the base memories of server.warmMemories and the default base are decoded in the background (world-v1, about 357k facts in 221 layers, takes about 12 s); the server answers at once. GET /v1/status reports readiness, the formalization strategies with their availability, the base memories with their warmup, the reasoning engines and the caches.

The chat page answers in plain English. Under every answer a trace panel follows the pipeline below: Pragmatic signals (kind, score, span, source and basis of each detected signal, the tone applied), Formalization (strategy, tier ladder, number of questions, escalated questions, cache, latency, cost), Vocabulary (the size of the schema neighbourhood and the vocabulary dialog), Session definitions and assumptions (each session definition), Linking, Retrieval (complete or not, the bounds), Route and verification, and the circuits. The Settings tab chooses the formalization strategy of the session (a strategy that cannot run is shown disabled with its reason), the first tier of the ladder (a select over the tiers), and shows a server status card; a new session forks the default base memory, the encyclopedic world-v1 (chatData.defaultBase; when it is not loaded, the minimal default, which imports core-min); another base memory is chosen in the New session dialog. The Base Memory tab marks the default and creates memories built on the encyclopedic, minimal or empty base. The contract is DS009; the API is on the API page.

The chat pipeline

One user message, in any language, goes through these steps. Only the request parser uses a language model; everything after it is checked code, and it is the same code whichever strategy wrote the circuit.

  1. Courtesy and emotion. The formalizer understands the whole message in one step: besides the query or the statements it writes what the message also does (a greeting, thanks, an apology, a goodbye, a polite word, a feeling such as frustration, confusion or urgency) as advisory pragmatic wires (LocalLLMStepByStep through its acts question). There is no word list or pattern pre-step (the earlier lexicon EmotionDetectionSystem is archived). A message of pragmatic wires only ("hello", "thanks!") gets a short reply, status: courtesy, no computation and no memory change; otherwise the wires never change the question and only set the tone of the answer. Contract: DS023.
  2. The conversation layer: every reply is data, chosen by reasoning. The chat holds no phrasing in code. Every sentence it says is a reply wire of the seed memory conversation-v1 (reviewed in /review); the turn's result packet becomes facts (status, unclear kind, pragmatic signals, answered or not, the closest names of the memory, its topics), the layer's rules and priorities derive the applicable replies, and the JS oracle picks the opening, body and closing (a random variant), reporting why in chatSop.reply and the trace (section 2c). A turn without an answer is never a dry refusal: the near-miss search (lib/near-miss.mjs, fuzzy names of the memory and the relations around them) offers "Did you mean Socrates (…)?", a message without a request gets what the assistant can do and what its memory holds most of. Questions about the assistant ("what do you know?", "what can you do?", "a random fact") are ordinary questions about the self layer assistant-v1 (imported by world-v1, statistics generated from the memory), with order random and limit for samples. The answer-formulation step rewrites the composed draft as a natural reply with the default model (answerLanguage.natural), keeping every number and name; the draft stays in the trace.
  3. The behaviour layer: instructions and drives. "From now on always start your answers with «I'm here:»" is an instruction wire of the formalizer; the runtime keeps it in the conversation's behaviour (saved with the conversation) and turns it into data of the conversation layer, a reply wire with the user's words and a rule (origin user), so the reasoner applies it on every later turn; "stop …" withdraws it and "what are my instructions?" lists them. Drives are preoccupations of the layer that surface when their occasion comes and their cooldown has passed (an interesting fact about the answer every few turns, a check-back after a frustrated or confused message, an offer of what else the assistant can do); the turn number and the time since each kind of reaction are facts, so a greeting within the hour is answered as a return. chatSop.reply explains every part; chatSop.behaviour lists the active instructions.
  4. Request parser: formalization. server/query-parser.mjs formalizes the message step by step with the session's formalization strategy (owner decision 2026-10-02). LocalLLMStepByStep (the default, method B) asks short questions (the kind of answer, which statements of the memory, which name fills which place, true or absent, the period, the data of a problem) and assembles the circuit itself; InternalReasoningStepByStep plans the same kind of questions from a protocol memory. The questions are answered by proxy tiers on the ladder queryParser.local.ladder (shipped tiny, then small, then good): each question goes to tiny and escalates to the next tier only when its answer cannot be read or the tier does not answer; a larger tier answers the same question, never writes a circuit (choosing the formalization model). The questions draw on the schema neighbourhood of the session's memory (lib/query-author/neighbourhood.mjs: the entities the message names, the relations used around them). The circuit holds only queries, constraints, unclear/unparsed markers, labelled session definitions and assumed lines; it never answers and never states a fact. One-shot authoring (LLMDirect, a model writing the whole circuit) is archived in probably_obsolete/one-shot-formalization/; a session that names it runs the step-by-step default with a note in the trace.
  5. Admission and repair. The validator (lib/query-author/validate.mjs, admit.mjs, condition-use.mjs) admits only the circuit surface of DS014 with the memory's declarations: an unknown predicate, an undeclared role, an unused mention, a dropped quantifier, a condition misuse (a constant in a position where the memory never holds it), a range given as a point in time (time_not_a_point) or as a bare role time (time_range_needs_quantifier) makes the step-by-step strategy re-ask the doubtful question for a bounded number of rounds. A circuit that stays invalid is reported as an honest unclear, never replaced by a guess.
  6. Session definitions and assumptions. A term the memory lacks may be defined by the author as a session predicate and rule over existing relations. Such a session definition is used for this turn only, labelled in the answer, and, once valid, stored in the session layer; assumed lines are reported or run as a separate hypothetical branch. Memory always wins over a conflicting assumption.
  7. Linking. The KnowledgeLinker links relation phrases and entity names to the base memory and asks when a name is ambiguous. It does not parse language.
  8. Slice retrieval and the completeness guard. Only the facts the question and the reachable rules can use are fetched by keyed lookups (slices, reasoning/slice/); the completeness guard never gives a count, a universal answer or an unknown from a partial slice.
  9. Routing and verification. The StrategyRouter chooses the js-reference oracle or an engine (sql-sqlite, datalog-souffle, asp-clingo) by the features of the circuit and the size of the slice; a routed answer is checked by oracle verification (route.verification). A requested backend is never substituted.
  10. Rendering. sop/answer-text.mjs renders the result packet as English text deterministically, naming the origin of each step (memory, definition by the author, assumption by the author) and the sources used. The English rendering is always kept in the trace (chatSop.english_text).
  11. Answer formulation. When the message does not look English (answerLanguage.mode auto, the default; always or off are the other modes), server/answer-language.mjs asks a model of answerLanguage.providers (by default the proxy tier small, called directly through the proxy; thinking off), to phrase the answer in the message's language. The model sees only the English answer and a compact result packet (status, answers, count, facts used with sources). Every number and Wikidata id of the English answer must survive; otherwise the next model is tried, and in the end the English answer is returned. The trace reports answer_language (mode, message language, applied, model, time, models tried, reason). Example: "Unde s-a născut Ada Lovelace?" is answered in Romanian from world-v1 (Londra, Regatul Unit…), with the formulation taking a few seconds.

There is no fallback parser and no silent substitution of strategies. When no model of the chosen strategy can run the turn answers 503 parse_unavailable; when the models ran and no valid circuit came back after the last round it answers 422 parse_failed; a circuit that is written but cannot be admitted or executed answers 422 model_output_rejected. Each error carries the parse record. A wrong circuit executes to a wrong answer, which is why the benchmark counts a wrong circuit apart from an honest unknown. What the user states is turn-local evidence kept in the caller's conversation context; nothing in a chat turn writes to a repository.

Worked example: one chat turn on world-v1

A real turn, recorded on 2026-10-02 in a session on the base memory world-v1 (a Wikidata subset, about 357k facts) with the model zai/glm-5.3 (the turn predates the direct path; the circuit and the later steps are the same code for every strategy). The user asks: "Is Paris located in Europe?"

  1. Formalization. The schema neighbourhood offered 11 predicates (born_in, contains, died_in, is_a, located_in, part_of, …; 23,832 of 24,000 bytes) and two ambiguous mentions (Paris: paris, san_francisco, bucharest; Europe: europe, council_of_europe, …). GLM 5.3 wrote the circuit in one round, 6.8 s, cost class subscription (nominal 0.0104 USD), cache miss; the vocabulary dialog was not needed (0 of 2 expansions):
    @q query
  where match
    relation "located_in"
    role subject "paris"
    role location "europe"
    polarity affirmed
  end
  2. Admission accepted it without repairs (parse.rounds: 1).
  3. Linking. The relation linked to located_in through the lexeme "be located in" (lx_located_in_en_copula, the only candidate, 9,453 facts); the names linked to paris and europe. The generated execution circuit:
    @q query
  where located_in paris europe

@host0 solve
  query $q

@host1 cnl
  result $host0
  language en
  4. Retrieval. The slice was complete (guard complete_slice): 4 facts and 8 rules over located_in, contains, capital_of and headquartered_in, class recursive, 32 keyed lookups, no scan, within the bounds of 10,000 facts and 60 s.
  5. Route. Requested auto, chosen js-reference by the rule caller_budget (the oracle defines the budget keys of a chat turn); datalog-souffle, sql-sqlite and asp-clingo were eligible alternatives; no fallback.
  6. Answer (status: supported, complete), rendered from the packet:
    Yes.
Paris is based in France (memory: Wikidata Q90 P17).
France is based in Europe (memory: Wikidata Q142 P30).
Sources used: memory (r_located_in_transitive), memory (c_2e2ee…) and memory (c_f061d…).

Formalization took about 7 s of the turn and the whole turn about 10 s. The proof used the rule r_located_in_transitive and two Wikidata facts; both facts were reinforced by proof use as the retention policy allows.

Choosing the formalization model

Proxy tiers. Every formalization calls its model directly through the local proxy LLMAPIProvider/ (node LLMAPIProvider/server.mjs; OpenAI-compatible, http://127.0.0.1:18080/v1). The configuration names tiers, not concrete models: tiny is the local Qwen3-4B (started on demand, falling back to DeepSeek v4 flash), small the openference Qwen3.8 27b (falling back to DeepSeek v4 flash), medium DeepSeek v4 flash through OpenRouter, good DeepSeek v4.1 flash, best is not configured. queryParser.local.ladder (shipped ["tiny", "small", {"tier": "good", "extraBody": {"reasoning": {"enabled": false}}}]) is the tier ladder of the step-by-step questions; without it queryParser.local.tier alone answers. Knowledge authoring uses ingest.tier (small). The proxy reports what served a call in x-llmapiprovider-model and x-llmapiprovider-tier; formalization calls are tagged x-llmapiprovider-purpose: formalize. When the first tier of the ladder is not reachable the turn fails with parse_unavailable and the reason; a higher tier that is not reachable only stops the escalation. The same proxy serves the answer-language step and the books judge (tools/eval/books/score.mjs --judge).

The step-by-step strategies. LocalLLMStepByStep and InternalReasoningStepByStep use the proxy tier ladder by default (queryParser.local.ladder, first tier tiny); the product starts no llama-server. The parse record lists the ladder, every answer with its tier, and the escalated questions; evaluations name one tier (--tier) so tiers are compared on the same questions. The model only answers short questions and numbered choices; the symbolic system assembles the circuit. An explicit queryParser.local.endpoint or gguf (evaluation harnesses) selects an external or managed llama-server instead, with one dedicated slot each, flash attention, full GPU offload, prompt cache on, and a stable prompt prefix evaluated once and restored before every request.

Selecting the strategy. Set CHATSOP_FORMALIZER=LocalLLMStepByStep (the default) or InternalReasoningStepByStep before npm start, set "strategy" in queryParser of the runtime configuration, or pick the strategy per session in the chat's Settings (Formalization card; POST /v1/sessions/{id}/settings {"formalizer": "LocalLLMStepByStep"}; formalizer_model names the tier the session's ladder starts at). GET /v1/status shows whether each strategy can run and its tier ladder. The archived name LLMDirect (and CodingAgent, LocalLLMDirect) runs the step-by-step default with a note in the trace.

An external llama-server (evaluation). Start it once with the same optimised flags, then point the chat server at it:

node tools/local-llm/serve.mjs --gguf <path-to>/Qwen3-4B-Q4_K_M.gguf --port 19601 --alias qwen3-4b --slots steps,reasoning --ctx-per-slot 16384
# then in config/runtime.json: "queryParser": {"strategy": "LocalLLMStepByStep", "local": {"endpoint": "http://127.0.0.1:19601/v1", "alias": "qwen3-4b"}}

Question protocol of LocalLLMStepByStep. queryParser.local.method chooses the protocol: B (default) is the generic protocol of DS022 "LocalLLMStepByStep": 13 answer kinds and 8 aspects in the cached prefix (3 more aspects in the checklist question), the message acts (greeting, thanks, apology, goodbye, politeness, a feeling) as pragmatic wires, places typed and pre-filled from the memory's facts, limits, options, exclusions, two-sided comparisons, groups, suppositions, chains and per-group counts written by the system, a forced-contrast confirmation, and an honest unclear instead of an invalid circuit. A is the first protocol; D and B-yesno are the measured variants (C and B-cue, which read a regular-expression cue table, were removed on 2026-10-02 with the table: every aspect, limit, option, exclusion, supposition and the message acts now come from the model's answers). After the removal, on 24 known-form and 10 natural rows, method B stayed at 21 of 24 and went from 6 to 7 of 10 correct, with about 1.7 more questions per request. On 89 development rows (known forms, held-out forms, compositions, natural questions) Qwen3-4B Q4 went from 23 correct and 24 wrong (A) to 73 correct and 3 wrong (B) at a median of 0.4–0.9 s per message; see eval/reports/current/omp-tasks/stepbystep-protocol.md.

InternalReasoningStepByStep. A further strategy asks the same kind of short questions, but its questioning protocol is a base memory of wires, config/knowledge/formalizer-protocol-v1 (questions as action wires with their texts and choices as facts, slots as facts, slot rules, early exits as default wires, consistency as integrity wires and the goal formalized; namespace fp_; not a chat base memory). Before every question the JS oracle plans to the goal over the protocol and the request's facts (observations from structure and memory data, the slots established so far): the first action of the cheapest plan is the next question, no plan means an honest unclear, and the derivation of the chosen question is the trace's reason for asking it. The code reads the answers structurally, assembles the circuit with the step-by-step circuit writer and validates it; validator problems become facts for the next decision. It runs on its own slot reasoning (CHATSOP_FORMALIZER=InternalReasoningStepByStep, or the session setting); queryParser.local.reasoningControl is plan (default) or greedy. node tools/formalizer-protocol/check.mjs lints the protocol, replay.mjs replays recorded answers after a protocol change. Specified in DS022 "InternalReasoningStepByStep"; measured in eval/reports/current/internal-reasoning/summary.md.

Only one GPU worker runs per machine: the managed server refuses to start while models/.training.lock or models/.parse-gpu.lock exists. A smaller model is a configuration change (gguf, alias); measured on the development benchmark (40 rows, 5 per family F2–F9), Qwen3.8-27B answers 36 of 40 correctly with LocalLLMStepByStep at a median of 2.2 s per request and Qwen3-4B Q4 27 of 40 at 0.34 s (eval/reports/current/omp-tasks/t10-stepbystep.md). The protocol is specified in DS022 "LocalLLMStepByStep".

Evaluating on the owner's problem books

The owner's problem books (datasets_sources/books/*.docx, rights owner-provided; the books and everything derived from their text stay in the gitignored datasets_sources/ and eval/reports/current/) are an end-to-end test of understanding, formalization, the memory and the reasoning engine. node tools/eval/books/extract.mjs reads the DOCX files with Node built-ins and writes about 7000 problems with answers to datasets_sources/books/eval/items.jsonl (node tools/eval/books/validate.mjs checks that every question and answer is verbatim in the book). node tools/eval/books/run.mjs --n 100 draws a stratified random sample (equal share per book, areas cycled, never an item run before unless --include-seen; also --seed, --books, --areas, --arms steps,direct, --tier tiny|small|good for who answers the questions, --endpoint URL to reuse a running local server) and runs the arms: steps is the product chat turn with LocalLLMStepByStep (method B) on a local Qwen3-4B-Instruct Q4_K_M, the problem text being the user message and the default base memory the base; direct is the same model answering directly; with --tier, the steps arm asks one named proxy tier, so tiers are compared on the same questions (the one-shot arms are archived). Each problem is its own conversation, and a session definition one problem adds is removed after it. A problem that states its own data is modelled from its own text (DS014 "Problems that state their own data"): session predicates for its vocabulary, stated data, session rules with exact decimal compute arithmetic, then the queries; LocalLLMStepByStep reaches the same circuits through its problem questions. The engineering loop and its results are in eval/reports/current/books-eval/problem-mode.md. Then score.mjs --run DIR scores by rule (yes/no, numbers, entities) and prepares blind judge batches for the rest, score.mjs --run DIR --merge adds the judge verdicts, and report.mjs --run DIR writes summary.md (per arm, book and area, what the system did, failure classes with examples) and eval/reports/current/books-eval/index.md.

Improving the step-by-step formalization

The step-by-step strategies read their problem questions, their order, conditions, early exits and texts from two base-memory layers: config/knowledge/formalizer-protocol-v1/0060-problem.sop and the learned-rules layer config/knowledge/formalizer-learned-v1 (lib/formalize/protocol-data.mjs). Every formalization error found anywhere goes to state/formalization-errors/inbox.jsonl; node tools/eval/formalization-regression/build.mjs turns it into the accumulating regression set eval/formalization-regression/cases.jsonl (references and labels only: the problem text and the gold answer are read at run time from the gitignored books extraction or the inbox; no sealed suite enters). node tools/eval/formalization-regression/run.mjs [--workers 4] [--learned DIR] [--against RUN] runs every case through the chat turn with LocalLLMStepByStep on the proxy tier tiny (no proxy fallback, calls tagged job:formalization-improve), scores it with the books rules and a cached judge, and writes state/formalization-regression/RUN/{results.jsonl,score.json,summary.md} with a failure cluster per case. node LLMJobs/run.mjs jobs/formalization-improve (one cluster, FI_CLUSTERS=... to choose) lets the tier good propose learned-layer fact wires; checks.mjs admits only hints, invented examples, replacement texts with the same placeholders and the problem-mode order and exits, refuses text copied from a case and lints the protocol; the sink runs the regression gate (tools/eval/formalization-regression/gate.mjs): the cluster's cases, then every case the baseline answers, then the fixed and lost cases once more; a change is written to the learned layer only if it fixes cases and loses none. Refusals and ESCALATE replies (a missing language construct) go to the run's escalations.jsonl for the formalization improver. node tools/eval/formalization-regression/wake.mjs --exit-due says whether enough new cases arrived (default 10) to start a run; --mark records a finished run.

The capability battery: no capability loss

Changing the language, a validator or an engine must never silently lose a capability. node tools/capabilities/inventory.mjs --write derives the capabilities from the grammar and the contracts (every wire type, keyword, enum value, condition word, validator code and strategy feature, and the meaningful pairs) into eval/capabilities/capabilities.json. node tools/capabilities/coverage.mjs [--capture] [--battery] --label NAME writes the coverage matrix to eval/reports/current/capabilities/coverage-NAME.md, counting the circuits that exercise each cell, read by parsing them. The battery has three layers. L1 is the generated validation cases per keyword (tools/capabilities/l1.mjs). L2 is generated programs on the oracle and every engine, all-pairs plus a sweep of every compute word, with metamorphic variants (tools/capabilities/l2-generator.mjs, l2-run.mjs). L3 is formalization messages scored by answer (eval/capabilities/l3/catalog.jsonl, tools/capabilities/l3-run.mjs; its failures go to the formalization inbox). node tools/capabilities/check.mjs [--tier fast|full] compares a run with the ledger eval/capabilities/ledger.json and fails on a lost capability or a new disagreement with the oracle. The fast tier runs in npm test. --tier full --update rewrites the ledger; a lower ledger needs --accept-loss "reason", which is journaled. The contract is in DS012, obligation 7.

Execution and publication

The parser checks each typed declaration. SOP relations use whitespace-separated terms such as works_at maria acme, with no parenthesized arguments or comma separators; arithmetic and solver-internal languages retain their own syntax. A stated or assumed wire of a coding-agent circuit is a string proposition that the KnowledgeLinker links and lowers to a turn-local fact, never a sourced repository fact or a write. The runtime compiles an inspectable circuit for linking, identity lookup, conditional assumptions, reasoning and rendering, and generates a specific clarify wire only when identity is unresolved or ambiguous or a required scalar is missing or nonunique; lack of evidence alone is not a clarification request. A linker selects approved definitions and retrieves facts from a memory engine; the selected reasoning strategy computes a result, binding, evidence and completeness information; CNL renders the result without changing it. Only an explicit trusted remember records facts in the selected session, and committing that session is a separate act. The grammar and execution contract are in DS004.

The repository separates users, sessions and forks. A claim's valid interval is distinct from when the claim became known; correction and retraction cannot be erased by choosing another memory engine. Referenced snapshots remain reachable GC roots. A missed retrieved fact is not a proof that it is false. See DS005.

Worked example on the fictional fixture: circuit to checked answer

The author sees the user's message and the schema neighbourhood and writes the circuit; the runtime links the strings, builds the execution circuit, and every reported value below comes from an actual runtime result over the reviewed fictional fixture.

Answer supported by reviewed knowledge

"Where does Maria work?"

@question query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

Generated execution circuit: the phrase "works at" with roles subject and object links to works_at; "Maria" is resolved as a person; the object role stays the variable.

@host0 resolve
  text "Maria"
  language en
  kind entity
  type person

@question query
  where works_at $host0 ?org
  select ?org

@host1 solve
  query $question

@host2 cnl
  result $host1
  language en

Observed result: status: supported, ?org = "lab_alpha", evidence works_at maria lab_alpha with SOURCE demo; the formalizer authored none of the resolve, solve or cnl steps

A user supposition stays hypothetical

"Suppose Carina is a parent of Ana. Who is Carina a parent of?"

@context stated
  relation "parent of"
  role subject "Carina"
  role object "Ana"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "parent of"
    role subject "Carina"
    role object ?who
    polarity affirmed
  end
  select ?who

The generated circuit lowers the supposition to @context fact … source assumption and adds assume $context to its solve. Observed result: status: supported with hypothetical: true, ?who = "ana", evidence SOURCE assumption, the rendered condition "You supposed: parent of (subject: Carina; object: Ana).", and the session still holds zero repository claims after the turn. Had the user asserted it (certainty asserted), the statement would be turn-local user evidence and the answer would not be hypothetical; it is still never recorded.

Both outputs were produced on 2026-09-28 by executing these programs with the runtime against tests/fixtures/bootstrap.sop at a fixed evaluation time.

KnowledgeLinker: strings to the predicates of the base memory

After the formalizer, the KnowledgeLinker links each relation phrase to a predicate of the chosen base memory. The words come from the base memory itself: a predicate whose id, label, lexeme form or reviewed relation lexicon entry equals the phrase binds first ("be the capital of" to capital_of), and an entity is found by its labels and aliases. Every session links against the lexicon of its own base memory (compiled from its circuits and those of the memories it imports, DS022 "Lexicon of a memory"), never a global one. The packet and the chat trace report what was linked as linking (surface, symbol, matched form, alternatives not taken). The plain copula has no predicate of its own: "Ana is a doctor.", "Is Paris in France?" and "Who is Ana?" are read with the copula readings the memory itself declares (reading class|occupation|attribute|identity|location|describe on its predicate wires), tried in order against the knowledge; a question keeps every reading that fits as an any group and a statement takes the first. The packet lists them as copula_readings; "Where is Paris?" (the bare copula with a location role) is the location reading. A memory that declares no reading gets a precise question ("Do you mean what Ana does, or who Ana is related to?"), never "I do not know the relation be". Details: DS014, "KnowledgeLinker: the copula and the relation lexicon". Three further rules close the gap between the words a circuit uses and the names a memory declares: a phrase that does not link as written is rewritten by the reviewed frames before the dictionary tiers (reported as frame_changes, never used by the strict link), a query role the predicate does not declare is renamed to the one declared role that is free (relabeled in the linking entry; never the subject), and a leading article is dropped from an entity name when the whole surface finds nothing. The rules of the memory's circuits (for example located_in transitivity) reach the chat turn's query the same way they reach POST /v1/sessions/{id}/query.

Knowledge wires and reasoning strategies

Knowledge written from a source (a manual, a regulation, an article) is a set of knowledge wires: predicate declarations with roles and types, fact, rule, default, integrity, aggregate, action, method, norm and procedure. They are written by the direct author (a chain model) or the owner, never by the query author, and checked before they are stored: node eval/smoke-reasoning/validator.mjs [--authoring] knowledge.sop query.sop runs the validator of sop/knowledge/, the single grammar source. The runtime stores the approved wires, selects a slice relevant to a question, and a strategy answers it; a question reaches the strategy only through the KnowledgeLinker, where the roles of a predicate place the circuit's strings in the predicate's positions.

What a question returns is a result packet: a status (supported, refuted, both, unknown, and for planning and conformance plan_found, blocked, compliant, non_compliant), complete, the rows with their own conditional assumptions, used (one sufficient set of claims with their versions), the route and a budget block. Two negations are never confused (not is explicit evidence, absent works only over a predicate declared closed); positive and negative evidence propagate independently, so a contradiction is reported as both and stays local; a default is blocked by an exception, a strict contrary or an overriding default that fires; counts and "every" over an open predicate are lower bounds or unknown; time is a snapshot (at, during throughout, overlaps, asof). A strategy that cannot express a question says not_expressible and never weakens it; a budget cut is budget_exhausted with a reason, never unknown or no_plan. Approved methods and norms (a "mode of work") bound what a plan may do, mode why_not names what blocks a step, and a change is negotiated as an amendment composed by the runtime and evaluated as a what-if. The manual is the section "Knowledge wires" of DS004, the strategy interface, budgets, shadow gate and routing rules are in DS006 "Strategies", and the comparison suite is in DS010. node eval/smoke-reasoning/run.mjs runs every strategy on the smoke cases.

From a memory to the reasoner: slices and the completeness guard

A base memory can hold hundreds of thousands of facts, so the reasoner never receives the memory. For each question linkKnowledge (reasoning/linker.mjs) takes the rules that can reach it and asks SliceRetrieval (reasoning/slice/) for the facts those rules and the question can use. A static plan, a magic-set style rewriting (demand.mjs), orders every conjunction by sideways information passing and decides, for each atom, whether it is keyed (a constant, a variable of an earlier atom, a head variable that every call site binds) or must be scanned. Keyed atoms are fetched by lookups of one position and value through the memory strategy (the SQLite bank indexes each position), the values coming from the facts already retrieved, until nothing more is owed: the fixpoint of the demand. A relation too large to read whole is never scanned when a constant can key it.

The slice is complete when that fixpoint was reached with no lookup truncated and no budget stopped it (facts, probes, lookups, wall-clock retrievalMs), and settled when every lookup was also answered by an exact view (an associative memory returns candidates and never closes a relation). The completeness guard (guard.mjs) then decides what may be said: a proof, a counterexample or an opposing fact stays valid over a partial slice and is returned with complete: false; a list of rows is widened and, if it cannot be completed, returned as a partial list; a count, a universal answer no counterexample decided, a ranking, and an unknown obtained by failure are widened and otherwise answered status: incomplete, reason: partial_retrieval, with the lower bound of a count as at_least. They are never given as closed-world answers. Every packet carries retrieval: the slice's size, its predicates, the bounds in force, whether it is complete, why not, and one trail entry per widening step. Retrieval reads only; it reinforces nothing.

POST /v1/sessions/{id}/query answers a knowledge-wire query circuit over the session's memory the same way (askMemory): the oracle gets the rules, defaults, aggregates and predicate declarations that can reach the query and the facts they need, and the guard reads the oracle's own sensitivity, so absent, aggregates and default conclusions are judged on the desugared program. Timing on synthetic SQLite memories: node tools/eval/slice-timing.mjs (report in eval/reports/current/slice-path/timing.json). Specifications: DS005, DS006, DS018.

Sessions, base memories and the direct author

Every chat runs in a session: a working copy of a chosen base memory under the gitignored folder chat_data/ (DS022). The lifecycle: (1) the owner prepares base memories: POST /v1/memories creates or imports one of a chosen memory strategy, POST /v1/memories/{id}/knowledge adds circuits that pass the knowledge validator, recorded with the acting user, and POST /v1/memories/{id}/fork forks one (a copy-on-write clone, or a replay into another strategy). (2) A chat starts with POST /v1/sessions {base}: the base memory's repository is cloned by hard links and its circuits are copied into chat_data/sessions/<id>/. (3) Each message is answered over base plus session (session_id in the chat request); asserted statements stay turn-local. (4) Attached files go to the direct author (a chain model called through the proxy, with the skill sop-wire-authoring, no tools) in a temporary folder under the session; the validator checks the circuits it writes and, with a session, the valid ones join the session layer at once (POST /v1/author; an invalid circuit is refused and nothing is stored). (5) There is no manual accept or reject: wrong knowledge is corrected through tests and interactions. (6) A user may commit the session to a new fork of its base memory (.../commit), validated again and recorded with provenance; the base memory the session started from does not change. (7) Temporary folders older than 24 hours and sessions idle for 14 days are removed. The endpoints, with executed examples, are in the API page sections 5 to 8.

The knowledge browser: what a memory knows

The page /review (menu Knowledge, signed in) shows what a base memory or a chat session knows, read only. A memory is seen as its layers: the import snapshots (core-min, core-en, commonsense-v1, …), its own circuits, one layer per document ingestion, and for a chat session the session layer. For each layer the page gives its provenance (who added it, from which source, when) and a risk view: the vocabulary and theory items with the most likely problems first. A flag is a hint, not a verdict: a lexeme form with no count in the mined corpus and no Wikidata label or alias of the property its source cites, a form that two predicates of the same arity claim (told apart only by restrict or weight), a converse frame ("employ" for works_at), a rule (it derives new facts), a predicate without a description or without an English form, and for world-v1 the mapping choices (a Wikidata property emitted flipped, several properties merged into one predicate); facts and plain entities are shown as groups per predicate and class with sample facts, never one by one. Next to each item is its evidence, and its effect rather than its syntax: a generated sentence for each form and the atom it maps to ("Ana works at Beta Labs" → works_at ana beta_labs, with real entities when the memory has facts of the predicate), the predicates the lexicon links the phrase to, and for a rule a derivation over the memory's own facts ("Babeș-Bolyai University is based in Cluj-Napoca" and "Cluj-Napoca is based in Romania" ⇒ "Babeș-Bolyai University is based in Romania"). A search box finds entities by label and alias, classes, predicates by their forms and descriptions, rules and the text values of facts, using the lexicon's token index and a per-layer index, never a scan of all facts. An entity card lists the classes closed over is_a, every stored fact in both directions with its layer and source, and the rules that can derive more; Derive asks the oracle, through bounded queries, what those rules conclude and shows each derived fact with its proof. A predicate card gives the roles, how people say it (forms with evidence), example facts and the rules that use or conclude it. There is no approve or reject step (AGENTS.md direction 8): problems found here are corrected systematically, through tests and interactions. The API is GET /v1/knowledge/* (API page section 9); the contract is DS022 "Knowledge browser".

Task-type base memories from documents

Learning in ChatSOP is adding knowledge to a base memory, not training a model (owner decision of 2026-10-02). A task-type base memory holds the facts, relations, rules and procedures of one kind of task, built from documents: (1) create the memory, usually importing core-min for the shared vocabulary (node tools/ingest-documents.mjs create-memory or POST /v1/memories); (2) ingest the document (tools/ingest-documents.mjs ingest --memory ID --file doc.md --rights cleared or POST /v1/memories/{id}/ingest): only documents with recorded rights are taken (DS011); the document is cut into chunks along its headings, and a model compiles each chunk with the skill sop-wire-authoring over the memory's vocabulary, the chunks merged before it and the entity symbols already in use, with a quote and a source on every fact and rule (by default one chat-completion conversation per chunk with Qwen3.8 27b through the proxy LLMAPIProvider, a few chunks at once, merged in document order; --author omp runs a full omp coding-agent session per chunk instead); (3) the validator and the quote check (each quote must be a passage of the chunk) run in the bounded repair rounds; a fact that duplicates or contradicts the memory is held back (memory wins); (4) read the report, whose chunks are already stored (report.md of the ingestion: extracted wires by type, rejected quotes, held-back conflicts, uncertain wires, what the agent could not express, rounds, time, cost); (5) every validated chunk is stored at once, with no acceptance step, through the knowledge validator with the document's provenance (SHA-256, URL, licence, section, lines) and the acting user; (6) start sessions on the memory (POST /v1/sessions {base}). Re-ingesting a document adds nothing, and an edited document adds only its changed chunks. Rules that answer one question form are kept as a procedure (a procedure bundle with a description of the form, POST /v1/memories/{id}/procedures); when a message matches the description, the query author is offered the procedure's head predicate and its rules and queries it instead of re-deriving it. Contract: DS022 "Ingesting documents into a base memory" and "Procedure library"; examples on the API page.

Batch work and large inputs: the job runner

Every LLM batch job (ingestion, labelling, knowledge mining, bulk review, calibrations, data generation) is a job spec run by LLMJobs/, a self-contained runner with deterministic control: a person or an agent writes the spec and reads a summary of at most 10 lines and the escalations, never the calls. A job folder under jobs/ holds job.json (inputs and the fields the prompt may see, packing, a model tier or a tier ladder, output format, checks plugin, repair rounds, budget, stages with stop rules, audit sample), prompt.md and its plugins; node LLMJobs/run.mjs jobs/<job> runs it through LLMAPIProvider with the job's purpose and run id, answers repeated calls from a content-addressed cache, resumes an interrupted run, and writes only its own folder state/llm-jobs/<job>/<run-id>/ (accepted.jsonl, rejected.jsonl, escalations.jsonl, summary.md, cost.json, run.json). Items that fail their checks are repaired, climb the tier ladder (tiny, small, medium, good; the start tier is learned per task kind from state/llm-jobs/tier-stats.jsonl), and what still fails goes to the decider tier, which retries with a hint, drops, or escalates. Large inputs with instructions run as tasks: node LLMJobs/run.mjs task --instructions "Learn this handbook" --attach handbook.md --target memory:hr-policies plans with the good tier over the templates of jobs/templates/ (ingest-document, extract-table, label-entities, bulk-review), validates the plan deterministically, runs it, stores the results through the existing store path and returns the summary. Contract: DS022 "Large inputs through the job runner (LLMJobs)"; manual: LLMJobs/README.md.

Alternative routes and limits

A runtime configuration under config/ independently selects memory.engine (recall-memory for RecallMemory, holo-memory for HoloMemory, sqlite, scan or hybrid; see DS005 and the per-strategy specifications DS016–DS021) and policy.reasoningStrategy (reference, the js-reference oracle through the runtime bridge; a wire that names an external backend maps to that backend's strategy id or returns unsupported with the backend named and fallback: null; the former separate JavaScript reasoner was retired on 2026-10-01). policy.reasoningStrategy (or a wire line reasoning auto) also accepts auto, the StrategyRouter v1 of DS006 "Routing rules": on the knowledge-wire path (POST /v1/sessions/{id}/query, body reasoning and verify) it chooses between the oracle and the engines sql-sqlite, datalog-souffle and asp-clingo by the features of the circuit (recursion, negation, aggregates, time, modes of work) and the size of the slice, reports the choice, the rule and the alternatives in route, and checks a routed answer against the oracle (a disagreement returns the oracle's answer with the discrepancy); on the typed path every answer carries a proof, so auto reports the oracle. The result records the actual route and fallback; a requested backend is never silently substituted, and a JavaScript result is never reported as a Prolog or Z3 measurement. Associative recall produces candidates subject to verification. The routing rules and the strategy × backend matrix are in DS006.

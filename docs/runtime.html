Overview / Runtime

ChatSOP Documentation

Local users run typed SOP circuits against reviewed knowledge and receive checked results. The host, not a source document or a language model, chooses the active user, permissions, runtime configuration, and approved definitions.

Local CLI

From the repository root, node server/cli.mjs help lists the local commands: init publishes a small reviewed fictional fixture, run --file examples/query.sop executes a circuit and validate checks a program. The command list and each command's observable behavior are owned by DS003. A chosen runtime configuration belongs under config/; chat runs the product chain through the SymbolicLM service, with the deterministic controlled-language answer and no LLM verbalizer.

Local server

npm start serves everything on one port (default 0.0.0.0:9999) and prints the home URL first. The home page at / shows whether you are signed in, whether the administrator password is set and the state of every managed model (stopped, starting, ready or error), and links to the browser chat (/chat), the corpus audit (/audit), the evaluation page (/eval, with its guide at /eval/guide), the project page (/experiments, which shows the append-only journal status/journal.jsonl and the preregistered experiments in status/experiments.json), the admin page (/admin) and this documentation. A signed-out browser opening a protected page is sent to /login, which chooses the administrator password on the first run and signs in afterwards; API calls keep answering JSON 401/403. The chat page has one mode, the product chain: an optional Clean before formalizing step, SymbolicLM, host linking and execution. The Model list shows the formalizers of config/formalizers.json (SymbolicLM, a service that needs no GGUF); the proofing models (LanguageProofingLLM, translator-llm, SymbolicProofingLLM) run inside the chain as CPU llama-server processes whose lifecycle (keep_open, on_demand, off; idleMinutes 60, maxRunning 6) is set in config/server-models.json. An Answer language list offers English, Română and Any: the language of the answer. Each answer shows a collapsible trace with the model that answered and the latency, and adds the model SOP, the host-generated execution circuit, status, backend, fallback, assumptions and reinforcement. A model that cannot start is reported with its reason (HTTP 503). The contract is DS012.

textToCleanEnglish: a user-validated step before formalization

Owner decision of 2026-09-30: formalization handles only clean English. Before a message is sent, the chat page's Clean before formalizing toggle (on by default) calls POST /v1/text-to-clean-english, which runs textToCleanEnglish (lib/text-to-clean-english/) entirely as host code before the model boundary: it corrects spelling and grammar, translates Romanian or mixed Romanian/English text to English, and simplifies wording, returning {original, clean, changed, reasons, spans, backend, confidence}. The host splits the message into sentences and a cheap gate skips every already-clean English sentence; only flagged sentences go to the backend, one request each (llm.sendAll: true sends all sentences; default false). English sentences go to LanguageProofingLLM, the fine-tuned Gemma 3 270M production build of run language-proofing-gemma270m-prod1 (registry entry language-proofing-llm, capability proofread, F16 GGUF, message-only prompt); Romanian and mixed sentences go to the translator-llm (Qwen3-4B Q4_K_M, with LanguageProofingLLM as fallback); the choice is in config/text-to-clean-english.json. An unreachable backend degrades to "no change" rather than blocking the message. When cleaning changes the message, the page shows the proposal as a word-level diff with three choices — Accept, Edit, or Send original — before anything reaches the formalizer; whichever text is finally sent is the formalizer's whole input, unchanged from DS021 "Model boundary", and the request may carry cleaning: {original, backend, changed} so the trace keeps both the original and the accepted wording. The contract is DS012 "textToCleanEnglish" and DS021 "textToCleanEnglish".

Understanding in the chat

Each answer carries a collapsible "I understood:" panel (the Show what I understood (CNL) setting, on by default): per sentence, short controlled English restating the analysis SymbolicLM actually used (DS021 "Interpretation CNL"), checked by a round trip; a sentence whose round trip fails is shown as an "uncertain interpretation" with a raw analysis summary, never as silent CNL. The panel also shows the spans that were not represented (highlighted in the message), whether each sentence's analysis is certified (identical default and accurate Stanza trees) and, when the SymbolicProofingLLM rewrite setting is gated or always, the original sentence, the rewrite and whether it was accepted. The Clean text before formalizing and Send every sentence settings control the LanguageProofingLLM step above. All settings are remembered per browser; the chat API takes the same choices (understanding, sendAll) and returns chatSop.understanding (DS012 "Understanding in the chat").

SymbolicLM: the symbolic formalizer

SymbolicLM (lib/symbolic-lm/) formalizes a message without a neural model and reads the message alone. On route translate it parses a Romanian sentence with the Romanian Stanza model and calls TranslatorService to realize it in plain English; it parses the English with the English Stanza model; and converts the parse into SOP Lang with the UD-to-SOP rules of lib/ud-to-sop/, mapping every value back to the words of the original message. English messages skip translation. Per-token language identification and the optional spelling correction are LanguagesUtil's job, called before routing. Every step is in the trace: token languages, spelling changes, the English text and where each word came from, both parses, rule notes and unparsed spans. An uncertainty signal lists why an analysis may be wrong (untranslated words, unparsed spans, rule fallbacks, unusual trees, and disagreement between the default and accurate Stanza parses); an optional rewrite function, such as SymbolicProofingLLM, may rewrite the English text before it is parsed again, only when the signal fires or always. Commands: node tools/symbolic-lm.mjs analyze "<message>" --trace, node tools/symbolic-lm.mjs english "<message>" (or --in rows.jsonl --out out.jsonl), and serve, which the chat starts on demand as the model symbolic-lm on the CPU. serve --rewrite-url <endpoint> [--rewrite-when always|uncertain] wires the SymbolicProofingLLM rewrite backend; in the product chain it is the registry entry symbolic-proofing-llm, the fine-tuned Gemma 3 270M iteration 3 (run symbolic-proofing-gemma270m-it3, F16 GGUF; the role id proofreader is frozen), and the rewrite is gated by default: it runs only when the uncertainty signal fires. The contract is DS021 "SymbolicLM".

LanguagesUtil: language identification and spelling

LanguagesUtil (lib/languages-util/) answers two questions about text, and nothing about UD, SOP or translation: per-token language identification (Romanian, English, name, number, punctuation, other, with its evidence) and matrix-language (frame) detection for a code-switched message, from its closed-class function words; and a conservative symbolic spelling correction. SymbolicLM and TranslatorService both call it; it calls neither. The contract is DS021 "LanguagesUtil".

TranslatorService: pluggable translation toward English

TranslatorService (lib/translator-service/) is the dedicated translation component SymbolicLM calls on route translate; SymbolicLM itself keeps only UD parsing, SOP generation, the uncertainty signal and routing. Backends are loaded by name (lib/translator-service/index.mjs): symbolic, the deterministic dictionary-and-rules translator (moved unchanged from the former lib/symbolic-lm/translate.mjs), is the only backend wired into the runtime pipeline; opus-mt and apertium are research backends, translating masked raw text through an external CPU translator, exercised only by the preregistered comparison eval-translator-compare-v1. The contract is DS021 "TranslatorService".

Execution and publication

The parser checks each typed declaration. SOP relations use whitespace-separated terms such as works_at maria acme, with no parenthesized arguments or comma separators; arithmetic and solver-internal languages retain their own syntax. A model-origin stated or assumed wire is a string proposition that the host links and lowers to a turn-local fact, never a sourced repository fact or a write. Approved host code compiles an inspectable circuit for linking, identity lookup, conditional assumptions, reasoning and rendering, and generates a specific clarify wire only when identity is unresolved or ambiguous or a required scalar is missing or nonunique; lack of evidence alone is not a clarification request. A linker selects approved definitions and retrieves facts from a memory engine; the selected reasoning strategy computes a result, binding, evidence and completeness information; CNL renders the result without changing it. Only an explicit trusted remember records facts in the selected session, and committing that session is a separate host action. The grammar and execution contract are in DS004.

The repository separates users, sessions and forks. A claim's valid interval is distinct from when the claim became known; correction and retraction cannot be erased by choosing another memory engine. Referenced snapshots remain reachable GC roots. A missed retrieved fact is not a proof that it is false. See DS005.

What the small language is for

(The current formalizer is SymbolicLM, which writes this language from a grammatical analysis; FormalizerLLM, the small fine-tuned model that was the earlier formalizer, is archived and removed from the product (2026-10-01); the boundary is the same. SymbolicLM parses English with the Stanza accurate package (electra-large parser, configuration config/symbolic-lm.json, environment CHATSOP_STANZA_PACKAGE=default|accurate); a batch of messages is parsed in one GPU pass, the optional uncertainty reason parsers_disagree compares the two packages and is off by default because it runs a second worker.) The small model describes problems, never actions or advice. It sees only the user's message — no vocabulary, identifiers, knowledge or clock — and may author only stated, assumed, unclear, query and constraint, as strings: what the user's message puts forward, what the model added, that the message is unintelligible, contains no request, or has several equally good readings, what is being asked, and which finite numeric claim must be decided. Linking the strings to knowledge, identity lookup, retrieval, reasoning, recording and rendering stay host work. The model never refuses: a request phrased as guidance ("what should I do?") is formalized into the question behind it; the host answers it, asks with a clarify when a relation, identity, date or scalar cannot be linked or determined, or states "I understood the question as …; I cannot compute this kind of answer yet" — the runtime never invents a recommendation, and the model cannot select a procedure or write memory. Answers are in English unless the user requests Romanian. The model surface, its scope, its non-goals and the conservative checklist for any future construct are specified in DS021.

Worked example: context-free question to checked answer

The model sees only the user's message and writes declarative SOP as strings; the host links the strings to its reviewed lexicon, builds the circuit, and every reported value below comes from an actual runtime result over the reviewed fictional fixture.

Answer supported by reviewed knowledge

"Where does Maria work?"

@question query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

Host-generated circuit: the phrase "works at" with roles subject and object links to works_at; "Maria" is resolved as a person; the object role stays the variable.

@host0 resolve
  text "Maria"
  language en
  kind entity
  type person

@question query
  where works_at $host0 ?org
  select ?org

@host1 solve
  query $question

@host2 cnl
  result $host1
  language en

Observed result: status: supported, ?org = "lab_alpha", evidence works_at maria lab_alpha with SOURCE demo; no model authored the resolve, solve or cnl steps.

A user supposition stays hypothetical

"Suppose Carina is a parent of Ana. Who is Carina a parent of?"

@context stated
  relation "parent of"
  role subject "Carina"
  role object "Ana"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "parent of"
    role subject "Carina"
    role object ?who
    polarity affirmed
  end
  select ?who

The generated circuit lowers the supposition to @context fact … source assumption and adds assume $context to its solve. Observed result: status: supported with hypothetical: true, ?who = "ana", evidence SOURCE assumption, the rendered condition "You supposed: parent of (subject: Carina; object: Ana).", and the session still holds zero repository claims after the turn. Had the user asserted it (certainty asserted), the statement would be turn-local user evidence and the answer would not be hypothetical; it is still never recorded.

Both outputs were produced on 2026-09-28 by executing these programs with the runtime against tests/fixtures/bootstrap.sop at a fixed evaluation time.

KnowledgeLinker: strings to the predicates of the base memory

After the model, the KnowledgeLinker links each relation phrase to a predicate of the chosen base memory. A predicate whose id, alias or reviewed relation lexicon entry equals the phrase binds first ("be the capital of" to capital_of). The plain copula has no predicate of its own: "Ana is a doctor.", "Is Paris in France?" and "Who is Ana?" are read with the copula readings the memory itself declares (reading class|occupation|attribute|identity|location|describe on its predicate wires), tried in order against the knowledge; a question keeps every reading that fits as an any group and a statement takes the first. The packet lists them as copula_readings. A memory that declares no reading gets a precise question ("Do you mean what Ana does, or who Ana is related to?"), never "I do not know the relation be". Details: DS021, "KnowledgeLinker: the copula and the relation lexicon".

Knowledge wires and reasoning strategies

Knowledge written from a source (a manual, a regulation, an article) is a set of knowledge wires: predicate declarations with roles and types, fact, rule, default, integrity, aggregate, action, method, norm and procedure. They are written by a coding agent or the owner, never by the model, and checked before they are stored: node eval/smoke-reasoning/validator.mjs [--authoring] knowledge.sop query.sop runs the validator of sop/knowledge/, the single grammar source. A host stores the approved wires, selects a slice relevant to a question, and a strategy answers it; the model's question reaches the strategy only through the host linking, where the roles of a predicate place the model's strings in the predicate's positions.

What a question returns is a result packet: a status (supported, refuted, both, unknown, and for planning and conformance plan_found, blocked, compliant, non_compliant), complete, the rows with their own conditional assumptions, used (one sufficient set of claims with their versions), the route and a budget block. Two negations are never confused (not is explicit evidence, absent works only over a predicate declared closed); positive and negative evidence propagate independently, so a contradiction is reported as both and stays local; a default is blocked by an exception, a strict contrary or an overriding default that fires; counts and "every" over an open predicate are lower bounds or unknown; time is a snapshot (at, during throughout, overlaps, asof). A strategy that cannot express a question says not_expressible and never weakens it; a budget cut is budget_exhausted with a reason, never unknown or no_plan. Approved methods and norms (a "mode of work") bound what a plan may do, mode why_not names what blocks a step, and a change is negotiated as an amendment composed by the host and evaluated as a what-if. The manual is the section "Knowledge wires" of DS004, the strategy interface, budgets, shadow gate and routing rules are in DS006 "Strategies", and the comparison suite is in DS013. node eval/smoke-reasoning/run.mjs runs every strategy on the smoke cases.

Sessions, base memories and the coding agent

Every chat runs in a session: a working copy of a chosen base memory under the gitignored folder chat_data/ (DS031). The lifecycle: (1) the owner prepares base memories: POST /v1/memories creates or imports one of a chosen memory strategy, POST /v1/memories/{id}/knowledge adds circuits that pass the knowledge validator, recorded with the approving administrator, and POST /v1/memories/{id}/fork forks one (a copy-on-write clone, or a replay into another strategy). (2) A chat starts with POST /v1/sessions {base}: the base memory's repository is cloned by hard links and its circuits are copied into chat_data/sessions/<id>/. (3) Each message is answered over base plus session (session_id in the chat request); asserted statements stay turn-local. (4) Attached files go to the coding agent (omp, with the skill sop-wire-authoring) in a temporary folder under the session; the host validates the circuits it writes and the circuits come back as proposed drafts. A scope detector or a SymbolicLM failure only suggests sending a message there; the agent runs only when the user attaches files, answers yes to the note, or sets "Always use the coding agent" (POST /v1/route, POST /v1/author). (5) The user accepts or rejects each draft; an accepted draft enters the session layer only (.../drafts/{draft}/accept). (6) An administrator may commit the session to a new fork of its base memory (.../commit), validated again and recorded with provenance; the base memory the session started from does not change. (7) Temporary folders older than 24 hours and sessions idle for 14 days are removed. The endpoints, with executed examples, are in the API page sections 10 to 14.

Alternative routes and limits

A runtime configuration under config/ independently selects memory.engine (recall-memory for RecallMemory, holo-memory for HoloMemory, sqlite, scan or hybrid; see DS005 and the per-strategy specifications DS023–DS028) and policy.reasoningStrategy (reference, the js-reference oracle through the runtime bridge; a wire that names an external backend maps to that backend's strategy id or returns unsupported with the backend named and fallback: null; the former separate JavaScript reasoner was retired on 2026-10-01). The result records the actual route and fallback; a requested backend is never silently substituted, and a JavaScript result is never reported as a Prolog or Z3 measurement. Associative recall produces candidates subject to verification. The routing rules and the strategy × backend matrix are in DS006.

ChatSOP Documentation

ChatSOP lets a user submit a checked SOP execution circuit or ask a local agent to formalize a declarative problem. Host-approved operations turn that problem into an inspectable circuit querying authorized, time-aware knowledge; a selected reasoner produces a result with evidence and a CNL explanation. A model is a proposer, not the authority that records claims, publishes facts, or declares proofs.

Current plan and names

Since the owner decisions of 2026-09-30 the formalizer is SymbolicLM (Stanza grammatical analysis plus the UD-to-SOP rules), evaluated on clean English. LanguagesUtil identifies languages and spells symbolically; TranslatorService holds the translation backends; textToCleanEnglish is the chat step, validated by the user, that turns bad input into acceptable English by calling LanguageProofingLLM; SymbolicProofingLLM rewrites correct English into the limited English SymbolicLM understands, only for what rules cannot fix. The three datasets are bad_english, symbolic_english (the regression suite) and neuro_english. The priority is improving SymbolicLM by rules and repairs. There is no fine-tuning until the owner approves after reviewing the datasets in the audit page, and base models must run at 30 to 40 tokens per second on an ordinary laptop CPU. The small formalizer LLM of the model-language pages is earlier work; its results are in the archive and history reports.

The model in one example

The formalizer (the earlier small model, and SymbolicLM under the same boundary) sees only the user's message and writes quoted strings, one keyword per line; the host links the strings to its reviewed knowledge, reasons, and answers in English (Romanian on request). "Maria works at Acme. Who else works there?" becomes:

@s1 stated
  relation "work at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  certainty asserted

@q query
  select ?who
  where match
    relation "work at"
    role subject ?who
    role object "Acme"
    polarity affirmed
  end
  except ?who "Maria"

What the user said is stated; anything the model adds would be assumed; an unintelligible, empty or undecidably ambiguous message is unclear. The model never reasons and never refuses; a question the host cannot compute is answered "I understood the question as …; I cannot compute this kind of answer yet".

Reviewing the project

For a review before any training: read How the model writes and Question types, then inspect the corpora at /audit (the message is all the model sees), the sealed and out-of-distribution suites at /eval with its guide at /eval/guide, and the gates and journal at /experiments. Training is prohibited until the owner approves it explicitly. The task procedures are the skills listed in skills/README.md.

Where work belongs

Each repository directory has one responsibility, listed in DS002 §"Directory responsibilities"; coding, dependency and test conventions are in DS001. The local server (npm start) serves the chat, the corpus audit (/audit), the evaluation page (/eval) and the project journal page (/experiments, backed by status/journal.jsonl).

ChatSOP Documentation

ChatSOP has one goal: to beat small LLMs at reasoning through symbolic processing, and to help small LLMs reason symbolically. A user submits a checked SOP circuit, or asks in plain language and lets a formalization strategy write the circuit: CodingAgent (omp with GLM 5.3, then GPT-6 Luna; the default), LocalLLMDirect (a local GGUF model) or LocalLLMStepByStep (in progress). The validator checks it and sends problems back for bounded repair rounds, the KnowledgeLinker links its names to authorized, time-aware knowledge, only the slice of knowledge the question needs is retrieved, the StrategyRouter sends the problem to the oracle or an engine and verifies a routed answer against the oracle, and the result comes back with evidence and a deterministic English rendering. Run it with npm start (port 9999) and open /chat; the worked chat turn follows one real question end to end.

Current plan

Owner decisions of 2026-10-01 and 2026-10-02: the small-model research branch is frozen; the work focuses on reasoning; the circuit is written by one of three formalization strategies, chosen per session. The default, CodingAgent, runs omp with the model chain of queryParser.models; a symbolic vocabulary dialog widens the schema neighbourhood when a term is missing. There is no fallback parser and no silent substitution of a strategy, so without a model the answer is parse_unavailable. The validation procedure is the benchmark of symbolic reasoning against small LLMs (experiments/proposal/symbolic-vs-llm-benchmark.md). Progress is tracked in TODO.md and shown under /experiments; this page never asserts progress.

Reasoning benchmark procedure

tools/datasets/diversity/build-benchmark.mjs produces development cases with independent construction and oracle gold. tools/eval/symbolic-vs-llm/run.mjs compares direct English-evidence answers (A), explicit derivations (A'), small-model circuits (B), subscription-model circuits (C) and subscription answers (D). The completion baseline selects an existing OpenAI-compatible endpoint without changing the product's omp authoring default. Evidence is rendered from the gold-retrieved slice; a capped sample is explicitly partial and scored separately. A development pilot is sanity evidence only. Sealed execution requires a frozen preregistration and proceeds in paired 100/300/600 stages; contracts and reporting rules are in DS012, DS007 and DS015.

Constrained circuit-authoring experiments

The development benchmark accepts B-grammar and B-structured as explicit completion variants. The first specializes a finite SOP grammar to the request's retrieved predicate ids, declared roles and literal candidates; the second constrains closed JSON question choices and compiles them deterministically to SOP. Both receive only the request and vocabulary, never answers or memory facts, and pass the unchanged validator and symbolic execution path. Decoder constraints do not prove that the circuit means the question: wrong answers, binding refusals, unknowns and failures remain separate. These variants do not change the chat's omp default, author session definitions, or run on sealed inputs; their contract is in DS014. Use --arms B-grammar,B-structured --pilot 30 with an explicitly development-only manifest and an existing local model; the harness checks GPU availability and stops only its own private server.

Controlled format and protocol comparisons

Explicit development adapters in lib/query-author/structured/ablation.mjs compare closed JSON with canonical minimal SOP, closed predicate/entity/form lists with free strings, and single-step authoring with constrained form, predicate-set and argument choices. They hold admitted circuit semantics constant and retain the original compiler and validator; greater decoder freedom grants no extra authority. Numeric and unclear forms skip predicate selection. Report per-step tokens and latency, repair rounds, symbolic execution, prompt processing, generation and streamed time-to-first-token separately. Serial throughput projections include those actual steps and repairs, not hypothetical batching. These are experimental adapters, not product defaults or evidence of model superiority; contracts are in DS014 and DS012.

The circuit in one example

The author sees the user's message and the schema neighbourhood of the memory and writes only circuits. "Where does Maria work?" becomes a query whose names are strings; the KnowledgeLinker links "Maria" to an entity, the router chooses a strategy, and the answer is rendered from the result packet.

@q query
  where match
    relation "works at"
    role subject "Maria"
    role object ?org
    polarity affirmed
  end
  select ?org

What the user stated stays turn-local evidence; anything the author adds is marked assumed or written as a labelled session definition that the user accepts or rejects; an unintelligible, empty or undecidably ambiguous message is unclear. The author never answers and never states a fact; a question the system cannot compute is answered "I understood the question as ...; I cannot compute this kind of answer yet".

The knowledge language

What the system knows is written separately from the chat, from sources, as knowledge wires (predicate, fact, rule, default, integrity, aggregate, action, method, norm, procedure) by a coding agent or the owner, and validated by sop/knowledge/. Several reasoning strategies answer questions over the same wires and are compared on one smoke suite. The user manual is the section "Knowledge wires" of DS004, with one help page per wire; the task procedure for compiling a long text into wires is skills/sop-wire-authoring/SKILL.md.

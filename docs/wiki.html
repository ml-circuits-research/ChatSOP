ChatSOP Documentation

This is the canonical terminology page for the local execution and research contracts. Each entry names an observable responsibility and its boundaries.

SOP

SOP is the typed circuit language used for executable knowledge, questions, approved definitions, and results in the sop-agent-3 profile. A CLI user writes .sop files, or a formalizer proposes them; the parser checks the declarations before the runtime invokes memory and reasoning. A declaration @id creates a wire, $id consumes its value, ~id refers to a definition, and ?x is a local logical unknown. JSON config, internal ASTs and JSONL training rows do not become competing knowledge languages, and an SOP proposal does not grant publication authority.

Formalizer

The formalizer is the model role that converts a user question and supplied assertions into a candidate SOP circuit using allowed symbols. The local agent sends it a prompt via a configured inference endpoint; the host then checks what it proposed and executes an admissible circuit. This role does not ingest a document as a trusted policy, choose identity, install a rule, or prove that an answer is correct. Source training scripts and configurations are not evidence that a trained formalizer or its language quality is available.

Agent

The local conversational agent coordinates a turn from the CLI chat command: prompt and candidate SOP, validation and guards, symbolic runtime, CNL result, and optional rewriting. It uses host-selected user/session state and configured endpoint settings. The user can inspect the previous SOP, CNL and proof packet with chat controls; uncommitted session changes remain subject to explicit commit or discard. The agent is not a publicly exposed ChatSOP API server, and its language model cannot certify privileged effects.

CNL

Controlled natural language is a deterministic rendering of the checked runtime result, status and available supporting information. It gives CLI users a readable answer without asking a second model to decide truth. The optional verbalizer can restate this message but cannot change a logical status, time, number, incompleteness marker, or evidence. A readable CNL string does not turn missing premises into an explicit negative proof.

Verbalizer

The verbalizer is an optional separate model role that rewrites an already evaluated CNL answer for readability. A local agent uses it only after the symbolic path has fixed the result; deterministic CNL remains the baseline if rewriting is not selected. A verbalizer must preserve negation, time, quantities, hypotheses, evidence and unknown or incomplete outcomes. Its fluent text cannot repair a wrongly formalized question or establish an unsupported inference.

Linker

The linker finds applicable approved definitions for a query, unifies its goal with their conclusions and retrieves relevant premises through the selected memory strategy. It sends explicit typed inputs to the reasoner and participates in exposing the route and retrieval completeness. The operator depends on this step to connect a fact or rule to a requested answer; neither SWI-Prolog nor Z3 autonomously discovers missing rules in associative banks. Linking two unrelated queries solely because each has ?x is invalid.

Repository

The repository manages reviewed base knowledge, per-user and per-session changes, forks, snapshots, and durable temporal provenance. The host uses it for init, commit, discard, maintenance and garbage collection. A claim has both a validity interval and a separate known-at time; retractions and corrections must remain interpretable across history. Referenced snapshots protect older data from collection, while private changes cannot be silently treated as other users' approved facts.

Memory engine

The memory engine is the physical bank selected by memory.engine for retaining or retrieving SOP premises. Available engine families include exact SQLite and scan, associative Weaver and Holo, and a hybrid of SQL exact premises with associative hints. The host chooses an engine independently of its reasoning strategy. Association yields candidates with retrieval limits; a missed premise or score does not certify negation, probability, or a unique answer, and different banks do not automatically share binary snapshots.

Reasoning strategy

A reasoning strategy selects how a typed linked problem is solved under policy.reasoningStrategy. The reference route uses bounded JavaScript methods; the advanced route can call optional SWI-Prolog for supported Horn work and Z3 for supported numeric problems, with explicit JavaScript fallback and route reporting. The host may choose a strategy without changing memory.engine or the SOP program. A fallback is not evidence that an external solver ran; unsupported dialects and incomplete search cannot be reported as full proofs.

GC

Garbage collection identifies snapshot or shard objects no longer referenced by approved bases, users, sessions or forks. An operator uses gc in dry-run form to inspect candidates and --apply to remove only proven-unreachable objects. A still-open historical session or fork can legitimately reference an older snapshot; collection must not discard it merely because a newer generation exists. Bounded working memory does not imply that all on-disk historical metadata disappears.

Semantic case

A semantic case groups one intended question/assertion meaning, its reviewed SOP target, source provenance, and linguistic variants under a stable identifier such as semantic_case_id. Corpus builders use it to assign all equivalent English or Romanian formulations, paraphrases, and associated contrast cases to consistent partitions. Executing its gold SOP tests that program against selected worlds, not a model's ability to understand unseen text. Similar meanings can still leak across IDs unless duplicates and linked contrasts are checked.

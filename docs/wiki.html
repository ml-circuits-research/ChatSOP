Overview / Concepts and execution flow

What the ChatSOP components do

ChatSOP separates understanding a question from answering it. A language model proposes a structured problem in SOP. Ordinary program code checks that proposal, retrieves permitted knowledge, and runs a solver. Another code step turns the result into text. An optional language model can then improve the wording. The model's fluent answer is not used as the proof.

Follow one question through the system

Suppose the user asks: “In which country does Maria work?” The permitted knowledge contains two facts—Maria works at Acme, and Acme is located in France—and an approved rule connecting those relations. The identifiers and relation names below are illustrative; the host must actually supply them before a model can use them.

  1. The conversational agent prepares the request. It reads the user's text, selects the permitted session, and supplies relevant entity names, relation names, and recent context to the formalizer. The host, not the model, chooses whose knowledge is visible.
  2. The formalizer returns SOP, not “France.” It represents the question as a relation such as works_in_country maria ?country and requests ?country. The intended small model performs this translation. If “Maria” cannot be identified safely, the turn needs resolution or clarification instead of a guessed identifier.
  3. The agent and runtime validate the proposal. They check allowed symbols, field syntax, references, variable types, and permitted operations. An invalid or unauthorized circuit is not made safe by a confident model response.
  4. The runtime executes the solve operation. For a knowledge query, it invokes the linker. The linker finds the approved rule whose conclusion answers the requested relation and asks the retrieval layer for the required premises.
  5. Retrieval reads the permitted repository view. It returns Maria's employment fact and Acme's location fact, with source/time information and completeness indicators. Retrieval chooses candidates; it does not itself prove the answer.
  6. The reasoner applies the rule and matches the query. It produces an answer assigning France to ?country, references to the supporting evidence, a status, and a completeness flag. With missing premises it must not invent France; with conflicting premises it must expose the conflict.
  7. The CNL renderer turns that result into text. It reports what follows from the admitted knowledge, including uncertainty or limits. The optional verbalizer may make the wording more natural without changing the result.
  8. The agent returns the answer and inspection data. The local interface can expose the generated SOP, evidence, and execution trace, rather than only a final sentence.

The numeric route is shorter. A constraint such as finding integers whose sum is five goes from validated variables and conditions to the numeric solver; it does not need to retrieve employment facts or domain rules. A model premise supplies conditional context without recording it. In a trusted full circuit, fact constructs a sourced value without storing it, and solve.data can use explicit local premises temporarily without recording them.

Two current authoring layers: the model may author only premise, query, or constraint. A premise is an interpreted assumption, not a sourced assertion: holds is required, valid is optional and defaults to timeless, and it has no source, quotation, or write field. The host keeps the original user input and its model-interpretation origin distinct from repository facts; no model premise is automatically remembered. Approved host operations build an inspectable execution circuit for identity lookup, reasoning, rendering and, when needed, clarification. A trusted tool may separately use remember to record an authorized sourced fact/event in the selected session. That recording neither proves truth nor publishes globally; session commit is a separate host action.

A compiled premise stays a premise value: the host passes it to solve.assume and labels conclusions depending on it hypothetical. Even when a host-generated pack groups such values, they do not become sourced facts; remember refuses a premise. Returned contextPremises carries the host-attached original input text and model-interpretation origin separately from the model-authored holds/valid fields.

@context premise
  holds works_at maria acme
@question query
  mode exists
  where works_at maria acme

The model states the condition and the question here, not how to store or solve them. The host may answer hypothetically under @context; inspecting the resulting execution circuit shows the generated assumption, solve, and rendering operations. This example does not authorize or perform a repository write.

SOP: the language passed between translation and execution

SOP is a text language for stating conditional premises, sourced facts, questions, numeric constraints, and operations over them. It is not the language model and it is not the solver. A model can author only declarative premises and problems; the host compiles an inspectable execution circuit and generates clarification requests when required. A person or coding agent can write trusted full circuits; the runtime checks and executes them. JSON may transport SOP or represent parsed objects, but does not replace the authored SOP language.

A header @question query declares a named, typed wire. A wire is a named piece of the circuit, not a separate operating-system process. $question consumes its produced value; ~definition refers to an approved definition; ?country is a logical unknown within a problem. Relations use [not ]predicate term1 term2 ... with one to four whitespace-separated terms, for example where works_at maria ?organization. Parentheses and comma separators are not SOP atom syntax; JSON double-quoted terms preserve embedded spaces, punctuation, and escapes. all, any, and end preserve the grouping of conditions. See wire help for executable examples and the field contract of each type.

pack groups values for trusted program or host plumbing; resolve performs actual identity lookup, which the host may instead do before giving the model canonical IDs. Neither is model-authored. The host generates a clarify wire when identity is unresolved/ambiguous or a required downstream scalar is missing/nonunique; it suspends dependent work pending a user response. Lack of evidence for an otherwise valid query does not automatically request clarification. A model-authored clarify wire is rejected.

Model constraint declarations express integer variables and domains, comparisons, a requested claim or optimization objective, and supported selected results. The host chooses the solver. In the trusted reference language, template and procedure currently use the same approved parameterized-circuit mechanism; policy sets host execution limits. theory carries a foreign-dialect body, but required theories have no registered compiler today and cannot run. None of these reference types becomes a required small-model lesson merely because its field grammar is documented.

One match can be represented by a structure of related variable assignments; several matches can be represented by an array of such structures. For example, [{person: "maria", country: "france"}, {person: "ana", country: "romania"}] preserves two person/country pairs. This is the intuition, not a universal wire return format. A question declares what to find; solving and an explicit output mode determine what is exported. Current rows outputs remain arrays even with one row, whereas one requests a unique scalar. Engines must document supported result forms, limits, and completeness; they must not silently change what the declared condition means.

Formalizer: translating the input into a problem

This is a role, not a particular model or model size. The formalizer receives natural-language input plus a host-supplied list of usable symbols and context. It returns only premise, query, or constraint declarations preserving who did what, negation, time, alternatives, unknowns, and requested results. premise denotes conditional interpretation, not a sourced fact or an instruction to store it. For “Who works at Acme?” the model should describe the employment query, not guess an employee's name or write an ungrounded clarification. If the identity is ambiguous, the host creates the user question.

The intended conversational implementation is the small model discussed in the authoring profile. A coding agent can perform the same role while converting supplied document content into SOP. When that agent implements an algorithm or a reusable procedure, it is doing a separate coding task. Neither role grants permission to publish knowledge, install definitions, or execute arbitrary code: the host controls those actions.

The current local agent invokes a configured inference endpoint for formalization, then checks the returned SOP. Training scripts and configurations are not proof that a trained small model exists or translates reliably; that requires evaluation of actual model outputs. The small model formulates the problem; the reasoner solves it.

Agent and host: who coordinates and authorizes the turn?

Here, the conversational agent is the application code that calls the model, validates its declarative proposal, builds and checks an inspectable execution circuit through host-approved metaprograms, invokes the runtime, and returns the answer. It is not synonymous with the model. The CLI's chat command uses this coordinator. Its inputs include the user text, session, configured model endpoints, and policy; its output includes the answer, generated SOP, result packet, and execution trace. The model-authored problem and host-expanded execution circuit have different authorship and authority.

Host means the application or operator-controlled environment that supplies identity, permissions, knowledge, schemas, and execution limits. The host chooses the user's session; approved metaprograms arrange resolve, pack, solve, cnl, or a grounded clarify as needed, rather than ask the small model to emit them. Explicit remember remains a trusted tool operation for authorized sourced facts/events, not an automatic consequence of conditional model premises. The host must not guess an intended identity or promote hypotheses, quotations, or inferences to stored claims. The model cannot grant itself global publication rights by writing a field in SOP.

A coding agent is a development assistant that can edit code or propose knowledge and procedures. It is a different use of “agent” from the local turn coordinator. Its permitted work may be broader than the small conversational model's, but its changes still need the applicable review and authorization. The same underlying language model can serve different roles without those roles becoming interchangeable.

Runtime: executing the circuit in dependency order

The runtime is ordinary interpreter code. The conversational agent or a direct program caller gives it SOP, a clock, schemas, repository/session access, and policy. It parses declarations, checks references and types, waits for required wire values, and runs the corresponding operations. For example, a solve using $question must wait until that query value exists; a consumer of an exported answer must wait until the answer is justified.

It calls the linker and reasoner for knowledge questions, the numeric solver for constraints, the repository for authorized writes, and the CNL renderer for explicit rendering operations. It returns values, execution traces, and the states of requested outputs. A blocked or ambiguous value is not silently replaced by the first available candidate.

The current implementation is in sop/runtime.mjs, with parsing in sop/parser.mjs and typed problem construction in sop/lower.mjs. Approved template/procedure expansion and system-side restricted expression evaluation are distinct capabilities; their existence does not require the small model to generate code.

Linker: finding facts and rules worth solving with

The runtime calls the linker with a query, approved definitions, and access to the permitted memory view. The linker works backward from the requested relation: which rule concludes it, and what premises would that rule need? In the Maria example, it selects the rule connecting employment and organization location, then requests those two kinds of facts.

Its output contains selected facts and rules, the original question, and retrieval diagnostics. It does not answer the question merely by selecting candidates. It must not invent a rule because two relation names sound similar, nor join unrelated queries merely because both use ?x.

The current linker uses rule-head matching, backward goal expansion, and bounded retrieval through a strategy registry. Those are program algorithms, not a separate language-model call. Choosing exact or associative retrieval changes how premises are found, not the intended meaning of the query. Prolog and Z3 do not independently search the repository for missing domain knowledge.

Repository: persistent knowledge, ownership, and history

The repository stores reviewed facts and rules, private user knowledge, session changes, and their history. For example, a user can submit the claim “Maria works at Acme” for recording through remember in a private session, query it there, and later commit or discard that change. Other users must not silently inherit the private claim. Recording does not prove the claim true.

The runtime or host calls repository operations to admit a sourced claim, record a correction, open a knowledge view, commit a session, or discard its changes. The repository returns claim identifiers, receipts, and authorized views. The linker and retrieval layer read those views when assembling a problem.

It distinguishes valid time—when Maria is said to work there—from knowledge time—when the system learned or corrected that claim. A historical question may need either or both. Snapshots and forks preserve earlier or separate views. The repository manages this history and ownership; the memory engine beneath it handles a particular storage/search representation. Neither component proves that an asserted claim is true in the world.

Memory engine: how stored facts are searched

The memory engine is the implementation used to retain and retrieve premises. The retrieval layer asks for a pattern such as works_at maria ?organization within an authorized time/session view. It gets candidate facts plus information about probes, limits, and completeness. The reasoner, not the memory score, decides what follows from the retrieved premises.

memory.engine selects the storage family. The retrieval strategy is a separate choice about how to search the available view: current strategies include exact lookup, engine-specific routes, automatic selection, and hybrid retrieval. Not every strategy can read every engine's stored representation; incompatible choices require a matching repository or explicit migration, not merely renaming a setting. Changing memory engines does not automatically change the reasoning algorithm.

Reasoner, backend, and strategy: how the problem is solved

The reasoner receives a typed problem and its admitted inputs from the runtime. For a relational query, those inputs are facts and approved rules. For a numeric problem, they are variable domains, requirements, a claim, and possibly an objective. It returns a status, answers or assignments, evidence where supported, and whether the computation was complete.

A backend is a concrete implementation that performs the calculation. A reasoning strategy selects the route and applies the host's limits. These are not names for additional language models.

RouteWhat executesWhen it is appropriate
Reference strategyBounded JavaScript algorithms for rule inference, temporal matching, finite integer search, and other supported operations.A local reference route with explicit budgets; numeric enumeration needs finite domains.
Advanced relational routeOptional SWI-Prolog for the supported rule profile, with JavaScript derivation/result checking.Supported point-in-time Horn queries; interval work uses the JavaScript route.
Advanced numeric routeOptional Z3 for supported integer constraints and optimization.Numeric problems within the portable arithmetic profile; supported output projections differ from finite enumeration.
Other supported reasoning operationsShared JavaScript search controllers, such as bounded hypothesis search or planning.An operation explicitly requesting that kind of reasoning, not an automatic license to guess missing facts.

The advanced strategy can report an explicit JavaScript fallback when an external solver is unavailable or unsuitable. A fallback does not mean Prolog or Z3 ran. Unsupported operations, exhausted budgets, and incomplete retrieval must remain visible. A satisfiable numeric assignment means “possible under these requirements,” not “necessarily true.” Missing relational support is not explicit negation, and contradictory facts must not make every conclusion provable.

Engines must document their supported semantics and result contracts: which variables are returned, scalar versus row projections, duplicate handling, ordering, limits, completeness, and ambiguity. Different implementations should preserve the meaning of the shared declared problem. They may reject unsupported features, but must not silently reinterpret them. See variable/result intuition for the structure-versus-array distinction.

CNL: turning the result into readable text

CNL means controlled natural language. Here it is a deterministic code step: it receives a computed result packet and renders its status, answers, time, and available supporting information. It does not call a model to decide the answer. If no admitted premise establishes the answer, its text must report that lack of support rather than turn it into “false.”

In a trusted full circuit, cnl explicitly consumes a real operation result. The runtime rejects a literal imitation of a result packet. For model-origin declarative input, the host constructs and checks that rendering operation rather than asking the model to author it.

Why keep rendering in the host? CNL reports computed status and evidence, not a new proposition in the user's question. The small model specifies the conditional problem; approved host code determines and renders its result without asking it to repeat boilerplate execution wires.

CNL is not entity resolution. resolve looks up which approved entity a name denotes. If “Maria” names several people, an identity-dependent query needs disambiguation. Adding a renderer cannot repair that missing identity.

Verbalizer: optionally improving the wording

The verbalizer is a language-model role at the end of the turn. The conversational agent calls its configured endpoint only when rewriting is enabled. It receives the checked CNL answer and associated result information, and returns a more natural formulation. Without it, the agent returns the deterministic CNL text.

For example, it can turn a terse supported-employment result into “According to the available records, Maria works at Acme.” It must not change the employer, drop the qualification, invent a date, or turn an unknown answer into a negative one. This is a fidelity requirement, not a new proof supplied by the rewriting model. The formalizer translates input language into a problem; the verbalizer rewrites an already computed answer into prose.

Semantic case: one meaning used to evaluate translation

A semantic case is evaluation data, not a running component. It groups an intended input meaning, a reviewed SOP target, source information, linguistic variants, and expectations in specified test situations under a stable identifier such as semantic_case_id. “Who works at Acme?” and “Which people are employed by Acme?” may be two phrasings of one case. “Who does not work at Acme?” is a different meaning, not an equivalent paraphrase.

Corpus-building code uses these cases to produce training and evaluation records and to keep equivalent phrasings together when splitting training, development, and test data. Otherwise a model could see one phrasing during training and be credited for “unseen” understanding on its near-duplicate. Related contrast cases and duplicate meanings also require leakage checks.

Two measurements must remain separate. Running the reviewed target SOP against test knowledge checks the program and system behavior. Running the model on the natural-language variants and judging its generated SOP checks translation. Passing the first does not establish the second. Case files, JSONL rows, and reports are different representations of this evaluation material, not additional query languages.

GC: deleting storage that no live view needs

Garbage collection is repository maintenance code. As sessions, corrections, snapshots, and forks accumulate, some stored objects become unreferenced. GC starts from the approved bases and existing user/session/fork views, determines which snapshot or shard objects remain reachable, and identifies the rest as removal candidates.

The operator can inspect a dry run before using gc --apply. For example, an old snapshot must stay if a historical session still references it, even when a newer snapshot exists. GC does not decide that a fact is false and does not remove a private session merely because it is old. Its purpose is reclaiming proven-unused storage without breaking a view someone can still open.

Overview / Concepts and execution flow

What the ChatSOP components do

ChatSOP separates understanding a question from answering it. A language model proposes a structured problem in SOP. Ordinary program code checks that proposal, retrieves permitted knowledge, and runs a solver. Another code step turns the result into text. An optional language model can then improve the wording. The model's fluent answer is not used as the proof.

Follow one question through the system

Suppose the user asks: “In which country does Maria work?” The permitted knowledge contains two facts—Maria works at Acme, and Acme is located in France—and an approved rule connecting those relations. The identifiers and relation names below are illustrative; the host must actually supply them before a model can use them.

  1. The conversational agent prepares the request. It reads the user's text and selects the permitted session. The formalizer receives the user's message and nothing else: no entity or relation names, identifiers, knowledge, earlier turns or clock. The host, not the model, chooses whose knowledge is visible and links the model's strings to it afterwards.
  2. The formalizer returns SOP, not “France.” It writes the question as strings: a match block with relation "work in", role subject "Maria" and role location ?country, and requests ?country. The intended small model performs this translation. The host then links "work in" to its predicate (for example works_in_country) and “Maria” to a known person; if either cannot be linked safely, the host asks the user instead of guessing an identifier.
  3. The agent and runtime validate the proposal. They check allowed symbols, field syntax, references, variable types, and permitted operations. An invalid or unauthorized circuit is not made safe by a confident model response.
  4. The runtime executes the solve operation. For a knowledge query, it invokes the linker. The linker finds the approved rule whose conclusion answers the requested relation and asks the retrieval layer for the required facts.
  5. Retrieval reads the permitted repository view. It returns Maria's employment fact and Acme's location fact, with source/time information and completeness indicators. Retrieval chooses candidates; it does not itself prove the answer.
  6. The reasoner applies the rule and matches the query. It produces an answer assigning France to ?country, references to the supporting evidence, a status, and a completeness flag. With missing facts it must not invent France; with conflicting facts it must expose the conflict.
  7. The CNL renderer turns that result into text. It reports what follows from the admitted knowledge, including uncertainty or limits. The optional verbalizer may make the wording more natural without changing the result.
  8. The agent returns the answer and inspection data. The local interface can expose the generated SOP, evidence, and execution trace, rather than only a final sentence.

The numeric route is shorter. A constraint such as finding integers whose sum is five goes from validated variables and conditions to the numeric solver; it does not need to retrieve employment facts or domain rules. A model stated supplies turn-local evidence or a supposition without recording it. In a trusted full circuit, fact constructs a sourced value without storing it, and solve.data can use explicit local facts temporarily without recording them.

Two current authoring layers: the model may author only stated, assumed, unclear, query, constraint or unparsed, written as context-free strings, one finite clause per wire: a quoted relation phrase (the lemma of the message's words, in the message's language or English), roles from a closed inventory with names as written in the message and other values normalized, ?variables in questions, temporal expressions as stated, link keyword lines (because $s2, if $s1, …) between clauses, and unparsed spans for what it could not formalize. The host translates content words with its dictionary. A stated proposition is what the message puts forward (with the user's certainty); an assumed one is what the model added. Neither has a source, quotation, or write field, and neither is automatically remembered; the host links the strings to its lexicon and asks when something is unknown or ambiguous. Approved host operations build an inspectable execution circuit for identity lookup, reasoning, rendering and, when needed, clarification. A trusted tool may separately use remember to record an authorized sourced fact/event in the selected session. That recording neither proves truth nor publishes globally; session commit is a separate host action.

An asserted statement is compiled to a turn-local fact … source user used as evidence for this turn only, and carried in caller-owned conversation context; a supposition, hedge or reported claim is supplied to solve.assume and conclusions depending on it are hypothetical; a model assumption is only reported unless host policy branches it into a separate hypothetical solve. None of them is stored or reinforced.

@context stated
  relation "works at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  certainty supposed
@question query
  mode exists
  where match
    relation "works at"
    role subject "Maria"
    role object "Acme"
    polarity affirmed
  end

The model states the condition and the question here, not how to store or solve them. The host may answer hypothetically under @context; inspecting the resulting execution circuit shows the generated assumption, solve, and rendering operations. This example does not authorize or perform a repository write.

SOP: the language passed between translation and execution

Name. SOP comes from Standard Operating Procedure. The language is properly called SOP Lang (shortened to SOP throughout this documentation): an attempt to formalize standard operating procedures, and the facts, questions and constraints they depend on, as inspectable, executable text rather than prose.

SOP is a text language for stating user statements and assumptions, sourced facts, questions, numeric constraints, and operations over them. It is not the language model and it is not the solver. A model can author only declarative statements, assumptions, questions and constraints, as strings; the host links them, compiles an inspectable execution circuit and generates clarification requests when required. A person or coding agent can write trusted full circuits; the runtime checks and executes them. JSON may transport SOP or represent parsed objects, but does not replace the authored SOP language.

A header @question query declares a named, typed wire. A wire is a named piece of the circuit, not a separate operating-system process. $question consumes its produced value; ~definition refers to an approved definition; ?country is a logical unknown within a problem. Relations use [not ]predicate term1 term2 ... with one to four whitespace-separated terms in host circuits and on the model surface (the knowledge language below allows zero to six), for example where works_at maria ?organization. Parentheses and comma separators are not SOP atom syntax; JSON double-quoted terms preserve embedded spaces, punctuation, and escapes. all, any, and end preserve the grouping of conditions. See wire help for executable examples and the field contract of each type.

pack groups values for trusted program or host plumbing; resolve performs actual identity lookup; the host generates it for the strings a model wrote (the model never sees identifiers). Neither is model-authored. The host generates a clarify wire when a relation, identity or date cannot be linked uniquely or a required downstream scalar is missing/nonunique; it suspends dependent work pending a user response. Lack of evidence for an otherwise valid query does not automatically request clarification. A model-authored clarify wire is rejected.

Model constraint declarations express integer variables and domains, comparisons, a requested claim or optimization objective, and supported selected results. The host chooses the solver. In the trusted reference language, template and procedure currently use the same approved parameterized-circuit mechanism; policy sets host execution limits. theory carries a foreign-dialect body, but required theories have no registered compiler today and cannot run. None of these reference types becomes a required small-model lesson merely because its field grammar is documented.

Knowledge wires. Besides the host circuits and the model surface, SOP has an authoring surface: the knowledge wires (predicate, fact, rule, default, integrity, aggregate, action, method, norm, procedure, argument, trace, and the host-composed amendment) that a coding agent or the owner writes from a source text and the host stores as reviewed knowledge. Their grammar, parser, validator, governance and desugarer are one module, sop/knowledge/, and the manual is the section "Knowledge wires" of DS004. The two surfaces meet only through the roles of a predicate declaration and the host linking: the model writes strings, the knowledge is written in symbols, and the model never sees an identifier. SOP Lang is still being discovered, so it has no version numbers; every change is documented in the specifications and the wire help in the same step.

One match can be represented by a structure of related variable assignments; several matches can be represented by an array of such structures. For example, [{person: "maria", country: "france"}, {person: "ana", country: "romania"}] preserves two person/country pairs. This is the intuition, not a universal wire return format. A question declares what to find; solving and an explicit output mode determine what is exported. Current rows outputs remain arrays even with one row, whereas one requests a unique scalar. Engines must document supported result forms, limits, and completeness; they must not silently change what the declared condition means.

Formalizer: translating the input into a problem

This is a role, not a particular model or model size. The formalizer receives the user's message only — no symbols, identifiers, knowledge, earlier turns or clock. It returns only stated, assumed, unclear, query, or constraint declarations, as strings, preserving who said what, what the model added, negation, time, alternatives, unknowns, and requested results; it never refuses. A statement is not a sourced fact or an instruction to store it. For “Who works at Acme?” the model should describe the employment query, not guess an employee's name or write an ungrounded clarification. If the identity is ambiguous, the host creates the user question.

Since the owner decision of 2026-09-30 the conversational implementation is SymbolicLM (Stanza grammatical analysis plus rules), evaluated on clean English; FormalizerLLM, the small fine-tuned LLM that wrote SOP Lang directly from the message, is archived and removed from the product (owner decision 2026-10-01): its results are in the archive and history reports, and the chat and the API offer SymbolicLM as the only formalizer. A coding agent can perform the same role while converting supplied document content into SOP. When that agent implements an algorithm or a reusable procedure, it is doing a separate coding task. Neither role grants permission to publish knowledge, install definitions, or execute arbitrary code: the host controls those actions.

The current local agent invokes the formalizer (SymbolicLM) and then checks the returned SOP. Training scripts and configurations are not proof that a trained model exists or works reliably; that requires evaluation of actual model outputs. The formalizer formulates the problem; the reasoner solves it.

Agent and host: who coordinates and authorizes the turn?

Here, the conversational agent is the application code that calls the model, validates its declarative proposal, builds and checks an inspectable execution circuit through host-approved metaprograms, invokes the runtime, and returns the answer. It is not synonymous with the model. The CLI's chat command uses this coordinator. Its inputs include the user text, session, configured model endpoints, and policy; its output includes the answer, generated SOP, result packet, and execution trace. The model-authored problem and host-expanded execution circuit have different authorship and authority.

Host means the application or operator-controlled environment that supplies identity, permissions, knowledge, schemas, and execution limits. The host chooses the user's session; approved metaprograms arrange resolve, pack, solve, cnl, or a grounded clarify as needed, rather than ask the small model to emit them. Explicit remember remains a trusted tool operation for authorized sourced facts/events, not an automatic consequence of model statements or assumptions. The host must not guess an intended identity or promote hypotheses, quotations, or inferences to stored claims. The model cannot grant itself global publication rights by writing a field in SOP.

A coding agent is a development assistant that can edit code or propose knowledge and procedures. It is a different use of “agent” from the local turn coordinator. Its permitted work may be broader than the small conversational model's, but its changes still need the applicable review and authorization. The same underlying language model can serve different roles without those roles becoming interchangeable.

Runtime: executing the circuit in dependency order

The runtime is ordinary interpreter code. The conversational agent or a direct program caller gives it SOP, a clock, schemas, repository/session access, and policy. It parses declarations, checks references and types, waits for required wire values, and runs the corresponding operations. For example, a solve using $question must wait until that query value exists; a consumer of an exported answer must wait until the answer is justified.

It calls the linker and reasoner for knowledge questions, the numeric solver for constraints, the repository for authorized writes, and the CNL renderer for explicit rendering operations. It returns values, execution traces, and the states of requested outputs. A blocked or ambiguous value is not silently replaced by the first available candidate.

The current implementation is in sop/runtime.mjs, with parsing in sop/parser.mjs and typed problem construction in sop/lower.mjs. Approved template/procedure expansion and system-side restricted expression evaluation are distinct capabilities; their existence does not require the small model to generate code.

Linker: finding facts and rules worth solving with

The runtime calls the linker with a query, approved definitions, and access to the permitted memory view. The linker works backward from the requested relation: which rule concludes it, and what facts would that rule need? In the Maria example, it selects the rule connecting employment and organization location, then requests those two kinds of facts.

Its output contains selected facts and rules, the original question, and retrieval diagnostics. It does not answer the question merely by selecting candidates. It must not invent a rule because two relation names sound similar, nor join unrelated queries merely because both use ?x.

The current linker uses rule-head matching, backward goal expansion, and bounded retrieval through a strategy registry. Those are program algorithms, not a separate language-model call. Choosing exact or associative retrieval changes how facts are found, not the intended meaning of the query. Prolog and Z3 do not independently search the repository for missing domain knowledge.

Base memory: a named, forkable knowledge store

A base memory is a named store of reviewed knowledge of one memory strategy (RecallMemory, HoloMemory, SQLite, scan or hybrid) with the validated circuits it was built from and a provenance log. It lives under chat_data/base_memories/<id>/. A fork copies it (copy-on-write when the strategy is the same, a replay of the circuits when it changes). Adding knowledge to a base memory is an administrator approval recorded with its approver; nothing enters it implicitly. See DS031.

Session: a chat's own copy of a base memory

A session is created from a base memory, clones it into its own folder and holds what the conversation adds: the circuits the user accepted, the drafts waiting for a decision, the transcript and the temporary request folders. Asserted statements stay turn-local. A session can be committed to a fork of its base memory by an administrator; the base memory it started from never changes. Abandoned sessions are removed by the cleanup policy. See DS031.

Coding agent (omp): writer of SOP circuits

The coding agent is the omp CLI run non-interactively on a temporary folder with the skill sop-wire-authoring. It writes knowledge circuits from attached files or instructions; the host validates them and repairs them for a bounded number of rounds, and they come back as proposed drafts that the user accepts or rejects. It never starts by itself: the user attaches files, answers yes to a scope note or sets "Always use the coding agent". See DS031 and the skill omp-run.

Repository: persistent knowledge, ownership, and history

The repository stores reviewed facts and rules, private user knowledge, session changes, and their history. For example, a user can submit the claim “Maria works at Acme” for recording through remember in a private session, query it there, and later commit or discard that change. Other users must not silently inherit the private claim. Recording does not prove the claim true.

The runtime or host calls repository operations to admit a sourced claim, record a correction, open a knowledge view, commit a session, or discard its changes. The repository returns claim identifiers, receipts, and authorized views. The linker and retrieval layer read those views when assembling a problem.

It distinguishes valid time—when Maria is said to work there—from knowledge time—when the system learned or corrected that claim. A historical question may need either or both. Snapshots and forks preserve earlier or separate views. The repository manages this history and ownership; the memory engine beneath it handles a particular storage/search representation. Neither component proves that an asserted claim is true in the world.

Memory engine: how stored facts are searched

The memory engine is the implementation used to retain and retrieve facts. The retrieval layer asks for a pattern such as works_at maria ?organization within an authorized time/session view. It gets candidate facts plus information about probes, limits, and completeness. The reasoner, not the memory score, decides what follows from the retrieved facts.

Changing memory engines does not automatically change the reasoning algorithm.

Reasoner, backend, and strategy: how the problem is solved

The reasoner receives a typed problem and its admitted inputs from the runtime. For a relational query, those inputs are facts and approved rules. For a numeric problem, they are variable domains, requirements, a claim, and possibly an objective. It returns a status, answers or assignments, evidence where supported, and whether the computation was complete.

A backend is a concrete implementation that performs the calculation. A reasoning strategy selects the route and applies the host's limits. These are not names for additional language models.

Beside these routes, the knowledge wires of DS004 are answered by strategies (reasoning/strategies/<id>/): each reads the same parsed, governed and desugared program and lowers it to its own engine (a nested-loop evaluator, tabled Prolog, SMT, Datalog, SQL, ASP, a planner). A strategy declares its capabilities, and a question that needs a feature it lacks is not_expressible, never silently weakened. The simple, auditable js-reference strategy is the oracle: another strategy is accepted by agreeing with it on the cases it declares (the shadow gate). Every result carries its status, complete, used (one sufficient support set), per-row conditional and a budget block; a budget cut is budget_exhausted with a reason, never unknown or no_plan. See DS006 "Strategies".

The advanced strategy is deprecated (its results say so in route.deprecated) and can report an explicit JavaScript fallback when an external solver is unavailable or unsuitable. A fallback does not mean Prolog or Z3 ran. Unsupported operations, exhausted budgets, and incomplete retrieval must remain visible. A satisfiable numeric assignment means “possible under these requirements,” not “necessarily true.” Missing relational support is not explicit negation, and contradictory facts must not make every conclusion provable.

Engines must document their supported semantics and result contracts: which variables are returned, scalar versus row projections, duplicate handling, ordering, limits, completeness, and ambiguity. Different implementations should preserve the meaning of the shared declared problem. They may reject unsupported features, but must not silently reinterpret them. See variable/result intuition for the structure-versus-array distinction.

CNL: turning the result into readable text

CNL means controlled natural language. Here it is a deterministic code step: it receives a computed result packet and renders its status, answers, time, and available supporting information. It does not call a model to decide the answer. If no admitted fact establishes the answer, its text must report that lack of support rather than turn it into “false.”

In a trusted full circuit, cnl explicitly consumes a real operation result. The runtime rejects a literal imitation of a result packet. For model-origin declarative input, the host constructs and checks that rendering operation rather than asking the model to author it.

Why keep rendering in the host? CNL reports computed status and evidence, not a new proposition in the user's question. The small model specifies the conditional problem; approved host code determines and renders its result without asking it to repeat boilerplate execution wires.

CNL is not entity resolution. resolve looks up which approved entity a name denotes. If “Maria” names several people, an identity-dependent query needs disambiguation. Adding a renderer cannot repair that missing identity.

Verbalizer: optionally improving the wording (not in the product)

The verbalizer is a language-model role at the end of a turn that no product path calls: no verbalizer model exists, the chat and the CLI return the deterministic CNL text, and the LLM verbalizer code is removed. As a design, it would receive the checked CNL answer and associated result information, and return a more natural formulation. Without it, the agent returns the deterministic CNL text.

For example, it can turn a terse supported-employment result into “According to the available records, Maria works at Acme.” It must not change the employer, drop the qualification, invent a date, or turn an unknown answer into a negative one. This is a fidelity requirement, not a new proof supplied by the rewriting model. The formalizer translates input language into a problem; the verbalizer rewrites an already computed answer into prose.

Semantic case: one meaning used to evaluate translation

A semantic case is evaluation data, not a running component. It groups an intended input meaning, a reviewed SOP target, source information, linguistic variants, and expectations in specified test situations under a stable identifier such as semantic_case_id. “Who works at Acme?” and “Which people are employed by Acme?” may be two phrasings of one case. “Who does not work at Acme?” is a different meaning, not an equivalent paraphrase.

Corpus-building code uses these cases to produce training and evaluation records and to keep equivalent phrasings together when splitting training, development, and test data. Otherwise a model could see one phrasing during training and be credited for “unseen” understanding on its near-duplicate. Related contrast cases and duplicate meanings also require leakage checks.

Two measurements must remain separate. Running the reviewed target SOP against test knowledge checks the program and system behavior. Running the model on the natural-language variants and judging its generated SOP checks translation. Passing the first does not establish the second. Case files, JSONL rows, and reports are different representations of this evaluation material, not additional query languages.

GC: deleting storage that no live view needs

Garbage collection is repository maintenance code. As sessions, corrections, snapshots, and forks accumulate, some stored objects become unreferenced. GC starts from the approved bases and existing user/session/fork views, determines which snapshot or shard objects remain reachable, and identifies the rest as removal candidates.

The operator can inspect a dry run before using gc --apply. For example, an old snapshot must stay if a historical session still references it, even when a newer snapshot exists. GC does not decide that a fact is false and does not remove a private session merely because it is old. Its purpose is reclaiming proven-unused storage without breaking a view someone can still open.

Glossary: data, evaluation and learning terms

These short definitions fix the meaning of terms used across the specifications and dataset tooling. The linked DS files are the normative source.

Surface
One natural-language phrasing of a semantic case (a question or request, in one language). Several surfaces (English, Romanian, mixed, with or without typing noise) share a semantic_case_id and always stay in the same split.
Gold
The reference answer recorded for a row: its declarative SOP target together with the expected, executed result. A gold is produced by the builder and executed against the real runtime; it is a reference for evaluation, not a human-reviewed truth unless an audit verdict says so.
Oracle
The independent procedure that decides the expected result of a case without trusting the SOP target under test, for example a handwritten computation over the case's finite world. A target that merely executes is not its own oracle.
Sealed test
The held-out split stored only under eval/suites/<corpus>/test.jsonl. It is never used for training or checkpoint selection, and connected case groups never cross into it from train or dev (DS008).
Epistemic status
What the system can claim about an answer, kept separate from whether a computation ran: supported, refuted, both (conflicting evidence) or unknown, qualified by complete and hypothetical. Lack of support is unknown, never an implicit negation (DS006).
Stated
A model proposition that surely comes from the user's message, written as strings with the user's certainty (asserted, hedged, supposed) and an optional reported speaker. An asserted statement is turn-local evidence carried in caller-owned conversation context; the others are used conditionally. Never stored or reinforced (DS021).
Assumed
A model proposition that the model added (a presupposition, a closure, a default, world knowledge). Reported in model_assumptions and ignored by the primary answer; host policy branch runs it in a separate hypothetical solve. Not carried across turns.
Basis
The optional, purely descriptive label of an assumption: closure, default, disambiguation, implicature or world. It never affects trust, admission or reasoning; its accuracy is measured separately under a preregistered keep/drop criterion.
Question forms
The one formalization of each question word in the model language (DS021): mode every with a scope for "all/every/no", role time ?t with select ?t for "when" and measure start|end|duration for "since when / until when / how long", mode count over ?t for "how many times", the location role for "where", the instrument role for "how", and mode explain for "why".
Question types
The eighteen labels the corpora put on a message (yes_no, wh, count, universal, when, since_when, until_when, how_long, how_many_times, where, why, how, claim_check, multi, numeric, none, unclear, ambiguous); each maps to one question form. See Question types.
Not computable
The host answer status: not_computable for a formalized problem that no engine can compute yet: "I understood the question as …; I cannot compute this kind of answer yet", with the formalization shown. It replaces a model refusal. unsupported is reserved for an explicitly requested backend that is unavailable in a trusted circuit (AGENTS rule 8).
Unclear
The only-wire model output for an unintelligible message (gibberish), one with neither a statement nor a question (no_request), or a visible ambiguity with no preferable reading (ambiguous, with 2–4 reading paraphrases); the host replies from a fixed table and lists the readings. Distinct from the host-generated clarify. When one reading is preferable, the model states it with assumed (basis disambiguation) instead.
SymbolicLM
Stanza grammatical analysis plus the UD-to-SOP rules (lib/symbolic-lm/, chat model symbolic-lm). It returns the grammatical analysis (the UD parse per sentence: id, form, lemma, upos, head, deprel) and, at a later stage, the SOP Lang generated from it. Its only input is the message, like the earlier small model's. It owns UD parsing (Stanza, English package accurate by default, default selectable in config/symbolic-lm.json), SOP generation from the analysis, and the uncertainty signal (with the optional parsers_disagree reason) and routing (direct/translate/auto). It calls LanguagesUtil for language identification and spelling and TranslatorService for translation, rather than doing either itself. Priority: improve SymbolicLM by rules and repairs; rewrite the input only for what rules cannot fix. Translation is a secondary route (mixed messages; monolingual Romanian is parsed directly, decided by eval-translator-compare-v1), not the main one, and the chat's textToCleanEnglish step is the intended way to turn bad input into English. Formalization is evaluated on clean English (DS021).
LanguagesUtil
Language identification (per token, message and frame; Romanian, English, name, number; evidence-based; frame detection for code-switched messages from closed-class function words) and symbolic spelling (lib/languages-util/, a conservative corrector). It knows nothing about UD, SOP or translation; SymbolicLM, TranslatorService and the clean-English classifier call it.
TranslatorService
The translation backends (lib/translator-service/) that SymbolicLM calls when a route needs translation toward English; it never parses UD or generates SOP. The symbolic backend (dictionary-and-rules realization from a Romanian UD parse) is the one wired into the runtime pipeline; opus-mt and apertium are research backends compared to it in eval-translator-compare-v1.
textToCleanEnglish
The chat UI step (lib/text-to-clean-english/), validated by the user, that turns bad input into acceptable English before formalization. A cheap gate skips it for a message that already reads as clean English; otherwise it splits the message into sentences and sends each flagged English sentence to LanguageProofingLLM and each Romanian or mixed sentence to the translator-llm (Qwen3-4B; LanguageProofingLLM is its fallback) and shows the proposal with a word diff for the user to accept, edit or send unchanged. It runs outside the formalizer and does not change what SymbolicLM receives once the user sends the message.
LanguageProofingLLM
A standard or separately fine-tuned language model that turns Romanian, mixed Romanian/English and badly written English into acceptable English (ideally a decent translator). Default base to try first: Gemma 3 270M; a larger model only if it fails. Current implementation: the fine-tuned Gemma 3 270M production build (run language-proofing-gemma270m-prod1, F16 GGUF, chat registry id language-proofing-llm); it replaced Qwen3-1.7B plus LanguageTool in the chat on 2026-10-01. Data: bad_english. Further fine-tuning only with the owner's explicit approval per run.
SymbolicProofingLLM
The small fine-tuned language model that rewrites correct English into the limited English SymbolicLM understands, preserving the meaning. Current implementation: the fine-tuned Gemma 3 270M iteration 3 (run symbolic-proofing-gemma270m-it3, F16 GGUF, rewrite gated by default), formerly called the "proofreader" (training role id proofreader, earlier run models/gemma/proofreader-gemma270m-v1: the role id and artifact paths are frozen, only the concept name changed; alias note in DS021). Used only for what rules cannot fix. Data: neuro_english. Further fine-tuning only with the owner's explicit approval per run.
FormalizerLLM
The earlier small fine-tuned language model that writes SOP Lang directly from the message (the registry models smollm2-135m, smollm2-360m and gemma-3-270m of the formalizer-v1 runs). It is distinct from SymbolicProofingLLM, the former "proofreader" that rewrites correct English into limited English and never writes SOP, and from SymbolicLM, the deterministic rules that are the chat default and the only formalizer the chat and the API offer. The model boundary (the prompt is the message alone; stated, assumed, unclear, query, constraint, unparsed; no translation) applies to it in full. Archived: its checkpoints, training code, evaluation tools and results stay as evidence in the archive and history reports.
EmotionDetectionSystem
The separate, switchable host component (lib/emotion-detection/, DS029) that classifies the pragmatic or emotional role of a message and of the spans SymbolicLM cannot formalize (greeting, thanks, politeness, urgency, hedge, frustration, possible irony, tag question, topic shift and others) with pluggable strategies (symbolic lexicons, optional neural classifiers, an LLM slot). It emits advisory pragmatic wires that let the reasoner regulate itself (answer length, strategy, re-checking, a courtesy-only reply); the signals are the system's subjective perception, never facts about the world, and the small formalizer never authors them.
The three datasets
The first level of datasets/ holds three dataset folders and the owner-message collection natural (legacy corpora live in datasets_archive/; the resolver is lib/dataset-paths.mjs). bad_english: Romanian, mixed and badly written English; evaluates and later fine-tunes LanguageProofingLLM. symbolic_english: correct English that SymbolicLM analyses correctly; stores the analysis, is the regression suite (tools/symbolic-regression.mjs) and the inventory of target forms. Membership is decided on the grammatical analysis, not on the SOP: every sentence has identical default and accurate Stanza trees and the DeepSeek parse judge (conditions a and c) says good enough; the SOP result stays on the row as sop_layer for the later layer (DS008). neuro_english: correct English that SymbolicLM does not analyse correctly (the two Stanza trees differ or the parse judge rejects the analysis); evaluation and fine-tuning material for SymbolicProofingLLM. Sealed tests are under eval/suites/<dataset>/test.jsonl. natural (owner decision of 2026-10-01, a fourth folder without splits or targets): the owner's own chat messages, the realism evaluation set read as a whole and the seeds for synthetic training rows that keep a message's form and change its words; tools/datasets/audit/natural-overlap.mjs fails closed on a repeated message or its content words. The audit page has one tab per dataset (DS020).
Policy: rules first, no fine-tuning yet, laptop speed
Formalization is evaluated on clean English. The priority is improving SymbolicLM by rules and repairs; rewriting is only for what rules cannot fix. There is no fine-tuning until the owner approves after reviewing the three datasets in the audit page. Base models must run at 30 to 40 tokens per second on an ordinary laptop CPU (measured table: eval/reports/current/cpu-speed/cpu-speed-table.json).
Host linking
The deterministic host step after the context-free model: relation phrase and role set to a lexicon predicate, quoted values to typed entities, temporal expressions to intervals; unknown or ambiguous links become a host clarify.
KnowledgeLinker
The deterministic step after SymbolicLM or the small model that links the words of a message to the predicates of the chosen base memory (name pending the owner's confirmation; the step of host linking). It reads a relation phrase by the memory's predicate ids and aliases and by the reviewed relation lexicon; the plain copula (be, be a, be in) it reads with the six closed copula readings class, occupation, attribute, identity, location and describe ("Who is Ana?"), looking up which predicates the base memory declares for each (reading NAME, describe_rank N on a predicate wire). The code names no predicate; with no declared reading it asks a precise question and never answers "unknown relation be". See DS021, "KnowledgeLinker: the copula and the relation lexicon".
Relation lexicon
Reviewed language data of the KnowledgeLinker (config/relation-lexicon.json): copula verb forms, articles, locative phrases, occupation nouns, attribute adjectives (English and Romanian) and the relations a base memory maps to its own predicates. It is the review: a phrase it does not cover stays unknown and the user is asked.
Host frame normalization
A reviewable frame and synonym list (sop/frames.mjs, config/dictionary/frames-*.tsv) that normalizes formalizer output as host work (owner answer to Q-SYM-2): a relation synonym becomes the frame's relation, a role name the frame does not declare is renamed when only one declared role is free, the relation/object boundary shifts when that names a frame, and a quoted time moves to validity or the query period. Evaluations report it as a separately labelled host-normalized score beside the strict one (DS016); it never changes the model language or a gold.
Role inventory
The closed, context-free argument names of model propositions: subject, object, recipient, location, source, destination, instrument, time, topic. Lexicon predicates map their positions to them with role NAME TYPE.
Knowledge wire
A wire of the authoring surface of SOP (predicate fact rule default integrity aggregate action method norm procedure argument trace, and the host-composed amendment), written from a source text and validated by sop/knowledge/. Never model output: the model-origin compiler rejects it. See the manual.
Closed predicate
A predicate declared closed true: the retained view holds every fact of the relation, so absent, counts, sums and every are meaningful. Declared only with the source sentence that says the list is exhaustive, accepted by host review over an archived or pinned view, never inferred.
Two negations
not p a is explicit evidence that p a is false (the source says so); absent p a means "no record of it" and is allowed only over a closed predicate. Absence of evidence is unknown, never false.
both
The reported status of an atom with positive and negative evidence. The two evidences propagate independently (a paraconsistent, monotone reading), so a contradiction stays local and nothing unrelated becomes derivable.
Default and override
A default is a defeasible rule ("usually"): it is blocked by an exception, by a strict contrary, or by the firing of a default it is overridden by (overrides). Two defaults of equal strength with contrary heads give both.
Norm
A norm forbids, obliges or permits an action or a state, with at most one temporal qualifier (always before after within sometime at_most_once), a severity (hard or soft) and a binding (strict by default, or advisory).
Method and procedure
A method is the manual's own ordered procedure for a task, with the choice points the engine may optimise; a procedure is a named bundle of wires. A procedure has no approval or version of its own: its members carry them.
Mode of work
The sum of approved methods, norms and procedures: the system acts by them, optimises within them, keeps them named, versioned and addressable, and lets an amendment be negotiated with the user. All of it is knowledge written from a source and approved by the host, never model output.
Governance
The fields version supersedes approval approved_by approved_at retired_at scope of the governed wires (rule, default, integrity, action, method, norm). The host writes the approval fields; only approved (and contested, flagged) wires bind; proposed and rejected wires bind only when a query supposes them; asof selects the version known at a date.
Amendment
A proposed change to a procedure or wire, composed by the host from the user's words, evaluated as a what-if (if $amendment) and accepted or rejected by a host write recorded in the journal.
conditional and used
conditional, per row, lists the assumptions (reported, hedged or supposed facts, proposed wires) a row rests on, verified by a second run. used is one sufficient support set of claims, with their versions, that re-derives the answer.
budget_exhausted
The status of an answer cut off by a budget (reason rounds probes horizon depth domain wall cancelled numeric_range). It never reads as unknown, refuted, no_plan or optimal.
not_expressible
The harness or router answer for a question that needs a feature the strategy does not declare. Distinct from unsupported, which stays reserved for an explicit backend request that cannot be honoured.
Oracle and shadow gate
The oracle is the js-reference strategy, a deliberately naive implementation of the whole core; a strategy is accepted by agreeing with it, with zero disagreements, on every case it declares. used is checked by replaying it alone in the oracle.
Reinforcement
Proof-use promotion of an admitted, metadata-verified observed fact. It happens only in a real, non-hypothetical proof, only when host policy (policy.reinforce !== false) and the memory retention setting (reinforceOnUse) both allow it, and the reason packet reports it. A read or retrieval alone never reinforces anything (DS006).
Ingestion
Turning source material into sourced SOP facts or candidate rules: extract passages, quote them exactly, draft facts, probe candidate rules, and publish only after independent host approval (DS011). Drafts are not runtime knowledge.
The two learning flows
Formalizer learning trains the small model to map a user's message (a question and its assertions) to declarative SOP (stated, assumed, unclear, query, constraint) with no other input; it changes model weights and needs explicit training approval. Material ingestion accumulates reviewed knowledge in the repository from quoted sources after host approval; it changes no weights. New knowledge therefore never requires retraining the model, and neither flow substitutes for the other.

Where these responsibilities live in the current code

The module that owns each responsibility (turn coordination and model calls, SOP parsing and execution, linking and retrieval, reasoning backends, rendering, data and evaluation) is listed in DS002. For exact wire fields and runnable examples, use wire help; for the small model's language, use the small-model language page.

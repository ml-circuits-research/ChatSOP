Overview / Architecture

Architecture

This page documents the product as the code is today: which components exist, how they call each other, where the trust boundaries are, and what is deliberately not part of the product. It was written from the source tree on 2026-10-01 (static import scan of lib/, sop/, memory/, reasoning/ and server/, then reading the call paths), not from the specifications. Where the code and a specification or this documentation disagree, the disagreement is listed in Discrepancies with a file and line. The contracts remain the specifications: DS002, DS012, DS031; the execution walk-through is Runtime and the names are in the Wiki.

a. Components and trust boundaries

Four boundaries matter. B1 is authentication: every route needs a bearer token or the administrator session cookie, except the documentation, the health check, the home and login pages and the administrator setup and login calls (server/http.mjs:200). B2 is the model boundary of DS021: the managed model processes receive the message alone and return text or SOP strings; the registry has exactly one entry with the formalize capability, the SymbolicLM service (config/formalizers.json:4). B3 is the fence around the coding agent omp (lib/omp/run.mjs:29). B4 is that stored knowledge changes only through the few explicit writers of diagram c; a base memory grows only through a validated, recorded addition. B5 is the solver rule: swipl and z3 run only when a wire names the backend (diagram d).

Static scan of the product entry points tools/serve-local.mjs, server/http.mjs, server/cli.mjs, lib/symbolic-lm/serve.mjs: 249 of 310 modules under lib/, sop/, memory/, reasoning/ and server/ are reachable through static or dynamic imports; 61 are not (listed in not in the product; the findings that concerned them are in hygiene findings).

b. One chat turn, end to end

The browser makes every call itself: it first cleans (step 2), then prefetches the understanding and the routing hint (step 3), then sends the final text (step 4). The chat call reuses the cached SymbolicLM answer (server/http.mjs:266), so the analysis shown to the user and the analysis executed are the same. The text is only rewritten inside the SymbolicLM service; Agent.turn has no rewrite step, and the server passes it no rewrite option. A courtesy-only message stops at server/agent.mjs:63 without compiling anything.

Steps 7 to 9 are one pipeline. compileDeclarative (sop/declarative.mjs:119) never executes anything: it returns the authored SOP, the generated execution SOP and the reports (clause links, translations, untranslated words, copula readings, repairs, unresolved spans). runDeclarative (sop/declarative.mjs:451) then runs the execution SOP through Runtime.run with origin generated; a relation or entity that does not link produces a clarify wire instead of a guess (sop/declarative.mjs:471). In Runtime the solve wire expands into link, reason and binding wires (sop/runtime.mjs:111); link calls linkKnowledge (sop/runtime.mjs:109), and reason picks the strategy with chooseReasoning (sop/runtime.mjs:56), by default the reference route (sop/runtime.mjs:30).

The chain stops being read-only in exactly one place: the proof-use reinforcement of an admitted, metadata-verified observed fact after a real, non-hypothetical proof, allowed only when policy.reinforce and the retention configuration both permit it (sop/runtime.mjs:148).

c. Memory: base memories, sessions, layers, SQLite, retention

A base memory is a folder whose circuits are the source of truth; its repository is derived from the fact wires (lib/chat-data/memories.mjs:120). The product creates SQLite memories only (lib/chat-data/memories.mjs:38); the other engines of memory/banks/ stay for research. A session copies the base circuits, clones the repository with hard links (lib/chat-data/sessions.mjs:89) and compiles its own lexicon from the base circuits followed by the circuits the user accepted (lib/chat-data/sessions.mjs:125); the lexicon is cached by the hash of those circuits (lib/chat-data/lexicons.mjs:12).

Repository.visible (memory/repository.mjs:111) lists the session's live layer, then the user chain, then the base chain, and retrieval reads across them. The shipped configuration keeps retention at mode: none with reinforceOnUse: true, and uses bounded sharding with a garbage collection every 32 writes (config/runtime.json:32). Temporary folders older than 24 hours and sessions idle for 14 days are removed by a scheduled cleanup (lib/chat-data/index.mjs:20).

There are two read paths with different inputs: a chat turn retrieves fact rows from the session repository through linkKnowledge, while POST /v1/sessions/{id}/query runs the oracle directly over the session theory, the circuits as text (server/product.mjs:175). The first sees only the facts stored in the repository; the second sees every wire of the circuits, rules and norms included, and answers a query circuit you send.

d. Reasoning strategies and backends, with rule 8

The registry has five ids: reference, js-reference and js-oracle (the same oracle, reasoning/registry.mjs:20) and the two external strategies prolog-tabling and z3-smt-bounded, each pinned to one backend (reasoning/registry.mjs:24). A wire that names backend prolog or backend z3 is routed to its strategy (sop/runtime.mjs:56). Rule 8 shows as four rejections (reasoning/registry.mjs:56, reasoning/registry.mjs:57, reasoning/registry.mjs:62, reasoning/registry.mjs:70) and as unsupported with fallback: null (reasoning/common.mjs:32) when a binary is missing (reasoning/registry.mjs:32). With Prolog, the oracle still answers first and the two results must agree (reasoning/bridge/external.mjs:64).

The 16 other directories under reasoning/strategies/ are the comparison set. Nothing in the product imports them; they are exercised by eval/smoke-reasoning/ and tests/strategy-*.test.mjs (owner decision H13: product reasoning is the oracle route until a router exists).

e. The authoring path

Routing is a pure function (lib/omp/routing.mjs:73) and its default setting is authoring: off: the coding agent runs only on an act of the user, and a scope detection only produces a suggestion. The agent has the read, write and edit tools and no shell (lib/omp/run.mjs:29); the repair loop is bounded by maxFixRounds (lib/omp/author.mjs:134). The result is a draft; accepting it (lib/chat-data/sessions.mjs:173) puts the circuit in the session layer and SessionRuntimes.refresh (server/session-runtime.mjs:53) makes it visible to open agents, including through a new session lexicon. Committing is a separate action (lib/chat-data/sessions.mjs:196).

f. Data, evaluation and training pipelines and their gates

Gates are drawn with a heavy outline. Training has three: a dataset qualification record (training/cli.mjs:126), a NEW explicit authorization receipt that names the model, run and qualification hash (training/cli.mjs:166) and the single training lock (training/cli.mjs:54). The leakage guard keeps generators and training code away from sealed tests (eval/leakage.mjs:21). The offline verification entry point is tools/verify.mjs:2. The training command line still accepts the roles formalizer, verbalizer and shared next to proofreader (training/cli.mjs:37); they serve the archived FormalizerLLM evidence.

ModelManager

Registry of the models the product uses and the on-demand processes behind them: it starts a CPU llama-server (or the SymbolicLM service) on a free loopback port, probes it, idles it and evicts the least recently used one when the count or memory budget is reached.

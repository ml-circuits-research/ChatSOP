resolve

resolve searches a host-reviewed lexicon for an exact or accent-folded surface form. It helps a formalizer avoid guessing the identity of an entity; it does not create an entity, infer a new synonym, or turn an ambiguous mention into a fact. The host must supply a lexicon; the source program alone cannot define a trusted ontology.

All supported fields

Field / multiplicityGrammar and matching
text — exactly one, requiredNonempty text, plain or JSON double-quoted. It is decoded by unquote, bounded to 1,600 UTF-8 bytes at lookup, and searched as a whole surface form, not as free-text inference. $other inside text is literal text: text does not create a value dependency. Normalization uses NFC, Romanian lowercase, cedilla replacements, collapsed whitespace; exact normalized matches are preferred, otherwise accent-folded matches.
language — exactly one, requiredTwo or three lowercase ASCII letters, e.g. en or ro. Lookup uses entries labeled in this language plus identifier aliases marked und. auto is a candidate-search feature, not an accepted resolve language.
kind — exactly one, requiredOne of entity, predicate, concept. Filters ontology entry kind before deciding whether the match is unique. A resolved predicate ID is not a dynamic predicate name inside atom syntax.
type — zero or oneNonempty text, only allowed for kind entity. Exact entity-type filter, such as organization, as declared in the host ontology's entity kind; no subtype inference. If supplied with predicate/concept, parsing rejects the field combination.
domain — zero or oneNonempty text matching the ontology entry's domain exactly. Narrows candidates; it does not define a domain or change a predicate's argument types.

Results and dependency behavior

The lexicon computes a version digest and records provenance with each resolution. Exactly one filtered match produces bound with canonical id, match method, type/domain and lexicon version. No match gives unknown; multiple give ambiguous with sorted candidates. Runtime records these statuses in outputs/trace. Only bound creates a usable $id value; a dependent wire is marked blocked if resolution is unknown or ambiguous, not silently assigned the first candidate. The checkResolvedTerms guard accepts a resolved value inside an atom only when its source is an entity, bound and compatible with the schema's argument position (not an integer/value position). Directly supply canonical predicate spellings in authored atoms; consider clarify if an identity remains ambiguous.

Current syntax examples

Both examples require a host lexicon with the indicated reviewed entries; without it, resolve raises resolve requires a host-reviewed lexicon. First, assume room_a is a reviewed entity labeled “Room A” in English, with type room, and a schema allows occupied(room):

@place resolve
  text "Room A"
  language en
  kind entity
  type room

@observation fact
  holds occupied($place)
  valid timeless
  source "operator note"

A unique approved match supplies room_a as an atom argument; this declaration alone does not write memory. Second, assume an approved entity lab_alpha has alias “Alpha Lab” in domain work:

@employer resolve
  text "Alpha Lab"
  language en
  kind entity
  type organization
  domain work

@question query
  where works_at(ana, $employer)
  mode explain

This produces a query value only if the entity is bound; a separate solve and admitted evidence would be required for an answer. The following parses but fails at resolution/atom consumption: selecting a predicate entry cannot supply an entity argument.

@relation resolve
  text "works at"
  language en
  kind predicate

@bad query
  where works_at(ana, $relation)

Simplified syntax proposal — not implemented

The proposed atom spelling could write works_at ana $employer; the approved lexicon and entity-only argument rule are current safeguards, not an implemented promise about a future reduced vocabulary. Whether resolve remains a model-authored wire is not settled.

@question query
  where works_at ana $employer

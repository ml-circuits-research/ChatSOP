assert

assert is the explicit write boundary for facts and events in the current repository session. A formalizer may propose admitted user statements for this route; it cannot create a host approval merely by emitting assert. A declared fact alone is only a value. Asserting it may make it visible to later session queries, but publication to a global library/approved base is a separate host action.

All supported fields

Field / multiplicityValue grammar and effect
input — one or more lines, requiredWhitespace-separated $value references or ~definition handles on each line; recursively flattens arrays from pack. Each item must materialize to a fact, event, or approved library definition type. Use $fact, not ~fact: the definition reader supports rule/research declarations and template/procedure handles but does not lower fact handles. Arbitrary query, clarify or solve packets cannot be stored here. Definitions require host-reviewed ingestion with allowRules; persistent definitions cannot capture transient $ wire dependencies. $ references create scheduling dependencies; ~ handles designate allowed declaration definitions, not mutable storage cells.
scope — 0–1, default sessionOnly session is accepted by runtime. Parser initially accepts arbitrary field text, but other values fail at execution. There is no global/library scope switch in a model-authored SOP write; host commit/review is distinct.
after — zero or morePlace an actual $wire reference in each line to force a value dependency, typically after $earlier_assert for sequential effects. The runtime does not parse the rest of this field as a separate command. Merely placing two asserts in file order is not an explicit ordering contract.

Transaction and receipts

Runtime requires a repository, session and policy.allowWrite. It gathers ready assert wires into one effect batch and calls repo.apply against a private working copy before publishing the session revision; each assert receives a receipt {status:'stored', ids:[...], count, revision}. The IDs correspond to applied operations: facts yield claim IDs, events yield event IDs. A correct event expands to retract old claim and add replacement fact, thus producing two IDs. event.target $receipt requires a receipt with exactly one claim ID, not a multi-item pack receipt or an event receipt. A pinned fact additionally requires allowPin; retention is not a truth guarantee. Claims carry validity (valid) and separate write time (knownAt), source/quote metadata and review boundaries. A solve's after $receipt is needed when it must see that write in the same run.

Library definitions require allowRules and reviewed ingestion; under origin='model' runtime refuses direct rule/template/procedure/action declarations. There is a documented normative rule that assumptions must not be published as evidence; the generic assert path does not uniformly enforce it, so consumers must not use assert.input for hypothetical solve.assume facts. event revision is not the same as an explicit negative fact.

Current syntax examples

With a writable session, a claim is added and the receipt holds its claim ID. The fact's source is metadata, not host verification:

@report fact
  holds repaired(pump_a)
  valid 2026-09-01 open
  source "technician log 17"

@record assert
  input $report
  scope session

The following stores two independent claims in one assert and then runs a query after the receipt. The expected answer depends on both the write and the selected repository retrieval strategy:

@one fact
  holds on_shelf(book_a)
  valid timeless

@two fact
  holds on_shelf(book_b)
  valid timeless

@batch pack
  items $one $two

@write assert
  input $batch

@request query
  where on_shelf(?book)
  select ?book

@answer solve
  query $request
  after $write
  output ?book many

This parses, but runtime rejects scope library: SOP writes target the current session only.

@report fact
  holds repaired(pump_a)
  valid timeless

@bad assert
  input $report
  scope library

Simplified syntax proposal — not implemented

A simpler atom spelling may replace repaired(pump_a) with repaired pump_a. No approved simplification removes the explicit session write boundary or grants the model global publication rights; the small-model field inventory remains open.

How the model writes

This page explains the model language from the model's point of view: what it receives, what it writes, and how it decides between stated, assumed, unclear, query and constraint. It is the guide a person should read before reviewing corpus targets at /audit. The normative contract is DS021; the eighteen question types are on Question types. Every example below is executed by tests/wire-help.test.mjs.

1. What the model receives and writes

Input: the user's message, nothing else. No list of known people or relations, no identifiers, no lexicon, no background facts, no earlier turns and no date or clock. The model therefore cannot know whether "Acme" exists, which predicate "works at" is, or what day "yesterday" was, and it must not pretend to.

Output: SOP wires, one keyword per line, with quoted strings. A proposition is a relation phrase, one to four role lines and a polarity. After the model, the host links the strings to its reviewed knowledge (relation phrase and role set → predicate, values → entities, time expressions → intervals) and asks the user with a host clarify when something is unknown or ambiguous. The model never chooses an identity, an engine or an answer.

RoleUse forExample (EN / RO)
subjectwho or what the relation is about (the grammatical subject of the active sentence)"Ana works at Acme" / "Ana lucrează la Acme"
objectthe direct counterpart: employer, team, parent, thing owned or taught"Ana works at Acme" / "Laura predă biologie"

destinationwhere to; visits, trips"Ana visited Cluj" / "Ana a mers la Sibiu"

The value is the mention as written (with its article, case ending or typo) in quotes, or a ?variable in a question. The relation is the phrase as meant, normalized to a simple form ("work at" for "works at", "worked at" or "wroks at"; "lucra la" for "lucrează la").

2. Step by step

  1. Is there anything to formalize? Unintelligible text → unclear kind gibberish. No statement and no question ("ok", "thanks", "write a poem") → unclear kind no_request. Otherwise continue; an odd, contradictory or seemingly irrelevant message is still formalized as written.
  2. Split the message into propositions. Each assertion, supposition or reported claim becomes a stated; each question becomes a query (or a constraint for a numeric problem). Remarks about the user's own situation or purpose ("I have a meeting tomorrow", "my boss asked me") are not part of the problem and are left out.
  3. Choose the question form from the question word, without rewriting it: see Question types.
  4. Write each proposition: relation as meant, values as written, polarity always explicit (negated only for an explicit "not", "no", "nu"), valid only when the message gives a time, and certainty on every stated.
  5. Make every interpretation visible. Whatever the model adds — a chosen reading, a presupposition, a closed list, a typical default — is an assumed proposition. If two readings are equally good, write only unclear kind ambiguous with the readings.
  6. Stop. The model does not answer, does not judge whether the question can be answered, and never refuses.

3. Worked examples in English and Romanian

EN “Maria has worked at Acme since 2021. Who else works there?”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object "Acme"
  polarity affirmed
  valid from "2021"
  certainty asserted

@q query
  select ?who
  where match
    relation "work at"
    role subject ?who
    role object "Acme"
    polarity affirmed
  end
  filter ?who != "Maria"

"there" has one antecedent and is written as "Acme". "else" excludes Maria with a filter whose literal is written as in the message; the host resolves it like a role value.

RO “Ana locuiește în Cluj din 2020. De când lucrează la Acme?”

@s1 stated
  relation "locui în"
  role subject "Ana"
  role location "Cluj"
  polarity affirmed
  valid from "2020"
  certainty asserted

@q query
  select ?t
  measure start
  where match
    relation "lucra la"
    role subject "Ana"
    role object "Acme"
    role time ?t
    polarity affirmed
  end

Romanian drops the subject pronoun; the only candidate is Ana, so the query names her without an assumption. The relation is written in the message's language; the host's lexicon carries Romanian aliases.

RO “Presupunem că Ion a plecat de la Zeta. Mai lucrează acolo?”

@s1 stated
  relation "pleca de la"
  role subject "Ion"
  role source "Zeta"
  polarity affirmed
  certainty supposed

@a1 assumed
  relation "lucra la"
  role subject "Ion"
  role object "Zeta"
  polarity affirmed
  basis implicature

@q query
  where match
    relation "lucra la"
    role subject "Ion"
    role object "Zeta"
    polarity affirmed
  end

"Presupunem" makes the claim a supposition (certainty supposed): the answer will be conditional. "Mai" ("still") presupposes that Ion worked at Zeta, which the user did not assert, so it is assumed with basis implicature, and with no valid line because the message gives no time.

4. Typos, missing diacritics and informal writing

Messages are often misspelled, written without Romanian diacritics, or in chat style. The model normalizes the relation (it is the meaning) but copies the values as written (they are what the user typed). The host then matches names after case and accent folding, so "Brasov" finds "Brașov"; it never resolves an identity by similarity, so a misspelled name that matches nothing becomes a question to the user rather than a guess. For a stated value, the agent guard accepts small typos when it checks that the value occurs in the message (up to one edit for tokens of four to seven characters, two beyond, and short inflections).

EN “does Maira wrok at acme??”

@q query
  where match
    relation "work at"
    role subject "Maira"
    role object "acme"
    polarity affirmed
  end

"wrok" becomes the relation "work at"; "Maira" and "acme" stay as written. If the host knows a "Maria" but no "Maira", it asks.

RO “unde locuieste ana acum? cred ca s-a mutat din brasov”

@s1 stated
  relation "se muta din"
  role subject "ana"
  role source "brasov"
  polarity affirmed
  certainty hedged

@q query
  select ?place
  where match
    relation "locui în"
    role subject "ana"
    role location ?place
    polarity affirmed
  end
  at "acum"

No diacritics and no capitals in the message; the relations are written normally, the values exactly as typed. "cred că" ("I think") makes the statement hedged. "acum" is a time expression the message gives, so it is copied into at; the host normalizes it against its clock.

5. stated or assumed?

The rule. stated only when the model is sure the claim comes from the user's message. Anything the model adds, infers, completes or presupposes is assumed. When in doubt, assumed.

stated has a certainty: asserted (the user says it), hedged ("I think", "probably", "cred că") or supposed ("suppose", "if", "presupunem că", "dacă"); reported speech ("Ion says that …", "Ion zice că …") adds speaker "Ion". Every value of a stated must occur in the message. assumed has no certainty and an optional, purely descriptive basis: closure, default, disambiguation, implicature or world. An assumption may even restate the queried proposition (a presupposition or a closure often does); it is reported, and by default never used to compute the answer.

MessageFormalizationWhy
"Since Nera left the lab, who runs it now?"stated (asserted) + queryAn assertion embedded in a question is still asserted.
"Is Ana still at Acme?" / "Mai e Ana la Acme?"assumed basis implicature + query"still" presupposes an earlier state the user did not assert.
"Room A and room B are booked. Is room C free?"two stated + assumed (room C not booked, basis closure) + queryTreating the list as complete is the model's addition.

"Suppose Maria works at Acme. Would she be paid?"stated certainty supposed + queryThe answer is conditional on the supposition.
"Ion says that Maria left." / "Ion zice că Maria a plecat."stated with speaker "Ion"Attributed to Ion, used only conditionally.
"Tweety is a bird. Can Tweety fly?"stated + optional assumed basis default + query"Birds fly" is general knowledge, not the user's claim.

EN “Room A and room B are booked. Is room C free?”

@s1 stated
  relation "be booked"
  role subject "Room A"
  polarity affirmed
  certainty asserted

@s2 stated
  relation "be booked"
  role subject "room B"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "be booked"
  role subject "room C"
  polarity negated
  basis closure

@q query
  where match
    relation "be free"
    role subject "room C"
    polarity affirmed
  end

Each booked room is its own proposition, and each value keeps the words of the message ("Room A" with its capital). The closure is the model's addition and is reported, not used, by default.

EN “Ion says that Maria left Acme in March 2024. Did she?”

@s1 stated
  relation "leave"
  role subject "Maria"
  role source "Acme"
  polarity affirmed
  valid on "March 2024"
  certainty asserted
  speaker "Ion"

@q query
  where match
    relation "leave"
    role subject "Maria"
    role source "Acme"
    polarity affirmed
  end
  during "March 2024"

The time is copied as written ("March 2024"), never converted by the model; the host normalizes it.

6. Vague messages and several readings

When a word, a pronoun or a scope has several readings and one is preferable, the model formalizes that reading and records the choice as an assumed with basis disambiguation, so the reader of the packet can see it. When none is preferable, the only output is unclear kind ambiguous with two to four reading lines in the message's language, and the host asks the user to choose.

EN “Ana manages Irina. Does she live in Cluj?”

@s1 stated
  relation "manage"
  role subject "Ana"
  role object "Irina"
  polarity affirmed
  certainty asserted

@a1 assumed
  relation "refer to"
  role subject "she"
  role object "Ana"
  polarity affirmed
  basis disambiguation

@q query
  where match
    relation "live in"
    role subject "Ana"
    role location "Cluj"
    polarity affirmed
  end

RO “Cine a făcut Ultimul bac?”

@a1 assumed
  relation "însemna"
  role subject "a făcut"
  role object "a scris"
  polarity affirmed
  basis disambiguation

@q query
  select ?x
  where match
    relation "face"
    role subject ?x
    role object "Ultimul bac"
    polarity affirmed
  end

The query keeps the user's verb; the assumption states the chosen sense ("made" as "wrote"). The host still links the verb and asks when its lexicon finds it ambiguous.

EN “Is the court free on Saturday?”

@u unclear
  kind ambiguous
  reading "the tennis court is free on Saturday"
  reading "the law court has no hearing on Saturday"

7. The "because" convention

"Because of" followed by a thing or a person is a role of the causal relation: role topic for "because of" / "din cauza", role source for "from" / "de la". A "because" clause that is a whole proposition is its own proposition: the observation is stated, and a proposed reason that the user asks about is the query. "I'm asking because …" introduces an ordinary assertion.

EN “Aurelia resigned. She quit because of Shirin, right?”

@s1 stated
  relation "resign"
  role subject "Aurelia"
  polarity affirmed
  certainty asserted

@q query
  where match
    relation "quit because of"
    role subject "Aurelia"
    role topic "Shirin"
    polarity affirmed
  end

EN “Jack stays home. Is that because he went to the book fair?”

@s1 stated
  relation "stay home"
  role subject "Jack"
  polarity affirmed
  certainty asserted

@q query
  where match
    relation "go to"
    role subject "Jack"
    role destination "the book fair"
    polarity affirmed
  end

The model does not decide whether the fair explains the absence; the host checks the asked proposition and, with mode explain questions, reports the derivation it found.

8. What the model never writes

  • Identifiers. No works_at, maria, lab_alpha: those belong to the host lexicon.
  • Invented context. No date, place, person or fact that the message does not contain, except inside an assumed proposition; no valid or at line computed from a clock.
  • Reasoning or answers. No conclusion, no "therefore", no status, no refusal, no advice. A contradiction in the message is formalized, not reported.
  • Plumbing. No fact, remember, resolve, solve, cnl, clarify, jsEval or host-only fields such as span. The retired premise wire does not exist.
@p premise
  holds works_at maria acme

The retired form: an atom of identifiers. Write stated with strings.

@s1 stated
  relation "work at"
  role subject maria
  role object "Acme"
  polarity affirmed
  certainty asserted

A bare identifier; the value must be the mention in quotes.

@q query
  where works_at ?who acme
  select ?who

An atom condition belongs to trusted circuits; the model writes a match block.

@f fact
  holds works_at maria acme
  valid timeless
  source user

The model never writes facts; an asserted stated is turn-local evidence.

One more rejection happens after parsing, in the agent guard: a stated value that does not occur in the message is rejected with stated_value_not_in_message; the model should have used assumed or a query variable.

Wire help / How the model writes

How the model writes

This page explains the model language from the model's point of view: what it receives, what it writes, and how it decides between stated, assumed, unclear, query, constraint and unparsed. It is the guide a person should read before reviewing corpus targets at /audit. The normative contract is DS021; the question types are on Question types. Every example below is executed by tests/wire-help.test.mjs, and every example shows the message it formalizes.

1. What the model receives and writes

Input: the user's message, nothing else. No list of known people or relations, no identifiers, no lexicon, no background facts, no earlier turns and no date or clock. The model therefore cannot know whether "Acme" exists, which predicate "works at" is, or what day "yesterday" was, and it must not pretend to.

Output: SOP wires, one keyword per line, with quoted strings. The keywords are always the English words of the language; the content words stay in the message's language, normalized (see content words). A proposition is a relation phrase, one to four role lines and a polarity; one clause of the message is one wire, related to its main clause by a link line. After the model, the host translates the words it needs with its dictionary, links the strings to its reviewed knowledge (relation phrase and role set → predicate, values → entities, time expressions → intervals) and asks the user with a host clarify when something is unknown or ambiguous. The model never chooses an identity, an engine or an answer.

A proper name (person, organization, place, title) is written as in the message (with its diacritics, case ending or typo) in quotes; any other value is the message's word, normalized; a question slot is a ?variable. The relation is the phrase as meant, normalized to its lemma ("work at" for "works at", "worked at", "wroks at"; "lucra la" for "lucrează la", "lucra", "lucrase la").

Content words: the message's language, normalized

The model reads English, Romanian and mixed messages and does not translate. It normalizes the words it copies; the host translates them afterwards with its reviewed dictionary (config/dictionary/) and links them to its English knowledge.

  • Relation phrases are lemmas in the message's language: English base form ("work at", "live in"), Romanian short infinitive without "a" ("lucra la", "locui în", "fi angajat la", "fi din"). A modal stays inside the relation ("be allowed to sign", "avea voie să semneze").
  • Common nouns and descriptions are put in the nominative with the message's determiners and definiteness, lower case: "sălii de sport" → "sala de sport", "the gym" → "the gym", "fratele meu" → "fratele meu". An obvious typo is repaired only when the intended word is unambiguous.
  • Romanian stays Romanian; English stays English; a mixed message keeps each word in its own language ("Maria lucrează la Alpha Lab" gives relation "lucra la" and role object "Alpha Lab").
  • Proper names stay exactly as written, diacritics and typos included ("Ayşe Şahin", "Pitești", "Kovács & Asociații", "Clujul"), because the host links them to its entities.
  • Dates and times are copied as written ("12 martie 2020", "acum", "March 2024"); the host normalizes Romanian and English expressions.
  • The first person is "the user" and "the user's brother" in an English message, and the message's own words in Romanian ("eu", "fratele meu"); the host reads both the same way.
  • Keywords are English in every language: relation, role subject, polarity, the link keywords because, if, … and the fixed disambiguation phrases relation "mean" and relation "refer to".

The host tries the phrase as written first; a phrase that does not link is retried with its dictionary translations and synonyms, and the lexicon picks (packet translations). A Romanian word the dictionary does not know is reported in untranslated; it is never guessed. English content words are also accepted for any message. After the dictionary, a reviewable frame and synonym list (sop/frames.mjs, config/dictionary/frames-*.tsv) may normalize the output as host work: a synonym becomes the frame's relation, a role name the frame does not declare is renamed when only one declared role is free, and a relation/object boundary is shifted when that names a frame ("get" + "the flu shot" → "get the flu shot"). The model writes what the message says; it never needs the list. The answer language is a separate host concern: English by default, Romanian when the caller or the message asks for it.

2. Step by step

  1. Is there anything to formalize? Unintelligible text → unclear kind gibberish. No statement and no question ("ok", "thanks", "write a poem") → unclear kind no_request. Otherwise continue; an odd, contradictory or seemingly irrelevant message is still formalized as written.
  2. Split the message into clauses. Each finite clause is one wire: an assertion, supposition or reported claim is a stated; a question is a query (or a constraint for a numeric problem). A subordinate clause is its own wire, and the main clause names it with one link line (because $s2, if $s1, …). Remarks about the user's own situation or purpose ("I have a meeting tomorrow", "I ask because my boss wants to know") are not part of the problem and are left out.
  3. Choose the question form from the question word, without rewriting it: see Question types.
  4. Write each proposition: relation as meant, values as written, content words in the message's language normalized, polarity always explicit (negated only for an explicit "not", "no", "nu"), valid only when the message gives a time, and certainty on every stated.
  5. Make every interpretation visible. Whatever the model adds — a chosen reading, a presupposition, a closed list, a typical default — is an assumed proposition. If two readings are equally good, write only unclear kind ambiguous with the readings.
  6. Say what you could not formalize. A part of the message the model cannot write (jargon, an idiom, a garbled fragment, "aia", "that one") is copied verbatim into an unparsed wire; the role it would fill gets a placeholder ?variable.
  7. Stop. The model does not answer, does not judge whether the question can be answered, and never refuses.

4. Typos, missing diacritics and informal writing

Messages are often misspelled, written without Romanian diacritics, or in chat style. The model normalizes the relation (it is the meaning, written as a lemma) but copies names as written (they are what the user typed). The host then matches names after case and accent folding, so "Brasov" finds "Brașov"; it never resolves an identity by similarity, so a misspelled name that matches nothing becomes a question to the user rather than a guess. For a stated value, the agent guard accepts small typos when it checks that the value occurs in the message (up to one edit for tokens of four to seven characters, two beyond, and short inflections).

EN “does Maira wrok at acme??”

@q query
  where match
    relation "work at"
    role subject "Maira"
    role object "acme"
    polarity affirmed
  end

"wrok" becomes the relation "work at"; "Maira" and "acme" stay as written. If the host knows a "Maria" but no "Maira", it asks.

5. stated or assumed?

The rule. stated only when the model is sure the claim comes from the user's message. Anything the model adds, infers, completes or presupposes is assumed. When in doubt, assumed.

stated has a certainty: asserted (the user says it), hedged ("I think", "probably", "cred că") or supposed ("suppose", "if", "presupunem că", "dacă"); reported speech ("Ion says that …", "Ion zice că …") adds speaker "Ion". Every value of a stated must come from the message: a name as written, or the message's own words, normalized. assumed has no certainty and an optional, purely descriptive basis: closure, default, disambiguation, implicature or world. An assumption may even restate the queried proposition (a presupposition or a closure often does); it is reported, and by default never used to compute the answer.

6. Vague messages and several readings

When a word, a pronoun or a scope has several readings and one is preferable, the model formalizes that reading and records the choice as an assumed with basis disambiguation (relation "refer to" for a pronoun, relation "mean" for a word sense; the values are the message's words), so the reader of the packet can see it. When none is preferable, the only output is unclear kind ambiguous with two to four reading lines in the message's language, and the host asks the user to choose. A phrasing that is ambiguous in a way the model may resolve (for example Romanian "pentru ce", which reads as "why" or as "for what") is formalized with one plausible reading; evaluation accepts every plausible reading (a row's sop_target plus its sop_targets_accepted), so no reading is dropped and the model never refuses.

The model writes words, never symbols or parentheses (owner decisions Q-LANG-1 to Q-LANG-7, DS021 "Words, not operators"). It does not compute, compare or choose: it writes the literal approximation, and the host computes what it can or answers not_computable.

7. One clause, one wire

Every finite clause of the message is one short wire; a whole clause is never packed into a string. A subordinate or result clause is related to its main clause by one keyword line on the main wire, KEYWORD $id, where $id is the wire of the clause the conjunction introduces. The keywords are English in every language; at most three link lines per wire, never inside a match block (syntax and host effects).

"Because of" a thing and "because" as a question

"Because of" followed by a thing or a person is a role of the relation, not a link: role topic for "because of" / "din cauza", role source for "from" / "de la". A proposed reason that the user asks about is itself the question; the model does not decide whether it explains the observation.

8. Say what you could not formalize

When the model cannot write a part of the message — jargon, an idiom, a garbled fragment, a reference to something said earlier ("aia", "el", "that one") — it formalizes the rest and copies that part verbatim into an unparsed wire: span "…", optionally near $id (the wire it belongs to) and hint (subject, object, time, location, value, relation, reference, other). The role it would fill holds a fresh placeholder ?variable, also in stated and assumed. The model never invents a value or a name; the host repairs what it can (dates, numbers, conversation references, names, the dictionary) and asks one question per span it cannot.

EN “Maria works at the new place near the station.”

@s1 stated
  relation "work at"
  role subject "Maria"
  role object ?place
  polarity affirmed
  certainty asserted

@u1 unparsed
  span "the new place near the station"
  near $s1
  hint object

RO “Cine mai lucrează la aia de lângă gară?”

@q query
  select ?who
  where match
    relation "lucra la"
    role subject ?who
    role object ?x
    polarity affirmed
  end

@u1 unparsed
  span "aia de lângă gară"
  near $q
  hint object

The span pairs with the query's non-selected object variable. With a previous question in the conversation that names exactly one place, the host resolves "aia"; otherwise it asks "La cine sau la ce vă referiți prin „aia de lângă gară”?".

9. What the model never writes

  • Identifiers. No works_at, maria, lab_alpha: those belong to the host lexicon.
  • Invented context. No date, place, person or fact that the message does not contain, except inside an assumed proposition; no valid or at line computed from a clock.
  • Translations it was not sure of. The model copies content words in the message's language; the host dictionary translates them.
  • Reasoning or answers. No conclusion, no "therefore" of its own, no status, no refusal, no advice. A contradiction in the message is formalized, not reported.
  • Plumbing. No fact, remember, resolve, solve, cnl, clarify, jsEval or host-only fields such as span on a query.
@p premise
  holds works_at maria acme

An atom of identifiers is not the model language. Write stated with strings.

@s1 stated
  relation "work at"
  role subject maria
  role object "Acme"
  polarity affirmed
  certainty asserted

A bare identifier; the value must be the mention in quotes.

@q query
  where works_at ?who acme
  select ?who

An atom condition belongs to trusted circuits; the model writes a match block.

@f fact
  holds works_at maria acme
  valid timeless
  source user

The model never writes facts; an asserted stated is turn-local evidence.

RO “Dacă Maria lucrează la Laboratorul Alfa, cine mai lucrează acolo?”

  role subject "Maria"

  select ?who
  except ?who "Maria"

    relation "lucra la"

"dacă" makes the clause a supposition: certainty supposed, not asserted.

RO+EN “Who works where? Și unde se află?”

@q query
  select ?p ?c
  where match
    relation "work at"
    role subject ?p
    role object ?c

@q2 query
  select ?l
  where match
    relation "se afla în"
    role subject $q

  end

$q stands for one answer value; the first query selects two. Here the second question is about the places (?c): write that variable's condition into the second query instead.

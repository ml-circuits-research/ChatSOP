Wire help / concept

concept

Declare a reviewed vocabulary concept and parent labels used by the host ontology. This is a host SOP ontology declaration consumed by Lexicon, not one of the 35 runtime circuit types. It is outside the small-formalizer output profile.

Every consumed keyword

KeywordCardinality and defaultValue grammar and meaning
is_aOptional; repeatable; default no parents.Literal parent name per line. Lexicon stores these strings; it does not prove parent existence, reject cycles, or turn them into deductive rules.
labelOptional; repeatable.label LANGUAGE "surface". LANGUAGE has two or three lowercase ASCII letters. The surface is one nonempty token after quote-aware splitting; JSON double quotes are required for a multiword surface to remain one token; canonical generated/training snippets quote one-word surfaces too. See quoted text syntax. The last label for a language supplies that language's display label; all forms remain lookup aliases.
aliasOptional; repeatable.alias LANGUAGE "surface", with the same language/text grammar. Use a JSON string encoder for embedded double quotes and backslashes, not single or smart quote delimiters. Adds a lookup form, not a new identity or semantic implication.
domainOptional; default null.Literal exact scope string. Use a simple canonical token; this field is read directly rather than evaluated as a reference or expression.

Identity, values, and validation

The header is @id concept with the ordinary identifier spelling. The host loads the complete ontology through Lexicon. Its content hash and source provenance accompany resolution. Each canonical ID also supplies an und-language lookup form. A declaration produces an indexed ontology entry, not a $id runtime value. Use resolve to obtain a runtime value from an approved lexical lookup.

The extensible ontology parse route has no strict per-type SPEC field list. Lexicon reads the fields above; unrelated keywords can be ignored rather than rejected. Singleton fields are consumed through the first occurrence; repeated labels have the special behavior described above. Reviewers must reject unknown fields and duplicate singleton fields rather than assuming the runtime profile's strict checking applies here. No $, ?, or ~ evaluation occurs in these metadata fields.

Example: reviewed declaration

@employment concept
  label en "Employment"
  domain staffing

Example: another declaration

@research_employment concept
  label en "Research employment"
  is_a employment
  domain staffing

The concept relationship is host metadata. A query cannot infer works_at or any other factual relation solely because research_employment has an is_a parent. Concepts do not become executable predicate declarations.

Invalid lexical form

@bad concept
  label english "Example"

Lexicon rejects english because the language code must have two or three lowercase letters. This is ontology-consumer validation, not ordinary runtime-wire validation. A multiword surface without quotes likewise splits into too many tokens.

Authority and educational boundary

Only the host installs the reviewed ontology. A user document or model-generated declaration cannot approve a new identity, alias, predicate direction, or concept hierarchy. Unknown or ambiguous mentions require resolution/clarification, not an invented ontology entry. The punctuation-free circuit proposal does not authorize rewriting this metadata grammar without a separately agreed ontology contract.

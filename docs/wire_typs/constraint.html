constraint

Declares an integer arithmetic question over specified variables and requirements. A separate solve or reason wire evaluates it; declaration alone proves nothing.

Status and author: A formalizer may propose this wire under host policy; it is not by itself a memory write.

Accepted fields

Single means at most once, repeatable means zero or more, and required means at least once at parse time. Other field names are rejected.

FieldCardinalityAccepted values and current behavior
varrepeatable; optional?name int or ?name int min max. Name matches lowercase letter then lowercase letters/digits/underscore; distinct declarations. Bounds are safe integers (literal or scalar $wire values), inclusive with min ≤ max. The JS solver requires finite bounds.
requirerepeatable; optionalBoolean expression of declared integer variables, constants and resolved $wire integer references. Every line is a conjunct restricting feasible assignments.
claimsingle; requiredBoolean proposition over the same variables; tested against feasible assignments for prove/possible, and treated as a feasibility condition for optimize.
tasksingle; optional, default proveOne of prove (all feasible models), possible (some feasible model), optimize (best objective among feasible models satisfying claim).
unitsingle; optional, default scalarUnquoted unit label carried in the problem/result for presentation; no automatic conversion or dimensional checking.
objectivesingle; required if optimize; forbidden otherwiseInteger arithmetic expression defining value to minimize/maximize.
directionsingle; optional, default minmin or max; meaningful for optimize, accepted but ignored for non-optimization tasks.

Execution and result

Portable Boolean syntax supports !, &&, ||, == === != !== < <= > >=; integer expressions support constants, declared ?x, unary minus, + -, and multiplication only with a constant operand. No arbitrary JavaScript, division, remainder, function calls, string comparisons or non-linear variable products. $wire must resolve to a safe integer. The parser first accepts expression-shaped fields; lowerConstraint enforces the smaller numeric grammar.

Reasoning strategy reference uses JS finite enumeration, bounded by maxAssignments (default 100,000). advanced selects Z3 if available, otherwise JS finite fallback; explicit backend z3 requires advanced and may return unsupported if unavailable. solve can project declared variables via output ports; reason alone has no output fields. For prove: entailed/refuted/unknown/inconsistent; for possible: possible/impossible/unknown/inconsistent; optimization returns optimal, feasible_bound or inconsistent, subject to completeness. Neither SAT nor a witness alone means universal entailment. Constraint and solve do not write memory.

Current SOP examples

Finite feasibility and projection

@deadline constraint
  var ?arrival int 0 100
  require ?arrival == 42
  claim ?arrival <= 45
  task possible
  unit minute

@check solve
  constraint $deadline
  output ?arrival one

With a complete finite search, the result is possible and the unique projected arrival is 42.

Objective among models satisfying claim

@slots constraint
  var ?slot int 0 8
  require ?slot >= 3
  claim ?slot <= 6
  task optimize
  objective ?slot
  direction max

@choice solve
  constraint $slots
  output ?slot one

The feasible objective candidates are 3–6, so a complete search has optimum 6 and a unique slot projection.

Invalid or unsafe example

@bad constraint
  var ?a int 0 10
  var ?b int 0 10
  require ?a * ?b == 6
  claim ?a > 0

This parses as an expression but fails numeric lowering: multiplication of two variables is not in the portable linear profile.

Simplified syntax proposal (not implemented)

Finite numeric questions can be composed with the proposed smaller query profile, but neither numeric field syntax nor backend support has been replaced by the proposed simplified atom notation.

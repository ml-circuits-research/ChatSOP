Query modes

The ten question forms of the knowledge language. Five are older (select exists count explain every); five are reasoning modes (why_not plan abduce conform procedure), all declarative question forms, never operations. The small model may write them as the mode of a query (DS021); the host supplies via, trace and policy.

The modes

ModeAsksAnswer
mode selectwhich bindings of select satisfy whererows, each with its own conditional list
mode existsdoes where holdsupported, refuted, both or unknown
mode counthow many distinct bindingscount; a lower bound (bound at_least) over an open relation
mode everydoes scope hold for every member of the where restrictionsupported, refuted with a counterexample, or unknown over an open domain
mode explainwhy does the claim holdthe status plus the derivation (the rules and facts used)
mode why_notwhat would make the claim derivable, or what blocks itthe minimal sets of base atoms to add plus the blocking atoms; on a planning goal, blocked with blocked_by
mode planhow is the goal reachedplan_found with the plan, its used versions, compliance and choices; or blocked, no_plan, budget_exhausted
mode abducewhat could explain the observationall inclusion-minimal explanations (atoms, or waive $norm); limit bounds the list
mode conformdoes a performed trace comply with the procedures and norms in forcecompliant or non_compliant with violations, deviations and total cost
mode procedurewhat is the approved procedure for the taskthe method as written, its version, the norms in force (no planning)

Rules of the fields

The validator checks the mode against the fields: mode every needs scope and no other mode takes one; mode conform needs trace (and needs no where) and no other mode takes trace; via is only for plan, why_not and abduce; at most one of at, during, overlaps; every selected variable occurs in where. A query belongs in a query circuit, never in a knowledge circuit.

why_not, plan, abduce, conform, procedure in detail

  • why_not is abduction over a restricted hypothesis space, not an unsat core: if the claim does not hold, its theory plus the negated claim is satisfiable and an unsat core explains only entailed claims. It returns the base atoms, in the vocabulary of the slice and respecting the predicate types, whose addition would make the claim derivable. With via ~hard_reset r7 on a goal it answers blocked when a plan would exist if the named norms or unmet requirements were waived, and no_plan when none exists even then.
  • plan returns the cheapest legal execution that satisfies the norms in force; with via the plan must contain the given steps. The packet carries plan, used: [{id, version}], compliance: {hard, soft_violations, total_cost} and choices for what the engine optimised.
  • abduce with waive hypotheses returns the minimal sets of norms whose relaxation unblocks a plan.
  • conform judges a trace against the versions in force at the time of each step (at on a step, asof for the others); leaving a strict method is non-compliance and is listed in deviations, under binding advisory it is only reported.
  • procedure renders the approved method as of asof.

These modes need strategies that declare plan, method, norms_hard, abduce_waive, check_plan and the like; the oracle js-reference expresses abduce over atoms, why_not over base atoms and plan over actions, and declares the norm and method features not_expressible. A question no strategy declares is understood and answered not_computable, never answered as a plain select.

Examples

@router predicate
  args subject:entity
@reset_done predicate
  args subject:entity
@hard_reset action
  params ?r
  requires router ?r
  adds reset_done ?r
@no_hard_reset norm
  forbid ~hard_reset ?r
  when router ?r
@f1 fact
  holds router r7
@q query
  mode why_not
  where reset_done r7
  via ~hard_reset r7

The answer is blocked with blocked_by [no_hard_reset].

@q query
  mode plan
  where reset_done r7

Invalid: conform without a trace

@q query
  mode conform

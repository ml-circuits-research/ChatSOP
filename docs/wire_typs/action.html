All wire types

action

An action describes a symbolic state transition for planning; it does not operate a physical device. Only trusted or reviewed ingestion can author actions in the current runtime, although a trusted system/tool circuit can use an approved action handle.

SOP syntax: @id type, exactly two leading spaces on each field line, $id for a computed value, ~id for a declaration handle, and ?x for a local logic variable or an output name. Atoms use [not ]predicate term1 [term2 [term3 [term4]]] with one to four whitespace-separated terms; lowercase predicate names, canonical symbols, JSON-quoted strings or safe integers. Parenthesized predicate(arg, …) and comma-separated arguments are not executable syntax.

Fields and inputs

KeywordCardinalityAccepted value, default and effect
paramsAt most once; optionalWhitespace-separated distinct ?variable names; default empty. Each must occur in a requires atom.
requiresRepeatable; requiredOne to any repeated predicate atoms describing preconditions. Their variables bind parameters and effects; an action needs at least one precondition.
addsRepeatable; optionalRepeatable effect atoms inserted into a hypothetical plan state. At least one adds or removes is required.
removesRepeatable; optionalRepeatable effect atoms removed from a hypothetical plan state; insertion also removes explicit opposing polarity.
costAt most once; optionalFinite nonnegative number, default 1; used in lowest-cost state search.
sourceAt most once; optionalPlain/quoted provenance text, default provided.
validAt most once; optionaltimeless (default) or start exclusive-end using ISO date/UTC timestamp, beginning/open; applies to whether the action can be used at planning time.

Pass ~action or $action (or a packed $array) to plan actions, or include actions in plan data if actions is omitted. Supplying a nonempty explicit actions set overrides action declarations from data.

Result and limits

The declaration produces a typed action with preconditions, effects, parameters, cost and validity. plan grounds variables against a candidate state and returns steps labelled planned-not-executed; no actuation or repository write happens.

Variables in params, adds and removes must occur in preconditions. The planning state is finite and search bounded by host or tighter policy; a missing plan under incomplete search is not proof of impossibility.

Executable examples

Move between connected places

@move action
  params ?robot ?from ?to
  requires located_in ?robot ?from
  requires connected ?from ?to
  removes located_in ?robot ?from
  adds located_in ?robot ?to
  cost 1

Planning can instantiate all three parameters from the two preconditions; the resulting step changes only a hypothetical state.

Release a reservation

@release action
  params ?item
  requires reserved ?item
  removes reserved ?item
  adds available ?item
  valid 2026-01-01 open

The transition can be considered on or after the start date and never performs an external release.

Invalid or unsafe use

@unsafe action
  requires ready machine
  adds ready ?other

The parser accepts both atoms, but lowering rejects ?other because effects must be range-restricted by preconditions.

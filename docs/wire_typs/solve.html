solve

solve connects a query or numeric constraint to the linker and a host-selected reasoning strategy. A formalizer can propose the question and its explicit premises; neither retrieval nor inference licenses it to invent a missing fact. The result is a checked packet, not a write. Explicit output fields request separately materialized binding wires.

All supported fields

Field / multiplicityValue grammar and route
query — 0–1; exactly one of query/constraint is required at semantic validation$id of a query value. Relational route creates an internal link then reason; linker sees repository/session when available plus facts/rules from data. A query can be local without repository if its data is provided.
constraint — 0–1; exclusive with query$id of a numeric constraint value. Direct numeric reason route: no generated linker. If present, data and assume are forbidden by parser shape validation; strategy can parse but is not consumed by this route.
data — 0–1, relational route only$id value; may be a pack array of facts/rules. Generated linker requires each item to be a fact or rule; hypotheses, patterns and arbitrary packets are not admitted as deductive premises. The same data value is passed onward to reasoning. Local data does not write the session and is not a historical repository snapshot.
backend — 0–1, default autoRoute-specific backend text: relational auto/js/prolog; numeric auto/js/z3. The reference strategy rejects external backends; advanced may use SWI-Prolog for point-in-time Horn queries or Z3 for numeric work, with route/fallback reported. The field also influences default strategy: explicit backend other than auto/js defaults to advanced unless reasoning overrides it.
strategy — 0–1, default host retrievalStrategyName of the registered memory-retrieval strategy. Consumed only by the generated relational link, subject to host allowedStrategies; it does not select the reasoning backend and does not run on the numeric path. hybrid is a configured default, not a mandatory keyword.
assume — 0–1, relational route only$id of a fact value or flat pack of fact values. Reasoning marks these premises assumed, filters by query validity time and excludes an assumption opposed by admitted evidence. Hypothetical premises must not be passed to assert as verified evidence. Numeric route rejects this field with constraint.
reasoning — 0–1, default host reasoningStrategy except backend preference aboveRegistered strategy name, ordinarily reference or advanced, checked against allowedReasoningStrategies when set. It is independent of retrieval strategy. Unknown strategy fails at runtime; an external backend is not guaranteed to be installed.
output — zero or moreEach line ?name [one|many|rows|count|status]; default one. Registers a generated $name output port; name unique among all ports and explicit wires, reserved names rejected. one/many on a relational query require ?name in query.select; numeric path requires corresponding declared constraint variable. one binds only a unique value; zero/multiple results are unavailable (no_answer/ambiguous). many collects unique values; rows retains answer bindings; count needs a count-result kind; status can bind even when result is incomplete or unfavorable. Completeness and conflict checks can prevent value bindings. Output ?name is not a free global logic variable.
after — zero or moreUse after $receipt to create an execution dependency on an earlier side-effect wire, especially assert. Runtime scheduling extracts $ references from this field; the field's remaining text is not otherwise interpreted. An unreferenced after line will not order an effect. No automatic storage follows a solve.

Result and provenance

The original solve wire aliases the generated reason packet; internal linker/reason/binding wires appear in generated epochs. A cnl wire can render this genuine packet. Result status, complete, answers, count, proof, epistemic/hypothetical flags and route delimit what can be reported. Candidate retrieval is not proof; the reasoner reinforces repository facts only if used in an actual proof/refutation and eligible for reinforcement. Binding states are exposed separately in outputs, including unavailable status; $name is only populated for a bound port. In the relational route, asof and valid-time come from query; a during query needs JS interval handling rather than Prolog point-in-time adapter.

Current syntax examples

A local positive answer can be projected without a session:

@evidence fact
  holds owns(ada, key_a)
  valid timeless

@question query
  where owns(ada, ?item)
  select ?item

@calculation solve
  query $question
  data $evidence
  reasoning reference
  backend js
  output ?item one

@report cnl
  result $calculation
  language en

The expected interpretation is an answer binding of key_a, subject to normal completeness checks. A request for explicit negation has a different meaning from asking whether evidence is absent:

@negative fact
  holds not open(door_a)
  valid 2026-01-01 open

@question query
  where not open(door_a)
  at 2026-04-01
  mode explain

@calculation solve
  query $question
  data $negative
  output ?state status

This asks whether the negative atom is supported. ?state is only the named status port, not a selected query variable. The next circuit parses (both are supported fields) but fails at runtime when the generated linker receives a non-fact/non-rule item:

@question query
  where open(door_a)

@message clarify
  text "Please identify the door."

@bad solve
  query $question
  data $message

Simplified syntax proposal — not implemented

The proposed atom spelling is open door_a rather than open(door_a). Output-port and dependency semantics cannot be silently inferred from the proposed atom change.

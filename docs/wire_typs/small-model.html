Small-model language

A small formalizer emits only six wire types: stated, assumed, unclear, query, constraint and unparsed. These declarative wires describe what the user said, what the model added, questions, finite numeric problems and the parts of the message the model could not formalize. They do not write facts, select a backend, retrieve memory or claim an answer. The normative contract is DS021.

Who writes this language today. Since 2026-09-30 the current formalizer is SymbolicLM (Stanza grammatical analysis plus rules), evaluated on clean English; it writes this same language under the same boundary. The small formalizer LLM this page was written for is earlier work, with its results in the archive and history reports. Fine-tuning any model waits for the owner's approval.

The model has no context. Its prompt is the user's message only: no vocabulary shortlist, no identifiers, no background knowledge and no date. It therefore writes strings: a quoted relation phrase, roles from a closed inventory (subject, object, recipient, location, source, destination, instrument, time, topic) with names as written in the message, ?variables in questions, and temporal expressions as written. Content words (relation phrases, common nouns) stay in the message's language, normalized to a lemma or the nominative ("work at", "lucra la", "sala de sport"); a mixed message keeps each word in its language, and the keywords are English. One clause of the message is one wire, related to its main clause by a link keyword (because $s2, if $s1, before $s1, …); a role value may name another wire ($s, $q). The host translates content words with its dictionary (config/dictionary/) and reports a word it does not know as untranslated. After the model, the host links the strings to its reviewed lexicon (relation phrase and role set to a predicate, values to entities, temporal expressions to intervals), compiles an inspectable execution circuit and asks the user with a host clarify when something is unknown or ambiguous.

No refusal and no plumbing. The model always formalizes a readable request; an understood question without an engine gets the host answer "I understood the question as …; I cannot compute this kind of answer yet". It cannot declare clarify, fact, remember, pack, resolve, solve, cnl, value, jsEval or expand. These remain available in trusted general-runtime circuits.

Clarification is host-generated: when an unparsed span cannot be repaired, or a relation phrase, an entity string or a temporal expression cannot be linked uniquely, or a downstream required scalar is absent/nonunique, symbolic orchestration suspends dependent work and produces an inspectable clarify request. Lack of evidence for an otherwise well-formed question is a reasoning result, not a request for more input.

A supposition and a question

User: “Suppose Maria works at Alpha Lab. Would Maria work at Alpha Lab?” The model states the supposition and the question as strings. No generated answer or session write is embedded here:

@context stated
  relation "works at"
  role subject "Maria"
  role object "Alpha Lab"
  polarity affirmed
  certainty supposed

@question query
  where match
    relation "work at"
    role subject "Maria"
    role object "Alpha Lab"
    polarity affirmed
  end
  mode exists

The host links both phrases to works_at, resolves the names, and compiles a solve with the supposition as a temporary assumption: the result is conditional on it, and no observed fact is recorded. An asserted statement would instead be turn-local user evidence and the answer would not be hypothetical.

Canonical literals: every value is a JSON double-quoted string (or an integer); quotes keep spaces, commas, parentheses and escapes inside one value. Keep ?variable and keywords unquoted. See quoted text.

What stays outside the small model

jsEval, expressions in value and JavaScript generation are excluded; the model-surface admission rejects them. Coding agents may author reviewed programs; invoking an approved abstraction through a bounded interface is distinct from writing its implementation. An approved host metaprogram may use expand to generate an inspectable circuit; that does not give the model authority to write its implementation.

Runtime bindings, linking, retrieval implementation choices, executable definition installation, and policy budgets belong to the host/system. Declarative AND/OR groups, comparisons, numeric requirements, and optimization objectives do not belong to this exclusion: they express the user's problem.

The corpora for this language are formalizer-v1 (train, dev and a sealed test) and the out-of-distribution suite formalizer-ood-v1, built by the diversity generator (DS022); they are not reviewed or training-approved yet. Syntax agreement, successful validation, and model-training authorization are three separate gates, and training stays prohibited until the owner approves it explicitly.

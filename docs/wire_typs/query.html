query

A SOP query describes a logical question. It does not retrieve premises or calculate an answer by itself: solve can consume its value. A formalizer may express the user's question without inventing missing evidence; a coding agent can compose a query against reviewed knowledge. This page describes the implemented sop-agent-3 syntax.

Every supported field

Field / multiplicityGrammar and effect
where — one or more, requiredOne atom per line, predicate(term, ...) or not predicate(term, ...); all lines are conjunctive. Atom has 1–4 comma-separated terms: canonical lower-case symbol, safe integer, JSON double-quoted string, ?name logical variable, or $name scalar value reference. Predicate name is literal, not a variable. Same ?name within this query joins positions; no implicit global output wire results. Schema, when configured, checks predicate arity and compatible variable/argument types. Explicit not matches explicit negative facts, never negation by failure.
select — 0–1, default emptyWhitespace-separated ?name variables. Each must appear in a where atom. Selected variables define the answer columns; no select + omitted mode defaults to exists. A selected variable does not create $name; use solve.output for a materialized port.
mode — 0–1, default select when select is nonempty, otherwise existsselect, exists, count, explain. select requires at least one selected variable; other modes may also carry select. count counts distinct matching bindings: selected columns if any, otherwise all bound variables. explain carries the proof packet; the query alone never proves it.
filter — zero or moreOne restricted expression per line using bound ?variables, e.g. ?degrees > 20. Every filter variable must occur in where. Expression must evaluate to literal boolean true to retain a row; the expression parser accepts JavaScript-like operators, strings, numbers, boolean operators and limited calls, not arbitrary JavaScript. Filter is applied after conjunctive matching, not to unrelated global values. Although the expression grammar parses $id, query filter evaluation receives only row variables, so a $id inside filter does not resolve to a wire value.
at — 0–1, default runtime nowValid-time instant, ISO date or UTC timestamp (or beginning/open accepted by the generic instant parser); a whole-field $value may supply an instant, including a safe-integer epoch-millisecond value. Cannot coexist with during. At a boundary, valid.from <= at < valid.until.
during — 0–1Valid-time timeless or two endpoints START END interpreted as [START, END). ISO dates/UTC timestamps, beginning and open; positive duration required. With during, answer and proof intervals intersect the requested span. Not a whole-field $value reference: interval() parses its literal text.
asof — 0–1, default runtime nowKnowledge-time cutoff, ISO date or UTC timestamp; whole-field $value also accepted, including a safe-integer epoch-millisecond value. Repository retrieval only sees claims/events known by this instant. Local data supplied to solve is not reconstructed as a historic repository snapshot: do not confuse this with at.
limit — 0–1, default 100Decimal text converted by Number to a safe integer from 1 to 10,000. Limits returned answers; truncation makes completeness false. Parsing may accept malformed numerical text as a field, but lowering rejects invalid limits.

Answer boundaries

With a single fully ground atom, an explicit opposing fact can yield refuted, both on overlapping intervals or mixed_temporal on disjoint intervals. An absent match is unknown, not a negative fact. A variable query can flag conflicting answer bindings when opposing ground facts exist. Rule derivation and retrieval limits affect completeness; a linker retrieves candidate premises and a reasoning strategy computes the result. A query value records where/select/filters/mode/limit/at or during/asof; it writes no session state.

Executable syntax examples

These are complete local circuits; the anticipated interpretation assumes the displayed facts are admitted as local solve.data, not stored in a repository.

@reading fact
  holds temperature(room_a, 23)
  valid 2026-09-01 2026-10-01

@search query
  where temperature(room_a, ?degrees)
  select ?degrees
  filter ?degrees > 20
  at 2026-09-20

@answer solve
  query $search
  data $reading
  output ?degrees one

Here ?degrees can bind to 23. A count across two matching records, with no selected columns, counts distinct complete bindings.

@north fact
  holds open(door_north)
  valid timeless

@south fact
  holds open(door_south)
  valid timeless

@records pack
  items $north $south

@doors query
  where open(?door)
  mode count

@total solve
  query $doors
  data $records
  output ?number count

The count projection is ?number, a port name for the count and not a query variable; assuming both local facts remain available, the count is two. The following parses as a query atom but fails at lowering because the selected variable was never bound in where:

@bad query
  where open(?door)
  select ?building

Simplified syntax proposal — not implemented

The proposed atom spelling removes parentheses and commas; it does not resolve the future role of ? or decide whether query/solve remain separate wire types. The small-model field inventory is not approved.

@search query
  where temperature room_a ?degrees
  select ?degrees

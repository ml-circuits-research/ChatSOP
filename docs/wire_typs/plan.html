All wire types

plan

Planning searches deterministic symbolic state transitions for a state satisfying an explicit goal. Plans describe hypothetical steps, not executable physical commands. The current runtime permits model-origin planning but does not permit model-origin action definitions.

The current executable profile is SOP sop-agent-3: @id type, exactly two leading spaces on each field line, $id for a computed value, ~id for a declaration handle, and ?x for a local logic variable or an output name. Atoms use predicate(arg, ...) or not predicate(arg, ...) with one to four arguments, lowercase predicate names, lowercase canonical tokens, quoted strings or safe integers. Space-separated predicate arg is not executable syntax.

Fields and inputs

KeywordCardinalityAccepted value, default and effect
dataAt most once; optionalOne $value, ~declaration or packed $array. Facts/rules form the initial model; actions inside data are used only when actions is absent or empty. Constraint objects cannot be silently dropped.
memoryAt most once; optionalOne optional $link retrieval result. Without it and with repository/session, the runtime links facts/rules against goal atoms plus action preconditions; otherwise it uses local data.
actionsAt most once; optionalOne $action, ~action or packed $array of action declarations. If nonempty, these actions replace action objects from data. Default empty (then data actions are used).
goalAt most once; requiredExactly one $goal or ~goal yielding a goal declaration. Required by parser and runtime. Goal atoms must be expressible by current predicate syntax.
reasoningAt most once; optionalA strategy name (plain token), default host policy.reasoningStrategy (reference by default). Built-ins: reference bounded JavaScript and advanced optional external backend for deduction, otherwise shared JavaScript controller. The host may restrict allowed strategies.
policyAt most once; optionalOne $policy value or ~policy declaration handle. It must lower to a policy object; each specified positive integer budget caps the corresponding host budget by min(host, wire). No policy reference means host limits alone.
outputRepeatable; optionalRepeatable ?name [one|many|rows|count|status] declaration, default one. Each output becomes a deferred $name value if bound; names must be unique and cannot collide with explicit wires. status binds result status even for incomplete results. Other modes require completeness; unusable/unselected modes become blocked, not arbitrary first answers.
afterRepeatable; optionalRepeatable $wire value-dependency reference. Orders execution after that producer; it does not alter inputs, proofs or output. A ~definition handle is graph-checked but is not a value-ordering dependency.

At run time a retrieval query is constructed from goal atoms and available action preconditions, at the current time. A returned memory view is filtered by this query; explicit memory must already be a retrieval. Rules are approved definitions; a model can reference approved ~action and ~rule, but cannot define them in model-origin code.

Result and limits

kind: planning returns plans (step action IDs, bindings, adds/removes, costs and goal proof), execution: false, optimal only when complete, and epistemic: planned. Status is plan_found, no_plan or unknown. Output one/many/rows projects plans, count unsupported, status projects status.

All operations use bounded search (host defaults include maxNodes 5000, maxDepth 8, maxCandidates 512, timeoutMs 3000); a ~policy can only tighten configured limits. The result records completeness and epistemic status relative to supplied finite inputs and the visible memory view, never calibrated truth probability. No operation here writes to the repository; after is only scheduling. Default maxPlans is 1. Search sorts states by accumulated nonnegative cost, skips conflicting closure states, obeys action validity and maxDepth. A found plan with incomplete search is not certified optimal. no_plan requires a complete bounded search and is relative to the supplied model.

Executable examples

Move a robot to a dock

@start fact
  holds located_in(robot7, bay)
  valid timeless
@road fact
  holds connected(bay, dock)
  valid timeless
@facts pack
  items $start $road
@move action
  params ?robot ?from ?to
  requires located_in(?robot, ?from)
  requires connected(?from, ?to)
  removes located_in(?robot, ?from)
  adds located_in(?robot, ?to)
@destination goal
  where located_in(robot7, dock)
@route plan
  data $facts
  actions ~move
  goal ~destination

Run as trusted code or use a reviewed ~move action. The planner can return a symbolic move step and does not command the robot.

Goal already reached

@charged fact
  holds charged(robot7)
  valid timeless
@ready goal
  where charged(robot7)
@route plan
  data $charged
  goal ~ready

The initial state itself satisfies the goal; a valid plan may contain zero steps.

Invalid or unsafe use

@ready goal
  where available(robot7)
@move action
  requires located_in(?robot, bay)
  adds available(?robot)
@bad plan
  goal ~ready
  actions ~move

Syntactically valid, but without a matching initial located_in fact the action is not applicable. Do not present a missing plan as proof that a physical route is impossible.

Simplified syntax proposal

Current runtime allows these operation wires in model-origin programs. Exclusion from the proposed first small-model training core is a proposed curriculum boundary, not a current Runtime.run permission change; it neither removes this existing route nor approves a new syntax.

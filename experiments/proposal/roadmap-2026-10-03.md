**The main reading.** The bottleneck is not model size. On the same questions the 35B MoE `tiny` beats the 27B `small`, and `good` solves none of the residue. The losses are (a) vague protocol questions, (b) routing that sends logical problems to numeric compute, (c) question formalization over knowledge that is already stored, and (d) failures after a correct formalization (reasoner, missing knowledge, missing constructs). On logical verdicts the symbolic paths are still clearly worse than the model answering directly; on numeric book problems they are competitive and verifiable. This is why the packages below target protocol, routing and the reasoner, not bigger models.

## 3. Rules for every work package

1. Read `AGENTS.md`. No hardcoded understanding: no word lists or regex over phrasings, no per-case fixes; fixes go to the language, the validator, protocol data or memory data. No user-facing text in code (reply wires).
2. Model calls only through TinyAgent with a purpose tag; prefer local `tiny` (free); cloud tiers only at `priority: background`; report credits from `tinyagent stats`.
3. Small first: 5–10 cases, fix, fresh small sample, then one measurement that answers the question; paired bootstrap for comparisons; stop when the answer is clear. Write the stopping rule down.
4. Every commit passes: `npm test`, `node tools/eval/formalization/regression/offline.mjs check` (0 lost), the capability battery fast tier (0 losses: `node tools/capabilities/check.mjs`), `node tools/shard-large-files.mjs --check`. New tests and harnesses are registered in `eval/registry.json` and the page regenerated (`node tools/inventory/tests-and-evals.mjs`).
5. Commit with an explicit pathspec, never sweep others' changes; never push; never touch port 9999 (the owner's server); restart 18080 only after `/v1/ops` shows nothing running, killing by PID.
6. Record: journal event (started/done), topic note, CHANGES.md, TODO.md; report every formalization error found with `reportFormalizationError()` (`lib/formalization-errors.mjs`).
7. Language (wire type) changes are allowed without asking the owner if nothing breaks (battery no-loss ledger + offline regression); record them in `experiments/proposal/wire-type-proposals.md`, DS004/DS014, `docs/wire_types.html` and `docs/wire_typs/` with executed examples.

## 4. Work packages

### WP1 — Route logical-verdict problems away from numeric compute (highest value, small)

- **Why.** In routed mode 24 of the 28 balanced argument problems go to compute path B, which answers "Yes" almost always: balanced accuracy 0.50, the same as a constant answer. The direct model reaches 0.89. Sending a "does it follow / is it valid / which option" problem to arithmetic is a category error, not a model weakness.
- **Where.** `lib/formalize/structure/route.mjs` (routing from structure labels), `lib/adapter/modes/` (routed, direct-verified), the structure role prompt `config/prompts/psm-v1.md`.
- **How.** Route by the goal type the structure role already labels (verdict / option choice / quantity); if the label is missing, add a goal-type field to the structure contract (data, not words). Verdict problems go to FOL; when FOL gives no answer, fall back to the direct answer marked *unverified* (never a silent substitute). Consider making direct-verified the default for verdict problems.
- **Acceptance.** Balanced argument set: routed ≥ forced-FOL arm and no class collapse (Yes and No both ≥ 50%); fresh-50 routed results not worse (replay with `--cache strict`). Offline regression 0 lost.

### WP2 — Clarify the protocol questions `problem_facts` and `problem_kind`

- **Why.** Even `small` and `good` disagree with each other on these two questions in 10 of 12 hard cases; a question that strong models answer differently is under-specified. These are the first steps of problem mode, so their errors propagate to every later step (102 "wrong answer at execution" cases on the MoE are mostly wrong facts or wrong kind).
- **Where.** `config/knowledge/formalizer-protocol-v1/` (question texts and options as data), readers in `lib/query-author/step-by-step/`, gate `tools/eval/formalization/regression/gate.mjs`.
- **How.** For each disagreement case, write down what an unambiguous question would have to fix (what counts as a fact vs a rule vs a value; deduce vs compute vs choose). Rewrite the question/options as data; add worked micro-examples to the protocol where needed. Re-record only the affected step with `tiny` (`regression-record`, `set: failed` or targeted ids) and let the gate decide: admitted only if it fixes cases and loses none.
- **Acceptance.** Gate passes with net gain; references now agree more often (re-ask `small` on the 12 at background priority).

### WP3 — Failures after a correct formalization (~20 cases)

- **Why.** About 20 regression failures have a plausible circuit, but the reasoner, the knowledge or a missing construct fails. These are pure symbolic-side losses: fixing them helps every model size.
- **Where.** `tools/eval/formalization/regression/offline.mjs` (`attribute`), reasoners `reasoning/`, oracle `js-reference`, capability battery `eval/capabilities/`.
- **How.** Classify each case: engine bug, missing general knowledge, missing construct. Engine bugs: fix with a battery case first. Knowledge: add general commonsense to a base-memory layer (admitted only if it fixes a problem and breaks nothing; never the problem's own answer). Constructs: write a P-n proposal and implement if the battery stays at 0 losses.
- **Acceptance.** Each fixed case in the regression; battery cases added for every engine fix.

### WP4 — The headline number: books, today's system vs the small LLM

- **Why.** The only "do we beat the small LLM" number on books is from the old 4B (27 vs 69/100). Since then: MoE tiny, the adapter, routed and direct-verified modes. Without a fresh number we cannot tell whether the direction works.
- **Where.** `tools/eval/books/` (`system.mjs` now uses `chatTurn`), adapter modes, `eval/registry.json`.
- **How.** Fresh stratified sample of 100 (exclude regression cases, already-evaluated items, gold defects), stage 1 = 30 with paired bootstrap, stage 2 only if undecided. Arms: stepwise, routed, direct-verified, tiny direct. Report correct / wrong / unknown separately, and verified precision. Preregister in `status/preregistrations/` (DS007).
- **Acceptance.** A dated row in the registry and the inventory page; topic note with the reading per arm.

### WP5 — Document question path and ingestion checks

- **Why.** Ingestion v2 stores much of the knowledge, but 14 of 31 misses are the question being formalized wrongly (wrong predicate, spurious extra condition, missing join or arithmetic). Fixing questions helps every document and the chat. Ingestion also writes negative predicate names (`ineligible_for_overtime`) and group-level facts that should be rules.
- **Where.** `tools/eval/ingestion/ingest-v1.mjs pipeline` (measures questions), memories `exp-ingest-*-v1|v2`, `lib/ingest/v2/` (repair round), vocabulary retrieval in `lib/query-author/`.
- **How.** Offline first: replay the question path against the stored v1 and v2 memories; fix predicate choice via vocabulary retrieval (labels, descriptions, examples as memory data). Add a deterministic ingestion check (structure, not words: a predicate whose label is a negation of another predicate's label in the memory's own lexicon; a fact whose subject is a class) that feeds the repair round.
- **Acceptance.** Question accuracy on both memories rises without new builds; one new build per document only after that. Then rerun analysis-v1 level (b) (`eval/analysis-v1/`).

### WP6 — Commonsense guard (20/32)

- **Why.** These are short everyday questions; failing them makes the chat look broken.
- **Where.** `tools/eval/formalization/` (commonsense replay), protocol data, commonsense layers.
- **How.** Per failing class: kinship in problem mode, unit conversion, "Can birds fly?" (a message word needed as a text value), "Is Paris a person?" (no "is a" statement chosen). Generic fixes only.
- **Acceptance.** ≥ 24/32 with 0 new wrong answers.

### WP8 — FOL path on arguments (after WP1)

- **Why.** fol-v3 compiles far more (27/30 vs 11/30) but its wrong answers come from two formalization habits: a reported correlation written as a rule, and "can X?" asked as "does not-X follow?". It also leaves 7/28 unanswered on the balanced set.
- **Where.** `config/prompts/fol-v3.md`, converter `lib/formalize/fol/`, balanced set replay.
- **How.** Prompt rules plus converter checks (structure: a modal "can" maps to consistency, not entailment of the negation); measure on the balanced set offline after one tiny re-recording.
- **Acceptance.** Balanced accuracy of forced FOL ≥ 0.7 with both classes ≥ 60%.

## 5. Why this order

1. WP1 is a routing error that costs half of all argument problems, and it is cheap to fix and to verify offline.
2. WP2 and WP3 attack the two largest measured loss sources of the regression; they are independent of model size, so every gain is durable.
3. WP4 must follow quickly so that the owner sees the real comparison against the small LLM with today's system; it also tells whether direct-verified should become the default.
4. WP5–WP6 bring the same question-formalization improvements to documents and everyday chat.
5. The rest are hygiene, follow-ups and research that only pay off once the core comparison is favourable.
